# Mesh Rules

Full operator docs live in `docs/mesh.md`. Keep this file to implementation invariants.

## Topologies And Runtime

- `MeshTopology` drives listeners: `Sidecar` uses inbound 15006 mTLS and outbound 15001 capture; `Ambient` uses HBONE 15008 and outbound 15001; `EastWestGateway` uses SNI passthrough on 15443; `EgressGateway` uses mTLS inbound 15090 to external ServiceEntry backends.
- All topologies share the normal proxy and plugin chain.
- Mesh runtime state is `ArcSwap<Option<MeshSlice>>` in `runtime.rs`; slice apply is lock-free hot-swap like `GatewayConfig`.
- `wait_for_first_slice()` blocks startup until the first valid slice arrives.
- Native config consumption uses `MeshConfigSync.MeshSubscribe` gRPC. xDS uses ADS for CDS/EDS/LDS/RDS/SDS/ECDS/RTDS with 25 ms debounce.
- **An RTDS knob that affects request handling must be materialized into the candidate plugin config, never published to a process-global store** (GHSA-83rc-23c9-3g9x). `runtime_overlay_consumers::apply_overlay` runs from `record_applied_slice`, i.e. AFTER `ProxyState::update_config` has published the new `RequestEpoch`, so anything behavioral it published would have two straddle windows: the publication gap (a new plugin reading the old value) and the entire lifetime of an already-admitted request (an old plugin reading the new value). `materialize_fault_runtime_overlay` and `materialize_transformer_runtime_overlay` are the correct pattern — they fold the accepted overlay into each instance's own config in `prepare_normalized_gateway_config_for_mesh`, so gate/percentage and rules are validated, built, and published as ONE generation and each instance resolves ONE immutable decision at construction. `RUNTIME_OVERLAY_MATERIALIZED_PLUGINS` + `reconcile_runtime_overlay_plugin_generations` are load-bearing: an RTDS-only change leaves every static field identical, so without the `updated_at` stamp `ConfigDelta` retains the old instance and the old value stays live under a nominally accepted slice. The transformer gate stores are STILL published post-accept, as provenance only — `response_caching` pins the response-side publication identity and `request_deduplication` folds its content fingerprint, so deleting those `apply_overlay` calls silently stops retiring cached/persisted representations across a policy change. That identity is NOT sufficient alone: it is published after the epoch, so a request whose auth phase spans an apply pins the OLD generation and the NEW identity. Every retained representation must therefore ALSO bind `RequestContext::response_presentation_policy_digest` (the request's own plugin-cache generation, which now covers the materialized gate as well as the static rules) — `response_caching` on its `CacheEntry`, `request_deduplication` via `ResponsePolicyProvenance`. A difference in either half retires it, and an unavailable digest retains nothing. `logging` is the one legitimate process-global consumer (diagnostics, not proxying).
- `FERRUM_MESH_CONFIG_PROTOCOL=file` is the localized source: `config_consumer::file_source` builds the slice DP-side from `FERRUM_MESH_FILE_CONFIG_PATH` via `MeshSlice::from_gateway_config` (same materialization as CP paths — do not fork it). The document is `{version?, mesh}` ONLY (`deny_unknown_fields` rejects gateway resources). Initial load is fail-closed at startup; SIGHUP reload keeps the last good slice on error. The file protocol requires no CP URLs / CP-DP JWT secret — `EnvConfig::validate()`'s Mesh arm and `MeshRuntimeConfig::from_env_config` gate those per protocol; do not re-add unconditional requirements.
- xDS apply uses make-before-break with a coherent required-version gate: the DP tracks each type's `version_info` independently but only builds a slice once all required types (CDS/EDS/LDS/RDS/ECDS — ECDS required so the first slice is never the unprotected name-only view) have the same `version_info` and `reverse_translate` succeeds. The prior slice keeps serving via `ArcSwap` until the new one is ready; genuine structural errors (e.g. malformed ECDS carrier) NACK + roll back. A route referencing a service not yet present in CDS/EDS/LDS is SKIPPED (debug-logged) and retained, NOT NACKed, because xDS types arrive as independent responses and a NACKed SotW resource is not resent until reconnect (do not reintroduce a hard error there). `MeshSlice.version` is observability-only (`content_eq` ignores it). The CP force-re-sends subscribed required mesh-slice types when any required type changes so CDS/EDS/LDS/RDS never advance independently of stale ECDS security carriers. Keep DP `REQUIRED_MESH_SLICE_TYPE_URLS` and the CP emitter in sync.
- Warming observability splits by sensitivity: the counter `ferrum_xds_warming_partial_applies_total{namespace}` is unauthenticated on `/metrics`, but the per-type `version_info` strings and still-missing required types ride the JWT-gated `GET /mesh/config-drift` `convergence` block (built by the DP via `MeshRuntimeState::set_xds_convergence`). Do NOT move per-type version strings onto `/metrics` — they embed config-change timestamps + content digests and would also explode label cardinality.
- xDS is Ferrum-CP-to-Ferrum-DP, not stock-Envoy/Istio-interoperable: CDS/EDS/LDS/RDS are name-only (service-port discovery); all security/policy slice fields and selector context (authz, PeerAuth, JWT, ServiceEntry, trust bundles, ProxyConfig, VirtualService L4 proxies, workloads, effective labels, outbound policy, telemetry, multi-cluster, sidecar egress scope) ride ECDS as Ferrum mesh-slice carriers. `src/xds/carrier.rs` (`MeshSliceCarrier`) is the single encode/decode source of truth; the CP emits via `translate_mesh_slice_carriers` and the DP recovers in `reverse_translate`, requiring both reserved resource name and matching inner type URL. **ACK-time validation covers every newly policy-bearing carrier field** (#2465/#2469): `validate_ecds_destination_rule_carrier` recognizes a DR carrier by its inner `type_url` alone — so reserved AND legacy/non-reserved names get the same fail-closed JSON + `validate_mesh_export_to` check, while genuinely unrelated ECDS extension configs still route untouched — and `validate_ecds_mesh_slice_carrier` validates both `VirtualServiceCorsPoliciesCarrier.export_to` and the `IstioRootNamespaceCarrier`'s lowercase RFC 1123 namespace value. Do NOT restore an early return for non-reserved DR names: a malformed same-namespace legacy carrier would then be ACKed and normalized and only become inert at materialization (fail-open). Diagnostics are field/index-shaped, capped at `XDS_CARRIER_DIAGNOSTIC_LIMIT`, and never echo the carrier-supplied value. An xDS-built slice must stay functionally equivalent to a native-built one.
- VirtualService L4 `sourceLabels` / `sourceNamespace` on the `mesh` arm are Sidecar source-workload applicability selectors, not authenticated inbound-peer predicates. Resolve them at slice apply from the unambiguous local workload identity/namespace/labels, drop non-applicable arms fail-closed, and leave remaining subnet/gateway/SNI predicates ordered and AND-combined. Named-gateway arms stay independent; ambient/NodeWaypoint retain exact runtime source-workload evidence. The namespace-projected L4 proxies ride `MeshSlice` (and the matching ECDS carrier), and `content_eq` compares them so updates/deletes cannot retain stale matcher state.
- Native and xDS clients use jittered exponential backoff from 1s to 30s, plus/minus 25%, multi-CP failover via `FERRUM_DP_CP_GRPC_URLS`, and JWT metadata.
- **Authoritative config-revision ordering is fail-closed and centralized in `MeshRuntimeState::install_slice`** (issue #2473). Slices carry `revision = (authority, sequence)`: `authority` is the CP-replica-shared ordering DOMAIN (`FERRUM_MESH_CONFIG_AUTHORITY_ID`, default `db`), `sequence` is the durable `config_changes` change-log cursor (explicit `CpScope::Single`/`Set` full-load stamps max scoped namespace cursors; `CpScope::All` stamps the store-global high-water mark; both boundaries are captured BEFORE their resource loads and only then combined with the in-process floor, so a concurrent write can be replayed but never skipped) — NOT a wall clock and NOT process-local (`MeshSlice.version` stays observability-only and is NOT comparable across replicas). CP startup rejects non-empty authority values containing control characters or exceeding 128 bytes without echoing them; empty explicitly disables publication. The gate (`modes::mesh::revision`) admits Bootstrap/Newer/Same and quarantines Older (`stale_revision`) / foreign authority (`incomparable_authority`) / absent-while-one-is-accepted (`missing_revision`) / present-but-ill-formed (`malformed_revision`) BEFORE the `ArcSwap` swap; a quarantine mutates nothing (no receive metric, no `last_install_at`, no watcher wake). A *present* ill-formed authority (blank / over-long / control characters) must NEVER be silently downgraded to absent — `admit` refuses it even on bootstrap (xDS reaches this gate without `MeshConfigUpdate` validation), while a genuinely absent revision still bootstraps for unsequenced authorities. **`Same` MUST install for IDENTICAL SEMANTIC CONTENT ONLY** — a reconnect replays the CP's initial slice at the unchanged revision, so exact-content replay (including from another replica) must install; but a scalar revision is only an ordering key if one `(authority, sequence)` names one content, and the K8s domain's MIN-over-scopes watermark does NOT guarantee that (replica A at scope watermarks `[110,100]` and replica B at `[100,100]` both publish `100` while A's snapshot carries the change at `110`). The gate therefore binds a deterministic content identity (`MeshRevisionContentIdentity`, from the canonical `grpc::mesh_slice_drift::slice_content_digest` — `version`/`revision` cleared, JSON canonicalized) to every accepted AND applied revision, compares it INSIDE the same admission critical section (never caller-side — that would be TOCTOU), and quarantines divergent equal-revision content as `divergent_content` / an uncomputable identity as `unidentified_content`, both stream-terminating. Both slots store the revision and its identity as a PAIR and every transition (admit/adopt/begin/commit/rollback/reset) moves the pair; the apply token carries the identity so a commit binds what was admitted. Remote-cluster discovery's separate gate binds the POST-validation/POST-trust-domain/POST-tagging endpoint set (`canonical_content_digest` over workloads+services), not the discarded slice fields. No digest, content fragment, or payload byte may reach a log line, metric label, or admin surface. Native and xDS quarantines TERMINATE their streams so multi-CP failover leaves the lagging CP. xDS does NOT rewind the ADS accumulator, which already absorbed and ACKed the response before the slice was built; the accumulator is per-CP-URL and reset wholesale by `reset_for_new_control_plane` during the resulting failover. Do not roll it back (that desynchronizes it from ACKed versions) and do not weaken the required-type/version-coherence gates. Admission is PROVISIONAL: the gate keeps TWO watermarks — `accepted` (received slot, the comparison baseline) and `applied` (what the proxy runtime accepted). `record_applied_slice` → `commit_applied` advances `applied` (including content-no-op/equal-revision replays); a runtime rejection in the apply loop → `record_rejected_slice` → `rollback_rejected` returns `accepted` to `applied`, gated on exact `(authority, sequence)` equality AND received-slot `Arc` identity so a LATE rejection of N never rolls back an already-received N+1. Never advance the authoritative watermark on receipt alone: one runtime-invalid slice at a far-future sequence would otherwise lock out every valid revision beneath it. `is_well_formed` refuses blank, control-character, and over-length authorities; the raw authority stays INSIDE the gate for exact ordering and every escaping copy (diagnostics, reset response, log lines) goes through `diagnostic_value`. The revision rides `MeshConfigUpdate.config_authority`/`config_sequence` (envelope↔slice agreement enforced in `update_validation`, reason `envelope_revision_mismatch`; present-but-ill-formed revisions use dedicated reason `malformed_revision` and are refused before agreement comparison so an empty envelope cannot smuggle a hostile embedded authority; raw non-empty whitespace-only envelope authorities are present/malformed, not proto-absent) and the xDS `ConfigRevisionCarrier` ECDS carrier, so native/xDS materialization stays at parity. `content_eq` deliberately IGNORES `revision` (ordering metadata, not content — CP dedupe must keep suppressing unchanged frames). An intentional rollback is a WRITE, so it arrives as a HIGHER sequence; never accept an old generation to roll back. No-lockout: a foreign authority is adopted after `FERRUM_MESH_CONFIG_REVISION_ADOPT_SECS` (default 300, 0 disables); a sequence rewind INSIDE one authority is NEVER auto-adopted and is recovered by `POST /mesh/config-revision/reset` (JWT + operator) or by bumping the authority id. `GatewayConfig.mesh_revision` is `#[serde(skip)]` CP-in-memory-only — do NOT put it on the ConfigSync `config_json` wire (`deny_unknown_fields` both sides).
- **A Kubernetes-controller CP publishes the SEPARATE `k8s` ordering domain** (issue #3611), authority `k8s` / `k8s:<FERRUM_MESH_CONFIG_K8S_AUTHORITY_ID>`, sequence = a `resourceVersion` convergence watermark (`k8s_controller::revision::K8sConfigRevisionTracker`). The two domains are NEVER comparable and the split is structural, not advisory: `k8s`/`k8s:…` is a reserved authority `EnvConfig::validate` refuses on a change-log CP, the composed `k8s:<qualifier>` is validated whenever the CRD controller is enabled — INDEPENDENTLY of the empty-`FERRUM_MESH_CONFIG_AUTHORITY_ID` disable switch, which is a different variable, so re-enabling publication can never fail on a value that already started once — and a `config_changes` cursor may only reach a revision through `MeshConfigRevision::advance_change_log_sequence`, which no-ops on a Kubernetes-domain revision (both `cas_publish_incremental_partitions` and `mesh_server::apply_mesh_delta_to_stream_config` go through it — do NOT reintroduce a raw `revision.sequence.max(cursor)`). `resolve_mesh_config_authority` still returns `None` when the K8s controller is enabled, because that CP's `mesh` block is authored WHOLLY by the K8s overlay (DB full loads clear `mesh` and re-merge from the overlay slot, #2982) — so the revision lives on `AcceptedK8sOverlay.mesh_revision` and BOTH publishers stamp it through the one `apply_k8s_mesh_revision` site; putting it on the DB snapshot would let the next poll wipe it. Per-scope evidence = max(boundary read taken BEFORE the generation's list and adopted only at `InitDone`, listed-object RVs buffered until that same `InitDone`, applied watch-event RVs — a `Delete` carries the DELETION revision, which is why deletion advances instead of rewinding). kube-rs surfaces neither list metadata nor bookmarks, but its list defaults to `ListSemantic::MostRecent` (quorum read at the current cluster revision), which is what makes a pre-list boundary a sound lower bound — a post-list read would NOT be. The published sequence is the MIN over registered scopes, read BEFORE `snapshot_all()` under the SAME `ResourceStoreSet` lock (stores only move forward in between); ANY registered scope without evidence (listing, relisting, non-numeric `resourceVersion`) makes it unavailable, and unavailable RETAINS the last published sequence rather than publishing an unsequenced or optimistic frame. Because that retained scalar can coincide with a newly evolved reflector mesh (incomplete evidence OR a quiet scope pinning the aggregate MIN), `publish_k8s_reconcile` binds mesh to the revision inside `CpPublicationGate`: equal revision + divergent mesh retains the previously accepted mesh in the overlay slot / `config_arc` / broadcast together; equal+identical is idempotent; an advanced sequence releases the newest mesh (including withdrawals); unversioned bootstrap is unchanged; non-mesh Gateway/API fields may still publish. A retaining publication MUST also call `K8sConfigRevisionTracker::request_evidence_refresh`, which nudges every watch scope to start a fresh generation (per-scope 5 s floor in `watcher.rs`); without it the aggregate MIN stays pinned by the quietest scope and mesh propagation stalls for a whole `FERRUM_K8S_WATCH_IDLE_RELIST_SECS` window — the ~350 s NodeWaypoint eBPF live-datapath outage. The refresh ACQUIRES proof and never fabricates a watermark: a scope that cannot relist still yields no evidence. Do NOT weaken `MeshRevisionGate` — it remains the cross-replica equal-content defense. Max-over-live-objects is fatally wrong (deleting the highest-versioned object rewinds a restarted replica below its running peer, and a rewind inside one authority is never auto-adopted); so are wall clocks and a reconcile-time current-revision read.
- **MeshSubscribe response binding is centralized and fail-closed** (`config_consumer::update_validation`, issue #2457). BOTH consumers — the local native client and multicluster remote discovery — validate a non-heartbeat `MeshConfigUpdate` against the exact `MeshSubscribeRequest` they sent (`MeshUpdateExpectation::from_subscribe_request`) BEFORE `install_slice` / endpoint import: present + major/minor-compatible `ferrum_version`, `update.version == slice.version`, `slice.node_id`/`slice.namespace` equal to the request, and — when the request PINNED `workload_spiffe_id`/`waypoint_name` — an exact echo, where an ABSENT echo is a mismatch (treating it as a pass would be a trivial bypass; an unpinned request gates nothing, since there is no unambiguous expectation). Do not fork these rules into a second implementation and do not add a "skip when the field is missing" branch. Rejection is metric-recorded inside the validator (`ferrum_mesh_config_update_rejections_total{consumer,reason}`, both labels `&'static str` from closed enums — never a CP-supplied value) with a sanitized, length-bounded `warn!`. `MeshUpdateRejectReason::terminates_stream` splits BINDING failures (drop the stream → multi-CP failover) from CONTENT failures (drop the frame, keep the stream); remote discovery fails the whole poll either way and keeps last-good endpoints. Remote discovery additionally retains a per-cluster `MeshRevisionGate` across one-shot reconnect polls, validates endpoint content before advancing it, and applies the configured foreign-authority adoption policy. Heartbeats stay explicit: they route to `validate_update_ferrum_version` only, and a heartbeat-marked frame reaching the install path is itself a rejection. Test CP stubs must echo the request scope (`functional_mesh_mode_test`'s stub does) or the DP will correctly refuse their slices.

## Datapath Layering: Two Transports (per topology) vs. Materialization

Keep two things distinct: the **transport** (how a peer is reached on the wire) and **materialization** (turning the slice into routable `Proxy`/`UpstreamTarget` objects `find_proxy` can match). "Outbound 404 / no routes" does NOT mean "no transport" — conflating them leads to re-implementing transport that exists, OR (worse) using the wrong transport for the topology.

**Mesh transports are PER-TOPOLOGY — never assume one (this is the trap):**
- **Ambient / NodeWaypoint / ServiceWaypoint** speak **HBONE** (HTTP/2 CONNECT over mTLS) on **:15008**.
- **Sidecar** speaks plain **SVID-mTLS HTTP** on **:15006** — it has **NO 15008 HBONE listener**. HBONE is NOT Sidecar's transport: a Sidecar peer can't accept an HBONE dial (it would `hbone_required`-502). (`listener_plan()` in `modes/mesh/mod.rs` is the source of truth: Sidecar = capture :15001 + mTLS :15006; Ambient = capture :15001 + HBONE :15008.)

- **Ingress (inbound) — DONE for both.** Sidecar inbound: `materialize_sidecar_inbound_proxies` → loopback routes (:15006 → `127.0.0.1:appPort`), **one sibling per HTTP-family service port**. **Sidecar `ingress[]` custom listeners (F6 §6.2)**: when the applicable Sidecar declares `ingress[]` (resolved CP-side into `MeshSlice.local_ingress_listeners`, gated by `FERRUM_MESH_SIDECAR_ENFORCED`, NOT dry-run; rides ECDS carrier `LocalIngressListenersCarrier`), they **REPLACE** the service-port default inbound materialization for that workload (Istio semantics) — `materialize_sidecar_ingress_listener_proxies` emits one `__mesh-ingress-{ns}-{svc}-{port}` loopback HTTP route per HTTP-family resolved listener and one `local_inbound_tcp_routes` relay per stream-family resolved listener (issue #3260; declared LISTENER port → the entry's `defaultEndpoint` loopback target; HTTP hosts = the local service's FQDN variants). **Fail closed on the DECLARED signal, not on what resolved**: `MeshSlice.sidecar_ingress_declared` (a separate bool marker riding its OWN carrier `SidecarIngressDeclaredCarrier` — set true whenever the applicable Sidecar DECLARES an `ingress` block, independent of how many entries resolved) gates the materializer; when declared, the service-port defaults are SKIPPED even if `local_ingress_listeners` is empty (all entries unsupported / no local-service anchor), so an all-unsupported `ingress[]` yields NO inbound routes rather than fail-open-exposing the defaults the operator replaced. **Omitted vs explicit-empty (round-2 fix, Istio-faithful):** an OMITTED `ingress` keeps the defaults; a DECLARED `ingress` — *including an explicit empty `ingress: []`* — replaces them. The K8s translator sets `MeshSidecar.ingress_declared` on `spec.ingress` PRESENCE (mirroring `egress_inherits_defaults`'s omitted-vs-explicit-empty split); `resolve_applicable_sidecar_ingress` folds it as `ingress_declared || !ingress.is_empty()` (non-empty always declares; the bool adds the explicit-empty case, default-false on the native source). **`content_eq` MUST compare `sidecar_ingress_declared`** (round-2 fix): the marker flips false→true while `local_ingress_listeners` stays empty (no-ingress → all-unsupported-ingress), so omitting it from slice equality would let MeshSubscribe/update dedupe keep serving the stale default routes. Ingress resolution + the local-service anchor are **decoupled from egress-scope inheritance** (an ingress-only Sidecar usually omits `spec.egress`, so `applicable_sidecar` for egress can be `None`; the slice resolves `local_inbound_services` independently for the ingress case via `select_applicable_sidecar` + `resolve_local_workloads`). Ingress ids classify as `Inbound` (`is_mesh_inbound_route_id`/`mesh_route_direction`) and fold into `mesh_inbound_ports`, reusing `select_mesh_inbound_port_route` — but the orig-dst AND authority both match the **listener port** (`MeshInboundSibling.orig_dst_match_port == authority_port == listener port`; default service-port siblings keep `orig_dst_match_port = backend_port`). **Authz on the LISTENER port (security)**: `MeshInboundPortGroup.is_ingress` makes `select_mesh_inbound_port_route` return the selected sibling's listener port, stamped onto `RequestContext.mesh_inbound_listener_authz_port`; `mesh_authz`'s `mesh_inbound_app_port` authorizes an ingress route on that LISTENER port (e.g. 8443), NOT the `defaultEndpoint` backend port — so an AuthorizationPolicy `port`/`destination.port` DENY scoped to the listener port is enforced (authorizing on the backend port would fail a DENY OPEN). Service-port default inbound routes keep authorizing on `backend_port`; an ingress id with no stamped listener port fails closed (never the backend port). Loopback (`127.0.0.1`/`::1`) and instance-IP (`0.0.0.0`/`::` → loopback) `host:port` endpoints resolve for modeled HTTP-family and stream-family (`tcp`/`tls`/db) protocols; admissible `unix://` endpoints resolve for supported HTTP-family protocols and remain subject to the data plane's explicit containment/ownership/mode gates; arbitrary IPs, `Udp`/`Unknown` protocols, inadmissible Unix paths, and omitted `defaultEndpoint` are dropped fail-closed and stay in `deferred_fields`. **Protocol classification:** a custom inbound listener routes recognized HTTP-family tokens onto HTTP routes and recognized stream-family tokens onto raw-TCP inbound relays (issue #3260). The K8s ingress translator uses `sidecar_ingress_app_protocol` (NOT the generic `app_protocol`): `https` → `Http2` (HTTP route); recognized stream tokens → their `AppProtocol` (TCP relay); a MISSING protocol → `Tcp` (Istio default, stream-modeled); an UNRECOGNIZED string (e.g. a `HTPS` typo) → `Unknown` (deferred) — never guessed as HTTP or as a live TCP listener. The native source rejects a mistyped `AppProtocol` at deserialization; an omitted native protocol stays `Unknown` and defers. The service-port default path keeps its own `Unknown → HTTP` convention via `is_http_family_mesh_protocol` (untouched). Status writer reports `ingress_modeled` count + per-reason deferrals via the SHARED modeled/HTTP/stream predicates (routing through `sidecar_ingress_app_protocol`), so translation/resolution and the report never diverge; the resource is still accepted. **Carrier re-validation (round-2 fix):** `local_ingress_listeners` can arrive already resolved over the xDS/native carrier, so BOTH the back-projection chokepoint (`mesh.local_ingress_listeners` in `prepare_*`, feeding the router grouping) AND `materialize_sidecar_ingress_listener_proxies` re-check each carried endpoint via `ResolvedIngressListener::endpoint_is_valid` (modeled protocol plus either a loopback host/nonzero listener+backend port or one mutually exclusive, syntactically valid and contained Unix backend — the same allowlists `resolve` and the data-plane Unix gate enforce); a malformed/hostile carrier (off-box host, `:0` port, `Unknown`/`Udp` protocol) is dropped fail-closed, never dialed. Unix backends are HTTP-family only and their carried protocol must agree with the derived h2c marker; stream-family ingress remains loopback TCP and never widens onto a Unix or UDP lane. **The carried `protocol` has NO compatibility default** (issue #3260): an OMITTED carrier `protocol` decodes to `Unknown` and is inert on BOTH lanes, exactly like an explicit `udp` — do NOT re-add a `default = Http` fn, that turns one omitted wire field into a live HTTP listener. **Authenticated CONNECT lane (issue #3260 — the identity-protected path):** a peer Sidecar's raw-TCP egress reaches the destination as a FRESH mesh-mTLS H2 CONNECT to `:15006` whose `:authority` is `pod-ip:<declared listener port>`, which NEVER touches the REDIRECT-captured `local_inbound_tcp_routes` table. `build_inbound_hbone_relay_proxy` therefore consults `MeshConfig::resolve_sidecar_ingress_connect_relay` BEFORE the ordinary open-relay guard and remaps the authority onto the listener's validated loopback `defaultEndpoint` (`pod-ip:16379` -> `127.0.0.1:6379`) through the reserved id `__mesh-ingress-connect-relay` (`MESH_INGRESS_HBONE_RELAY_PROXY_ID`), stamping the DECLARED listener port onto `RequestContext.mesh_inbound_listener_authz_port` so `mesh_authz` authorizes on it (the id carries `MESH_INGRESS_PROXY_ID_PREFIX`, so an unstamped ingress id fails closed instead of authorizing on the backend). PeerAuthentication resolves on the `defaultEndpoint` app port on BOTH shapes (direct capture translates the listener port via `MeshInboundTlsPolicy.app_port_by_orig_dst_port`; the remap arrives with `backend_port` already equal to it). The remap is NARROW and fail-closed: byte-stream CONNECT only (never `connect-udp` — do not widen UDP), the authority host must be in the unambiguously resolved local-service workload set (`MeshConfig.local_workload_addresses`) AND equal the accepted connection's concrete local IP (so a sibling replica sharing the service identity is refused), and the declared port must resolve to EXACTLY ONE valid, owner-stamped, STREAM-family listener; ambiguity / missing owner / off-box / `:0` / `Unknown`/`Udp` / HTTP-family / unavailable accepted local IP all Deny. `MeshConfig.sidecar_ingress_declared` is back-projected independently of the surviving listener list: once an ingress block is declared, unlisted ports and explicit-empty/all-invalid/carrier-rejected sets Deny instead of falling through to the ordinary transparent relay; only an omitted ingress block returns `NotDeclared`. The marker back-projection is **`MeshTopology::Sidecar` ONLY** (mirroring `materialize_sidecar_inbound_proxies`'s own topology early return): `FERRUM_MESH_SIDECAR_ENFORCED` is topology-independent, so an Ambient/Waypoint proxy can carry a slice whose applicable Sidecar declares `ingress[]` — and those topologies materialize NO inbound routes, so an ungated marker would `Deny` every transparent-relay CONNECT (an inbound outage, not a fail-closed refinement). `handle_hbone_request` re-checks the EFFECTIVE destination against the same declared mapping (`sidecar_ingress_connect_relay_endpoint_matches`) after the plugin chain, so a `mesh_route_dispatch` override / upstream selection / mid-flight withdrawal cannot widen it. The Ambient-only relay behaviors keyed on `MESH_INBOUND_HBONE_RELAY_PROXY_ID` (NodeWaypoint socket mark, Ambient UDP source scoping, ServiceWaypoint destination-scope superset) deliberately do NOT apply to the ingress id. Omitted `defaultEndpoint` deserializes to empty (`#[serde(default)]`, matching the K8s path) and defers at `resolve()`. Custom `bind` opens NO separate OS listener (capture funnels through :15006; issue #3266 is separate); `captureMode: NONE` not honored. `validate_unique_listen_paths` exempts ingress siblings as direction code `2` (outbound=0, service-port inbound=1, ingress=2). Listener identity/grouping is forward-derived from `local_ingress_listeners` (`mesh_ingress_listener_groups`, ids via stamped `owner_namespace`/`owner_service`), never parsed. Multi-port disambiguation is post-match (`select_mesh_inbound_port_route`; groups from `mesh_inbound_service_groups` over the LOCAL-INBOUND view `MeshConfig.local_inbound_services` — a `serde(skip)` runtime back-projection set in `prepare_normalized_gateway_config_for_mesh`, because the egress-narrowed `services` can lack the local service), by priority: inbound orig-dst (REDIRECT-captured plain inbound; port = CONTAINER port, matched against `proxy.backend_port`) → request authority port (peer-sidecar direct dials; port = SERVICE port, the channel the multi-port-aware egress rewrites) → single-DECLARED-port passthrough → **fail-closed 502** (`PortSignalUnavailable`/`PortNotMaterialized`; a present-but-unmatched orig-dst never falls through to the authority). **The single-port passthrough is for NON-ingress SERVICE-default groups only (round-2 fix):** a single-listener INGRESS group (`is_ingress`) requires a present port signal to MATCH the declared listener port — a request naming an undeclared port fails closed (`PortNotMaterialized`) instead of being absorbed onto the sole listener; a no-signal request still falls through to it. (A single-port service-default group keeps the back-compat any-port passthrough.) The inbound materializer's operator-yield scan excludes only the service's OWN sibling ids — another local service's route on an overlapping bare-name host still wins first-materialized. `orig_dst` is now read on BOTH directions' capture listeners (one getsockopt per accept), but the accepted socket's own local address (`RequestConnectionMetadata.accepted_local_addr`, the CONNECT remap's replica proof) is resolved ONLY on the INBOUND mesh listener and only for a wildcard bind — do not widen that gate to `mesh_direction.is_some()`, which charges a `getsockname` to every captured EGRESS accept whose `orig_dst` already answers `destination.ip`; the outbound direction keeps its own LAZY `getsockname` fallback inside `connection_destination_ip`. ## Scope And Policy Semantics

- Scope-aware resources must use the shared `policy_scope_applies_to_workload` / `scope_applies_to_workload` helpers. Do not fork predicates.
- Single-winner precedence (`WorkloadSelector` > `Namespace` > `MeshWide`) applies only where one effective setting is resolved, such as `PeerAuthentication` and `MeshProxyConfig`.
- `MeshPolicy` and `MeshRequestAuthentication` are additive after filtering. `MeshTelemetryResource` merges by section.
- Authorization evaluation is DENY first, then ALLOW. Any ALLOW rule with no match causes implicit deny.
- `RequestMatch` negative fields (`not_methods`, `not_paths`, `not_hosts`, `not_ports`, `not_port_patterns`) are conjunctive with positive fields in one rule. Do not split them into separate deny policies.
- **Outbound traffic policy has THREE precedence tiers and ONE resolver** (issue #3262): `MeshSlice::effective_outbound_traffic_policy` = workload-scoped `sidecar_outbound_traffic_policy` → mesh-wide `outbound_traffic_policy` → `FERRUM_MESH_OUTBOUND_TRAFFIC_POLICY`. Both consumers call it — `inject_mesh_global_plugins` (HTTP-family `mesh_outbound_registry`) and `refresh_mesh_outbound_enforcement` (stream-family `MeshOutboundEnforcement` slot) — so the two transport families can never disagree about whether the gate is **armed**; do not re-derive the precedence at a call site. That shared input is the armed/disarmed DECISION ONLY, **not** the admitted registry CONTENTS: on the multicluster path HTTP-family injection runs against the MERGED materialization slice (`merged_slice`, poller-discovered remote workloads/services unioned into `workloads`/`services`) while `refresh_mesh_outbound_enforcement` runs against the UN-MERGED base slice, so a remote-cluster destination can be admitted on HTTP and refused on a stream connect (the fail-closed direction). Do not restate this as "the two lanes are identical". The Sidecar tier is resolved CP-side by `resolve_applicable_sidecar_outbound_policy` (`select_applicable_sidecar` tier precedence, NO egress `inherits_defaults` walk — Istio picks one Sidecar per workload and an omitted block simply inherits the mesh-wide value) and is gated by `sidecar_enforced && !sidecar_dry_run`, the INGRESS gate, not the looser egress one: arming/disarming the registry gate is a live behavior change and dry-run must not do it. **One `select_applicable_sidecar` scan is shared** with `resolve_selected_sidecar_ingress` (same gate, same tier precedence, same `effective_labels`); egress keeps its own scan because `resolve_applicable_sidecar_egress` walks `inherits_defaults` under the looser gate. **`labels_ambiguous` must not relax the gate** (security): `effective_labels` is then only the INTERSECTION of several same-SPIFFE workloads' divergent label sets, so a real `workloadSelector` `REGISTRY_ONLY` Sidecar can miss the intersection and selection would fall through to a namespace-default `ALLOW_ANY`. The resolver therefore takes the `policy_candidate_labels` candidate sets (empty unless ambiguous), resolves each on its own, and folds by `outbound_policy_strictness` keeping the strictest — rank `Some(RegistryOnly) > None (inherit, which may itself be RegistryOnly) > Some(AllowAny)`. The fold includes the intersection answer, so it can only ever TIGHTEN; `max` is order-independent, so precedence stays deterministic; it is cold-path and bounded (`candidates × sidecars`, once per slice build). Do not "simplify" it back to the intersection alone. `select_applicable_sidecar` also ranks a ROOT-namespace `workloadSelector` Sidecar ABOVE a selector-less default in the workload's own namespace — a deliberate divergence from Istio (which resolves the workload's namespace entirely before consulting the root namespace) so a tenant cannot displace a targeted mesh-operator rule with a permissive namespace catch-all; since #3262 it also decides egress enforcement, so re-deciding it is a security change, not a cleanup. `content_eq` MUST compare `sidecar_outbound_traffic_policy` — an edit to only `Sidecar.outboundTrafficPolicy.mode` leaves every other field identical, so omitting it lets dedupe keep a stale gate live. Its own ECDS carrier (`SidecarOutboundTrafficPolicyCarrier`) is deliberately separate from `OutboundTrafficPolicyCarrier`: collapsing the tiers would make a Sidecar `ALLOW_ANY` indistinguishable from a mesh-wide one and break the delete-falls-back-to-mesh-wide path. K8s translation preserves the Istio Sidecar API default WITHOUT rejecting the resource (`classify_sidecar_outbound_traffic_policy`, shared with `istio_status::sidecar_status` so enforced and reported never diverge): an omitted/null `mode` in a present object resolves to `AllowAny` with no deferral; omitting the entire block still means inherit. An unrecognized/non-string `mode`, a non-object block (an explicit top-level `outboundTrafficPolicy: null` included — the operator asked for a policy, so the ambiguity fails closed rather than inheriting), or a present NON-NULL `egressProxy` resolves to `RegistryOnly` + a `deferred_fields` reason. An explicit `egressProxy: null` IS normalized to absent (proto-JSON "unset"), so it does not force `REGISTRY_ONLY`; the declared mode is honored, or the `ALLOW_ANY` API default applies when mode is omitted/null. The degradation is reported per-resource in `deferred_fields` (always current) plus a per-occurrence `debug!` and exactly ONE process-lifetime `warn!` — translation re-runs on every reconcile and full sync, so a per-resource `warn!` re-fires forever for a permanently unrepresentable Sidecar; do not reintroduce one, and do not add per-resource dedupe state. `status.ferrum.translation.outbound_traffic_policy_enforced` is resource-local and means ONLY "translatable policy present AND the rollout gate is on" — NOT that this Sidecar was selected for any workload (a `workloadSelector` matching nothing still reports `true`); a REJECTED Sidecar reports it explicitly `false`. Do NOT "fix" this by returning `Err` — a rejected Sidecar is DROPPED by `translate_k8s_objects_collecting_skips`, which also drops its `egress` narrowing and WIDENS both the slice service view and the derived registry. `ALLOW_ANY` relaxes ONLY the registry gate; egress scope, `mesh_authz`, PeerAuthentication/mTLS and peer-SVID pinning, the HBONE/mesh-mTLS open-relay guard, DNS/raw-IP strict indexes, and topology transport gates are independent and still apply.
- Istio empty-rule translation must preserve action semantics: ALLOW with no `rules` is allow-nothing via a never-matching rule; DENY and AUDIT with no `rules` are no-ops.
- NodeWaypoint per-pod policy scoping (`per_pod_policy_scoping`) is resolved per request from `node_waypoint_policy_scope`. The HTTP/HBONE accept path populates it from the resolver (`proxy/mod.rs`); the TCP/UDP stream accept loops always pass `None`, so only `MeshWide` policies are evaluated on streams. A config-apply that has stream proxies + scoped policies in NodeWaypoint topology must keep emitting the one-shot warning. Do not silently start enforcing scoped stream policies without wiring the resolver end-to-end and updating `docs/mesh.md`.
- Mesh authz `source.ip`/`ipBlocks` uses `direct_client_ip` (immediate peer) and `remote.ip`/`remoteIpBlocks` uses `client_ip` (trusted XFF/PROXY-resolved) on both the HTTP and stream paths. IP-block matchers fail closed when the typed IP evidence is absent.
- **`when:` conditions cover the complete documented Istio key set and distinguish ABSENT from UNSOURCEABLE** (issue #3236). `classify_mesh_condition_key` / `MeshConditionKeyKind` (`src/modes/mesh/config.rs`) is the one typed classification; `validate_mesh_condition` is the one validator behind all three surfaces (K8s translator `condition_match`, `validate_mesh_config`, `mesh_authz`'s `validate_policy_ip_inputs`) and emits field-specific diagnostics. Dynamic header/claim keys MUST match Istio `validateMapKey`: first `[` + final `]` around a non-empty interior only, with NO `HeaderName` parse or interior-bracket/whitespace restriction. Known pseudo-headers (`:authority`, `:method`, `:path`, `:scheme`) source typed `RequestContext` facts; other unmaterializable interiors remain absent. An attribute the path CAN source but that this request lacks follows ordinary Istio `values` / `notValues` rules. An attribute the path can NEVER source — an HTTP-only key on L4 (`MeshAuthzRequest.protocol == MeshAuthzProtocol::L4`), a source/remote/destination IP or destination port with no transport evidence, or any `experimental.envoy.filters.*` key — is resolved by `condition_kind_is_sourceable` and is fail-closed BOTH ways: DENY ignores the field and still matches, ALLOW/AUDIT can never match. **Value grammar is PER KEY, not one generic matcher** — `condition_scalar_value_matches` classifies once per `when[]` entry and dispatches: IP-valued keys are CIDR containment; `source.serviceAccount` is EXACT over `<namespace>/<service-account>`, with a bare `<service-account>` resolved against the OWNING `MeshPolicy.namespace` (threaded from `evaluate_mesh_authorization_policies` → `rule_matches` → `matches_conditions`, compared in place so no per-candidate `String` is built) and every `*` rejected at admission because Istio compiles it to an exact matcher; `source.namespace` uses the general `wildcard_match` because Istio's `srcNamespaceGenerator` rewrites EVERY `*` to `.*` (mid-string and repeated stars included); `source.trustDomain` keeps the presence/prefix/suffix matcher ONLY because `validate_mesh_condition` enforces Istio's `CheckTrustDomainValues` grammar (exact, `*`, one leading or one trailing `*`, no `/`) first. Everything else is `matcher.StringMatcherWithPrefix`, where a mid-string `*` IS a literal exact match. `source.serviceAccount` additionally carries Istio's stricter 16-entry / 320-byte caps on BOTH `values` and `notValues`; the common 64-condition / 256-entry / 512-byte caps still govern every other key. Do NOT re-express unsourceable as a missing attribute; a `notValues`-only ALLOW would then grant every raw connection. A documented-but-unsourceable key must stay ADMITTED at translation — rejecting the resource drops the whole AuthorizationPolicy, which is fail-OPEN for a DENY. `MeshAuthzRequest::default()` is deliberately `L4`; both production callers set `protocol` explicitly. HTTP `destination.ip` comes from `orig_dst` before `RequestContext::destination_ip`. Stream authz reads `StreamConnectionContext::connection_destination_*`, which prefers capture/trusted-PROXY evidence and may fall back to the accepted socket local address; L4 `stream_match.destinationSubnets` reads ONLY `StreamConnectionContext::destination_*`, so an ordinary listener bind address never becomes original-destination routing evidence. None of these facts comes from a header; the HTTP wildcard-bind `getsockname()`/`Connection::local_ip()` fallback is gated on `OperatingMode::Mesh` so non-mesh accept loops are unchanged.

## HBONE Identity Boundary

- HBONE is HTTP/2 CONNECT over mTLS on port 15008.
- `is_hbone_connect()` only detects the wire shape (H2 CONNECT + optional `x-ferrum-mesh-protocol`/`x-istio-protocol: hbone` marker); it does not imply authentication and is only safe for non-relay decisions (path normalization, metadata tagging, body-buffering branch).
- Relaying a CONNECT as an HBONE tunnel requires an authenticated, trust-domain-verified peer (`ctx.peer_spiffe_id.is_some()`, i.e. `is_authenticated_hbone_connect()`). `handle_hbone_request` rejects a peerless CONNECT — bare or marker-bearing — with `403 Forbidden` before dialing/circuit-breaking any backend, stamping `mesh_authz.deny_policy=hbone_unauthenticated_peer`. The explicit marker path is not a bypass. This is separate from (and additive to) TLS-time trust-bundle peer verification.
- Baggage `source.principal` rewrites the authz principal only when the authenticated peer is in `mesh_authz.trusted_hbone_assertors` and the baggage trust domain matches the peer cert or `FERRUM_MESH_TRUST_DOMAIN_ALIASES`. Ambient UDP may additionally carry `source.pod_uid`; use it for namespace/selector scope ONLY after that same principal trust gate succeeds and the live slice maps the exact, unambiguous pod UID to the same SPIFFE ID. Missing/malformed/stale/mismatched/untrusted UDP evidence evaluates mesh-wide policies only.
- Untrusted assertors keep their own peer-cert identity even when baggage is present.
- Never infer Ambient UDP pod scope per datagram. `NetnsUdpCaptureManager` fixes the node-agent-registry-derived `(pod UID, SPIFFE ID)` evidence per pod-netns producer and `get_datagram_tunnel` stamps it on the authenticated CONNECT. Conflicting identities in one shared netns suppress the stamp (mesh-wide fallback).
- Dropped baggage must surface in transaction metadata as `mesh_authz.ignored_baggage.untrusted_assertor=true`; denied requests contribute `mesh_authz.deny_policy=untrusted_assertor`.
- Trust-domain mismatches use the existing `trust_domain_mismatch` reason.
- Default trusted assertor service accounts are `ztunnel` and `waypoint`. `FERRUM_MESH_TRUSTED_HBONE_ASSERTORS` accepts bare service-account names or full SPIFFE IDs.
- Explicit empty `trusted_hbone_assertors: []` disables baggage rewriting entirely.
- Keep fallback baggage key aliases in `HboneIdentity::from_headers()` in sync with tests.

## Node-Waypoint Per-Pod Policy Scope

- One node-waypoint listener serves many pods; source pod identity comes from the eBPF `connect4`/`connect6` cgroup-stamped `SO_COOKIE` record, resolved through `NodeWaypointIdentityResolver`. The hooks read the identity from `FERRUM_WORKLOAD_IDENTITY` keyed by `bpf_get_current_cgroup_id()` — the *container leaf* cgroup, a child of the pod cgroup on every K8s cgroup driver — so the node-agent enrolls the identity under the **whole pod cgroup subtree** (pod inode + descendant container-cgroup inodes via `cgroup::collect_cgroup_tree_inodes`) and re-walks on reconcile so late-starting/restarted containers are picked up. Keying only the pod inode would miss the leaf and fail closed in real pods. `FERRUM_INCLUDE_PORTS` (per-pod `includeOutboundPorts` narrowing) is keyed the same way and enrolls the same subtree, re-walking on every reconcile (like identity) so a container leaf that starts/restarts after the initial pod event still picks up the policy; unannotated pods short-circuit before any walk.
- **Lazy-identity reclamation:** the production enrollment path (hash-join in `resolve_record`) binds no cgroup and nothing calls `remove_identity`, so the periodic sweep (`sweep_cgroup_stale_identities`, gated by `FERRUM_MESH_NODE_WAYPOINT_CGROUP_SWEEP_INTERVAL_SECS`) reclaims a non-cgroup-bound identity only when its `pod_uid` is no longer referenced by any live cookie record **and** its identity `Arc` has no other holder (`strong_count == 1`) — a churned pod's accept-side cookies age out of `cookie_records` (the `sock_ops` program removes the orig-dst record on TCP close, so closed-connection cookies don't linger in the LRU map until pressure — without that, dead pods would never age out on a low-churn node), so its orphaned identity and per-pod scope are reclaimed instead of accumulating. The `strong_count` guard is load-bearing, not decoration: HTTP/HBONE connections store the resolved identity `Arc` for their lifetime and re-query the per-pod scope per request, so the BPF LRU evicting a live connection's cookie must not let the sweep drop its scope (it would downgrade later streams to mesh-wide); the held `Arc` keeps the pod un-evictable until the connection closes. TCP resolves its scope once at accept and never re-queries, so it's covered by the cookie-reference check alone. A still-live idle pod re-enrolls on its next connection. cgroup-bound identities remain the cgroup-binding pass's domain — the idle pass never touches them.
- HBONE/HTTP and raw **TCP** stream accept paths both resolve the connection's pod identity and stamp `node_waypoint_policy_scope` (HTTP: `RequestContext`, TCP: `StreamConnectionContext`) via `policy_scope_for_pod(pod_uid)`, so `mesh_authz` enforces Namespace/WorkloadSelector-scoped policies per source pod. The TCP path threads the resolver `ProxyState` → `StreamListenerManager::set_node_waypoint_identity_resolver` (injected before the first stream reconcile) → `TcpListenerConfig` → accept loop (`resolve_node_waypoint_stream_scope`).
- **GAP-2M accept-side bridge** (applies to both HBONE/HTTP and TCP paths equally; **IPv4 and IPv6**): `connect4`/`connect6` key the orig-dst record by the connecting-socket cookie, but accept paths look up the accept-side `SO_COOKIE`. The bridge is implemented in the kernel `sock_ops` program (`ebpf/ferrum-ebpf/src/sock_ops.rs`): at active-established it re-keys the record by `(netns cookie, connection tuple)` (`FERRUM_ORIG_DST_BY_TUPLE4` / `FERRUM_ORIG_DST_BY_TUPLE6`), and at passive-established it re-stamps it into `FERRUM_ORIG_DST4`/`FERRUM_ORIG_DST6` under the accept-side cookie, so the resolver (fed by `orig_dst_bridge`) resolves scoped policies with no further proxy-side changes. The IPv6 ctx address words (`local_ip6`/`remote_ip6`) are read element-by-element with verifier-safe **volatile** per-`u32` loads at explicit ctx offsets (`read_ctx_ip6` over the four offsets — the same per-element technique `connect6` uses; a whole-`[u32;4]` ctx copy trips the verifier), keyed by `ConnTuple6`, so v6 resolves on the same footing as v4 (the userspace resolver already merges both families by socket cookie, so only the kernel re-stamp was missing). Per-pod identity enrollment is wired with no separate channel: slice apply installs a `workload_spiffe_hash` → SPIFFE index alongside the policy scopes, and `resolve_record` lazily enrolls `pod_uid` → identity by hash-joining that index against the eBPF-stamped `(pod_uid, workload_spiffe_hash)` on first sight (an unmatched hash fails closed as `UnknownPod`). The current slice index is re-checked on **every** resolve, not only first-sight: a cached `pod_uid` whose workload a later slice removes (its hash leaves the index) stops resolving — the cached-identity branch fails closed (HBONE drops, TCP downgrades to mesh-wide) instead of serving the orphaned identity, and re-validates for free if the workload returns. The gate (`workload_spiffe_hash`→SPIFFE) and the scope index are **one `ArcSwap<NodeWaypointSlice>` generation**: scope is keyed **strictly** by the exact **pod UID** the eBPF stamps (`scopes_by_pod_uid`, built from the slice's per-pod workloads' `metadata.uid`) — a captured pod is **never** resolved through a SPIFFE-keyed index, so pods that share a service account (one SPIFFE) but carry different labels are scoped independently (each against its own labels) rather than collapsed to the label intersection, and a pod whose workload is absent from the live slice fails closed (no scope) instead of borrowing a same-SPIFFE workload's labels. Scope is reclaimed by slice updates, not identity lifecycle (`remove_identity`/sweep do not touch it). `resolve_*` returns the identity **and** its scope from a single load of that generation, so a slice reload can never pair a resolved identity with an old/missing scope (the "never partial" invariant for scoped authz). The TCP path captures both at accept and persists them for the stream; HBONE/HTTP re-queries the scope per request, each read from one coherent generation. The `netns_cookie` (`bpf_get_netns_cookie`) is load-bearing, not decoration: captured connections all target `127.0.0.1:15001` / `[::1]:15001`, so the tuple collapses to loopback + an ephemeral port that can collide across pod netns in this one global map — the per-netns cookie keeps each pod's key distinct (preventing cross-pod record overwrite / identity misattribution) while staying identical for the two ends of a same-netns connection. Do not drop it from the key. (**Distinct from** the in-netns OUTBOUND capture listener + `connect6`'s `ipv6_outbound_deny`, which remain IPv4-only — those concern the pod-loopback redirect datapath, not the accept-side cookie bridge fixed here.) **Verification:** CI compile-checks the program (`build-ebpf`) and load/attach-tests every program — incl. the bridge — on a real ≥5.7 kernel (`ebpf-live`, which already caught and forced fixes for `connect6`/`getpeername6`/`sock_ops` verifier rejections); the full connect→capture→accept datapath (tuple byte-order, end-to-end resolution) is **not** CI-verified and needs a live multi-pod node. Safe by construction: a tuple/byte-order mismatch writes no accept-side record → resolution stays fail-closed, never misattributed.
- **In-netns outbound capture listeners** (always on for NodeWaypoint topology): `connect4` rewrites a captured pod's outbound to `127.0.0.1:15001` in the **pod's** loopback, but a single outbound listener bound `127.0.0.1:15001` in the host/proxy netns can never receive a pod loopback connection — so a host-only listener leaves node-waypoint outbound capture non-functional on a real multi-pod node (connections refused, scoped enforcement never engages); the GAP-2M `sock_ops` cookie bridge also independently requires the accept socket to share the connecting pod's netns. `NetnsCaptureManager` (`src/proxy/netns_capture.rs`) opens one `127.0.0.1:15001` listener **inside each enrolled pod's netns** (`setns(CLONE_NEWNET)` on a dedicated thread, deduped by netns inode), so captured pod-loopback connections are accepted there and the same-netns cookie bridge resolves source identity. Pod discovery reuses the pinned-path IPC pattern: the node-agent publishes a registry dir `FERRUM_MESH_NODE_WAYPOINT_POD_REGISTRY_DIR` (default `/run/ferrum/node-waypoint-pods`), one file per enrolled pod (name = pod UID, contents = pod cgroup path), written on enroll / removed on teardown; the manager polls and reconciles listeners (open on add, close on removal). The listener binds pod loopback on the configured `outbound_listen_addr` port (not a hardcoded `15001`, and not the configured IP — `connect4` always rewrites to loopback; skipped when that port is `0`), shares one `max_connections`-sized connection semaphore across all in-netns listeners, reopens when the pod's registered IP changes (so `source_ip_override` tracks the pod IP; the marker is retracted before reopen so a failed reopen can't look ready), and closes when a pod UID moves to a different netns (preserving the transient-unresolvable grace). **Deferred-redirect readiness gate:** to avoid redirecting a pod before its listener exists, the node-agent defers attaching `connect4` at enrollment (`connect6` is instead attached up front as a **fail-closed IPv6 denier** — the in-netns listener and bridge are IPv4-only, so the `ipv6_outbound_deny` capture-config flag makes `connect6` return `EPERM` for captured v6 rather than letting IPv6 egress bypass `mesh_authz`; excluded v6 via CIDR/port excludes still flows) and enables `connect4` only after the proxy writes `<registry_dir>/.ready/<pod_uid>` (on listener open; removed on close/reopen), polling on a 1s tick with a ~30s bounded fallback — so the registry dir must be mounted RW for the proxy. Linux-only (`setns`, `/proc/<pid>/ns/net`); non-Linux is an unsupported stub. Reconcile/registry logic is unit-tested; the `setns`/bind path and full pod-loopback datapath are **not** CI-testable (need a live multi-pod node) — implemented, live-datapath-unverified.
- A missing scope sets `mesh_authz.scope_missing=true` and, when any namespace/selector-scoped policy is configured, **fails closed** (Reject 403, `mesh_authz.deny_policy=scope_missing`) on **both** the HTTP/HBONE request path (per request) and TCP/UDP streams (at accept) — a missing scope means the pod's workload left the live slice generation (it is derived from the same generation that vouches the identity, so it is not an enrollment race), so a long-lived HTTP/2 connection from a removed workload must not keep serving with scoped policies silently withheld. With only mesh-wide policies the mesh is fully evaluable and both paths fall through to mesh-wide-only. (At connection accept the HBONE listener still drops outright on an *unresolved identity*; this per-request/per-connection check additionally covers a workload removed *after* accept.)
- **UDP/DTLS** stream proxies stay mesh-wide-only and pass `node_waypoint_policy_scope: None`: a shared UDP frontend socket carries one cookie for all clients and there are no UDP capture hooks, so there is no per-source-pod cookie to resolve. Do not "fix" this by resolving the listener socket's cookie — that misattributes every session to one identity.
- Only `NodeWaypoint` topology installs the resolver. Sidecar/Ambient/east-west/egress and non-mesh stream proxies pass `None` and are unchanged.
- **Transparent inbound CAPTURE relay (#3287) stamps a DESTINATION scope, not a source one.** The tc ingress redirect steers unauthenticated direct plaintext into `proxy/node_waypoint_ingress_capture.rs`; the peer is off-node so there is no connect-side cookie and no source scope, but `per_pod_policy_scoping` is on for the topology — an absent `node_waypoint_policy_scope` would deny every captured connection `scope_missing`. `build_node_waypoint_capture_relay_entry` therefore resolves the captured `orig_dst` to **exactly one** slice `Workload` (no match, or two records with divergent `PolicyScopeCache`, fails closed) and carries that workload's scope on `MeshTcpInboundEntry.node_waypoint_policy_scope`, which `handle_mesh_tcp_inbound` stamps. The SAME workload resolution also yields the effective PeerAuthentication mode via `slice::resolve_effective_mtls_mode` against its own namespace/labels — **never** `ProxyState::mesh_inbound_tls_policy.modes_by_port`, which is keyed by port alone and would let a PERMISSIVE pod admit plaintext to a STRICT pod sharing the app port. Ownership resolves BEFORE the posture gate for that reason. Sidecar `MeshTcpInboundEntry`s (built in `RouterCache`) keep `socket_mark: None` + `node_waypoint_policy_scope: None`; do not stamp either there.
- **The capture resolver reads a DEDICATED cross-namespace inventory, never `mesh.workloads` / `mesh.peer_authentications`.** A NodeWaypoint in `ferrum` captures for enrolled pods in `payments`; both ordinary views are narrowed to the SUBSCRIPTION namespace, so they cannot name the destination and — worse — carry none of its PeerAuthentication, which made `resolve_effective_mtls_mode` default PERMISSIVE and admit direct plaintext to a STRICT pod. `MeshSlice.node_waypoint_capture_destinations` (workloads whose trusted `Workload.node_waypoint.spiffe_id` equals THIS NodeWaypoint's `workload_spiffe_id`) + `MeshSlice.node_waypoint_capture_peer_authentications` (candidates applicable to those destinations, via `peer_auth_applies_to_workload`) are the only inputs; `MeshConfig` back-projects both as `serde(skip)` runtime fields in `prepare_normalized_gateway_config_for_mesh`. Gated by `MeshSliceRequest.node_waypoint_capture_scoping` (topology `NodeWaypoint` only) — do NOT overload `ambient_udp_source_scoping`: NodeWaypoint UDP is mesh-wide-only by architecture. The CP resolves it in `filter_mesh_config_to_request` BEFORE the `workloads`/`peer_authentications` retains and AFTER `node_waypoint_capture_namespace_allowed` (the strict `Single`-scope evidence boundary shared with Ambient UDP) + the bearer `ns` claim; the value is PRESERVED on incremental refilter for the same reason assertors are (the stream-local config is already narrowed; deltas never carry mesh). Transports: proto field 9, `XdsNodeMetadata.node_waypoint_capture_scoping`, and two ECDS carriers. NEVER fold the inventory into `workloads`/`services`/`peer_authentications` (it would widen routing, known-destinations, the outbound registry, and this proxy's own inbound posture). `content_eq` MUST compare both fields or a STRICT flip is deduped away. Empty inventory = refuse the connection (`relay_destination_denied`), never fall back to `workloads`.

## PeerAuthentication And TLS Reload

- By default, inbound mesh mTLS mode resolves once from the initial slice.
- When all three `FERRUM_GATEWAY_SVID_*` paths are set, the inbound mTLS/HBONE listener uses a SPIFFE client-cert verifier that validates the peer SAN's trust domain against the gateway SVID local bundle plus slice federated bundles; without SVID material it falls back to chain-only verification over `FERRUM_FRONTEND_TLS_CLIENT_CA_BUNDLE_PATH`. STRICT requires a peer cert; PERMISSIVE trust-domain-validates an offered cert but still admits cert-less peers. The HBONE baggage trust-gate rests on this verified identity.
- Gateway SVID material also backs the inbound listener's **server identity** when no explicit `FERRUM_FRONTEND_TLS_CERT_PATH`/`KEY_PATH` is set (`load_mesh_frontend_server_identity` resolves the SVID leaf+key live from the slot as the server cert via `svid_rotating_mesh_server_identity`): a SVID-only mesh serves mTLS inbound instead of falling open to plaintext under PERMISSIVE. Explicit frontend TLS still takes precedence.
- The gateway SVID slot is fed by **either** configured material (`FERRUM_GATEWAY_SVID_*`, watched + rotated by `identity::svid_source_watch`) **or** a **CA backend** (`FERRUM_MESH_CA_BACKEND=spire|internal`): file/`file://` sources poll every second, provider sources use their configured secret-refresh cadence, and inline PEM remains static until configuration reload. Mesh startup runs `start_mesh_ca_backend_svid_source` (`src/modes/mesh`), which for `spire` fetches the gateway's own SVID from the SPIRE Agent Workload API (`FERRUM_MESH_SPIRE_AGENT_SOCKET`) by reusing the identity `fetch_loop` (`SvidFetchHandle::from_slot` + `with_installer`), and for `internal` self-issues from the dev-only `bootstrap_dev_root` `InternalCa`; either way it live-rotates the SVID into the **same** `gateway_svid_bundle` slot (and publishes it to a live inbound peer-verifier slot), so the inbound `SvidServerCertResolver`, the SPIFFE peer verifier, and the backend pools all pick rotations up with no restart. Startup blocks on the first SVID (`MESH_CA_INITIAL_SVID_TIMEOUT`, 30s; fail-closed) so the inbound listener never binds identity-less, a CA backend REQUIRES `FERRUM_MESH_WORKLOAD_SPIFFE_ID` (the fetched identity is pinned to it), and explicit `FERRUM_GATEWAY_SVID_*` configured material takes precedence when both are configured. Do NOT add a second source-of-truth slot — feed `gateway_svid_bundle`.
- Runtime inbound mTLS fail-closed (`enforce_mesh_inbound_fail_closed` + `decide_mesh_inbound_fail_closed`, issue #1523), at the startup TLS-setup path **and on PeerAuthentication live reload** (`plan_mesh_inbound_tls_reload`). Two cases, deliberately different severity: (1) a listener that would serve **plaintext** (resolved `ServerConfig` `None` — PeerAuthentication DISABLE or no usable server identity) is **refused under `FERRUM_MESH_PRODUCTION_MODE=true`**; **dev** allows it with a loud warning — an explicit DISABLE, or a no-identity posture already acknowledged by the config-time `FERRUM_MESH_ALLOW_NO_CA` gate, is intentional, so the runtime gate does not re-consult the opt-out. (2) a **configured-but-unloadable SVID verifier** (all three `FERRUM_GATEWAY_SVID_*` named but `build_mesh_inbound_spiffe_slot` returned `None` while the listener serves TLS) is a genuine fault — **fatal regardless of production** (mirrors the hard error a broken SVID cert/key gets in `load_mesh_frontend_server_identity`; `decide_*` is NOT consulted for it). At reload, "refuse" means reject the slice and keep the last-good mTLS config in its entirety (fail-closed by retention — never crash a live data plane, matching the failed-`ServerConfig`-rebuild contract above). `FERRUM_MESH_PRODUCTION_MODE` is read once at startup and threaded through `MeshInboundTlsReloadState.production` (process-fixed; a per-apply env read would also be test-racy). EastWestGateway (SNI passthrough, no termination listener) is exempt.
- The mesh `RequestAuthentication` (`jwks_auth`) plugin requires the JWT `exp` claim by default (`FERRUM_MESH_REQUEST_AUTH_REQUIRE_EXP=true`); operators may relax it. Expiry validation (rejecting present-but-expired `exp`) is always on.
- With `FERRUM_MESH_PEER_AUTH_LIVE_RELOAD_ENABLED=true`, only resolved mTLS mode, frontend client CA verifier, and the lock-free SPIFFE SVID bundle slot (federated trust domains) may hot-swap on slice apply.
- Frontend cert/key paths remain restart-required inputs for mesh peer auth reload.
- Coverage includes mesh HTTP/HBONE termination listeners and mesh-shared TCP+TLS / UDP+DTLS stream listeners.
- `apply_mesh_inbound_tls_reload` publishes swapped `ServerConfig` into HBONE, shared stream TLS, and active `DtlsServer` frontend DTLS configs.
- A failed inbound `ServerConfig` rebuild (or a client-CA-bundle snapshot read failure) is computed before proxy-config apply and **rejects the whole slice**, keeping the last good config in its entirety (the one `ServerConfig` backs both HTTP/HBONE and the shared TCP+TLS slot, so no authz/policy/ServiceEntry/endpoint update from that slice applies either) — fail-closed. Only the post-accept DTLS `FrontendDtlsConfig` rebuild keeps the previous config for that path and logs a warning without rejecting the slice. Do not reword the `ServerConfig`/snapshot warns back to a path-local "keeping previous TLS config" framing.
- `Disable` is rejected for Ambient and EgressGateway slice updates and keeps the last good config.

## DestinationRule And Materialization

- DestinationRule `connectionPool.tcp.connectTimeout` lands on `Upstream.port_overrides[port].connect_timeout_ms` and is enforced by HTTP/H2/H3, gRPC, TCP, and HBONE dispatch.
- Port-level `loadBalancer` and `outlierDetection` land on the same override slot and use isolated per-port LB counters/hash rings and passive thresholds for HTTP-family, gRPC, WebSocket, and HBONE.
- `connectionPool.http.maxRequestsPerConnection` remains parsed/validated but deferred at EVERY scope. `idleTimeout` and `http2MaxRequests` land on the existing per-port override fields at top-level and `portLevelSettings` scope, and are DEFERRED at subset scope (`ResolvedSubsetTrafficPolicy` carries neither, so a subset value reaches no effective proxy) — the translator warns and status lists them, keyed by the `subsets[].trafficPolicy.connectionPool.http.*` labels. `h2UpgradePolicy`, `maxRetries`, and `http1MaxPendingRequests` are carried at top-level, `portLevelSettings`, and subset scope with field-level precedence **per-port > selected subset > top-level**. `SubsetTrafficPolicy` and `ResolvedSubsetTrafficPolicy` preserve them; `GatewayConfig::resolve_dispatch_port_overrides` overlays the exact selected subset onto a per-proxy inherited fallback, so sibling subsets and unmatched proxies cannot leak policy. `h2UpgradePolicy` remains plain-HTTP-only; `DoNotUpgrade` restricts reqwest ALPN to `http/1.1`, and all HTTP-family pool keys include `upstream_subset` (the reqwest key also has its `h1` behavior discriminator). `maxRetries` caps only an existing per-request retry policy and never synthesizes retries. `http1MaxPendingRequests` is an honestly reinterpreted concurrent-in-flight-H1 cap keyed by `(host, DestinationRule policy port, selected subset)`; its sharded RAII guard releases on every success/error/deadline/cancellation/retry exit. Initial and rotated targets resolve effective policy from the immutable proxy snapshot. Invalid values fail closed with field-specific, value-redacted diagnostics. Translator and status must list `maxRequestsPerConnection` (all scopes) plus subset-scoped `idleTimeout` / `http2MaxRequests` as deferred, and nothing else.
- Dispatch projects port overrides through `resolve_effective_proxy_for_target()` onto the owned `Proxy` clone; direct H2 and gRPC builders consume H2 caps through `max_concurrent_streams` and `initial_max_send_streams`.
- **INHERITED top-level `connectionPool.http` fallback (#1806, extended to subsets)**: `Upstream.dispatch_port_override_fallback` (`#[serde(default, skip)]` derived) is the cold-path carrier for the inheritable top-level HTTP overlay. The three SUBSET-INHERITABLE fields (`h2UpgradePolicy`/`maxRetries`/`http1MaxPendingRequests`) accumulate there for EVERY upstream (`apply_subset_inheritable_connection_pool_http_to_port_override`) so a selected subset can overlay them without losing source-tier identity; non-SD upstreams still fan the REMAINING top-level HTTP fields (`idleTimeout`/`http2MaxRequests`) out onto `port_overrides` as before (`apply_non_subset_connection_pool_http_to_port_override`). An SD upstream (`service_discovery` set) can't fan the *top-level* overlay onto a known apply-time port set (targets resolve at runtime), so `apply_destination_rules` accumulates ALL of its top-level HTTP fields on that same fallback via the SAME `apply_connection_pool_http_to_port_override` helper. `resolve_dispatch_port_overrides` projects the fallback onto `Proxy.dispatch_port_override_fallback` (`#[serde(skip)]`), overlaying the EXACT effective selected subset's `ResolvedSubsetTrafficPolicy` (`dispatch_port_override_fallback_for_selected_subset`) into a proxy-local derived value — it never mutates the shared upstream and never consults a sibling subset, so sibling subsets and unmatched proxies cannot leak policy. `resolve_effective_proxy_for_target` and `cap_proxy_retry_for_target` consult the fallback (the TOP-LEVEL + selected-subset overlay ONLY — `dispatch_port_override_fallback_from_upstream` does NOT fold per-port entries into it; folding cross-leaks between ports on a multi-port upstream) ONLY when the selected target's POLICY port (`target.dispatch_policy_port()`) has no explicit `dispatch_port_overrides` entry — so an explicit `portLevelSettings` entry wins, giving field-level precedence **per-port > selected subset > top-level**. **Named `targetPort` is covered** (the former #1816 deferral): mesh SD targets whose resolved workload dial port differs from the declared Service port carry the owning Service port in the serde-skipped `UpstreamTarget.service_port_policy_key`, so dispatch keys DR policy by `dispatch_policy_port()` while still dialing `target.port` — an explicit per-port entry is honored even under a named `targetPort` remap (see `docs/mesh.md` "An explicit `portLevelSettings` entry..."). Immediate route-TABLE rebuild on a DR-only fallback/TLS/per-port projection edit is wired (#3243 / #1826): `ProxyState::delta_routes_changed` and the empty-delta publish path compare `#[serde(skip)]` DR-derived proxy fields (`dispatch_port_overrides`, `dispatch_port_override_fallback`, `resolved_tls`, mesh stream-relay dispatch maps) so route-held `Arc<Proxy>` values cannot stay stale. This is runtime-by-selected-port application of the overlay, NOT runtime-resolved target materialization (the rejected outbound-SD rework — see below). Adding these two derived fields churns every `Proxy`/`Upstream` struct literal (E0063) — run `cargo build --lib`.
- **HTTP/3 frontend effective-proxy coverage (#1806/#2020)**: the H3→HTTP plain bridge (`src/http3/cross_protocol.rs` `dispatch_plain`) resolves `resolve_effective_proxy_for_target` per attempt INSIDE its retry loop (an entry-level resolution backs the port-independent retry/buffering decisions), so the per-port `connectionPool.http` effective-proxy overrides (idleTimeout/http2MaxRequests/connectTimeout/TLS/h2UpgradePolicy-ALPN + the SD fallback) apply on the H3→plain reqwest bridge — `get_client` builds the client from the effective proxy and `build_plain_request_builder` reads its `backend_connect_timeout_ms` — and its local dispatch-policy rejects (per-port backend-TLS-SNI incompatibility → 502; `http1MaxPendingRequests` pending-cap → 503) run BEFORE backend admission per attempt, matching H1/H2 ordering. The standalone H3 frontend (`src/http3/server.rs`) applies the selected-target pipeline across ALL FOUR flavors: `cap_proxy_retry_for_target` runs right after target selection (so a DR `maxRetries` cap governs the H3 retry loops and the retry-dependent buffering / native-H3-suppression decisions), the first target's effective proxy backs the native-H3/streaming dispatch decisions, `ctx.matched_proxy` carries the retry-capped BASE proxy (H1/H2 parity — per-port TLS/timeouts are dispatch-time-only, never plugin-visible), and every loop that can rotate retry targets — the buffered native-H3 retry loop, the H3→plain and H3→gRPC bridges, and the H3 WebSocket dial loop — re-resolves the effective proxy per attempt from the capped UNRESOLVED base proxy so a rotated target never inherits the first target's port-level TLS/SNI/H1 policy. Mesh capture itself is TCP/UDP-only, so the H3 FRONTEND is never a mesh capture listener; it IS a mesh EGRESS surface for gRPC since #3284 (see `proxy-protocols.md` → “HTTP/3 And gRPC”), so do not read this as “H3 has no mesh dispatch”. Keep `docs/mesh.md` "Dispatch-path coverage" and the textual pins in `tests/unit/gateway_core/http3_selected_target_policy_tests.rs` in sync.
- `http_max_requests_per_connection` is a legacy carrier only; new DR translation does not populate or consume it.
- `connectionPool.tcp.maxConnections` and `tcpKeepalive` land on `max_connections` and `tcp_keepalive`. `maxConnections` is enforced by EVERY transport whose physical connection lifecycle Ferrum owns, all against ONE shared `backend_conn_limit::BackendConnectionLimiter` on `ProxyState.backend_conn_limit` keyed `(host, DestinationRule policy port)` — stream-family (TCP/TCP+TLS) dispatch; HTTP-family WebSocket dispatch (H1/H2 in `proxy/mod.rs`, H3 in `http3/websocket.rs`), which holds an RAII `BackendConnectionGuard` for the session and rejects over-cap upgrades with 503; the pooled multiplexed transports (see the next bullet); and the reqwest transports (HTTP/1.1 AND ALPN-negotiated HTTP/2), admitted at reqwest's own connector. `tcpKeepalive` is enforced by stream-family dispatch AND the socket-owning H2-family pools (direct-H2 `http2_pool`, `grpc_proxy`, HBONE `hbone_pool`, mesh-mTLS `mesh_mtls_pool`) via the shared `socket_opts::apply_pooled_tcp_keepalive` resolved at connection creation — direct-H2/gRPC key the override by the dial `backend_port`; HBONE/mesh-mTLS key it by the destination's APP/service port (NOT the transport dial port `:15008`/`:15006`) and apply it inside the shared `dial_h2_connect_sender` (so HBONE egress, Sidecar mesh-mTLS egress, raw-TCP egress on both transports, and WebSocket-over-HBONE/-mesh-mTLS are all covered). The per-port DR override takes precedence; the global `pool_config.tcp_keepalive_seconds` remains the fallback. Keepalive is NOT a pool-key field (see `proxy-protocols.md`), so on the shared/pooled HTTP-family connections the FIRST dispatcher to materialize the connection fixes the keepalive (first-materializer tradeoff, like `idleTimeout`/`maxRequestsPerConnection`). The reqwest-backed HTTP pool (shared client) and H3/QUIC (UDP transport) are documented residuals — reqwest keeps the global seconds-only keepalive; QUIC keep-alive is N/A.
- `maxConnections` on the pooled multiplexed transports (direct H2, gRPC, native H3, HBONE, mesh-mTLS) is a PHYSICAL-connection bound, never a request-concurrency counter: the slot is reserved at the moment a NEW connection is constructed (after the pool has already missed its cache, so reuse takes none) and handed to that connection's own lifecycle owner — the spawned hyper/`h2` connection-driver task for the H2-family pools, and the spawned `h3` connection-driver task for QUIC (it owns the `h3_quinn::Connection`, so `poll_close` resolves when the QUIC connection really ends). The slot is deliberately NOT parked on the pooled `H3PooledConnection`/`Http2Sender` handle: an evicted or force-drained handle can drop while the socket is still open, releasing the slot early and letting a replacement push the destination past the cap. That makes retirement exact for free: create failure drops it, idle eviction / unhealthy replace / `clear()` / `force_drain_svid_generation` / reload-update-delete / shutdown end the driver, and multiplexed streams are unbounded (`h2_max_concurrent_streams` is still the stream knob). The reservation is cloned per DNS candidate so a failed candidate frees its clone. An over-cap create is a pre-wire, backend-health-NEUTRAL `ErrorClass::BackendConnectionLimit` (`Http2PoolError::MaxConnectionsExceeded`, `GrpcBackendUnavailableKind::MaxConnections`, `HbonePoolError::MaxConnectionsExceeded`, and for native H3 a typed `BackendConnectionLimitExceeded` preserved in the `anyhow` source chain — a plain `anyhow!` message would classify `RequestError`, which `request_reached_wire` treats as POST-wire). Do NOT downgrade it to the generic `ConnectionPoolError`: that class IS a backend-health signal, so a saturated operator-configured ceiling would record a circuit-breaker failure, a passive-health failure, an LB penalty sample and an adaptive-concurrency shrink, ejecting a perfectly healthy destination. `BackendConnectionLimit` is in `client_side_no_backend_signal` AND pre-wire, which is the full raw-TCP over-cap posture (rotate targets + `cb.record_neutral()`); the retry loops' per-attempt breaker records honor the same neutrality. direct-H2, gRPC and native H3 first fall back to an already-established shard, so a cap below `http2_connections_per_host` / `http3_connections_per_backend` converges on `cap` connections and multiplexes. Only a cap refusal takes that fallback (`pool::is_max_connections_refusal`, which recognizes both the creator's typed chain and a coalesced waiter's `SharedPoolCreateKind::MaxConnections`), and only ALREADY-CACHED healthy shards are reused, so no unrelated create failure is silently retried and no cap is bypassed. A cap refusal is also NOT capability evidence: the H2/H3 capability probes preserve the prior classification instead of downgrading a healthy backend that merely happened to be at its ceiling when the refresh ran. HBONE/mesh-mTLS key the lane by the destination's APP/service policy port, not `:15008`/`:15006`. reqwest (H1 and H2 alike) is admitted in reqwest's CONNECTOR — the one place a new physical socket is dialed — through the vendored `ClientBuilder::connection_admission` hook (`docs/upstream-reqwest-patches/003-connection-admission-hook/`); pooled reuse and multiplexed H2 streams never reach it, and the token it returns is owned by the connection object, so an idle socket reqwest retains after a request STILL holds its slot. A request-lifetime slot would have been wrong on both counts (it reads zero while sockets stay open, and it counts H2 streams). One shared hook across every `reqwest::Client` means divergent pool keys (TLS material, `rcfg`, forced-H1 ALPN, subset) for one destination share ONE ceiling. The dispatch path binds the destination lane (dial `(host, port)` → policy port + cap) to its own dispatch with an RAII `ReqwestLaneLease` held across `send()`, and only when a cap is configured — so a lane exists exactly while a capped request can cause a dial, a removed cap drains with its requests (no epoch registry to sweep or leak), and the retry path leases its own (possibly rotated) target. Because `maxConnections` is deliberately NOT reqwest pool-key material, several logical upstreams can resolve different `(policy port, cap)` for one dial address and SHARE one socket pool; per-connect binding cannot enforce the stricter cap there (the laxer upstream's socket is reused by the stricter one), so conflicts resolve to the STRICTEST live lane — order-independent and fail-closed. Do not replace that with last-writer-wins global state. See `docs/mesh.md` "DestinationRule `maxConnections` enforcement scope" and `src/backend_conn_limit.rs`.
- `maxConnections` exhaustion returns `StreamSetupKind::BackendMaxConnectionsExceeded` on stream-family, a 503 (`rejection_phase=backend_max_connections`) on WebSocket, a pre-wire, health-neutral `ErrorClass::BackendConnectionLimit` on the pooled transports, and a `DispatchPolicyRejected` 503 (backend-health neutral) on reqwest, recognized from the connector error chain via `backend_conn_limit::is_backend_connection_limit_error`; keepalive setsockopt failures warn and continue.
- TCP/UDP/DTLS stream paths engage per-port **LB algorithm** and **`localityLbSetting`** at selection time when all upstream targets share a single port (`initial_dispatch_port_override` non-zero); per-port `connectTimeout`, `maxConnections`, and `tcpKeepalive` also apply. Active/passive health context is threaded into stream target selection unconditionally; the `maxEjectionPercent` cap resolves at the per-port tier only under that same single-port condition and at the upstream/global tiers otherwise. Outlier thresholds are not recorded on stream paths themselves (raw relay sessions carry no response status), so stream-only traffic does not create new passive ejections, but active health and existing passive ejections are honored.
- Phantom DestinationRule ports are skipped with a warning.
- Materialized per-port outbound upstreams (`__mesh-out-upstream-{ns}-{name}-{port}`) accept `portLevelSettings` ONLY for their owning Service port (forward-derived `outbound_upstream_owner_port` map in `apply_destination_rules` — never parse ids) and FAN that one entry OUT to every distinct target dial port: targets dial the per-workload resolved `targetPort` (numeric or **named**, which can resolve differently across replicas), dispatch keys overrides by the LB-selected target's port, and every target is owned by the one Service port by construction. This closes the former named-`targetPort` residual statically. Do NOT move these upstreams to runtime service discovery for this: SD-resolved targets are absent from `Upstream.targets`, so the capability registry never probes them and `retain_keys` evicts their records — every Ambient HBONE dial would 502 `hbone_required`; SD also drops per-pod one-to-one identity pinning, local-cluster filtering, and slice-atomic endpoint freshness (30 s poll + delta-gated reconcile).
- Admin API POST/PUT of `Upstream.port_overrides` is rejected; DestinationRule is canonical.
- `materialize_east_west_gateway_proxies()` creates SNI-passthrough TCP proxies only for east-west topology.
- `materialize_egress_gateway_proxies()` creates HTTP-family proxies from `mesh_external` ServiceEntries only for egress topology.
- **DestinationRule lookup-tier evidence must AGREE between CP admission and DP materialization (#2465/#2469).** `policy_target_service_ref` (slice build) and `MaterializationTierScope::eligible_tier` (`apply_destination_rules`) resolve the destination host's owner through ONE shared helper, `slice::destination_host_owner`: `.svc[.cluster-domain]` syntax → inventory-confirmed two-label `name.namespace` → `service_entry_host_owner` (single owner; cross-namespace duplicates and an empty declaring namespace ⇒ `Ambiguous` ⇒ NO service tier). Istio short-name self-scoping stays OUT of it — it reads the POLICY's namespace, so it belongs to `policy_target_service_ref` alone. Both the SOURCES and their ORDER are load-bearing: (a) when the host owner IS resolved it is AUTHORITATIVE for the service tier — do NOT widen it with a conflicting `Upstream.namespace` (`by_upstream.min(by_host)` lets an operator-authored / multi-target upstream in `evil` manufacture service-tier policy for a host owned by `beta`); (b) retain upstream-namespace fallback ONLY when host ownership cannot be resolved — `build_egress_upstream` stamps every ServiceEntry-derived EgressGateway upstream with the GATEWAY's namespace, and the host-owner arm recovers the declaring ServiceEntry for external hosts so owner-authored `trafficPolicy` still applies; (c) do NOT hoist the ServiceEntry arm above the `.svc`/inventory arms — a carrier-supplied ServiceEntry declaring `reviews.beta[.svc…]` would then transfer ownership of `beta`'s service to its own namespace. Missing/empty/whitespace root provenance fails closed (refuse Unscoped; keep independently provable client/service tiers; never restore pre-#2469 permissive bucketing). Re-stamping the synthesized upstream's namespace is the wrong repair — `Upstream.namespace` participates in `FERRUM_NAMESPACE` filtering and per-namespace uniqueness. The DP builds its identity index from the slice's already-narrowed `services`, the CP from the full inventory; that is the one intended divergence. **Per-host LOOKUP is not per-host APPLICATION**: every field a winning rule projects lands on the shared `Upstream`, so `apply_destination_rules` REFUSES (returns `Err` → slice rejected → last-good retained; no mutation) an upstream whose match hosts resolve to DIFFERENT winning rule SETS. Do NOT "fix" that by merging them in sorted order — that is order-dependent cross-service policy transfer, which the deleted test `an_upstream_spanning_two_services_resolves_each_host_independently` masked by choosing non-conflicting fields. Hosts with NO winner do not participate (a destination no rule targets cannot disagree), so single-destination, multi-port, and static-fallback-target upstreams are unaffected. The ambiguity-warning dedup map (`DESTINATION_RULE_AMBIGUITY_REPORTED`) is keyed by the SUBSCRIBER namespace and must stay bounded by namespace count, per-namespace count-values, **and retained key bytes** (`DESTINATION_RULE_AMBIGUITY_NAMESPACE_BUDGET` × `DESTINATION_RULE_AMBIGUITY_COUNTS_PER_NAMESPACE`, with keys over `DESTINATION_RULE_AMBIGUITY_NAMESPACE_KEY_MAX_BYTES` never retained); every saturation path fails toward visibility, never silence.

## Injector, Node Agent, And CNI

- Injector mode serves `POST /mutate` Kubernetes AdmissionReview and emits JSON patches only.
- Sidecars run as `PROXY_UID`; optional iptables init container requires `NET_ADMIN`.
- IPv4/IPv6 capture CIDRs must stay partitioned into `iptables` and `ip6tables` blocks. `FERRUM_MESH_IP6TABLES_ENABLED=auto|true|false` controls IPv6 fan-out.
- **UDP capture uses TPROXY, not REDIRECT** (F3 §3.3 Stage 2, `FERRUM_MESH_CAPTURE_UDP_ENABLED` default-OFF/inert): TCP's `nat` REDIRECT rewrites the destination (orig-dst via `SO_ORIGINAL_DST`), which has no UDP analogue, so captured UDP uses `mangle`-table TPROXY (`FERRUM_MESH_UDP_INBOUND`/`FERRUM_MESH_UDP_OUTBOUND`, `-j TPROXY --on-port <FERRUM_MESH_CAPTURE_UDP_PORT, default 15011> --tproxy-mark <FERRUM_MESH_TPROXY_MARK, default 0x733>/<mask>`) — delivers the datagram WITHOUT rewriting dest (orig-dst recovered per-datagram from `IP_RECVORIGDSTADDR` in Stage 3) — plus raw `ip rule add priority 100 fwmark <mark>/<mask> lookup 33133` + `ip route add local 0.0.0.0/0 dev lo table 33133` (and `ip -6` under the v6 fan-out). **The `ip rule` priority is a low constant `TPROXY_ROUTE_RULE_PRIORITY=100`, SEPARATE from the routing TABLE `TPROXY_ROUTE_TABLE=33133`** (codex r2): the RPDB is priority-ordered and the kernel `main` rule is priority 32766, so the fwmark rule MUST sit below it or `main` resolves the marked datagram first and captured UDP black-holes. Table `33133` is Ferrum-owned, NOT Istio's `133`, so cleanup never risks a co-resident Istio table. **Capture is EGRESS-ONLY (#1808):** the OUTBOUND chain rides `mangle PREROUTING` scoped `-m addrtype ! --dst-type LOCAL` (remote dest). The INBOUND `--dst-type LOCAL` catch-all chain/jump is **gated off** (`emit_inbound = false` in `udp_tproxy_commands_for_family`) — there is no inbound UDP relay yet, and the egress-only capture listener would divert pod-app-bound UDP and DROP it (black-hole for UDP-serving pods), so inbound-to-pod UDP is left uncaptured and flows normally to the app; teardown still reaps any prior inbound chain. The OUTBOUND `! --dst-type LOCAL` scope is the pod-IP-agnostic mirror of the TCP chains' hook separation; re-enable inbound (the gated catch-all, kept ordered after the outbound jump) when an inbound UDP relay lands. **Fail closed when routing is unavailable** (codex r2): the setup script FATALLY preflights `command -v ip` BEFORE any UDP rule (no `iproute2` ⇒ `set -e` exits, installing NOTHING — TPROXY and routing go in together or not at all, never a TPROXY-without-routing black-hole) and the load-bearing routing ADDs are NOT `|| true`; only the delete-before-add (idempotence) and cleanup stay best-effort. **Routing is installed BEFORE the two `mangle PREROUTING` jumps** (codex r5): the jumps start steering UDP into the chains, the injector init script has NO cleanup trap, so a routing ADD that failed after the jumps were appended would leave TPROXY live without policy routing (the half-installed black-hole) — emitting `ip rule`/`ip route` first aborts `set -e` before any capture is wired (chains/rules are inert until the jumps append last). **Pod-netns ONLY (host-netns node-agent limitation, codex r5):** the `--dst-type LOCAL` split is correct only where the pod IP is LOCAL (the injector's pod netns); the node-agent DaemonSet runs `hostNetwork: true` where pod IPs are FORWARDED, so inbound-to-pod would match the OUTBOUND `! --dst-type LOCAL` discriminator. There is no host-netns-safe `addrtype` discriminator without per-pod IP knowledge the fallback lacks, so `CaptureConfig::host_netns` makes `udp_tproxy_commands_for_family` emit NO UDP TPROXY rules for the node-agent (a one-shot warn when UDP capture is on) — eBPF is the supported node-agent UDP path; the host-netns iptables fallback is TCP-only. The UDP listener port is DISTINCT from the TCP outbound port (UDP+TCP can't share a socket). The default mark `0x733` (1843) is Ferrum-owned and deliberately NOT Istio's conventional TPROXY mark `0x539` — Ferrum's `ip rule` matches the mark to steer into the Ferrum table, so defaulting to `0x539` would hijack a co-resident Istio's marked packets (and break Istio); `0x733` sits in a gap clear of Istio's exact marks AND of common MASKED CNI mark classes — Cilium matches `skb->mark & 0xF00`, so the prior default `0xFE3` ALIASED Cilium's `0xF00` class (`0xFE3 & 0xF00 == 0xF00`) and could be misclassified by a co-resident CNI, whereas `0x733 & 0xF00 == 0x700` does not (compile-time asserts in `src/capture/mod.rs` pin the masked-class non-aliasing) — and is collision-free within Ferrum (no other packet marks; the `1337` proxy UID is a socket-owner match, disjoint from `skb->mark`). **TPROXY runs only in PREROUTING** (jumping into a `-j TPROXY` chain from `mangle OUTPUT` is invalid), so the pod's OWN locally-generated UDP egress (which never traverses PREROUTING) is captured via a separate **MARK-only `FERRUM_MESH_UDP_OUTPUT_MARK` chain jumped from `mangle OUTPUT`**: it MARKs egress with the TPROXY fwmark (the proxy-UID `-m owner` self-exclusion lives HERE — owner-match is OUTPUT-context-only, invalid in the PREROUTING chains), the fwmark `ip rule` reroutes the marked datagram to `lo`, and a mark-match `FERRUM_MESH_UDP_REINJECT` PREROUTING rule TPROXY-captures the looped datagram. So sidecar-self-egress UDP IS handled (no longer deferred); the full loop's live validation rides `netns-capture-live`. Default OFF because the consuming UDP listener arrives in Stage 3 — an upgraded injector must not redirect UDP into a void; when off NO mangle/TPROXY/routing rules are emitted. Cleanup removes the mangle chains + tears down routing by deleting the EXACT Ferrum-owned rule (`ip rule del priority 100 lookup 33133`) + exact route, never by-lookup or table-flush. The 3 vars are parsed in ONE place (`capture::udp_capture_settings_from_env`), shared by `CaptureConfig::from_env` (node-agent) and the injector.
- **UDP datagram-over-mesh egress (F3 §3.3 Stage 4, DUAL-TRANSPORT — mirrors raw-TCP egress)**: the Stage-3 capture→drop is replaced by capture→frame→mesh-tunnel→peer→unframe→local `UdpSocket`, plus the return path. - **The chained conflist is a node-wide pod-creation dependency, not an optimization** (#3609): ADD fails closed on IPC failure, so while the chain is installed an unreachable node-agent leaves every new pod on the node in `ContainerCreating`. That posture is deliberate — do not relax ADD to pass through unenrolled — but its lifecycle is load-bearing and must not be weakened. `install` publishes in a FIXED order and each step exists to make the next failure recoverable: under the install lock, preflight the configured target conflist (absent → proceed; present → proceed only when it is a bounded regular single-link file opened `O_NOFOLLOW` whose Ferrum marker names this same owner — refuse unmarked/malformed/oversized/symlink/non-regular/hard-link/other-owner with no shared side effects; REMEMBER the marker + device/inode/length) → **find the primary, build the chained conflist, and serialize it, ALL before any shared write** (these are the steps that fail on input the installer does not control, so they must not run after the manifest or binary has been touched) → stage the binary in the destination dir under an `O_EXCL | O_NOFOLLOW` unguessable temp name (hashing as it is written) → **gate the shared binary** → write the sibling `.ferrum-cni-owned.marker` manifest (owner/generation, `confFileName`+`binaryFileName`, the staged digest and an ATTESTED previous digest) → publish the binary by atomic same-dir `rename` → write the conflist LAST. The manifest lands BEFORE the shared binary, so nothing this install can leave behind is un-provable and therefore nothing is un-removable; the conflist lands last because the moment it does every pod ADD traverses `ferrum-cni`. Do NOT reorder the binary ahead of the manifest, and do NOT move validation/construction back after the shared writes. **`previousBinarySha256` is an attestation, not an observation**: hashing whatever occupies `/opt/cni/bin/ferrum-cni` proves nothing, so it is recorded ONLY when the manifest already on disk carries this same owner, names these exact artifact names, and had itself already recorded that digest; every other case writes `null` and the pre-existing binary stays unremovable (inert, so chain cleanup still succeeds). **Install applies the shared-binary rule in the other direction too**: while another remaining `.conf`/`.conflist`/`.json` names `ferrum-cni`, the shared executable is NOT replaced with different bytes — byte-identical republication is allowed, an unclassifiable installed object or an unscannable directory fails safe (`SharedBinaryInUse`, no shared mutation). **A failed install must not strand a same-owner chain**: on the ordinary error path, if the preflight found this owner's previous chain, install removes it under the same lock after re-proving owner AND generation AND device/inode — a different owner or a generation that overtook the run is retained and logged, and the original error is always surfaced. Without that, a failed N-1 → N upgrade leaves every pod ADD traversing a dead socket while the replacement's watcher (scoped to the never-published N) correctly reports `NeverPublished` and removes nothing. In-place upgrade semantics are part of the contract: publish is `rename`-only (never truncate-in-place, so an already-exec'd plugin keeps a valid inode), and a staged digest identical to the installed one SKIPS the rename entirely. `uninstall` removes ONLY marker-matching artifacts, conflist FIRST then binary. `/opt/cni/bin/ferrum-cni` is SHARED: it goes only when this chain is cleared, NO remaining `.conf`/`.conflist`/`.json` names `ferrum-cni`, the manifest names THESE artifacts, and the digest matches — an unscannable directory or mis-bound manifest keeps it (retaining an inert file beats breaking another release). Every mutating run holds an exclusive `flock` on `.ferrum-cni-install.lock` in the conf dir for its whole duration; artifacts are opened `O_NOFOLLOW`, classified against the OPEN HANDLE, read under a hard byte cap that does not trust the pre-read length, hashed through that SAME handle, and removed only after a re-open confirms the same device/inode. Cleanup succeeds only when the conflist is gone or provably another owner's; a foreign conflist exits non-zero rather than declaring success. `rollback-watch` (chart: a native sidecar ordered BEFORE the installer) runs in TWO phases: it first waits for a conflist carrying its OWN owner AND generation to appear (the install-completed proof — the readiness budget MUST NOT start before that, or the watcher can delete state an installer is still publishing), then applies the readiness budget. Phase 1 must NOT probe STATUS at all: the socket path is node-scoped and outlives an install, so an `Ok` from an earlier node-agent generation would return `Ready` and permanently disarm the rollback for a chain this generation has not published yet (pinned by `a_status_probe_before_publication_can_never_disarm_the_rollback`). Outcomes are distinct and truthful — `Ready` / never-published / rolled-back / superseded / incomplete — and only rolled-back may claim the dependency was lifted. Helm wires cleanup as a `pre-delete` **DaemonSet** (one pod per node; a Job strands a multi-node cluster) whose readiness marker is retracted at process start (never following symlinks; a non-regular file at the marker path is REFUSED, not deleted) and published atomically only after THIS run's cleanup succeeded — never add `pre-upgrade`/`pre-rollback` to that hook, or a rolling replacement would uninstall still-required CNI state. Both cleanup pods MUST stay `hostNetwork: true`: a pod needing its own CNI sandbox cannot start on a node whose chain is broken, so the hook would deadlock exactly where it is needed. **Helm hook-deletion semantics decide the rest of the graph**: on Helm **3.19+ and v4** a hook failure deletes every EARLIER hook carrying `hook-succeeded` (`deleteHooksByPolicy(executingHooks[0:i], HookSucceeded, ...)` in `pkg/action/hooks.go`; 3.18 and older delete only the FAILING hook via its `hook-failed` policy and reach the succeeded sweep only when the whole phase passed — do not restate this as "v3 and v4"), so the cleanup ServiceAccounts + Role + RoleBinding are ORDINARY release resources (never hooks) and the cleanup DaemonSet carries `before-hook-creation` ONLY. That policy would ALSO delete the DaemonSet the instant it was created on every Helm version (`WatchUntilReady` treats a non-Job/Pod kind as succeeded on creation), so the shape is right regardless of Helm version. The wait Job (which may keep `hook-succeeded`, being last) deletes that DaemonSet itself with FOREGROUND propagation and refuses to report success until the API server 404s it; its Role is `get`+`delete` on the named DaemonSet plus `get` on its status — no list/watch/unnamed access, ever. A controller-observed `0/0` cleanup report is a failure, not vacuous success: with no scheduled cleanup pod there is no evidence that any node's chain was lifted, so the wait Job retains the DaemonSet and blocks release deletion. A failed wait therefore leaves the DaemonSet, its logs and the identity intact and `helm uninstall` retries cleanly. Hosted evidence is the Rust integration suite plus the normal CI Helm rendering/static contract assertions; there is no privileged live CNI lifecycle workflow in this PR.

- If `FERRUM_K8S_WATCH_NAMESPACES` is unset, watch scope falls back to CP scope: `Single`/`Set` use namespaced watches, `All` uses cluster-wide.
- **A reflector-backed store can go silently stale, and only `FERRUM_K8S_WATCH_IDLE_RELIST_SECS` bounds it.** kube-rs surfaces an error only when a watch *fails*; a watch that stops delivering without failing leaves the watcher task alive while its store serves a frozen object set, so later Gateway API / Istio resources never reach any reconcile. (The conformance artifact that motivated this proves the SYMPTOM — scope initialized, four TCPRoutes present, the sibling ReferenceGrant watcher still receiving events, the controller alive and reconciling, the TCPRoute store frozen, no watcher error/restart/status for 120s — which is consistent with a silently stalled or black-holed watch, but carries NO transport-level proof of where the stream was lost. Keep the prose symptom-shaped: the repair is a bounded authoritative recovery for ANY no-event stall.) `FERRUM_K8S_FULL_SYNC_INTERVAL_SECS` cannot recover that — it re-reconciles the SAME store — and watch bookmarks are consumed inside kube-rs, so there is no liveness signal to observe. `watcher::run_watcher_generations` therefore rebuilds a scope's reflector once it has delivered no event for the idle window (default **300s**, `0` disables, clamped `0..=86_400` at parse time so the doubled readiness timeout / `Instant` deadline / ms jitter conversion cannot overflow). The default is 300 and not 60 because a healthy quiet scope is INDISTINGUISHABLE from a stalled one and therefore always relists: a three-namespace controller carries ~39 scope watchers (~69 with Istio/core, scaling with namespaces), so the window IS the per-scope full-list rate against the API server. The per-scope offset mixes an FNV hash of `(apiVersion, kind, scope)` with a `RandomState`-derived **per-process** seed — a target-only hash would make every control-plane replica list the same scope in the same instant. Never assert an exact offset in a test; assert bounds (`< window/4`). The swap is **make-before-break**: the previous store stays registered and keeps serving until the replacement emits `InitDone`, then `ResourceStoreSet::replace_store_for_scope` swaps it in place under one lock — never remove-then-add, which would make a relist look like a mass deletion and broadcast a config wipe. A replacement that never finishes listing is abandoned after `readiness_timeout` (two idle windows, floored at 30s) and retried, still without blanking the scope. Relisting is in-task: it spawns nothing, registers nothing new with `ControllerTaskRegistry`, and leaves the stream-end contract (deregister the scope, return, let the CRD reprobe loop restart it) untouched.
- Istio status writer patches `status.conditions[]` (a `FerrumAccepted` condition plus a `status.ferrum.translation` detail block) for all ten translated Istio kinds when `watch_istio == true`: AuthorizationPolicy, PeerAuthentication, RequestAuthentication, DestinationRule, VirtualService, ServiceEntry, WorkloadEntry, Sidecar, Telemetry, and ProxyConfig. Successful translation writes `FerrumAccepted=True`; a `K8sTranslateError` writes `FerrumAccepted=False`/`Invalid` with the translator's reason so rejections are visible to `kubectl`.
- Cross-namespace `WorkloadEntry.spec.service` hosts (`svc.ns.svc` / FQDN) are accepted only when a Gateway API `ReferenceGrant` in the **target Service namespace** permits `WorkloadEntry` → core `Service` and the target Service exists in the translated inventory. Stamp `Workload.service_namespace` for attachment matching while keeping SPIFFE/`Workload.namespace` on the WorkloadEntry namespace; missing/unauthorized/stale targets fail closed and must not widen attachment. Same-namespace hosts need no grant.
- Keep `istio_api_resource`/`is_supported_istio_kind` in `src/k8s_controller/istio_status.rs` in lock-step with `ISTIO_CRDS` in `src/k8s_controller/watcher.rs` (group + plural).
- Parsed-but-unenforced fields are surfaced as `status.ferrum.translation.deferred_fields` rather than only logged: DestinationRule `connectionPool.http.maxRequestsPerConnection` at EVERY scope (top-level, `portLevelSettings`, and `subsets[].trafficPolicy`) via `DEFERRED_CONNECTION_POOL_HTTP_FIELDS`, plus `idleTimeout` and `http2MaxRequests` at **subset scope only** via `DEFERRED_SUBSET_ONLY_CONNECTION_POOL_HTTP_FIELDS` — those two ARE enforced at top-level/`portLevelSettings` scope but the subset apply layer projects neither into `ResolvedSubsetTrafficPolicy`, so a subset value is inert and must be reported rather than silently accepted (`translate_connection_pool_http` emits the matching `TrafficPolicyScope::Subset` warning). `h2UpgradePolicy`, `maxRetries`, and `http1MaxPendingRequests` are APPLIED at all three scopes (subset scope rides `SubsetTrafficPolicy`/`ResolvedSubsetTrafficPolicy` — see the DestinationRule materialization rules above; `http1MaxPendingRequests` as the concurrent-in-flight-H1 cap described there) and must NOT produce ignored/deferred diagnostics — keep translator and status predicates in lock-step (also now APPLIED, not deferred: per-subset `connectionPool.tcp.connectTimeout` → overrides `backend_connect_timeout_ms` for subset-bound proxies; `portLevelSettings[].tls` → per-port backend TLS resolved onto `port_overrides[port].tls` and projected onto the effective proxy's `resolved_tls`; the full per-subset `outlierDetection` → *thresholds* resolved into the subset passive-health overlay consulted by `passive_health_for_target` AND the `maxEjectionPercent` *cap* resolved per-subset by `LoadBalancerCache::max_ejection_percent_resolved_from`, both with the same per-port > per-subset > upstream precedence so cap and thresholds share one tier); VirtualService `http[].corsPolicy` **only when the policy combination is unrepresentable** — a malformed/unknown origin matcher, an `allowOrigins[]` list over 64 entries, a matcher value over 512 bytes, an un-compilable/over-complex `regex`, an unparseable `maxAge`, an invalid method/header token, or credentialed exact `*`. `exact`/`prefix`/`regex` `StringMatch` and legacy `allowOrigin` policies are otherwise translated to a proxy-scoped `cors` plugin via the shared `config_sources::k8s::cors_policy_translatable` predicate, which the translator and status writer both call so they never diverge. Istio `exact` projects onto the plugin's LITERAL `{"exact": ...}` matcher, NEVER its plain-string form (which canonicalizes and reads a leading `*` as native wildcard-subdomain syntax), so a wildcard-shaped or noncanonical exact is preserved rather than widened or deferred (#3254); origin admission (count/byte/complexity bounds) lives once in `plugins::cors` and is shared by the translator, the plugin, and `modes::mesh::config` slice validation — do not fork it (#3253); `mirror`/`mirrorPercentage`, `redirect`, and `rewrite` are fully translated); and Sidecar `ingress[]` listeners Ferrum can't model (see below — resolvable loopback HTTP listeners are materialized, not deferred). VirtualService `spec.tcp[]` and `spec.tls[]` L4 route blocks are translated to stream proxies via `virtual_service_l4_proxies` (`tls[]` → passthrough TCP keyed by SNI, `tcp[]` → plain TCP keyed by port, reusing `proxy_for_route` + the stream/SNI machinery); L4 match predicates (`sourceLabels`/`sourceSubnets`/`destinationSubnets`/`gateways`/`sourceNamespace`) compile onto `Proxy.stream_match`; weighted multi-destination splits materialize an upstream-backed stream proxy (`istio-vs-l4-upstream-*`, carried on `MeshSlice.virtual_service_l4_upstreams`), while `destination.subset` (on ANY L4 destination, single or weighted), invalid weights, and multi-destination `destination.port` disagreement without `match.port` fail closed as `FerrumAccepted=False`/`Invalid`, not as `deferred_fields`. A generated `istio-vs-l4-upstream-` id MUST be listed in `K8S_MANAGED_UPSTREAM_ID_PREFIXES` (`src/k8s_controller/reconciler.rs`) — that list is the only withdrawal mechanism for translator-generated upstreams, and a missing prefix makes every compose append another copy instead of replacing it. Sidecar `ingress[]` is now MODELED (F6 §6.2): resolvable loopback HTTP listeners (incl. `https`) materialize inbound routes and are reported via `status.ferrum.translation.ingress_modeled`; only listeners Ferrum can't represent (inadmissible `unix://` path / non-loopback `defaultEndpoint`, non-HTTP-family protocol — including a MISSING or MISTYPED `port.protocol`, which is deferred not guessed-as-HTTP — and omitted `defaultEndpoint`) stay in `deferred_fields`. The status writer's `classify_sidecar_ingress_entries` mirrors `MeshSidecarIngress::resolve` fail-closed semantics on the raw spec (via the shared `sidecar_ingress_protocol_is_http_family` → `sidecar_ingress_app_protocol` mapping) — keep the two in lock-step. The DR `connectionPool.http` deferred set is mirrored by a translator warning in `src/config_sources/k8s/istio.rs`; keep the two lists in sync.
- Status writer failures, such as missing `subresources.status`, warn and no-op; they never abort reconcile.
- `ProxyConfig` is watched as served `networking.istio.io/v1beta1` (`ISTIO_CRDS` + chart `proxyconfigs` RBAC), translated into `MeshProxyConfig`, transported on native/`ProxyConfigsCarrier`, and status-written — Istio's CRD declares `subresources.status`. Both numeric fields fail closed at translation: `spec.concurrency` outside `u32`, and `spec.tracing.sampling` that is non-numeric or outside `0..=100` (an unvalidated value would reach every matching workload's injected `workload_metrics.sampling_percentage`) — keep the latter in lock-step with `Telemetry.tracing.randomSamplingPercentage`. Reachability caveat: Istio's `proxyconfigs.networking.istio.io` v1beta1 CRD has a *structural* spec schema whose only properties are `selector`, `concurrency`, `image`, and `environmentVariables`, with no `x-kubernetes-preserve-unknown-fields` on `spec`. `spec.tracing` is therefore pruned by the API server and never reaches the watcher; `tracing_sampling` is a Ferrum mesh-model field supplied over native/file/xDS mesh config, so cluster-sourced ProxyConfigs always report `tracing.sampling: <unset>` in `FerrumAccepted`. Do not document it as a `kubectl apply`-able Istio field.
