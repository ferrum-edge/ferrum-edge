# Mesh Rules

Full operator docs live in `docs/mesh.md`. Keep this file to implementation invariants.

## Topologies And Runtime

- `MeshTopology` drives listeners: `Sidecar` uses inbound 15006 mTLS and outbound 15001 capture; `Ambient` uses HBONE 15008 and outbound 15001; `EastWestGateway` uses SNI passthrough on 15443; `EgressGateway` uses mTLS inbound 15090 to external ServiceEntry backends.
- All topologies share the normal proxy and plugin chain.
- Mesh runtime state is `ArcSwap<Option<MeshSlice>>` in `runtime.rs`; slice apply is lock-free hot-swap like `GatewayConfig`.
- `wait_for_first_slice()` blocks startup until the first valid slice arrives.
- Native config consumption uses `MeshConfigSync.MeshSubscribe` gRPC. xDS uses ADS for CDS/EDS/LDS/RDS/SDS/ECDS/RTDS with 25 ms debounce.
- `FERRUM_MESH_CONFIG_PROTOCOL=file` is the localized source: `config_consumer::file_source` builds the slice DP-side from `FERRUM_MESH_FILE_CONFIG_PATH` via `MeshSlice::from_gateway_config` (same materialization as CP paths — do not fork it). The document is `{version?, mesh}` ONLY (`deny_unknown_fields` rejects gateway resources). Initial load is fail-closed at startup; SIGHUP reload keeps the last good slice on error. The file protocol requires no CP URLs / CP-DP JWT secret — `EnvConfig::validate()`'s Mesh arm and `MeshRuntimeConfig::from_env_config` gate those per protocol; do not re-add unconditional requirements.
- xDS apply uses make-before-break with a coherent required-version gate: the DP tracks each type's `version_info` independently but only builds a slice once all required types (CDS/EDS/LDS/RDS/ECDS — ECDS required so the first slice is never the unprotected name-only view) have the same `version_info` and `reverse_translate` succeeds. The prior slice keeps serving via `ArcSwap` until the new one is ready; genuine structural errors (e.g. malformed ECDS carrier) NACK + roll back. A route referencing a service not yet present in CDS/EDS/LDS is SKIPPED (debug-logged) and retained, NOT NACKed, because xDS types arrive as independent responses and a NACKed SotW resource is not resent until reconnect (do not reintroduce a hard error there). `MeshSlice.version` is observability-only (`content_eq` ignores it). The CP force-re-sends subscribed required mesh-slice types when any required type changes so CDS/EDS/LDS/RDS never advance independently of stale ECDS security carriers. Keep DP `REQUIRED_MESH_SLICE_TYPE_URLS` and the CP emitter in sync.
- Warming observability splits by sensitivity: the counter `ferrum_xds_warming_partial_applies_total{namespace}` is unauthenticated on `/metrics`, but the per-type `version_info` strings and still-missing required types ride the JWT-gated `GET /mesh/config-drift` `convergence` block (built by the DP via `MeshRuntimeState::set_xds_convergence`). Do NOT move per-type version strings onto `/metrics` — they embed config-change timestamps + content digests and would also explode label cardinality.
- xDS is Ferrum-CP-to-Ferrum-DP, not stock-Envoy/Istio-interoperable: CDS/EDS/LDS/RDS are name-only (service-port discovery); all security/policy slice fields and selector context (authz, PeerAuth, JWT, ServiceEntry, trust bundles, ProxyConfig, workloads, effective labels, outbound policy, telemetry, multi-cluster, sidecar egress scope) ride ECDS as Ferrum mesh-slice carriers. `src/xds/carrier.rs` (`MeshSliceCarrier`) is the single encode/decode source of truth; the CP emits via `translate_mesh_slice_carriers` and the DP recovers in `reverse_translate`, requiring both reserved carrier resource name and matching inner type URL. An xDS-built slice must stay functionally equivalent to a native-built one.
- Native and xDS clients use jittered exponential backoff from 1s to 30s, plus/minus 25%, multi-CP failover via `FERRUM_DP_CP_GRPC_URLS`, and JWT metadata.
- **MeshSubscribe response binding is centralized and fail-closed** (`config_consumer::update_validation`, issue #2457). BOTH consumers — the local native client and multicluster remote discovery — validate a non-heartbeat `MeshConfigUpdate` against the exact `MeshSubscribeRequest` they sent (`MeshUpdateExpectation::from_subscribe_request`) BEFORE `install_slice` / endpoint import: present + major/minor-compatible `ferrum_version`, `update.version == slice.version`, `slice.node_id`/`slice.namespace` equal to the request, and — when the request PINNED `workload_spiffe_id`/`waypoint_name` — an exact echo, where an ABSENT echo is a mismatch (treating it as a pass would be a trivial bypass; an unpinned request gates nothing, since there is no unambiguous expectation). Do not fork these rules into a second implementation and do not add a "skip when the field is missing" branch. Rejection is metric-recorded inside the validator (`ferrum_mesh_config_update_rejections_total{consumer,reason}`, both labels `&'static str` from closed enums — never a CP-supplied value) with a sanitized, length-bounded `warn!`. `MeshUpdateRejectReason::terminates_stream` splits BINDING failures (drop the stream → multi-CP failover) from CONTENT failures (drop the frame, keep the stream); remote discovery fails the whole poll either way and keeps last-good endpoints. Heartbeats stay explicit: they route to `validate_update_ferrum_version` only, and a heartbeat-marked frame reaching the install path is itself a rejection. Test CP stubs must echo the request scope (`functional_mesh_mode_test`'s stub does) or the DP will correctly refuse their slices.

## Datapath Layering: Two Transports (per topology) vs. Materialization

Keep two things distinct: the **transport** (how a peer is reached on the wire) and **materialization** (turning the slice into routable `Proxy`/`UpstreamTarget` objects `find_proxy` can match). "Outbound 404 / no routes" does NOT mean "no transport" — conflating them leads to re-implementing transport that exists, OR (worse) using the wrong transport for the topology.

**Mesh transports are PER-TOPOLOGY — never assume one (this is the trap):**
- **Ambient / NodeWaypoint / ServiceWaypoint** speak **HBONE** (HTTP/2 CONNECT over mTLS) on **:15008**.
- **Sidecar** speaks plain **SVID-mTLS HTTP** on **:15006** — it has **NO 15008 HBONE listener**. HBONE is NOT Sidecar's transport: a Sidecar peer can't accept an HBONE dial (it would `hbone_required`-502). (`listener_plan()` in `modes/mesh/mod.rs` is the source of truth: Sidecar = capture :15001 + mTLS :15006; Ambient = capture :15001 + HBONE :15008.)

- **Ingress (inbound) — DONE for both.** Sidecar inbound: `materialize_sidecar_inbound_proxies` → loopback routes (:15006 → `127.0.0.1:appPort`), **one sibling per HTTP-family service port**. **Sidecar `ingress[]` custom listeners (F6 §6.2)**: when the applicable Sidecar declares `ingress[]` (resolved CP-side into `MeshSlice.local_ingress_listeners`, gated by `FERRUM_MESH_SIDECAR_ENFORCED`, NOT dry-run; rides ECDS carrier `LocalIngressListenersCarrier`), they **REPLACE** the service-port default inbound materialization for that workload (Istio semantics) — `materialize_sidecar_ingress_listener_proxies` emits one `__mesh-ingress-{ns}-{svc}-{port}` loopback route per resolved listener (declared LISTENER port → the entry's `defaultEndpoint` loopback target; hosts = the local service's FQDN variants). **Fail closed on the DECLARED signal, not on what resolved**: `MeshSlice.sidecar_ingress_declared` (a separate bool marker riding its OWN carrier `SidecarIngressDeclaredCarrier` — set true whenever the applicable Sidecar DECLARES an `ingress` block, independent of how many entries resolved) gates the materializer; when declared, the service-port defaults are SKIPPED even if `local_ingress_listeners` is empty (all entries unsupported / no local-service anchor), so an all-unsupported `ingress[]` yields NO inbound routes rather than fail-open-exposing the defaults the operator replaced. **Omitted vs explicit-empty (round-2 fix, Istio-faithful):** an OMITTED `ingress` keeps the defaults; a DECLARED `ingress` — *including an explicit empty `ingress: []`* — replaces them. The K8s translator sets `MeshSidecar.ingress_declared` on `spec.ingress` PRESENCE (mirroring `egress_inherits_defaults`'s omitted-vs-explicit-empty split); `resolve_applicable_sidecar_ingress` folds it as `ingress_declared || !ingress.is_empty()` (non-empty always declares; the bool adds the explicit-empty case, default-false on the native source). **`content_eq` MUST compare `sidecar_ingress_declared`** (round-2 fix): the marker flips false→true while `local_ingress_listeners` stays empty (no-ingress → all-unsupported-ingress), so omitting it from slice equality would let MeshSubscribe/update dedupe keep serving the stale default routes. Ingress resolution + the local-service anchor are **decoupled from egress-scope inheritance** (an ingress-only Sidecar usually omits `spec.egress`, so `applicable_sidecar` for egress can be `None`; the slice resolves `local_inbound_services` independently for the ingress case via `select_applicable_sidecar` + `resolve_local_workloads`). Ingress ids classify as `Inbound` (`is_mesh_inbound_route_id`/`mesh_route_direction`) and fold into `mesh_inbound_ports`, reusing `select_mesh_inbound_port_route` — but the orig-dst AND authority both match the **listener port** (`MeshInboundSibling.orig_dst_match_port == authority_port == listener port`; default service-port siblings keep `orig_dst_match_port = backend_port`). **Authz on the LISTENER port (security)**: `MeshInboundPortGroup.is_ingress` makes `select_mesh_inbound_port_route` return the selected sibling's listener port, stamped onto `RequestContext.mesh_inbound_listener_authz_port`; `mesh_authz`'s `mesh_inbound_app_port` authorizes an ingress route on that LISTENER port (e.g. 8443), NOT the `defaultEndpoint` backend port — so an AuthorizationPolicy `port`/`destination.port` DENY scoped to the listener port is enforced (authorizing on the backend port would fail a DENY OPEN). Service-port default inbound routes keep authorizing on `backend_port`; an ingress id with no stamped listener port fails closed (never the backend port). Only loopback (`127.0.0.1`/`::1`) and instance-IP (`0.0.0.0`/`::` → loopback) `host:port` HTTP-family endpoints resolve; `unix://`, arbitrary IPs, non-HTTP protocols, and omitted `defaultEndpoint` are dropped fail-closed and stay in `deferred_fields`. **Protocol classification (round-2 fix — do NOT revert to routing the lossy `Unknown` bucket):** a custom inbound listener routes ONLY *recognized* HTTP-family `port.protocol` tokens (`http`/`http2`/`grpc`/`grpc-web`/`https`). The K8s ingress translator uses `sidecar_ingress_app_protocol` (NOT the generic `app_protocol`) to set `MeshSidecarIngress.protocol`: `https` → `Http2` (routed); a MISSING or UNRECOGNIZED string (e.g. a `HTPS` typo) → `Tcp` (deferred as `NonHttpProtocol`) — so a typo/missing protocol is NEVER guessed as HTTP and exposed on the request path (Istio defaults an unset port to TCP; the native source rejects a mistyped `AppProtocol` at deserialization). The service-port default path keeps its own `Unknown → HTTP` convention via `is_http_family_mesh_protocol` (untouched). Status writer reports `ingress_modeled` count + per-reason deferrals via the SHARED `sidecar_ingress_protocol_is_http_family` predicate (which routes through `sidecar_ingress_app_protocol`), so translation/resolution and the report never diverge; the resource is still accepted. **Carrier re-validation (round-2 fix):** `local_ingress_listeners` can arrive already resolved over the xDS/native carrier, so BOTH the back-projection chokepoint (`mesh.local_ingress_listeners` in `prepare_*`, feeding the router grouping) AND `materialize_sidecar_ingress_listener_proxies` re-check each carried endpoint via `ResolvedIngressListener::endpoint_is_valid` (loopback host + nonzero listener/backend port — the same allowlist `resolve` enforces); a malformed/hostile carrier (off-box host, `:0` port) is dropped fail-closed, never dialed. Omitted `defaultEndpoint` deserializes to empty (`#[serde(default)]`, matching the K8s path) and defers at `resolve()`. Custom `bind` opens NO separate OS listener (capture funnels through :15006); `captureMode: NONE` not honored. `validate_unique_listen_paths` exempts ingress siblings as direction code `2` (outbound=0, service-port inbound=1, ingress=2). Listener identity/grouping is forward-derived from `local_ingress_listeners` (`mesh_ingress_listener_groups`, ids via stamped `owner_namespace`/`owner_service`), never parsed. Multi-port disambiguation is post-match (`select_mesh_inbound_port_route`; groups from `mesh_inbound_service_groups` over the LOCAL-INBOUND view `MeshConfig.local_inbound_services` — a `serde(skip)` runtime back-projection set in `prepare_normalized_gateway_config_for_mesh`, because the egress-narrowed `services` can lack the local service), by priority: inbound orig-dst (REDIRECT-captured plain inbound; port = CONTAINER port, matched against `proxy.backend_port`) → request authority port (peer-sidecar direct dials; port = SERVICE port, the channel the multi-port-aware egress rewrites) → single-DECLARED-port passthrough → **fail-closed 502** (`PortSignalUnavailable`/`PortNotMaterialized`; a present-but-unmatched orig-dst never falls through to the authority). **The single-port passthrough is for NON-ingress SERVICE-default groups only (round-2 fix):** a single-listener INGRESS group (`is_ingress`) requires a present port signal to MATCH the declared listener port — a request naming an undeclared port fails closed (`PortNotMaterialized`) instead of being absorbed onto the sole listener; a no-signal request still falls through to it. (A single-port service-default group keeps the back-compat any-port passthrough.) The inbound materializer's operator-yield scan excludes only the service's OWN sibling ids — another local service's route on an overlapping bare-name host still wins first-materialized. `orig_dst` is now read on BOTH directions' capture listeners (one getsockopt per accept). Ambient/Waypoint inbound: **no materialization** — an authenticated HBONE CONNECT that matches no route is relayed transparently by `handle_hbone_request` (`src/proxy/hbone_proxy.rs`), which dials the CONNECT `:authority` (the original destination). The request path synthesizes the relay proxy in the route-miss arm (`build_inbound_hbone_relay_proxy`, only when `mesh_direction == Inbound` and `is_hbone_connect`); `connect_backend` dials that proxy's `backend_host:port` = the authority. **Open-relay guard** (`inbound_hbone_relay_destination_allowed`): the authority must be a SAFE local target — loopback, or an in-mesh workload address+port the slice (`epoch.config.mesh.workloads`) declares — so an authenticated peer can never relay to an arbitrary host. `handle_hbone_request` additionally rejects a peerless CONNECT (403) before dialing. (`connect_backend` historically dialed the matched proxy's backend, so Ambient inbound 404'd before this — fixed; the relay is exercised by `functional_mesh_ambient_egress_routes_a_to_b_over_hbone`.)
- **Egress (outbound) — DONE for both captured topologies** (`materialize_mesh_outbound_proxies`, topology-aware): Ambient emits **HBONE** targets, Sidecar emits **SVID-mTLS** targets; a target carries exactly one transport tag.
  - **Ambient egress** → host-routed `/` routes whose upstream targets are `mesh.hbone`-tagged (dial peer :15008, or the `mesh.hbone_port` tag stamped from `FERRUM_MESH_EGRESS_HBONE_PORT`): `current_dispatch_hbone` (gated by `supports_hbone_backend` = `HttpPool` dispatch + tag + `gateway_svid_bundle` + capability-registry) → `proxy_to_backend_hbone` → `HboneConnectionPool` (`hbone_pool.rs`); a `mesh.hbone=true` target that can't dispatch HBONE → **502 fail-closed** (`hbone_required`).
  - **Sidecar egress** → host-routed `/` routes whose upstream targets are `mesh.mtls`-tagged (dial peer :15006, or the `mesh.mtls_port` tag from `FERRUM_MESH_EGRESS_MTLS_PORT`): `current_dispatch_mesh_mtls` (gated by `supports_mesh_mtls_backend` = `HttpPool` dispatch + tag + `gateway_svid_bundle`; **no capability registry** — `mesh.mtls` peers are slice-declared sidecars by construction) → `proxy_to_backend_mesh_mtls` → `MeshMtlsConnectionPool` (`mesh_mtls_pool.rs`, plain HTTP/2 over mutual TLS, ALPN `["h2"]`); a `mesh.mtls=true` target that can't dispatch → **502 fail-closed**. Do **NOT** tag Sidecar egress `mesh.hbone` (that's Ambient's 15008 transport).
  - **Peer identity is PINNED on both transports**: targets carry `mesh.spiffe_id` (tag builders `mesh_hbone_target_tags` / `mesh_sidecar_mtls_target_tags` in `service_discovery::mesh`, sharing one core); the pools pass it as `expected_peer` to `build_spiffe_outbound_config`, so the peer's server SVID URI SAN must EQUAL the destination workload identity — trust-domain membership alone is not enough. The pinned identity is part of the pool key (a session verified against one identity is never reused for another), and the HBONE capability probe pins the same identity as dispatch. A present-but-invalid `mesh.spiffe_id` fails the dial closed; a `mesh.mtls` target additionally REQUIRES the tag (`target_mesh_mtls_expected_peer`). HBONE targets without the tag (operator-supplied) keep trust-domain-only verification.
  - Sidecar egress **yields to the local service's inbound route** (route table holds one proxy per (host,path); the yield scan skips only sibling `__mesh-outbound-*` routes, so inbound routes and operator proxies both win); Ambient has no materialized inbound routes so no such collision.
  - **Multi-port egress (original-destination routing) — BOTH topologies**: one route + one upstream per HTTP-family service port. **Sibling identity is derived FORWARD from the prepared config's `mesh` block** (`modes::mesh::mesh_outbound_service_groups` — each service's expected per-port ids via `mesh_outbound_proxy_id` plus its DECLARED HTTP-port count; `mesh_inbound_service_groups` mirrors it for inbound) — NEVER by parsing ids backwards: the `{ns}-{name}` join is lossy (ns `a`/svc `b-c` collides with ns `a-b`/svc `c`) and would conflate distinct services. Consumers: `RouterCache::build_route_table` inserts only the lowest-port materialized representative into the (host, path) tiers (siblings would clobber) and registers the group in `HostRouteTable.mesh_outbound_ports`/`mesh_inbound_ports`; `validate_unique_listen_paths` exempts same-(service, DIRECTION) sibling pairs (the swap path runs it on every slice apply — without the exemption multi-port slices are rejected at `update_config`; a cross-direction pair of one service still conflicts — its coexistence is a materializer bug); the request path (`select_mesh_outbound_port_route`) swaps in the sibling matching `ctx.orig_dst.port()`. `orig_dst` is read ONCE per accepted connection on mesh capture listeners (`socket_opts::original_dst`, `SO_ORIGINAL_DST`/`IP6T_SO_ORIGINAL_DST`; `None` = not captured/non-Linux/direct dial — never an error) and fans out to every request on the connection via `RequestConnectionMetadata`. **Fail-closed 502**: a service DECLARING >1 HTTP port + no orig-dst (`OrigDstUnavailable` — applies even when only one sibling materialized, e.g. unresolved named targetPort: the surviving port must not absorb the skipped port's traffic), or a captured dial to a non-routed port (`PortNotMaterialized`) — never guess a port. Single-DECLARED-port services keep orig-dst-free behavior (direct dials / functional tests unaffected). **Sidecar multi-port egress rewrites the `:authority`** to `<host>:<owning service port>` in `proxy_to_backend_mesh_mtls` (tag `mesh.mtls_authority_port`, stamped ONLY for multi-port destinations by `build_outbound_mesh_targets`; corrupt tag → port-less authority → the destination 502s, never misroutes; the original client Host rides `x-forwarded-host`) — the destination's per-port INBOUND siblings disambiguate by it (their `:15006` dials are direct, never NATed). The mesh-mTLS pool key includes the app port (per-port connection isolation, parity with HBONE); `mesh_mtls_key_svid_fingerprint` parses the key POSITIONALLY — keep its index in sync with `write_mesh_mtls_pool_key`. Version skew is fail-closed both ways (old destination: 404 no-route, never misrouted; old source: no multi-port egress routes).
  - **Raw-TCP egress (orig-dst) — BOTH captured topologies**: stream-family ports (`service_tcp_stream_ports`; PARTITIONS `AppProtocol` with `service_http_family_ports` — `Unknown` stays HTTP-family, `Tls` is opaque passthrough) materialize per-port UPSTREAMS only (`materialize_mesh_outbound_tcp_upstreams`, `mesh_outbound_tcp_upstream_id`) — NO route proxies (raw streams carry no Host; a config stream proxy would demand its own `listen_port`). The per-port targets carry the topology's egress transport tag (Ambient `mesh.hbone`, Sidecar `mesh.mtls`) via `build_outbound_mesh_targets`, exactly like HTTP egress. The accept loop branches PRE-hyper (`HostRouteTable.mesh_tcp_egress` via `mesh_tcp_egress_decision`, built STRICTLY from `(MeshService.cluster_ips VIP, service port)` — populated from `Service.spec.clusterIPs` by the K8s translator, plain schema on the file source; IPs canonicalized for mapped-IPv6; then, ON A MISS, the direct-pod-IP / headless `by_workload_addr` index — see below) → `proxy::mesh_tcp_egress::handle_mesh_tcp_egress`, which LB-selects then branches by the selected target's transport tag: **Ambient `mesh.hbone`** = HBONE gate (tag + SVID + capability record) + pinned `mesh.spiffe_id` (corrupt → close) → `HboneConnectionPool::get_tunnel` (dial `:15008`, `hbone` marker); **Sidecar `mesh.mtls`** = SVID + REQUIRED pinned `mesh.spiffe_id` (`target_mesh_mtls_expected_peer`; missing/corrupt → close), **NO capability registry** (slice-declared sidecars speak mesh-mTLS by construction) → `MeshMtlsConnectionPool::open_connect_tunnel` (dial `:15006`/`mesh.mtls_port`, **bare** CONNECT — no marker, no baggage; the peer authenticates this gateway by its client SVID), which is **1:1** (one fresh mesh-mTLS H2 connection per captured stream — NOT pooled like HTTP Sidecar egress or HBONE; SVID rotation is automatic, pooling is a documented follow-up). Both transports share the raw-`h2` CONNECT primitive `dial_h2_connect_sender` + `open_h2_connect_stream` + the `H2ConnectTunnel` type (all in `hbone_pool.rs`; the HBONE pool's `create_sender`/`open_connect_stream` are now thin wrappers over them) and end in `bidirectional_copy_for_relay`. **DESTINATION inbound relay is transport-agnostic**: a bare authenticated H2 CONNECT on the Sidecar `:15006` listener funnels through the SAME `build_inbound_hbone_relay_proxy` path (gated `is_hbone_connect` + `mesh_direction == Inbound`, NOT topology) and the SAME open-relay guard (`inbound_hbone_relay_destination_allowed`) as the Ambient HBONE relay — no destination-side changes. **Never port-only matching** (two services can share a port number; a non-mesh dial must not be tunnelled on a coincidence); a declared-but-unroutable pair is CLOSED; anything else falls through to hyper unchanged. The TCP upstreams are referenced by NO config proxy, so `collect_mesh_tcp_egress_capability_targets` enrolls ONLY the `mesh.hbone` targets from the SAME deterministic synthesized relay proxy (`mesh_outbound_tcp_relay_proxy`, scheme `Tcp` so plain-HTTP probes never touch a raw app port; HBONE probe gate accepts `Http | Tcp`) — `mesh.mtls` targets are skipped (no capability probe, never dial a non-existent `:15008`); without enrollment `retain_keys` evicts the HBONE records and the dispatch gate fails closed forever. **Direct pod-IP / headless raw-TCP dials (F3 §3.4)**: a client that resolved a HEADLESS service itself and dials a POD IP directly bypasses the VIP table (VIP-less services warn+skip the VIP loop, a raw stream has no Host). These route via the `by_workload_addr` index (`HostRouteTable.mesh_tcp_egress_by_workload` via `mesh_tcp_egress_by_workload_decision`, consulted only ON A VIP MISS): a SINGLE forward-derivation source (`modes::mesh::mesh_outbound_tcp_bywl_upstreams` over each stream-family service port × backing LOCAL-CLUSTER workload × workload address that parses as an IP — DNS-name addresses skipped, target/container port resolved with the SAME fail-closed `targetPort` rule as `build_outbound_mesh_targets`) materializes ONE single-target upstream per `(canonical workload IP, target port)` (`mesh_outbound_tcp_bywl_upstream_id`, DISTINCT id space) identity-pinned to that workload's `mesh.spiffe_id` over the topology transport, and keys the index `(canonical workload IP, target port) → Relay{entry}` (canonicalized the SAME way as the VIP keys; first-wins on collision). Strict exact addr+port, fail closed (declared-but-unroutable → `CloseNotRoutable`); a non-matching dial falls through to hyper unchanged. The per-workload upstreams carry the SAME capability-enrollment trap, so the capability collector runs a SECOND pass over `mesh_outbound_tcp_bywl_upstreams` enrolling the Ambient `mesh.hbone` per-workload targets via their own deterministic relay proxy (`mesh_outbound_tcp_bywl_relay_proxy`; `mesh.mtls` skipped), and they join the DR owner-port map under their owning Service port. NO `:authority` rewrite (a direct pod-IP dial already carries the app port in its orig-dst; the `mesh.mtls_authority_port` tag is intentionally absent — that is a VIP-multi-port concern). HTTP-family headless already routes by Host (`mesh_service_host_variants`), so this is the RAW-TCP-only gap. DR per-port policy fans onto TCP upstreams via the shared owner-port map; passive-health/outlier recording is absent on the raw relay (no response status — matches stream proxies); the HBONE relay-failure metric records HBONE mid-relay failures only, but BOTH transports increment `ferrum_mesh_tcp_egress_connections_total{transport,result}` once per established relay (success/failure). The full source-capture→relay e2e for raw-TCP rides the `netns-capture-live` follow-up; the destination relay reuses the Ambient-tested machinery. UDP egress does NOT ride this raw-TCP datapath (REDIRECT/`SO_ORIGINAL_DST` don't apply to UDP) — UDP uses a separate **TPROXY** capture model (F3 §3.3): Stage 2 emits flag-gated/inert TPROXY rules (`src/capture/mod.rs` `udp_tproxy_commands_for_family` + injector wiring; `FERRUM_MESH_CAPTURE_UDP_ENABLED` default-off), Stage 3 binds the consuming listener, and **Stage 4 is datagram-over-mesh egress (DUAL-TRANSPORT: Ambient HBONE :15008, Sidecar mesh-mTLS :15006)** — see the UDP egress rule below.
  - **WebSocket egress — BOTH captured topologies, DIFFERENT inbound primitives per topology (the trap)**: a WS upgrade to a `mesh.mtls`/`mesh.hbone` destination rides the topology's secured transport over a FRESH mesh H2 connection — NOT the pre-mesh direct dial. WS bypasses the HttpPool dispatch gates (early `handle_websocket_request_authenticated` return BEFORE `current_dispatch_mesh_mtls`), so the branch lives in the WS backend-dial loop: `connect_mesh_websocket_backend` (gated `websocket_mesh_egress` reading `target_mesh_mtls_enabled`/`target_hbone_enabled` on the LB-selected target), keyed by transport tag:
    - **Sidecar (`mesh.mtls`) = RFC 8441 Extended CONNECT** via `MeshMtlsConnectionPool::open_ws_connect_tunnel` (dial `:15006`) → shared primitive `open_h2_ws_connect_stream` (`hbone_pool.rs`: full `https://<authority><path_and_query>` URI so `:scheme`/`:path`+query survive, `h2::ext::Protocol::from_static("websocket")` extension, forwards the WS handshake headers, **checks `SendRequest::is_extended_connect_protocol_enabled()` and fails closed `ExtendedConnectUnsupported` BEFORE sending** if the peer never negotiated it), returning `H2WsConnectTunnel` (`H2ConnectTunnel` + negotiated subprotocol from the 200). The tunnel body IS the raw WS frame stream — NO inner H1 handshake (source wraps `WebSocketStream::from_raw_socket(Role::Client)`). Sidecar materializes inbound WS routes, so its `:15006` `auto` listener (`.enable_connect_protocol()`, `is_h2_websocket_connect`) recognizes the Extended CONNECT and bridges to the local app over H1 upgrade. Multi-port Sidecar `:authority` rewrite via `mesh.mtls_authority_port`.
    - **Ambient/Waypoint (`mesh.hbone`) = BARE HBONE CONNECT byte tunnel + INNER H1 handshake** via `HboneConnectionPool::get_ws_byte_tunnel` (dial `:15008`, HBONE marker+baggage, bare `open_h2_connect_stream` whose CONNECT `:authority` is the workload's APP addr:port `target.host:target.port`) → `client_async_with_config(ws_request, WsActivityIo<H2ConnectTunnel>, cfg)` drives an INNER H1 WS handshake THROUGH the byte tunnel. **codex-finding-#1 FIX:** Ambient/Waypoint materialize NO inbound routes and the route-miss transparent relay (`build_inbound_hbone_relay_proxy`, gated by `hbone_proxy::is_connect_request`'s `Protocol::is_none()` — requires `:protocol` ABSENT) EXCLUDES a `:protocol=websocket` Extended CONNECT, so a `:15008` Extended CONNECT 404s for EVERY Ambient destination. Routing the bare byte tunnel to the app addr:port lets the same Ambient HBONE relay byte-copy the upgrade to the loopback app, which performs the handshake — no destination-side change (symmetric with raw-TCP egress). SERVICE `:authority`+`:path` ride the inner H1 `Host`/request-target. **Do NOT resurrect a `:protocol`-bearing Extended CONNECT to an Ambient `:15008`** (it 404s); `get_ws_byte_tunnel` is the HBONE WS path, NOT `open_ws_connect_tunnel`/Extended CONNECT.
    - **Shared**: `run_websocket_proxy<C, B>` is generic over backend transport `B` so the TCP/TLS path and BOTH mesh paths (`WebSocketStream<WsActivityIo<H2ConnectTunnel>>`) share one frame relay (H3 call site unchanged). **1:1, NOT pooled** (one fresh mesh H2 connection per WS session; SVID rotation automatic per dial — like raw-TCP egress); `BackendConnectionGuard` (`maxConnections`) preserved (acquired in the WS connect loop). Client `:path`+query preserved byte-for-byte (codex finding #2: `ws://svc-b/ws?room=1` → `/ws?room=1`, not `/`), derived from the same computed backend URL the direct path dials, threaded into both transports. Identity PINNED (`mesh.spiffe_id`; REQUIRED for `mesh.mtls`). **Fail-closed**: a mesh-tagged WS target that can't dispatch over its secured transport (no SVID/peer/Extended-CONNECT/relay) fails the upgrade — `connect_mesh_websocket_backend` NEVER calls `connect_websocket_backend`, no plaintext fallback. The H3 WS bridge (`src/http3/websocket.rs`) has NO mesh fork at all: its connect loop screens the selected target with `direct_http_mesh_transport_refusal` at the loop top (initial AND retry-rotated) and refuses the upgrade 502 pre-dial — do not assume H3 WS dispatches over mesh. The mesh WS dial returns `HbonePoolError` boxed; `retry::classify_boxed_setup_error` (via `classify_typed_chain`) downcasts it (`error_class()`) FIRST so pre-wire mesh setup failures keep connect-failure semantics (codex finding #3 — else misclassified post-wire, corrupting `retry_on_connect_failure`/backend-admission `connection_error`/CB passive health).
  - **E2E coverage**: `functional_mesh_{ambient,sidecar}_egress_*` spawn two real gateways (A captures a plaintext request → mesh transport → echo backend behind B) plus an untrusted-CA negative; they live in `functional_mesh_mode_test.rs` and ride the data-plane CI shard. The live UDP **source-capture** (TPROXY → tunnel → return-source spoofing) e2e is a remaining `netns-capture-live` follow-up, AND the full e2e Ambient relay to an enrolled destination pod is NOT yet functional pending a TC-inbound UDP admit + a dest-side in-netns reply socket (fail-CLOSED — dropped, not leaked; tracked under #2013).
- **Inbound vs. egress slice views — keep them separate.** `MeshSlice.services` is the egress/outbound-narrowed view: it is gated by Sidecar egress scope and feeds `build_known_destinations` / `mesh_outbound_registry`. Egress scope must NOT gate inbound serving, so sidecar inbound materialization reads `MeshSlice.local_inbound_services` instead — the local workload's own service(s) captured **un-narrowed** in `from_gateway_config`. Never fold the local service back into `services` (that widens the outbound registry/egress scope — a security regression). Identify the local workload with `slice::workload_is_local` (SPIFFE id + non-vacuous label/cluster match), never the service-account SPIFFE alone (it is not pod-unique). On xDS, `local_inbound_services` rides its own ECDS carrier (`MeshSliceCarrier::LocalInboundServices`), and the DP's workload SPIFFE reaches the CP via `Node.metadata` (`carrier::{encode,decode}_node_metadata`) — a hostname `node_id` alone cannot identify the workload, so without it the CP narrows the local service away before the carrier is built.

## Scope And Policy Semantics

- Scope-aware resources must use the shared `policy_scope_applies_to_workload` / `scope_applies_to_workload` helpers. Do not fork predicates.
- Single-winner precedence (`WorkloadSelector` > `Namespace` > `MeshWide`) applies only where one effective setting is resolved, such as `PeerAuthentication` and `MeshProxyConfig`.
- `MeshPolicy` and `MeshRequestAuthentication` are additive after filtering. `MeshTelemetryResource` merges by section.
- Authorization evaluation is DENY first, then ALLOW. Any ALLOW rule with no match causes implicit deny.
- `RequestMatch` negative fields (`not_methods`, `not_paths`, `not_hosts`, `not_ports`) are conjunctive with positive fields in one rule. Do not split them into separate deny policies.
- Istio empty-rule translation must preserve action semantics: ALLOW with no `rules` is allow-nothing via a never-matching rule; DENY and AUDIT with no `rules` are no-ops.
- NodeWaypoint per-pod policy scoping (`per_pod_policy_scoping`) is resolved per request from `node_waypoint_policy_scope`. The HTTP/HBONE accept path populates it from the resolver (`proxy/mod.rs`); the TCP/UDP stream accept loops always pass `None`, so only `MeshWide` policies are evaluated on streams. A config-apply that has stream proxies + scoped policies in NodeWaypoint topology must keep emitting the one-shot warning. Do not silently start enforcing scoped stream policies without wiring the resolver end-to-end and updating `docs/mesh.md`.
- Mesh authz `source.ip`/`ipBlocks` uses `RequestContext::direct_client_ip` (immediate peer) and `remote.ip`/`remoteIpBlocks` uses `client_ip` (XFF-resolved) on the HTTP path; the stream path (`on_stream_connect`) has only `client_ip`, so both collapse to it. IP-block matchers fail closed when the tested IP is absent.

## Mesh Plugin Injection

- `inject_mesh_global_plugins()` auto-injects reserved-ID globals on slice apply: `__mesh_spiffe_identity` priority 940, `__mesh_authz` priority 2075, `__mesh_workload_metrics`, `__mesh_request_auth` only when JWT rules exist, and `__mesh_access_log` (a `stdout_logging` instance carrying the Telemetry `accessLogging` filter).

- Mesh plugin injection must preserve normal plugin lifecycle ordering and transaction logging.

## HBONE Identity Boundary

- HBONE is HTTP/2 CONNECT over mTLS on port 15008.
- `is_hbone_connect()` only detects the wire shape (H2 CONNECT + optional `x-ferrum-mesh-protocol`/`x-istio-protocol: hbone` marker); it does not imply authentication and is only safe for non-relay decisions (path normalization, metadata tagging, body-buffering branch).
- Relaying a CONNECT as an HBONE tunnel requires an authenticated, trust-domain-verified peer (`ctx.peer_spiffe_id.is_some()`, i.e. `is_authenticated_hbone_connect()`). `handle_hbone_request` rejects a peerless CONNECT — bare or marker-bearing — with `403 Forbidden` before dialing/circuit-breaking any backend, stamping `mesh_authz.deny_policy=hbone_unauthenticated_peer`. The explicit marker path is not a bypass. This is separate from (and additive to) TLS-time trust-bundle peer verification.
- Baggage `source.principal` rewrites the authz principal only when the authenticated peer is in `mesh_authz.trusted_hbone_assertors` and the baggage trust domain matches the peer cert or `FERRUM_MESH_TRUST_DOMAIN_ALIASES`. Ambient UDP may additionally carry `source.pod_uid`; use it for namespace/selector scope ONLY after that same principal trust gate succeeds and the live slice maps the exact, unambiguous pod UID to the same SPIFFE ID. Missing/malformed/stale/mismatched/untrusted UDP evidence evaluates mesh-wide policies only.
- Untrusted assertors keep their own peer-cert identity even when baggage is present.
- Never infer Ambient UDP pod scope per datagram. `NetnsUdpCaptureManager` fixes the node-agent-registry-derived `(pod UID, SPIFFE ID)` evidence per pod-netns producer and `get_datagram_tunnel` stamps it on the authenticated CONNECT. Conflicting identities in one shared netns suppress the stamp (mesh-wide fallback).
- Dropped baggage must surface in transaction metadata as `mesh_authz.ignored_baggage.untrusted_assertor=true`; denied requests contribute `mesh_authz.deny_policy=untrusted_assertor`.
- Trust-domain mismatches use the existing `trust_domain_mismatch` reason.
- Default trusted assertor service accounts are `ztunnel` and `waypoint`. `FERRUM_MESH_TRUSTED_HBONE_ASSERTORS` accepts bare service-account names or full SPIFFE IDs.
- Explicit empty `trusted_hbone_assertors: []` disables baggage rewriting entirely.
- Keep fallback baggage key aliases in `HboneIdentity::from_headers()` in sync with tests.

## Node-Waypoint Per-Pod Policy Scope

- One node-waypoint listener serves many pods; source pod identity comes from the eBPF `connect4`/`connect6` cgroup-stamped `SO_COOKIE` record, resolved through `NodeWaypointIdentityResolver`. The hooks read the identity from `FERRUM_WORKLOAD_IDENTITY` keyed by `bpf_get_current_cgroup_id()` — the *container leaf* cgroup, a child of the pod cgroup on every K8s cgroup driver — so the node-agent enrolls the identity under the **whole pod cgroup subtree** (pod inode + descendant container-cgroup inodes via `cgroup::collect_cgroup_tree_inodes`) and re-walks on reconcile so late-starting/restarted containers are picked up. Keying only the pod inode would miss the leaf and fail closed in real pods. `FERRUM_INCLUDE_PORTS` (per-pod `includeOutboundPorts` narrowing) is keyed the same way and enrolls the same subtree, re-walking on every reconcile (like identity) so a container leaf that starts/restarts after the initial pod event still picks up the policy; unannotated pods short-circuit before any walk.
- **Lazy-identity reclamation:** the production enrollment path (hash-join in `resolve_record`) binds no cgroup and nothing calls `remove_identity`, so the periodic sweep (`sweep_cgroup_stale_identities`, gated by `FERRUM_MESH_NODE_WAYPOINT_CGROUP_SWEEP_INTERVAL_SECS`) reclaims a non-cgroup-bound identity only when its `pod_uid` is no longer referenced by any live cookie record **and** its identity `Arc` has no other holder (`strong_count == 1`) — a churned pod's accept-side cookies age out of `cookie_records` (the `sock_ops` program removes the orig-dst record on TCP close, so closed-connection cookies don't linger in the LRU map until pressure — without that, dead pods would never age out on a low-churn node), so its orphaned identity and per-pod scope are reclaimed instead of accumulating. The `strong_count` guard is load-bearing, not decoration: HTTP/HBONE connections store the resolved identity `Arc` for their lifetime and re-query the per-pod scope per request, so the BPF LRU evicting a live connection's cookie must not let the sweep drop its scope (it would downgrade later streams to mesh-wide); the held `Arc` keeps the pod un-evictable until the connection closes. TCP resolves its scope once at accept and never re-queries, so it's covered by the cookie-reference check alone. A still-live idle pod re-enrolls on its next connection. cgroup-bound identities remain the cgroup-binding pass's domain — the idle pass never touches them.
- HBONE/HTTP and raw **TCP** stream accept paths both resolve the connection's pod identity and stamp `node_waypoint_policy_scope` (HTTP: `RequestContext`, TCP: `StreamConnectionContext`) via `policy_scope_for_pod(pod_uid)`, so `mesh_authz` enforces Namespace/WorkloadSelector-scoped policies per source pod. The TCP path threads the resolver `ProxyState` → `StreamListenerManager::set_node_waypoint_identity_resolver` (injected before the first stream reconcile) → `TcpListenerConfig` → accept loop (`resolve_node_waypoint_stream_scope`).
- **GAP-2M accept-side bridge** (applies to both HBONE/HTTP and TCP paths equally; **IPv4 and IPv6**): `connect4`/`connect6` key the orig-dst record by the connecting-socket cookie, but accept paths look up the accept-side `SO_COOKIE`. The bridge is implemented in the kernel `sock_ops` program (`ebpf/ferrum-ebpf/src/sock_ops.rs`): at active-established it re-keys the record by `(netns cookie, connection tuple)` (`FERRUM_ORIG_DST_BY_TUPLE4` / `FERRUM_ORIG_DST_BY_TUPLE6`), and at passive-established it re-stamps it into `FERRUM_ORIG_DST4`/`FERRUM_ORIG_DST6` under the accept-side cookie, so the resolver (fed by `orig_dst_bridge`) resolves scoped policies with no further proxy-side changes. The IPv6 ctx address words (`local_ip6`/`remote_ip6`) are read element-by-element with verifier-safe **volatile** per-`u32` loads at explicit ctx offsets (`read_ctx_ip6` over the four offsets — the same per-element technique `connect6` uses; a whole-`[u32;4]` ctx copy trips the verifier), keyed by `ConnTuple6`, so v6 resolves on the same footing as v4 (the userspace resolver already merges both families by socket cookie, so only the kernel re-stamp was missing). Per-pod identity enrollment is wired with no separate channel: slice apply installs a `workload_spiffe_hash` → SPIFFE index alongside the policy scopes, and `resolve_record` lazily enrolls `pod_uid` → identity by hash-joining that index against the eBPF-stamped `(pod_uid, workload_spiffe_hash)` on first sight (an unmatched hash fails closed as `UnknownPod`). The current slice index is re-checked on **every** resolve, not only first-sight: a cached `pod_uid` whose workload a later slice removes (its hash leaves the index) stops resolving — the cached-identity branch fails closed (HBONE drops, TCP downgrades to mesh-wide) instead of serving the orphaned identity, and re-validates for free if the workload returns. The gate (`workload_spiffe_hash`→SPIFFE) and the scope index are **one `ArcSwap<NodeWaypointSlice>` generation**: scope is keyed **strictly** by the exact **pod UID** the eBPF stamps (`scopes_by_pod_uid`, built from the slice's per-pod workloads' `metadata.uid`) — a captured pod is **never** resolved through a SPIFFE-keyed index, so pods that share a service account (one SPIFFE) but carry different labels are scoped independently (each against its own labels) rather than collapsed to the label intersection, and a pod whose workload is absent from the live slice fails closed (no scope) instead of borrowing a same-SPIFFE workload's labels. Scope is reclaimed by slice updates, not identity lifecycle (`remove_identity`/sweep do not touch it). `resolve_*` returns the identity **and** its scope from a single load of that generation, so a slice reload can never pair a resolved identity with an old/missing scope (the "never partial" invariant for scoped authz). The TCP path captures both at accept and persists them for the stream; HBONE/HTTP re-queries the scope per request, each read from one coherent generation. The `netns_cookie` (`bpf_get_netns_cookie`) is load-bearing, not decoration: captured connections all target `127.0.0.1:15001` / `[::1]:15001`, so the tuple collapses to loopback + an ephemeral port that can collide across pod netns in this one global map — the per-netns cookie keeps each pod's key distinct (preventing cross-pod record overwrite / identity misattribution) while staying identical for the two ends of a same-netns connection. Do not drop it from the key. (**Distinct from** the in-netns OUTBOUND capture listener + `connect6`'s `ipv6_outbound_deny`, which remain IPv4-only — those concern the pod-loopback redirect datapath, not the accept-side cookie bridge fixed here.) **Verification:** CI compile-checks the program (`build-ebpf`) and load/attach-tests every program — incl. the bridge — on a real ≥5.7 kernel (`ebpf-live`, which already caught and forced fixes for `connect6`/`getpeername6`/`sock_ops` verifier rejections); the full connect→capture→accept datapath (tuple byte-order, end-to-end resolution) is **not** CI-verified and needs a live multi-pod node. Safe by construction: a tuple/byte-order mismatch writes no accept-side record → resolution stays fail-closed, never misattributed.
- **In-netns outbound capture listeners** (always on for NodeWaypoint topology): `connect4` rewrites a captured pod's outbound to `127.0.0.1:15001` in the **pod's** loopback, but a single outbound listener bound `127.0.0.1:15001` in the host/proxy netns can never receive a pod loopback connection — so a host-only listener leaves node-waypoint outbound capture non-functional on a real multi-pod node (connections refused, scoped enforcement never engages); the GAP-2M `sock_ops` cookie bridge also independently requires the accept socket to share the connecting pod's netns. `NetnsCaptureManager` (`src/proxy/netns_capture.rs`) opens one `127.0.0.1:15001` listener **inside each enrolled pod's netns** (`setns(CLONE_NEWNET)` on a dedicated thread, deduped by netns inode), so captured pod-loopback connections are accepted there and the same-netns cookie bridge resolves source identity. Pod discovery reuses the pinned-path IPC pattern: the node-agent publishes a registry dir `FERRUM_MESH_NODE_WAYPOINT_POD_REGISTRY_DIR` (default `/run/ferrum/node-waypoint-pods`), one file per enrolled pod (name = pod UID, contents = pod cgroup path), written on enroll / removed on teardown; the manager polls and reconciles listeners (open on add, close on removal). The listener binds pod loopback on the configured `outbound_listen_addr` port (not a hardcoded `15001`, and not the configured IP — `connect4` always rewrites to loopback; skipped when that port is `0`), shares one `max_connections`-sized connection semaphore across all in-netns listeners, reopens when the pod's registered IP changes (so `source_ip_override` tracks the pod IP; the marker is retracted before reopen so a failed reopen can't look ready), and closes when a pod UID moves to a different netns (preserving the transient-unresolvable grace). **Deferred-redirect readiness gate:** to avoid redirecting a pod before its listener exists, the node-agent defers attaching `connect4` at enrollment (`connect6` is instead attached up front as a **fail-closed IPv6 denier** — the in-netns listener and bridge are IPv4-only, so the `ipv6_outbound_deny` capture-config flag makes `connect6` return `EPERM` for captured v6 rather than letting IPv6 egress bypass `mesh_authz`; excluded v6 via CIDR/port excludes still flows) and enables `connect4` only after the proxy writes `<registry_dir>/.ready/<pod_uid>` (on listener open; removed on close/reopen), polling on a 1s tick with a ~30s bounded fallback — so the registry dir must be mounted RW for the proxy. Linux-only (`setns`, `/proc/<pid>/ns/net`); non-Linux is an unsupported stub. Reconcile/registry logic is unit-tested; the `setns`/bind path and full pod-loopback datapath are **not** CI-testable (need a live multi-pod node) — implemented, live-datapath-unverified.
- A missing scope sets `mesh_authz.scope_missing=true` and, when any namespace/selector-scoped policy is configured, **fails closed** (Reject 403, `mesh_authz.deny_policy=scope_missing`) on **both** the HTTP/HBONE request path (per request) and TCP/UDP streams (at accept) — a missing scope means the pod's workload left the live slice generation (it is derived from the same generation that vouches the identity, so it is not an enrollment race), so a long-lived HTTP/2 connection from a removed workload must not keep serving with scoped policies silently withheld. With only mesh-wide policies the mesh is fully evaluable and both paths fall through to mesh-wide-only. (At connection accept the HBONE listener still drops outright on an *unresolved identity*; this per-request/per-connection check additionally covers a workload removed *after* accept.)
- **UDP/DTLS** stream proxies stay mesh-wide-only and pass `node_waypoint_policy_scope: None`: a shared UDP frontend socket carries one cookie for all clients and there are no UDP capture hooks, so there is no per-source-pod cookie to resolve. Do not "fix" this by resolving the listener socket's cookie — that misattributes every session to one identity.
- Only `NodeWaypoint` topology installs the resolver. Sidecar/Ambient/east-west/egress and non-mesh stream proxies pass `None` and are unchanged.

## PeerAuthentication And TLS Reload

- By default, inbound mesh mTLS mode resolves once from the initial slice.
- When all three `FERRUM_GATEWAY_SVID_*` paths are set, the inbound mTLS/HBONE listener uses a SPIFFE client-cert verifier that validates the peer SAN's trust domain against the gateway SVID local bundle plus slice federated bundles; without SVID material it falls back to chain-only verification over `FERRUM_FRONTEND_TLS_CLIENT_CA_BUNDLE_PATH`. STRICT requires a peer cert; PERMISSIVE trust-domain-validates an offered cert but still admits cert-less peers. The HBONE baggage trust-gate rests on this verified identity.
- Gateway SVID material also backs the inbound listener's **server identity** when no explicit `FERRUM_FRONTEND_TLS_CERT_PATH`/`KEY_PATH` is set (`load_mesh_frontend_server_identity` resolves the SVID leaf+key live from the slot as the server cert via `svid_rotating_mesh_server_identity`): a SVID-only mesh serves mTLS inbound instead of falling open to plaintext under PERMISSIVE. Explicit frontend TLS still takes precedence.
- The gateway SVID slot is fed by **either** file-based material (`FERRUM_GATEWAY_SVID_*`, watched + rotated by `run_gateway_svid_file_rotation_loop`) **or** a **CA backend** (`FERRUM_MESH_CA_BACKEND=spire|internal`): mesh startup runs `start_mesh_ca_backend_svid_source` (`src/modes/mesh`), which for `spire` fetches the gateway's own SVID from the SPIRE Agent Workload API (`FERRUM_MESH_SPIRE_AGENT_SOCKET`) by reusing the identity `fetch_loop` (`SvidFetchHandle::from_slot` + `with_installer`), and for `internal` self-issues from the dev-only `bootstrap_dev_root` `InternalCa`; either way it live-rotates the SVID into the **same** `gateway_svid_bundle` slot (and publishes it to a live inbound peer-verifier slot), so the inbound `SvidServerCertResolver`, the SPIFFE peer verifier, and the backend pools all pick rotations up with no restart. Startup blocks on the first SVID (`MESH_CA_INITIAL_SVID_TIMEOUT`, 30s; fail-closed) so the inbound listener never binds identity-less, a CA backend REQUIRES `FERRUM_MESH_WORKLOAD_SPIFFE_ID` (the fetched identity is pinned to it), and explicit `FERRUM_GATEWAY_SVID_*` file material takes precedence when both are configured. Do NOT add a second source-of-truth slot — feed `gateway_svid_bundle`.
- Runtime inbound mTLS fail-closed (`enforce_mesh_inbound_fail_closed` + `decide_mesh_inbound_fail_closed`, issue #1523), at the startup TLS-setup path **and on PeerAuthentication live reload** (`plan_mesh_inbound_tls_reload`). Two cases, deliberately different severity: (1) a listener that would serve **plaintext** (resolved `ServerConfig` `None` — PeerAuthentication DISABLE or no usable server identity) is **refused under `FERRUM_MESH_PRODUCTION_MODE=true`**; **dev** allows it with a loud warning — an explicit DISABLE, or a no-identity posture already acknowledged by the config-time `FERRUM_MESH_ALLOW_NO_CA` gate, is intentional, so the runtime gate does not re-consult the opt-out. (2) a **configured-but-unloadable SVID verifier** (all three `FERRUM_GATEWAY_SVID_*` named but `build_mesh_inbound_spiffe_slot` returned `None` while the listener serves TLS) is a genuine fault — **fatal regardless of production** (mirrors the hard error a broken SVID cert/key gets in `load_mesh_frontend_server_identity`; `decide_*` is NOT consulted for it). At reload, "refuse" means reject the slice and keep the last-good mTLS config in its entirety (fail-closed by retention — never crash a live data plane, matching the failed-`ServerConfig`-rebuild contract above). `FERRUM_MESH_PRODUCTION_MODE` is read once at startup and threaded through `MeshInboundTlsReloadState.production` (process-fixed; a per-apply env read would also be test-racy). EastWestGateway (SNI passthrough, no termination listener) is exempt.
- The mesh `RequestAuthentication` (`jwks_auth`) plugin requires the JWT `exp` claim by default (`FERRUM_MESH_REQUEST_AUTH_REQUIRE_EXP=true`); operators may relax it. Expiry validation (rejecting present-but-expired `exp`) is always on.
- With `FERRUM_MESH_PEER_AUTH_LIVE_RELOAD_ENABLED=true`, only resolved mTLS mode, frontend client CA verifier, and the lock-free SPIFFE SVID bundle slot (federated trust domains) may hot-swap on slice apply.
- Frontend cert/key paths remain restart-required inputs for mesh peer auth reload.
- Coverage includes mesh HTTP/HBONE termination listeners and mesh-shared TCP+TLS / UDP+DTLS stream listeners.
- `apply_mesh_inbound_tls_reload` publishes swapped `ServerConfig` into HBONE, shared stream TLS, and active `DtlsServer` frontend DTLS configs.

## DestinationRule And Materialization

- DestinationRule `connectionPool.tcp.connectTimeout` lands on `Upstream.port_overrides[port].connect_timeout_ms` and is enforced by HTTP/H2/H3, gRPC, TCP, and HBONE dispatch.

Scope is strictly plain-HTTP — NEVER touch gRPC (always H2) or HBONE/mesh-mTLS transport selection. `connectionPool.http.http1MaxPendingRequests` lands on `port_overrides[port].http1_max_pending_requests` → `Proxy.pool_http1_max_pending_requests` (also `#[serde(skip)]` DERIVED-ONLY, DB loaders start it `None`) and is enforced as a per-`(host, port)` CONCURRENT-IN-FLIGHT-H1 CAP on the reqwest/HTTP-1.1 dispatch path only — an **honest reinterpretation of Envoy's connection-pending-queue** (reqwest's `send()` resolves at response-headers with no connection-acquire hook, so true pending-queue depth is unmeasurable; see `docs/mesh.md`) (`proxy_to_backend` → `state.backend_pending_limit.try_acquire`, `src/backend_pending_limit.rs` — a sharded `CachePadded` atomic CAS-bumped exactly like `backend_conn_limit`): a request that cannot get an in-flight slot is SHED with a 503 ("upstream overflow", `error_class=DispatchPolicyRejected` — a `client_side_no_backend_signal`, so it is NOT retried and is NEUTRAL to backend health: no CB trip, no passive-health ding, no adaptive-concurrency shrink, since the backend was never dialed), the slot held for the in-flight window (dispatch → response-headers; RAII guard dropped the moment `send()` returns). NO body-shape exclusion — bodyless and streamed-upload H1 requests are capped alike. HTTP/1.1-SCOPED by design (the knob is `http1*`): the direct-H2/gRPC/H3/HBONE/mesh-mTLS branches return before the reqwest path, so they never consult it (their concurrency = `http2MaxRequests`/`h2_max_concurrent_streams`); the connection-failure retry path (`proxy_to_backend_retry`) RE-ENTERS the same gate per attempt (the initial attempt's slot is released before the retry loop runs, so an attempt + its retry never double-count). The three of `h2UpgradePolicy`/`maxRetries`/`http1MaxPendingRequests` are applied at TOP-LEVEL/`portLevelSettings` only; set inside a `subsets[].trafficPolicy` they are DEFERRED+WARNED (subset → `SubsetTrafficPolicy` carries no `connectionPool.http`) and surfaced via `istio_status.rs` `SUBSET_DEFERRED_CONNECTION_POOL_HTTP_FIELDS` (keep in lock-step with the translator's `TrafficPolicyScope::Subset` warning loop). `connectionPool.http.maxRetries` lands on `port_overrides[port].max_retries` and is a **per-request retry-count CAP** (NOT Envoy's cluster-wide outstanding-retry budget — honest reinterpretation, see `docs/mesh.md`): `cap_proxy_retry_for_target` caps `Proxy.retry.max_retries` to `min(existing, dr)` once the target port is known and before any retry loop reads `proxy.retry`; it NEVER increases retries and does NOT synthesize a policy when `Proxy.retry` is `None`. Zero/negative `maxRetries` and unknown `h2UpgradePolicy` enum values are rejected at translate time.

## Injector, Node Agent, And CNI

- Injector mode serves `POST /mutate` Kubernetes AdmissionReview and emits JSON patches only.
- Sidecars run as `PROXY_UID`; optional iptables init container requires `NET_ADMIN`.
- IPv4/IPv6 capture CIDRs must stay partitioned into `iptables` and `ip6tables` blocks. `FERRUM_MESH_IP6TABLES_ENABLED=auto|true|false` controls IPv6 fan-out.
- **UDP capture uses TPROXY, not REDIRECT** (F3 §3.3 Stage 2, `FERRUM_MESH_CAPTURE_UDP_ENABLED` default-OFF/inert): TCP's `nat` REDIRECT rewrites the destination (orig-dst via `SO_ORIGINAL_DST`), which has no UDP analogue, so captured UDP uses `mangle`-table TPROXY (`FERRUM_MESH_UDP_INBOUND`/`FERRUM_MESH_UDP_OUTBOUND`, `-j TPROXY --on-port <FERRUM_MESH_CAPTURE_UDP_PORT, default 15011> --tproxy-mark <FERRUM_MESH_TPROXY_MARK, default 0x733>/<mask>`) — delivers the datagram WITHOUT rewriting dest (orig-dst recovered per-datagram from `IP_RECVORIGDSTADDR` in Stage 3) — plus raw `ip rule add priority 100 fwmark <mark>/<mask> lookup 33133` + `ip route add local 0.0.0.0/0 dev lo table 33133` (and `ip -6` under the v6 fan-out). **The `ip rule` priority is a low constant `TPROXY_ROUTE_RULE_PRIORITY=100`, SEPARATE from the routing TABLE `TPROXY_ROUTE_TABLE=33133`** (codex r2): the RPDB is priority-ordered and the kernel `main` rule is priority 32766, so the fwmark rule MUST sit below it or `main` resolves the marked datagram first and captured UDP black-holes. Table `33133` is Ferrum-owned, NOT Istio's `133`, so cleanup never risks a co-resident Istio table. **Capture is EGRESS-ONLY (#1808):** the OUTBOUND chain rides `mangle PREROUTING` scoped `-m addrtype ! --dst-type LOCAL` (remote dest). The INBOUND `--dst-type LOCAL` catch-all chain/jump is **gated off** (`emit_inbound = false` in `udp_tproxy_commands_for_family`) — there is no inbound UDP relay yet, and the egress-only capture listener would divert pod-app-bound UDP and DROP it (black-hole for UDP-serving pods), so inbound-to-pod UDP is left uncaptured and flows normally to the app; teardown still reaps any prior inbound chain. The OUTBOUND `! --dst-type LOCAL` scope is the pod-IP-agnostic mirror of the TCP chains' hook separation; re-enable inbound (the gated catch-all, kept ordered after the outbound jump) when an inbound UDP relay lands. **Fail closed when routing is unavailable** (codex r2): the setup script FATALLY preflights `command -v ip` BEFORE any UDP rule (no `iproute2` ⇒ `set -e` exits, installing NOTHING — TPROXY and routing go in together or not at all, never a TPROXY-without-routing black-hole) and the load-bearing routing ADDs are NOT `|| true`; only the delete-before-add (idempotence) and cleanup stay best-effort. **Routing is installed BEFORE the two `mangle PREROUTING` jumps** (codex r5): the jumps start steering UDP into the chains, the injector init script has NO cleanup trap, so a routing ADD that failed after the jumps were appended would leave TPROXY live without policy routing (the half-installed black-hole) — emitting `ip rule`/`ip route` first aborts `set -e` before any capture is wired (chains/rules are inert until the jumps append last). **Pod-netns ONLY (host-netns node-agent limitation, codex r5):** the `--dst-type LOCAL` split is correct only where the pod IP is LOCAL (the injector's pod netns); the node-agent DaemonSet runs `hostNetwork: true` where pod IPs are FORWARDED, so inbound-to-pod would match the OUTBOUND `! --dst-type LOCAL` discriminator. There is no host-netns-safe `addrtype` discriminator without per-pod IP knowledge the fallback lacks, so `CaptureConfig::host_netns` makes `udp_tproxy_commands_for_family` emit NO UDP TPROXY rules for the node-agent (a one-shot warn when UDP capture is on) — eBPF is the supported node-agent UDP path; the host-netns iptables fallback is TCP-only. The UDP listener port is DISTINCT from the TCP outbound port (UDP+TCP can't share a socket). The default mark `0x733` (1843) is Ferrum-owned and deliberately NOT Istio's conventional TPROXY mark `0x539` — Ferrum's `ip rule` matches the mark to steer into the Ferrum table, so defaulting to `0x539` would hijack a co-resident Istio's marked packets (and break Istio); `0x733` sits in a gap clear of Istio's exact marks AND of common MASKED CNI mark classes — Cilium matches `skb->mark & 0xF00`, so the prior default `0xFE3` ALIASED Cilium's `0xF00` class (`0xFE3 & 0xF00 == 0xF00`) and could be misclassified by a co-resident CNI, whereas `0x733 & 0xF00 == 0x700` does not (compile-time asserts in `src/capture/mod.rs` pin the masked-class non-aliasing) — and is collision-free within Ferrum (no other packet marks; the `1337` proxy UID is a socket-owner match, disjoint from `skb->mark`). **TPROXY runs only in PREROUTING** (jumping into a `-j TPROXY` chain from `mangle OUTPUT` is invalid), so the pod's OWN locally-generated UDP egress (which never traverses PREROUTING) is captured via a separate **MARK-only `FERRUM_MESH_UDP_OUTPUT_MARK` chain jumped from `mangle OUTPUT`**: it MARKs egress with the TPROXY fwmark (the proxy-UID `-m owner` self-exclusion lives HERE — owner-match is OUTPUT-context-only, invalid in the PREROUTING chains), the fwmark `ip rule` reroutes the marked datagram to `lo`, and a mark-match `FERRUM_MESH_UDP_REINJECT` PREROUTING rule TPROXY-captures the looped datagram. So sidecar-self-egress UDP IS handled (no longer deferred); the full loop's live validation rides `netns-capture-live`. Default OFF because the consuming UDP listener arrives in Stage 3 — an upgraded injector must not redirect UDP into a void; when off NO mangle/TPROXY/routing rules are emitted. Cleanup removes the mangle chains + tears down routing by deleting the EXACT Ferrum-owned rule (`ip rule del priority 100 lookup 33133`) + exact route, never by-lookup or table-flush. The 3 vars are parsed in ONE place (`capture::udp_capture_settings_from_env`), shared by `CaptureConfig::from_env` (node-agent) and the injector.

A topology with NO UDP relay (EastWestGateway / EgressGateway / waypoints) with `FERRUM_MESH_CAPTURE_UDP_ENABLED=true` emits NO listener/producer + a one-time `warn!`. `EnvConfig::reserved_gateway_ports()` reserves the host capture port for **Sidecar ONLY** — the Ambient producer binds in the pod netns, so the host port stays free. **Injector/init TPROXY-rule gating for Sidecar is MATCHED to the listener gate** (#1808): the injector only emits Sidecar pods, and `injector::sidecar_udp_capture_supported()` (a central `const fn` switch, now `true`) ENABLES the init container's UDP TPROXY rules, the sidecar's runtime-enable env, AND the transparent-bind capability (`NET_ADMIN`) TOGETHER — so an injected Sidecar with the operator's `udp_capture_enabled` flag set both diverts UDP and binds a listener (the first working end-to-end UDP path). (`udp_tproxy_commands_for_family` itself still gates only on `host_netns`; the topology decision lives in the injector, the only pod-netns emitter. The node-agent/ambient host-netns path installs no UDP rules (`host_netns` short-circuits `udp_tproxy_commands_for_family`); Ambient's UDP source-capture instead rides the **per-pod-netns producer** (#2013, installs rules INSIDE each pod netns) and relays over HBONE. eBPF UDP capture (#1803) stays a non-goal.) **Egress datapath** (`mesh_udp_capture.rs`): the recv loop does route lookup + admit + drop-on-full `try_send` only (hot-path-light); a per-session mpsc+task opens the datagram tunnel via a **dual-transport branch mirroring `mesh_tcp_egress::handle_mesh_tcp_egress`** (1:1 dial, `udp` marker): **Ambient `mesh.hbone`** → `HboneConnectionPool::get_datagram_tunnel` (dial `:15008`, capability-record-gated + pinned `mesh.spiffe_id` plus optional per-pod source evidence); **Sidecar `mesh.mtls`** → `MeshMtlsConnectionPool::open_datagram_tunnel` (dial `:15006`/`mesh.mtls_port`, REQUIRED pinned `mesh.spiffe_id` via `target_mesh_mtls_expected_peer`, NO capability registry); a target with neither tag ends the session. Both share the LB guard + gateway-SVID-present gate; frames+writes. A `LoadBalancerConnectionGuard` is held for the session's lifetime (acquired right after LB selection, like `mesh_tcp_egress`), so least-connections LB sees active UDP sessions. Session teardown removes the map entry via `remove_if` keyed on a per-session `session_id` token (not unconditional `remove`), so an idle-sweep reap + same-key replacement in the gap before the task observes its closed channel never clobbers the replacement / double-decrements the cap. **Egress idle is bidirectional** (codex r2 P2, mirrors `relay_hbone_udp`): a shared `last_activity` atomic is bumped on BOTH client→egress sends and return-path (tunnel→client) datagrams, watched by one watchdog — a one-way reply stream (client quiet, dest streaming) does NOT time out mid-flow. **Tunnel writes are bounded** (codex r2 P2): the framed `write_all` onto the tunnel is wrapped in a write-deadline `timeout` (the idle window, or a fixed fallback when idle is disabled); a stalled HBONE peer / exhausted flow-control tears the session down (drop tunnel, decrement `active_sessions`, `remove_if`-owned) instead of leaking a stuck task. **Return path (risk #1)**: a per-session transparent `UdpSocket` bound NON-LOCALLY (via `IP_TRANSPARENT`) to the captured orig-dst, so replies are SOURCED FROM the VIP:port the pod dialed (PKTINFO sets only the source IP, not port — a bound transparent socket sets both). **IPv4-mapped clients are canonicalized at capture** (codex r2 P1): the dual-stack `[::]` socket reports IPv4 senders as `::ffff:a.b.c.d` (`SocketAddr::V6`) while the orig-dst cmsg for the same packet is `SocketAddr::V4`; the client addr is unmapped to its V4 form BEFORE keying the session and building the reply socket, so the reply socket's family matches the orig-dst family and `send_to(client)` succeeds (genuine IPv6 clients are untouched). The session key uses the canonicalized client so key + reply agree. **Dest side**: `is_udp_hbone_connect` flows through the SAME transparent-relay synthesis (`build_inbound_hbone_relay_proxy` + open-relay guard) as the byte-stream relay (a combined `is_hbone_connect_any` drives path-norm / body-buffering-avoidance / CONNECT-405-bypass / route-miss-synthesis); `handle_hbone_udp_request` unframes the tunnel into a local `UdpSocket` to the CONNECT authority (open-relay guard applies — AND is RE-CHECKED on the post-route-override EFFECTIVE destination via `inbound_hbone_relay_destination_allowed`, since the unknown-id synthesized relay proxy inherits the global plugin chain and a route-override plugin could otherwise move the destination outside the loopback / slice-declared-workload allowlist after the build-time guard ran; codex r6 P2) and frames replies back. `relay_hbone_udp`'s idle is refreshed on activity in BOTH directions (shared `last_activity` atomic + watchdog), so a one-way tunnel→app flow (e.g. telemetry) doesn't time out while the tunnel is active. The destination relay (`handle_hbone_udp_request`/`relay_hbone_udp`) is e2e functional-tested by `functional_mesh_udp_dest_*` **in isolation** (Stage 7: a `udp` mTLS CONNECT → framed datagram → local (non-enrolled) UDP echo → framed reply; + off-allowlist-refused + untrusted-peer-fail-closed; no root/netns needed) — this does NOT cover the destination pod being an ENROLLED Ambient pod, where the `tc_inbound` eBPF guard drops UDP to the pod IP and the pod's own OUTPUT-mark rules re-capture the app's reply to a host-netns relay socket. Two gaps remain, both fail-CLOSED (dropped, not leaked) and out of scope for the transport-half producer (#2030): (1) the live **source-capture** e2e (TPROXY → tunnel → return-source spoofing), which rides the §3.1 `netns-capture-live` follow-up; and (2) the full **e2e Ambient relay to an enrolled destination pod**, pending a TC-inbound UDP admit keyed on the relay socket's mark/identity (`ebpf/ferrum-ebpf/src/tc_inbound.rs`) + moving the dest-side inbound relay socket INSIDE the destination pod netns (so the reply is pod-LOCAL, excluded by the existing `! --dst-type LOCAL` scope) — a two-pod (both enrolled) live verification (tracked under #2013). **DTLS passthrough (Stage 5):** there is NO `Dtls` `AppProtocol` — a DTLS port is declared `protocol: UDP` and rides this SAME egress datapath **OPAQUELY**: the mesh never terminates DTLS, parses the ClientHello, or routes on DTLS SNI (UNLIKE the standalone `passthrough` UDP/DTLS stream proxy, which peeks the ClientHello for SNI). The inner DTLS stays end-to-end between workloads; the outer mesh hop is HBONE/mesh-mTLS-secured. East-west pod→peer only; EgressGateway external-UDP/DTLS stays out of scope. Opaque relay pinned by `dtls_handshake_datagram_round_trips_opaque` in `mesh_udp_frame`.
- **UDP fail-closed contract (F3 §3.3 Stage 6 — consolidates Stage 3–4 hardening; full gate table in `docs/mesh.md`)**: the UDP datapath mirrors the raw-TCP egress fail-closed table gate-for-gate, and **every gate drops/rejects on doubt with NO plaintext or alternate-hop fallback** — every dial-error path ENDS the session. Do not regress any of: **routability** (orig-dst ∈ `mesh_udp_egress`; non-match drops BEFORE a slot/task is reserved), **gateway SVID present** (no SVID ⇒ end session, never plaintext), **Ambient capability probe** (un-enrolled `Udp` ⇒ drop, never blind-dial; the probe gate stays `Http|Tcp|Udp`), **pinned-peer SPIFFE** (missing/corrupt ⇒ refuse dial), **transport selection** (materializer stamps exactly one of `mesh.hbone`/`mesh.mtls`; runtime precedence HBONE→mesh-mTLS, neither ⇒ end session; a both-tags target — corrupted-only — resolves to HBONE, never relaxing a gate), **dest authenticated-peer** (`peer_spiffe_id.is_none()` ⇒ 403 before any socket opens; enforced inline in the handler, predicate-pinned; the fail-closed OUTCOME is e2e-tested by `functional_mesh_udp_dest_untrusted_peer_fails_closed` — under STRICT inbound the unchained peer is rejected at TLS, handler 403 stays predicate-pinned), **dest open-relay guard** (loopback / slice-declared workload addr+port only, RE-checked on the post-route-override effective destination ⇒ 403), **marker discipline** (`is_udp_hbone_connect`/`is_hbone_connect` disjoint AND exhaustive — a present-but-unparseable/non-UTF-8 marker fails closed to neither, NOT markerless; an unknown/future/malformed marker ⇒ neither ⇒ the dispatcher 405s the unrecognized CONNECT, pinned by `connect_marker_classification_is_exhaustive_and_fail_closed`), **session DoS bounds** (count + queued-bytes + idle), **return-path isolation** (per-session transparent socket bound to orig-dst, send-only, reply only to the captured client). Each gate has a named regression pin (see the `docs/mesh.md` table); posture confirmed by two independent audits + an adversarial red-team over 10 attack classes (no fail-open found). The ONE residual — the inbound guard validating the destination *string* before DNS resolution — is **not UDP-specific** (identical to the byte-stream relay's `connect_backend`) and inert in practice (workload addresses are pod IPs/loopback); out of scope for this stage.
- Cleanup scripts are best-effort even when `ip6tables` is missing.
- Injected SPIFFE ID format is `spiffe://{trust_domain}/ns/{namespace}/sa/{service_account}`.
- JWT secrets in injected manifests use `SecretKeyRef`, never plaintext.
- Opt in with `ferrum.io/inject=true` or `ferrum.io/mesh=enabled`; opt out with `sidecar.istio.io/inject=false` or `ferrum.io/inject=false`.
- Node-agent CNI is opt-in with `FERRUM_NODE_AGENT_CNI_ENABLED=false` by default.
- When enabled, node-agent binds `FERRUM_NODE_AGENT_CNI_SOCKET_PATH` and the `ferrum-cni` binary forwards kubelet ADD/DEL/CHECK over that socket.
- kube-rs watcher remains source of truth; CNI only closes the kubelet-vs-watcher race and does not carry labels or annotations.

## Kubernetes Controller

- `FERRUM_K8S_CONTROLLER_ENABLED` and `FERRUM_K8S_POD_DISCOVERY_ENABLED` default true inside pods detected by `KUBERNETES_SERVICE_HOST`; outside pods they default false.
- Explicit operator `false` wins over pod detection.
- If `FERRUM_K8S_WATCH_NAMESPACES` is unset, watch scope falls back to CP scope: `Single`/`Set` use namespaced watches, `All` uses cluster-wide.
- Istio status writer patches `status.conditions[]` (a `FerrumAccepted` condition plus a `status.ferrum.translation` detail block) for all nine translated Istio kinds when `watch_istio == true`: AuthorizationPolicy, PeerAuthentication, RequestAuthentication, DestinationRule, VirtualService, ServiceEntry, WorkloadEntry, Sidecar, and Telemetry. Successful translation writes `FerrumAccepted=True`; a `K8sTranslateError` writes `FerrumAccepted=False`/`Invalid` with the translator's reason so rejections are visible to `kubectl`.
- Keep `istio_api_resource`/`is_supported_istio_kind` in `src/k8s_controller/istio_status.rs` in lock-step with `ISTIO_CRDS` in `src/k8s_controller/watcher.rs` (group + plural).
- Parsed-but-unenforced fields are surfaced as `status.ferrum.translation.deferred_fields` rather than only logged: DestinationRule `connectionPool.http.{http1MaxPendingRequests,h2UpgradePolicy,maxRetries}` ONLY when set inside a `subsets[].trafficPolicy` (all three applied at top-level/`portLevelSettings` per F5.1 — `http1MaxPendingRequests` as the concurrent-in-flight-H1 cap described above — see the DestinationRule materialization rules above — but a subset's `SubsetTrafficPolicy` carries no `connectionPool.http`, so they are deferred for subsets via `SUBSET_DEFERRED_CONNECTION_POOL_HTTP_FIELDS`, kept in lock-step with the translator's `TrafficPolicyScope::Subset` warning loop) (also now APPLIED, not deferred: per-subset `connectionPool.tcp.connectTimeout` → overrides `backend_connect_timeout_ms` for subset-bound proxies; `portLevelSettings[].tls` → per-port backend TLS resolved onto `port_overrides[port].tls` and projected onto the effective proxy's `resolved_tls`; the full per-subset `outlierDetection` → *thresholds* resolved into the subset passive-health overlay consulted by `passive_health_for_target` AND the `maxEjectionPercent` *cap* resolved per-subset by `LoadBalancerCache::max_ejection_percent_resolved_from`, both with the same per-port > per-subset > upstream precedence so cap and thresholds share one tier); VirtualService `http[].corsPolicy` **only when it uses `prefix`/`regex` origin matchers** (exact-origin / legacy `allowOrigin` policies are translated to a proxy-scoped `cors` plugin via the shared `config_sources::k8s::cors_policy_translatable` predicate, which the translator and status writer both call so they never diverge; `mirror`/`mirrorPercentage`, `redirect`, and `rewrite` are fully translated); and Sidecar `ingress[]` listeners Ferrum can't model (see below — resolvable loopback HTTP listeners are materialized, not deferred). VirtualService `spec.tcp[]` and `spec.tls[]` L4 route blocks are translated to stream proxies via `virtual_service_l4_proxies` (`tls[]` → passthrough TCP keyed by SNI, `tcp[]` → plain TCP keyed by port, reusing `proxy_for_route` + the stream/SNI machinery); their unsupported match predicates (`sourceLabels`/`sourceSubnets`/`destinationSubnets`/`gateways`/`sourceNamespace`) and weighted multi-destination splitting fail closed as `FerrumAccepted=False`/`Invalid`, not as `deferred_fields`. Sidecar `ingress[]` is now MODELED (F6 §6.2): resolvable loopback HTTP listeners (incl. `https`) materialize inbound routes and are reported via `status.ferrum.translation.ingress_modeled`; only listeners Ferrum can't represent (Unix-socket/non-loopback `defaultEndpoint`, non-HTTP-family protocol — including a MISSING or MISTYPED `port.protocol`, which is deferred not guessed-as-HTTP — and omitted `defaultEndpoint`) stay in `deferred_fields`. The status writer's `classify_sidecar_ingress_entries` mirrors `MeshSidecarIngress::resolve` fail-closed semantics on the raw spec (via the shared `sidecar_ingress_protocol_is_http_family` → `sidecar_ingress_app_protocol` mapping) — keep the two in lock-step. The DR `connectionPool.http` deferred set is mirrored by a translator warning in `src/config_sources/k8s/istio.rs`; keep the two lists in sync.
- Status writer failures, such as missing `subresources.status`, warn and no-op; they never abort reconcile.
- `ProxyConfig` is translated but not watched (`ISTIO_CRDS`) and not surfaced by the status writer.
