# Mesh Rules

Full operator docs live in `docs/mesh.md`. Keep this file to implementation invariants. Subsystem
invariants live in `mesh-hbone-waypoint.md`, `mesh-capture-cni.md`, and `mesh-k8s-controller.md`.

## Topologies And Runtime

- `MeshTopology` drives listeners: `Sidecar` uses inbound 15006 mTLS and outbound 15001 capture; `Ambient` uses HBONE 15008 and outbound 15001; `EastWestGateway` uses SNI passthrough on 15443; `EgressGateway` uses mTLS inbound 15090 to external ServiceEntry backends.
- All topologies share the normal proxy and plugin chain.
- Mesh runtime state is `ArcSwap<Option<MeshSlice>>` in `runtime.rs`; slice apply is lock-free hot-swap like `GatewayConfig`.
- `wait_for_first_slice()` blocks startup until the first valid slice arrives.
- Native config consumption uses `MeshConfigSync.MeshSubscribe` gRPC. xDS uses ADS for CDS/EDS/LDS/RDS/SDS/ECDS/RTDS with 25 ms debounce.
- **An RTDS knob that affects request handling must be materialized into the candidate plugin config, never published to a process-global store** (GHSA-83rc-23c9-3g9x). `runtime_overlay_consumers::apply_overlay` runs from `record_applied_slice`, i.e. AFTER `ProxyState::update_config` has published the new `RequestEpoch`, so anything behavioral it published would have two straddle windows: the publication gap (a new plugin reading the old value) and the entire lifetime of an already-admitted request (an old plugin reading the new value). `materialize_fault_runtime_overlay` and `materialize_transformer_runtime_overlay` are the correct pattern — they fold the accepted overlay into each instance's own config in `prepare_normalized_gateway_config_for_mesh`, so gate/percentage and rules are validated, built, and published as ONE generation and each instance resolves ONE immutable decision at construction. `RUNTIME_OVERLAY_MATERIALIZED_PLUGINS` + `reconcile_runtime_overlay_plugin_generations` are load-bearing: an RTDS-only change leaves every static field identical, so without the `updated_at` stamp `ConfigDelta` retains the old instance and the old value stays live under a nominally accepted slice. The transformer gate stores are STILL published post-accept, as provenance only — `response_caching` pins the response-side publication identity and `request_deduplication` folds its content fingerprint, so deleting those `apply_overlay` calls silently stops retiring cached/persisted representations across a policy change. That identity is NOT sufficient alone: it is published after the epoch, so a request whose auth phase spans an apply pins the OLD generation and the NEW identity. Every retained representation must therefore ALSO bind `RequestContext::response_presentation_policy_digest` (the request's own plugin-cache generation, which now covers the materialized gate as well as the static rules) — `response_caching` on its `CacheEntry`, `request_deduplication` via `ResponsePolicyProvenance`. A difference in either half retires it, and an unavailable digest retains nothing. `logging` is the one legitimate process-global consumer (diagnostics, not proxying).
- `FERRUM_MESH_CONFIG_PROTOCOL=file` is the localized source: `config_consumer::file_source` builds the slice DP-side from `FERRUM_MESH_FILE_CONFIG_PATH` via `MeshSlice::from_gateway_config` (same materialization as CP paths — do not fork it). The document is `{version?, mesh}` ONLY (`deny_unknown_fields` rejects gateway resources). Initial load is fail-closed at startup; SIGHUP reload keeps the last good slice on error. Since issue #3776 both the initial load and the SIGHUP reload run on `spawn_blocking` through the shared bounded reader `config::stable_file` (opened-target regular-file check, Unix `O_NONBLOCK`, 64 MiB ceiling streamed at `limit + 1`, byte-identical dual identity/content probe, bounded instability retry) — the same primitive `ferrum.conf` (1 MiB) and the file-mode gateway config (64 MiB) use. Format selection is **extension-only** (`.json` → JSON; `.yaml`/`.yml`/unknown/extensionless → YAML): do NOT re-add the content-sniffing heuristic, which parsed the whole document once just to classify it and again to deserialize it. Format selection does not inspect content, but every YAML document receives the shared bounded libyaml event preflight before `serde_yaml`; an alias-bearing document receives a second bounded composition/traversal pass, with the exact admission ceilings documented in `docs/configuration.md` and `docs/mesh.md`. Rapid SIGHUP coalesces to ONE in-flight generation plus at most one follow-up, and the requested generation advances when the signal is **observed**, so an older completed load can never install over a newer request; watcher shutdown stops accepting candidates without awaiting a started (non-cancellable) blocking job, and the select is `biased` with shutdown first so a simultaneous completion cannot publish. A rejected reload (read/parse/validation/revision-gate/join/apply) retains last-good AND raises the authenticated-`/health` `config_rejected` signal through `file_source::MeshLocalSourceRecovery`, shared with the `stock_xds` policy watcher; that flag clears ONLY after the proxy apply lifecycle accepts the EXACT current recovery candidate (Applied or content-identical no-op) — never on a provisional `install_slice` or a policy channel send. Every recovery transition (cancel, new candidate, policy-identity bind, proxy accept, proxy reject) and its `config_rejected` write share ONE critical section of the transition lock, so an older callback can neither clear health after a newer failure nor cancel a newer pending recovery; an uncomputable content identity and a poisoned transition lock both fail closed. The file protocol requires no CP URLs / CP-DP JWT secret — `EnvConfig::validate()`'s Mesh arm and `MeshRuntimeConfig::from_env_config` gate those per protocol; do not re-add unconditional requirements.
- xDS apply uses make-before-break with a coherent required-version gate: the DP tracks each type's `version_info` independently but only builds a slice once all required types (CDS/EDS/LDS/RDS/ECDS — ECDS required so the first slice is never the unprotected name-only view) have the same `version_info` and `reverse_translate` succeeds. The prior slice keeps serving via `ArcSwap` until the new one is ready; genuine structural errors (e.g. malformed ECDS carrier) NACK + roll back. A route referencing a service not yet present in CDS/EDS/LDS is SKIPPED (debug-logged) and retained, NOT NACKed, because xDS types arrive as independent responses and a NACKed SotW resource is not resent until reconnect (do not reintroduce a hard error there). `MeshSlice.version` is observability-only (`content_eq` ignores it). The CP force-re-sends subscribed required mesh-slice types when any required type changes so CDS/EDS/LDS/RDS never advance independently of stale ECDS security carriers. Keep DP `REQUIRED_MESH_SLICE_TYPE_URLS` and the CP emitter in sync.
- Warming observability splits by sensitivity: the counter `ferrum_xds_warming_partial_applies_total{namespace}` is unauthenticated on `/metrics`, but the per-type `version_info` strings and still-missing required types ride the JWT-gated `GET /mesh/config-drift` `convergence` block (built by the DP via `MeshRuntimeState::set_xds_convergence`). Do NOT move per-type version strings onto `/metrics` — they embed config-change timestamps + content digests and would also explode label cardinality.
- xDS is Ferrum-CP-to-Ferrum-DP, not stock-Envoy/Istio-interoperable: CDS/EDS/LDS/RDS are name-only (service-port discovery); all security/policy slice fields and selector context (authz, PeerAuth, JWT, ServiceEntry, trust bundles, ProxyConfig, VirtualService L4 proxies, workloads, effective labels, outbound policy, telemetry, multi-cluster, sidecar egress scope) ride ECDS as Ferrum mesh-slice carriers. `src/xds/carrier.rs` (`MeshSliceCarrier`) is the single encode/decode source of truth; the CP emits via `translate_mesh_slice_carriers` and the DP recovers in `reverse_translate`, requiring both reserved resource name and matching inner type URL. **ACK-time validation covers every newly policy-bearing carrier field** (#2465/#2469): `validate_ecds_destination_rule_carrier` recognizes a DR carrier by its inner `type_url` alone — so reserved AND legacy/non-reserved names get the same fail-closed JSON + `validate_mesh_export_to` check, while genuinely unrelated ECDS extension configs still route untouched — and `validate_ecds_mesh_slice_carrier` validates both `VirtualServiceCorsPoliciesCarrier.export_to` and the `IstioRootNamespaceCarrier`'s lowercase RFC 1123 namespace value. Do NOT restore an early return for non-reserved DR names: a malformed same-namespace legacy carrier would then be ACKed and normalized and only become inert at materialization (fail-open). Diagnostics are field/index-shaped, capped at `XDS_CARRIER_DIAGNOSTIC_LIMIT`, and never echo the carrier-supplied value. An xDS-built slice must stay functionally equivalent to a native-built one.
- VirtualService L4 `sourceLabels` / `sourceNamespace` on the `mesh` arm are Sidecar source-workload applicability selectors, not authenticated inbound-peer predicates. Resolve them at slice apply from the unambiguous local workload identity/namespace/labels, drop non-applicable arms fail-closed, and leave remaining subnet/gateway/SNI predicates ordered and AND-combined. Named-gateway arms stay independent; ambient/NodeWaypoint retain exact runtime source-workload evidence. The namespace-projected L4 proxies ride `MeshSlice` (and the matching ECDS carrier), and `content_eq` compares them so updates/deletes cannot retain stale matcher state.
- Native and xDS clients use jittered exponential backoff from 1s to 30s, plus/minus 25%, multi-CP failover via `FERRUM_DP_CP_GRPC_URLS`, and JWT metadata.
- **Authoritative config-revision ordering is fail-closed and centralized in `MeshRuntimeState::install_slice`** (issue #2473). Slices carry `revision = (authority, sequence)`: `authority` is the CP-replica-shared ordering DOMAIN (`FERRUM_MESH_CONFIG_AUTHORITY_ID`, default `db`), `sequence` is the durable `config_changes` change-log cursor (explicit `CpScope::Single`/`Set` full-load stamps the saturating sum of scoped namespace cursors; `CpScope::All` stamps the store-wide sum of per-namespace high-water marks; both boundaries are captured BEFORE their resource loads and only then combined with the in-process floor, so a concurrent write can be replayed but never skipped) — NOT a wall clock and NOT process-local (`MeshSlice.version` stays observability-only and is NOT comparable across replicas). CP startup rejects non-empty authority values containing control characters or exceeding 128 bytes without echoing them; empty explicitly disables publication. The gate (`modes::mesh::revision`) admits Bootstrap/Newer/Same and quarantines Older (`stale_revision`) / foreign authority (`incomparable_authority`) / absent-while-one-is-accepted (`missing_revision`) / present-but-ill-formed (`malformed_revision`) BEFORE the `ArcSwap` swap; a quarantine mutates nothing (no receive metric, no `last_install_at`, no watcher wake). A *present* ill-formed authority (blank / over-long / control characters) must NEVER be silently downgraded to absent — `admit` refuses it even on bootstrap (xDS reaches this gate without `MeshConfigUpdate` validation), while a genuinely absent revision still bootstraps for unsequenced authorities. **`Same` MUST install for IDENTICAL SEMANTIC CONTENT ONLY** — a reconnect replays the CP's initial slice at the unchanged revision, so exact-content replay (including from another replica) must install; but a scalar revision is only an ordering key if one `(authority, sequence)` names one content, and the K8s domain's MIN-over-scopes watermark does NOT guarantee that (replica A at scope watermarks `[110,100]` and replica B at `[100,100]` both publish `100` while A's snapshot carries the change at `110`). The gate therefore binds a deterministic content identity (`MeshRevisionContentIdentity`, from the canonical `grpc::mesh_slice_drift::slice_content_digest` — `version`/`revision` cleared, JSON canonicalized) to every accepted AND applied revision, compares it INSIDE the same admission critical section (never caller-side — that would be TOCTOU), and quarantines divergent equal-revision content as `divergent_content` / an uncomputable identity as `unidentified_content`, both stream-terminating. Both slots store the revision and its identity as a PAIR and every transition (admit/adopt/begin/commit/rollback/reset) moves the pair; the apply token carries the identity so a commit binds what was admitted. Remote-cluster discovery's separate gate binds the POST-validation/POST-trust-domain/POST-tagging endpoint set (`canonical_content_digest` over workloads+services), not the discarded slice fields. No digest, content fragment, or payload byte may reach a log line, metric label, or admin surface. Native and xDS quarantines TERMINATE their streams so multi-CP failover leaves the lagging CP. xDS does NOT rewind the ADS accumulator, which already absorbed and ACKed the response before the slice was built; the accumulator is per-CP-URL and reset wholesale by `reset_for_new_control_plane` during the resulting failover. Do not roll it back (that desynchronizes it from ACKed versions) and do not weaken the required-type/version-coherence gates. Admission is PROVISIONAL: the gate keeps TWO watermarks — `accepted` (received slot, the comparison baseline) and `applied` (what the proxy runtime accepted). `record_applied_slice` → `commit_applied` advances `applied` (including content-no-op/equal-revision replays); a runtime rejection in the apply loop → `record_rejected_slice` → `rollback_rejected` returns `accepted` to `applied`, gated on exact `(authority, sequence)` equality AND received-slot `Arc` identity so a LATE rejection of N never rolls back an already-received N+1. The apply loop is NOT the only runtime gate: on native / xDS / stock-xDS the FIRST slice is installed BEFORE it is converted, so `wait_for_initial_mesh_config` owes the identical rollback (issue #4041) — without it a conversion-invalid first slice pins `accepted` at its sequence, an in-place CP correction republished at that SAME sequence is refused as `divergent_content`, a lower-sequence revert is `stale_revision`, and the DP stays NotReady until a strictly higher sequence or `POST /mesh/config-revision/reset`. Every stage that can refuse a received candidate resolves its verdict through the ONE guard `MeshRuntimeState::evaluate_received_slice`, which rolls the watermark back on DROP unless the stage called `pass()` — do not open-code `record_rejected_slice` in a new stage, and do not add a stage that returns early without resolving the guard. The localized `file` source is exempt only because it converts before `install_slice` and refuses startup outright. Rolling back re-opens same-sequence and lower-sequence candidates against the REFUSED one only; once a generation is applied, divergent content at its sequence is still `divergent_content` and anything below is still `stale_revision`. Never advance the authoritative watermark on receipt alone: one runtime-invalid slice at a far-future sequence would otherwise lock out every valid revision beneath it. `is_well_formed` refuses blank, control-character, and over-length authorities; the raw authority stays INSIDE the gate for exact ordering and every escaping copy (diagnostics, reset response, log lines) goes through `diagnostic_value`. The revision rides `MeshConfigUpdate.config_authority`/`config_sequence` (envelope↔slice agreement enforced in `update_validation`, reason `envelope_revision_mismatch`; present-but-ill-formed revisions use dedicated reason `malformed_revision` and are refused before agreement comparison so an empty envelope cannot smuggle a hostile embedded authority; raw non-empty whitespace-only envelope authorities are present/malformed, not proto-absent) and the xDS `ConfigRevisionCarrier` ECDS carrier, so native/xDS materialization stays at parity. `content_eq` deliberately IGNORES `revision` (ordering metadata, not content — CP dedupe must keep suppressing unchanged frames). An intentional rollback is a WRITE, so it arrives as a HIGHER sequence; never accept an old generation to roll back. No-lockout: a foreign authority is adopted after `FERRUM_MESH_CONFIG_REVISION_ADOPT_SECS` (default 300, 0 disables); a sequence rewind INSIDE one authority is NEVER auto-adopted and is recovered by `POST /mesh/config-revision/reset` (JWT + operator) or by bumping the authority id. `GatewayConfig.mesh_revision` is `#[serde(skip)]` CP-in-memory-only — do NOT put it on the ConfigSync `config_json` wire (`deny_unknown_fields` both sides).
- **A Kubernetes-controller CP publishes the SEPARATE `k8s` ordering domain** (issue #3611), authority `k8s` / `k8s:<FERRUM_MESH_CONFIG_K8S_AUTHORITY_ID>`, sequence = a `resourceVersion` convergence watermark (`k8s_controller::revision::K8sConfigRevisionTracker`). The two domains are NEVER comparable and the split is structural, not advisory: `k8s`/`k8s:…` is a reserved authority `EnvConfig::validate` refuses on a change-log CP, the composed `k8s:<qualifier>` is validated whenever the CRD controller is enabled — INDEPENDENTLY of the empty-`FERRUM_MESH_CONFIG_AUTHORITY_ID` disable switch, which is a different variable, so re-enabling publication can never fail on a value that already started once — and a `config_changes` cursor may only reach a revision through `MeshConfigRevision::advance_change_log_sequence`, which no-ops on a Kubernetes-domain revision (both `cas_publish_incremental_partitions` and `mesh_server::apply_mesh_delta_to_stream_config` go through it — do NOT reintroduce a raw `revision.sequence.max(cursor)`). `resolve_mesh_config_authority` still returns `None` when the K8s controller is enabled, because that CP's `mesh` block is authored WHOLLY by the K8s overlay (DB full loads clear `mesh` and re-merge from the overlay slot, #2982) — so the revision lives on `AcceptedK8sOverlay.mesh_revision` and BOTH publishers stamp it through the one `apply_k8s_mesh_revision` site; putting it on the DB snapshot would let the next poll wipe it. Per-scope evidence = max(boundary read taken BEFORE the generation's list and adopted only at `InitDone`, listed-object RVs buffered until that same `InitDone`, applied watch-event RVs — a `Delete` carries the DELETION revision, which is why deletion advances instead of rewinding). kube-rs surfaces neither list metadata nor bookmarks, but its list defaults to `ListSemantic::MostRecent` (quorum read at the current cluster revision), which is what makes a pre-list boundary a sound lower bound — a post-list read would NOT be. The published sequence is the MIN over registered scopes, read BEFORE `snapshot_all()` under the SAME `ResourceStoreSet` lock (stores only move forward in between); ANY registered scope without evidence (listing, relisting, non-numeric `resourceVersion`) makes it unavailable, and unavailable RETAINS the last published sequence rather than publishing an unsequenced or optimistic frame. Because that retained scalar can coincide with a newly evolved reflector mesh (incomplete evidence OR a quiet scope pinning the aggregate MIN), `publish_k8s_reconcile` binds mesh to the revision inside `CpPublicationGate`: equal revision + divergent mesh retains the previously accepted mesh in the overlay slot / `config_arc` / broadcast together; equal+identical is idempotent; an advanced sequence releases the newest mesh (including withdrawals); unversioned bootstrap is unchanged; non-mesh Gateway/API fields may still publish. A retaining publication MUST also call `K8sConfigRevisionTracker::request_evidence_refresh`, which nudges every watch scope to start a fresh generation (per-scope 5 s floor in `watcher.rs`); without it the aggregate MIN stays pinned by the quietest scope and mesh propagation stalls for a whole `FERRUM_K8S_WATCH_IDLE_RELIST_SECS` window — the ~350 s NodeWaypoint eBPF live-datapath outage. The refresh ACQUIRES proof and never fabricates a watermark: a scope that cannot relist still yields no evidence. Do NOT weaken `MeshRevisionGate` — it remains the cross-replica equal-content defense. Max-over-live-objects is fatally wrong (deleting the highest-versioned object rewinds a restarted replica below its running peer, and a rewind inside one authority is never auto-adopted); so are wall clocks and a reconcile-time current-revision read.
- **MeshSubscribe response binding is centralized and fail-closed** (`config_consumer::update_validation`, issue #2457). BOTH consumers — the local native client and multicluster remote discovery — validate a non-heartbeat `MeshConfigUpdate` against the exact `MeshSubscribeRequest` they sent (`MeshUpdateExpectation::from_subscribe_request`) BEFORE `install_slice` / endpoint import: present + major/minor-compatible `ferrum_version`, `update.version == slice.version`, `slice.node_id`/`slice.namespace` equal to the request, and — when the request PINNED `workload_spiffe_id`/`waypoint_name` — an exact echo, where an ABSENT echo is a mismatch (treating it as a pass would be a trivial bypass; an unpinned request gates nothing, since there is no unambiguous expectation). Do not fork these rules into a second implementation and do not add a "skip when the field is missing" branch. Rejection is metric-recorded inside the validator (`ferrum_mesh_config_update_rejections_total{consumer,reason}`, both labels `&'static str` from closed enums — never a CP-supplied value) with a sanitized, length-bounded `warn!`. `MeshUpdateRejectReason::terminates_stream` splits BINDING failures (drop the stream → multi-CP failover) from CONTENT failures (drop the frame, keep the stream); remote discovery fails the whole poll either way and keeps last-good endpoints. Remote discovery additionally retains a per-cluster `MeshRevisionGate` across one-shot reconnect polls, validates endpoint content before advancing it, and applies the configured foreign-authority adoption policy. Heartbeats stay explicit: they route to `validate_update_ferrum_version` only, and a heartbeat-marked frame reaching the install path is itself a rejection. Test CP stubs must echo the request scope (`functional_mesh_mode_test`'s stub does) or the DP will correctly refuse their slices.

## Datapath Layering: Two Transports (per topology) vs. Materialization

Keep two things distinct: the **transport** (how a peer is reached on the wire) and **materialization** (turning the slice into routable `Proxy`/`UpstreamTarget` objects `find_proxy` can match). "Outbound 404 / no routes" does NOT mean "no transport" — conflating them leads to re-implementing transport that exists, OR (worse) using the wrong transport for the topology.

**Mesh transports are PER-TOPOLOGY — never assume one (this is the trap):**
- **Ambient / NodeWaypoint / ServiceWaypoint** speak **HBONE** (HTTP/2 CONNECT over mTLS) on **:15008**.
- **Sidecar** speaks plain **SVID-mTLS HTTP** on **:15006** — it has **NO 15008 HBONE listener**. HBONE is NOT Sidecar's transport: a Sidecar peer can't accept an HBONE dial (it would `hbone_required`-502). (`listener_plan()` in `modes/mesh/mod.rs` is the source of truth: Sidecar = capture :15001 + mTLS :15006; Ambient = capture :15001 + HBONE :15008.)
- **Client-visible failure wording follows the transport, not the shared error type** (issue #3927). `MeshMtlsConnectionPool` and `HboneOutboundPool` both surface `HbonePoolError`; `MeshTransportLabel` (in `proxy/hbone_pool.rs`) picks the public noun. Sidecar dispatch goes through `mesh_mtls_pool_error_response` / `mesh_mtls_hyper_error_response` / `sidecar_mtls_*_body_too_large_response` (`Sidecar mTLS backend unavailable`, log noun `Sidecar mTLS`); Ambient/waypoint keeps the `hbone_*` wrappers. Never call an `hbone_*` response builder from `proxy_to_backend_mesh_mtls[_after_ready]`. Pool-setup bodies obtain their reason through `MeshTransportLabel::unavailable_body_for_error(&HbonePoolError)`, which selects the fixed `HbonePoolError::public_reason()` internally and appends `HbonePoolError::public_status()` (the peer's own CONNECT admission status; `ConnectRejected` ONLY — the NodeWaypoint eBPF live gate matches `… tunnel rejected by peer with status 403` to prove a destination POLICY denial, so do not collapse it into the bare reason); post-establishment and DNS bodies are separately fixed. Never interpolate `Display` into client bodies or the pool-error operator `error!` record — `Display` can carry peer address, SPIFFE ID, cert subject, trust-root, and raw rustls/SPIFFE verifier text as an error value. Operator logs on this path emit closed-cardinality `error_kind`, `error_phase` (`public_reason()`), and `peer_status` only for `ConnectRejected`. Classification, retry/pre-wire boundary, circuit-breaker accounting, and `error_class` stay transport-identical.
- **`FERRUM_MESH_CA_BACKEND=internal` is process-local with no export path** (issue #3927). Two processes bootstrapping it hold unrelated roots and cannot mTLS. Do not add persist/export/import of the dev root. Local multi-process meshes use file SVIDs (`FERRUM_GATEWAY_SVID_CERT_PATH` / `KEY_PATH` / `TRUST_BUNDLE_PATH`, all three or none — enforced in `EnvConfig::validate` for mesh mode AND in `load_gateway_svid_bundle`), documented in `docs/mesh.md` → "File-Based SVIDs: Two-Process Local Mesh".

- **Ingress (inbound).** Sidecar inbound: `materialize_sidecar_inbound_proxies` → loopback routes (:15006 → `127.0.0.1:appPort`), **one sibling per HTTP-family service port**. **Sidecar `ingress[]` custom listeners (F6 §6.2)**: when the applicable Sidecar declares `ingress[]` (resolved CP-side into `MeshSlice.local_ingress_listeners`, gated by `FERRUM_MESH_SIDECAR_ENFORCED`, NOT dry-run; rides ECDS carrier `LocalIngressListenersCarrier`), they **REPLACE** the service-port default inbound materialization for that workload (Istio semantics) — `materialize_sidecar_ingress_listener_proxies` emits one `__mesh-ingress-{ns}-{svc}-{port}` loopback HTTP route per HTTP-family resolved listener and one `local_inbound_tcp_routes` relay per stream-family resolved listener (issue #3260; declared LISTENER port → the entry's `defaultEndpoint` loopback target; HTTP hosts = the local service's FQDN variants). **Fail closed on the DECLARED signal, not on what resolved**: `MeshSlice.sidecar_ingress_declared` (a separate bool marker riding its OWN carrier `SidecarIngressDeclaredCarrier` — set true whenever the applicable Sidecar DECLARES an `ingress` block, independent of how many entries resolved) gates the materializer; when declared, the service-port defaults are SKIPPED even if `local_ingress_listeners` is empty (all entries unsupported / no local-service anchor), so an all-unsupported `ingress[]` yields NO inbound routes rather than fail-open-exposing the defaults the operator replaced. **Omitted vs explicit-empty (Istio-faithful):** an OMITTED `ingress` keeps the defaults; a DECLARED `ingress` — *including an explicit empty `ingress: []`* — replaces them. The K8s translator sets `MeshSidecar.ingress_declared` on `spec.ingress` PRESENCE (mirroring `egress_inherits_defaults`'s omitted-vs-explicit-empty split); `resolve_applicable_sidecar_ingress` folds it as `ingress_declared || !ingress.is_empty()` (non-empty always declares; the bool adds the explicit-empty case, default-false on the native source). **`content_eq` MUST compare `sidecar_ingress_declared`**: the marker flips false→true while `local_ingress_listeners` stays empty (no-ingress → all-unsupported-ingress), so omitting it from slice equality would let MeshSubscribe/update dedupe keep serving the stale default routes. Ingress resolution + the local-service anchor are **decoupled from egress-scope inheritance** (an ingress-only Sidecar usually omits `spec.egress`, so `applicable_sidecar` for egress can be `None`; the slice resolves `local_inbound_services` independently for the ingress case via `select_applicable_sidecar` + `resolve_local_workloads`). Ingress ids classify as `Inbound` (`is_mesh_inbound_route_id`/`mesh_route_direction`) and fold into `mesh_inbound_ports`, reusing `select_mesh_inbound_port_route` — but the orig-dst AND authority both match the **listener port** (`MeshInboundSibling.orig_dst_match_port == authority_port == listener port`; default service-port siblings keep `orig_dst_match_port = backend_port`). **Authz on the LISTENER port (security)**: `MeshInboundPortGroup.is_ingress` makes `select_mesh_inbound_port_route` return the selected sibling's listener port, stamped onto `RequestContext.mesh_inbound_listener_authz_port`; `mesh_authz`'s `mesh_inbound_app_port` authorizes an ingress route on that LISTENER port (e.g. 8443), NOT the `defaultEndpoint` backend port — so an AuthorizationPolicy `port`/`destination.port` DENY scoped to the listener port is enforced (authorizing on the backend port would fail a DENY OPEN). Service-port default inbound routes keep authorizing on `backend_port`; an ingress id with no stamped listener port fails closed (never the backend port). Loopback (`127.0.0.1`/`::1`) and instance-IP (`0.0.0.0`/`::` → loopback) `host:port` endpoints resolve for modeled HTTP-family and stream-family (`tcp`/`tls`/db) protocols; admissible `unix://` endpoints resolve for supported HTTP-family protocols and remain subject to the data plane's explicit containment/ownership/mode gates; arbitrary IPs, `Udp`/`Unknown` protocols, inadmissible Unix paths, and omitted `defaultEndpoint` are dropped fail-closed and stay in `deferred_fields`. **Protocol classification:** a custom inbound listener routes recognized HTTP-family tokens onto HTTP routes and recognized stream-family tokens onto raw-TCP inbound relays (issue #3260). The K8s ingress translator uses `sidecar_ingress_app_protocol` (NOT the generic `app_protocol`): `https` → `Http2` (HTTP route); recognized stream tokens → their `AppProtocol` (TCP relay); a MISSING protocol → `Tcp` (Istio default, stream-modeled); an UNRECOGNIZED string (e.g. a `HTPS` typo) → `Unknown` (deferred) — never guessed as HTTP or as a live TCP listener. The native source rejects a mistyped `AppProtocol` at deserialization; an omitted native protocol stays `Unknown` and defers. The service-port default path keeps its own `Unknown → HTTP` convention via `is_http_family_mesh_protocol` (untouched). Status writer reports `ingress_modeled` count + per-reason deferrals via the SHARED modeled/HTTP/stream predicates (routing through `sidecar_ingress_app_protocol`), so translation/resolution and the report never diverge; the resource is still accepted. **Carrier re-validation:** `local_ingress_listeners` can arrive already resolved over the xDS/native carrier, so `admit_sidecar_ingress_listeners` (called from `materialize_sidecar_ingress_listener_proxies`) re-checks each carried endpoint via `ResolvedIngressListener::endpoint_is_valid` (modeled protocol plus either a loopback host/nonzero listener+backend port or one mutually exclusive, syntactically valid and contained Unix backend — the same allowlists `resolve` and the data-plane Unix gate enforce) plus owner/duplicate/dedicated-bind ownership; the surviving set is written onto `mesh.local_ingress_listeners` and `prepare_*` preserves that admitted set rather than rebuilding from the raw slice (so conflict-rejected entries cannot reappear for router grouping / CONNECT). A malformed/hostile carrier (off-box host, `:0` port, `Unknown`/`Udp` protocol) is dropped fail-closed, never dialed. Unix backends are HTTP-family only and their carried protocol must agree with the derived h2c marker; stream-family ingress remains loopback TCP and never widens onto a Unix or UDP lane. **The carried `protocol` has NO compatibility default** (issue #3260): an OMITTED carrier `protocol` decodes to `Unknown` and is inert on BOTH lanes, exactly like an explicit `udp` — do NOT re-add a `default = Http` fn, that turns one omitted wire field into a live HTTP listener. **Authenticated CONNECT lane (issue #3260 — the identity-protected path):** a peer Sidecar's raw-TCP egress reaches the destination as a FRESH mesh-mTLS H2 CONNECT to `:15006` whose `:authority` is `pod-ip:<declared listener port>`, which NEVER touches the REDIRECT-captured `local_inbound_tcp_routes` table. `build_inbound_hbone_relay_proxy` therefore consults `MeshConfig::resolve_sidecar_ingress_connect_relay` BEFORE the ordinary open-relay guard and remaps the authority onto the listener's validated loopback `defaultEndpoint` (`pod-ip:16379` -> `127.0.0.1:6379`) through the reserved id `__mesh-ingress-connect-relay` (`MESH_INGRESS_HBONE_RELAY_PROXY_ID`), stamping the DECLARED listener port onto `RequestContext.mesh_inbound_listener_authz_port` so `mesh_authz` authorizes on it (the id carries `MESH_INGRESS_PROXY_ID_PREFIX`, so an unstamped ingress id fails closed instead of authorizing on the backend). PeerAuthentication resolves on the `defaultEndpoint` app port on BOTH shapes (direct capture translates the listener port via `MeshInboundTlsPolicy.app_port_by_orig_dst_port`; the remap arrives with `backend_port` already equal to it). The remap is NARROW and fail-closed: byte-stream CONNECT only (never `connect-udp` — do not widen UDP), the authority host must be in the unambiguously resolved local-service workload set (`MeshConfig.local_workload_addresses`) AND equal the accepted connection's concrete local IP (so a sibling replica sharing the service identity is refused), and the declared port must resolve to EXACTLY ONE valid, owner-stamped, STREAM-family listener; ambiguity / missing owner / off-box / `:0` / `Unknown`/`Udp` / HTTP-family / unavailable accepted local IP all Deny. `MeshConfig.sidecar_ingress_declared` is back-projected independently of the surviving listener list: once an ingress block is declared, unlisted ports and explicit-empty/all-invalid/carrier-rejected sets Deny instead of falling through to the ordinary transparent relay; only an omitted ingress block returns `NotDeclared`. The marker back-projection is **`MeshTopology::Sidecar` ONLY** (mirroring `materialize_sidecar_inbound_proxies`'s own topology early return): `FERRUM_MESH_SIDECAR_ENFORCED` is topology-independent, so an Ambient/Waypoint proxy can carry a slice whose applicable Sidecar declares `ingress[]` — and those topologies materialize NO inbound routes, so an ungated marker would `Deny` every transparent-relay CONNECT (an inbound outage, not a fail-closed refinement). `handle_hbone_request` re-checks the EFFECTIVE destination against the same declared mapping (`sidecar_ingress_connect_relay_endpoint_matches`) after the plugin chain, so a `mesh_route_dispatch` override / upstream selection / mid-flight withdrawal cannot widen it. Omitted `defaultEndpoint` deserializes to empty (`#[serde(default)]`, matching the K8s path) and defers at `resolve()`. **`bind` (issue #3266):** omitted/empty/unspecified (`0.0.0.0`/`::`) keeps the shared `:15006` capture contract; a supported dedicated loopback bind (`127.0.0.1`/`::1`) is conflict-checked against Gateway/stream/mesh listener ownership and materialized as a real OS listener on `bind:port` (`__mesh-ingress-bind:`-prefixed proxies + `MeshConfig.sidecar_ingress_bind_overrides` consulted by GatewayListenerManager/StreamListenerManager) while capture-path routes remain for mesh peers; dedicated-bind HTTP routes are exact-listener only and never arm single-listener Service remap (a lone bind must not steal `:15006` matches from the port-agnostic capture sibling); Unix/hostname/`ip:port`/non-loopback binds and dedicated-bind+unix-endpoint or port-conflict cases fail closed for the WHOLE entry with field-specific diagnostics (never inert metadata): conflict-rejected listeners are removed from the prepared `mesh.local_ingress_listeners` set as well as bind-proxy/capture materialization, so there is no silent shared-capture or authenticated-CONNECT fallback; `sidecar_ingress_declared` and `declared_ingress_http_ports` remain independent of that admission. `captureMode: NONE` not honored. `validate_unique_listen_paths` exempts ingress siblings as direction code `2` (outbound=0, service-port inbound=1, ingress=2). Multi-port disambiguation is post-match (`select_mesh_inbound_port_route`; groups from `mesh_inbound_service_groups` over the LOCAL-INBOUND view `MeshConfig.local_inbound_services` — a `serde(skip)` runtime back-projection set in `prepare_normalized_gateway_config_for_mesh`, because the egress-narrowed `services` can lack the local service), by priority: inbound orig-dst (REDIRECT-captured plain inbound; port = CONTAINER port, matched against `proxy.backend_port`) → request authority port (peer-sidecar direct dials; port = SERVICE port, the channel the multi-port-aware egress rewrites) → single-DECLARED-port passthrough → **fail-closed 502** (`PortSignalUnavailable`/`PortNotMaterialized`; a present-but-unmatched orig-dst never falls through to the authority). **The single-port passthrough is for NON-ingress SERVICE-default groups only:** a single-listener INGRESS group (`is_ingress`) requires a present port signal to MATCH the declared listener port — a request naming an undeclared port fails closed (`PortNotMaterialized`) instead of being absorbed onto the sole listener; a no-signal request still falls through to it. (A single-port service-default group keeps the back-compat any-port passthrough.) The inbound materializer's operator-yield scan excludes only the service's OWN sibling ids — another local service's route on an overlapping bare-name host still wins first-materialized. `orig_dst` is now read on BOTH directions' capture listeners (one getsockopt per accept), but the accepted socket's own local address (`RequestConnectionMetadata.accepted_local_addr`, the CONNECT remap's replica proof) is resolved ONLY on the INBOUND mesh listener and only for a wildcard bind — do not widen that gate to `mesh_direction.is_some()`, which charges a `getsockname` to every captured EGRESS accept whose `orig_dst` already answers `destination.ip`; the outbound direction keeps its own LAZY `getsockname` fallback inside `connection_destination_ip`. Ambient/Waypoint inbound: **no materialization** — an authenticated HBONE CONNECT that matches no route is relayed transparently by `handle_hbone_request` (`src/proxy/hbone_proxy.rs`), which dials the CONNECT `:authority` (the original destination). The request path synthesizes the relay proxy in the route-miss arm (`build_inbound_hbone_relay_proxy`, only when `mesh_direction == Inbound` and `is_hbone_connect`); `connect_backend` dials that proxy's `backend_host:port` = the authority. **Open-relay guard** (`inbound_hbone_relay_destination_decision` on the current `RequestEpoch` mesh snapshot): the authority must be a destination this terminator owns (ownership-scoped termination inventory), not merely anything the slice declares. Loopback / DNS `localhost` is Sidecar-only (own-pod namespace); Ambient / waypoints / gateways refuse it even if inventory-listed. Ordinary TCP and UDP then screen concrete DNS answers immediately before dial — mixed answers keep only safe candidates, all-loopback fails closed. Sidecar `ingress[]` remaps and separately authorized EgressGateway external UDP remain distinct (they skip that screen). An authenticated peer can never relay to an arbitrary host. `handle_hbone_request` additionally rejects a peerless CONNECT (403) before dialing. - **Inbound vs. egress slice views — keep them separate.** `MeshSlice.services` is the egress/outbound-narrowed view: it is gated by Sidecar egress scope and feeds `build_known_destinations` / `mesh_outbound_registry`. Egress scope must NOT gate inbound serving, so sidecar inbound materialization reads `MeshSlice.local_inbound_services` instead — the local workload's own service(s) captured **un-narrowed** in `from_gateway_config`. Never fold the local service back into `services` (that widens the outbound registry/egress scope — a security regression). Identify the local workload with `slice::workload_is_local` (SPIFFE id + non-vacuous label/cluster match), never the service-account SPIFFE alone (it is not pod-unique). On xDS, `local_inbound_services` rides its own ECDS carrier (`MeshSliceCarrier::LocalInboundServices`), and the DP's workload SPIFFE reaches the CP via `Node.metadata` (`carrier::{encode,decode}_node_metadata`) — a hostname `node_id` alone cannot identify the workload, so without it the CP narrows the local service away before the carrier is built.

## Scope And Policy Semantics

- Scope-aware resources must use the shared `policy_scope_applies_to_workload` / `scope_applies_to_workload` helpers. Do not fork predicates.
- Single-winner precedence (`WorkloadSelector` > `Namespace` > `MeshWide`) applies only where one effective setting is resolved, such as `PeerAuthentication` and `MeshProxyConfig`.
- `MeshPolicy` and `MeshRequestAuthentication` are additive after filtering. `MeshTelemetryResource` merges by section.
- Authorization evaluation is DENY first, then ALLOW. Any ALLOW rule with no match causes implicit deny.
- `RequestMatch` negative fields (`not_methods`, `not_paths`, `not_hosts`, `not_ports`, `not_port_patterns`) are conjunctive with positive fields in one rule. Do not split them into separate deny policies.
- **Outbound traffic policy has THREE precedence tiers and ONE resolver** (issue #3262): `MeshSlice::effective_outbound_traffic_policy` = workload-scoped `sidecar_outbound_traffic_policy` → mesh-wide `outbound_traffic_policy` → `FERRUM_MESH_OUTBOUND_TRAFFIC_POLICY`. Both consumers call it — `inject_mesh_global_plugins` (HTTP-family `mesh_outbound_registry`) and `refresh_mesh_outbound_enforcement` (stream-family `MeshOutboundEnforcement` slot) — so the two transport families can never disagree about whether the gate is **armed**; do not re-derive the precedence at a call site. That shared input is the armed/disarmed DECISION ONLY, **not** the admitted registry CONTENTS: on the multicluster path HTTP-family injection runs against the MERGED materialization slice (`merged_slice`, poller-discovered remote workloads/services unioned into `workloads`/`services`) while `refresh_mesh_outbound_enforcement` runs against the UN-MERGED base slice, so a remote-cluster destination can be admitted on HTTP and refused on a stream connect (the fail-closed direction). Do not restate this as "the two lanes are identical". The Sidecar tier is resolved CP-side by `resolve_applicable_sidecar_outbound_policy` (`select_applicable_sidecar` tier precedence, NO egress `inherits_defaults` walk — Istio picks one Sidecar per workload and an omitted block simply inherits the mesh-wide value) and is gated by `sidecar_enforced && !sidecar_dry_run`, the INGRESS gate, not the looser egress one: arming/disarming the registry gate is a live behavior change and dry-run must not do it. **One `select_applicable_sidecar` scan is shared** with `resolve_selected_sidecar_ingress` (same gate, same tier precedence, same `effective_labels`); egress keeps its own scan because `resolve_applicable_sidecar_egress` walks `inherits_defaults` under the looser gate. **`labels_ambiguous` must not relax the gate** (security): `effective_labels` is then only the INTERSECTION of several same-SPIFFE workloads' divergent label sets, so a real `workloadSelector` `REGISTRY_ONLY` Sidecar can miss the intersection and selection would fall through to a namespace-default `ALLOW_ANY`. The resolver therefore takes the `policy_candidate_labels` candidate sets (empty unless ambiguous), resolves each on its own, and folds by `outbound_policy_strictness` keeping the strictest — rank `Some(RegistryOnly) > None (inherit, which may itself be RegistryOnly) > Some(AllowAny)`. The fold includes the intersection answer, so it can only ever TIGHTEN; `max` is order-independent, so precedence stays deterministic; it is cold-path and bounded (`candidates × sidecars`, once per slice build). Do not "simplify" it back to the intersection alone. `select_applicable_sidecar` also ranks a ROOT-namespace `workloadSelector` Sidecar ABOVE a selector-less default in the workload's own namespace — a deliberate divergence from Istio (which resolves the workload's namespace entirely before consulting the root namespace) so a tenant cannot displace a targeted mesh-operator rule with a permissive namespace catch-all; since #3262 it also decides egress enforcement, so re-deciding it is a security change, not a cleanup. `content_eq` MUST compare `sidecar_outbound_traffic_policy` — an edit to only `Sidecar.outboundTrafficPolicy.mode` leaves every other field identical, so omitting it lets dedupe keep a stale gate live. Its own ECDS carrier (`SidecarOutboundTrafficPolicyCarrier`) is deliberately separate from `OutboundTrafficPolicyCarrier`: collapsing the tiers would make a Sidecar `ALLOW_ANY` indistinguishable from a mesh-wide one and break the delete-falls-back-to-mesh-wide path. K8s translation preserves the Istio Sidecar API default WITHOUT rejecting the resource (`classify_sidecar_outbound_traffic_policy`, shared with `istio_status::sidecar_status` so enforced and reported never diverge): an omitted/null `mode` in a present object resolves to `AllowAny` with no deferral; omitting the entire block still means inherit. An unrecognized/non-string `mode`, a non-object block (an explicit top-level `outboundTrafficPolicy: null` included — the operator asked for a policy, so the ambiguity fails closed rather than inheriting), or a present NON-NULL `egressProxy` resolves to `RegistryOnly` + a `deferred_fields` reason. An explicit `egressProxy: null` IS normalized to absent (proto-JSON "unset"), so it does not force `REGISTRY_ONLY`; the declared mode is honored, or the `ALLOW_ANY` API default applies when mode is omitted/null. The degradation is reported per-resource in `deferred_fields` (always current) plus a per-occurrence `debug!` and exactly ONE process-lifetime `warn!` — translation re-runs on every reconcile and full sync, so a per-resource `warn!` re-fires forever for a permanently unrepresentable Sidecar; do not reintroduce one, and do not add per-resource dedupe state. `status.ferrum.translation.outbound_traffic_policy_enforced` is resource-local and means ONLY "translatable policy present AND the rollout gate is on" — NOT that this Sidecar was selected for any workload (a `workloadSelector` matching nothing still reports `true`); a REJECTED Sidecar reports it explicitly `false`. Do NOT "fix" this by returning `Err` — a rejected Sidecar is DROPPED by `translate_k8s_objects_collecting_skips`, which also drops its `egress` narrowing and WIDENS both the slice service view and the derived registry. `ALLOW_ANY` relaxes ONLY the registry gate; egress scope, `mesh_authz`, PeerAuthentication/mTLS and peer-SVID pinning, the HBONE/mesh-mTLS open-relay guard, DNS/raw-IP strict indexes, and topology transport gates are independent and still apply.
- Istio empty-rule translation must preserve action semantics: ALLOW with no `rules` is allow-nothing via a never-matching rule; DENY and AUDIT with no `rules` are no-ops.
- NodeWaypoint per-pod policy scoping (`per_pod_policy_scoping`) is resolved per request from `node_waypoint_policy_scope`. The HTTP/HBONE accept path populates it from the resolver (`proxy/mod.rs`); the TCP/UDP stream accept loops always pass `None`, so only `MeshWide` policies are evaluated on streams. A config-apply that has stream proxies + scoped policies in NodeWaypoint topology must keep emitting the one-shot warning. Do not silently start enforcing scoped stream policies without wiring the resolver end-to-end and updating `docs/mesh.md`.
- Mesh authz `source.ip`/`ipBlocks` uses `direct_client_ip` (immediate peer) and `remote.ip`/`remoteIpBlocks` uses `client_ip` (trusted XFF/PROXY-resolved) on both the HTTP and stream paths. IP-block matchers fail closed when the typed IP evidence is absent.
- **`when:` conditions cover the complete documented Istio key set and distinguish ABSENT from UNSOURCEABLE** (issue #3236). `classify_mesh_condition_key` / `MeshConditionKeyKind` (`src/modes/mesh/config.rs`) is the one typed classification; `validate_mesh_condition` is the one validator behind all three surfaces (K8s translator `condition_match`, `validate_mesh_config`, `mesh_authz`'s `validate_policy_ip_inputs`) and emits field-specific diagnostics. Dynamic header/claim keys MUST match Istio `validateMapKey`: first `[` + final `]` around a non-empty interior only, with NO `HeaderName` parse or interior-bracket/whitespace restriction. Known pseudo-headers (`:authority`, `:method`, `:path`, `:scheme`) source typed `RequestContext` facts; other unmaterializable interiors remain absent. An attribute the path CAN source but that this request lacks follows ordinary Istio `values` / `notValues` rules. An attribute the path can NEVER source — an HTTP-only key on L4 (`MeshAuthzRequest.protocol == MeshAuthzProtocol::L4`), a source/remote/destination IP or destination port with no transport evidence, or any `experimental.envoy.filters.*` key — is resolved by `condition_kind_is_sourceable` and is fail-closed BOTH ways: DENY ignores the field and still matches, ALLOW/AUDIT can never match. **Value grammar is PER KEY, not one generic matcher** — `condition_scalar_value_matches` classifies once per `when[]` entry and dispatches: IP-valued keys are CIDR containment; `source.serviceAccount` is EXACT over `<namespace>/<service-account>`, with a bare `<service-account>` resolved against the OWNING `MeshPolicy.namespace` (threaded from `evaluate_mesh_authorization_policies` → `rule_matches` → `matches_conditions`, compared in place so no per-candidate `String` is built) and every `*` rejected at admission because Istio compiles it to an exact matcher; `source.namespace` uses the general `wildcard_match` because Istio's `srcNamespaceGenerator` rewrites EVERY `*` to `.*` (mid-string and repeated stars included); `source.trustDomain` keeps the presence/prefix/suffix matcher ONLY because `validate_mesh_condition` enforces Istio's `CheckTrustDomainValues` grammar (exact, `*`, one leading or one trailing `*`, no `/`) first. Everything else is `matcher.StringMatcherWithPrefix`, where a mid-string `*` IS a literal exact match. `source.serviceAccount` additionally carries Istio's stricter 16-entry / 320-byte caps on BOTH `values` and `notValues`; the common 64-condition / 256-entry / 512-byte caps still govern every other key. Do NOT re-express unsourceable as a missing attribute; a `notValues`-only ALLOW would then grant every raw connection. A documented-but-unsourceable key must stay ADMITTED at translation — rejecting the resource drops the whole AuthorizationPolicy, which is fail-OPEN for a DENY. `MeshAuthzRequest::default()` is deliberately `L4`; both production callers set `protocol` explicitly. HTTP `destination.ip` comes from `orig_dst` before `RequestContext::destination_ip`. Stream authz reads `StreamConnectionContext::connection_destination_*`, which prefers capture/trusted-PROXY evidence and may fall back to the accepted socket local address; L4 `stream_match.destinationSubnets` reads ONLY `StreamConnectionContext::destination_*`, so an ordinary listener bind address never becomes original-destination routing evidence. None of these facts comes from a header; the HTTP wildcard-bind `getsockname()`/`Connection::local_ip()` fallback is gated on `OperatingMode::Mesh` so non-mesh accept loops are unchanged.

## PeerAuthentication And TLS Reload

- By default, inbound mesh mTLS mode resolves once from the initial slice.
- When all three `FERRUM_GATEWAY_SVID_*` paths are set, the inbound mTLS/HBONE listener uses a SPIFFE client-cert verifier that validates the peer SAN's trust domain against the gateway SVID local bundle plus slice federated bundles; without SVID material it falls back to chain-only verification over `FERRUM_FRONTEND_TLS_CLIENT_CA_BUNDLE_PATH`. STRICT requires a peer cert; PERMISSIVE trust-domain-validates an offered cert but still admits cert-less peers. The HBONE baggage trust-gate rests on this verified identity.
- Gateway SVID material also backs the inbound listener's **server identity** when no explicit `FERRUM_FRONTEND_TLS_CERT_PATH`/`KEY_PATH` is set (`load_mesh_frontend_server_identity` resolves the SVID leaf+key live from the slot as the server cert via `svid_rotating_mesh_server_identity`): a SVID-only mesh serves mTLS inbound instead of falling open to plaintext under PERMISSIVE. Explicit frontend TLS still takes precedence.
- The gateway SVID slot is fed by **either** configured material (`FERRUM_GATEWAY_SVID_*`, watched + rotated by `identity::svid_source_watch`) **or** a **CA backend** (`FERRUM_MESH_CA_BACKEND=spire|internal`): file/`file://` sources poll every second, provider sources use their configured secret-refresh cadence, and inline PEM remains static until configuration reload. Mesh startup runs `start_mesh_ca_backend_svid_source` (`src/modes/mesh`), which for `spire` fetches the gateway's own SVID from the SPIRE Agent Workload API (`FERRUM_MESH_SPIRE_AGENT_SOCKET`) by reusing the identity `fetch_loop` (`SvidFetchHandle::from_slot` + `with_installer`), and for `internal` self-issues from the dev-only `bootstrap_dev_root` `InternalCa`; either way it live-rotates the SVID into the **same** `gateway_svid_bundle` slot (and publishes it to a live inbound peer-verifier slot), so the inbound `SvidServerCertResolver`, the SPIFFE peer verifier, and the backend pools all pick rotations up with no restart. Startup blocks on the first SVID (`MESH_CA_INITIAL_SVID_TIMEOUT`, 30s; fail-closed) so the inbound listener never binds identity-less, a CA backend REQUIRES `FERRUM_MESH_WORKLOAD_SPIFFE_ID` (the fetched identity is pinned to it), and explicit `FERRUM_GATEWAY_SVID_*` configured material takes precedence when both are configured. Do NOT add a second source-of-truth slot — feed `gateway_svid_bundle`.
- Runtime inbound mTLS fail-closed (`enforce_mesh_inbound_fail_closed` + `decide_mesh_inbound_fail_closed`, issue #1523), at the startup TLS-setup path **and on PeerAuthentication live reload** (`plan_mesh_inbound_tls_reload`). Two cases, deliberately different severity: (1) a listener that would serve **plaintext** (resolved `ServerConfig` `None` — PeerAuthentication DISABLE or no usable server identity) is **refused under `FERRUM_MESH_PRODUCTION_MODE=true`**; **dev** allows it with a loud warning — an explicit DISABLE, or a no-identity posture already acknowledged by the config-time `FERRUM_MESH_ALLOW_NO_CA` gate, is intentional, so the runtime gate does not re-consult the opt-out. (2) a **configured-but-unloadable SVID verifier** (all three `FERRUM_GATEWAY_SVID_*` named but `build_mesh_inbound_spiffe_slot` returned `None` while the listener serves TLS) is a genuine fault — **fatal regardless of production** (mirrors the hard error a broken SVID cert/key gets in `load_mesh_frontend_server_identity`; `decide_*` is NOT consulted for it). At reload, "refuse" means reject the slice and keep the last-good mTLS config in its entirety (fail-closed by retention — never crash a live data plane, matching the failed-`ServerConfig`-rebuild contract above). `FERRUM_MESH_PRODUCTION_MODE` is read once at startup and threaded through `MeshInboundTlsReloadState.production` (process-fixed; a per-apply env read would also be test-racy). EastWestGateway (SNI passthrough, no termination listener) is exempt.
- The mesh `RequestAuthentication` (`jwks_auth`) plugin requires the JWT `exp` claim by default (`FERRUM_MESH_REQUEST_AUTH_REQUIRE_EXP=true`); operators may relax it. Expiry validation (rejecting present-but-expired `exp`) is always on.
- With `FERRUM_MESH_PEER_AUTH_LIVE_RELOAD_ENABLED=true`, only resolved mTLS mode, frontend client CA verifier, and the lock-free SPIFFE SVID bundle slot (federated trust domains) may hot-swap on slice apply.
- Frontend cert/key paths remain restart-required inputs for mesh peer auth reload.
- Coverage includes mesh HTTP/HBONE termination listeners and mesh-shared TCP+TLS stream listeners. Terminating UDP+DTLS is OWNER-SCOPED (issue #3858, below), not part of this fanout. Opaque datagram-over-mesh UDP stays opaque. PeerAuthentication reload must never mutate ordinary `FERRUM_DTLS_*` servers, active or future.
- `apply_mesh_inbound_tls_reload` publishes swapped `ServerConfig` into HBONE and the shared TCP+TLS stream slot ONLY. It must never call a process-wide `DtlsServer` fanout: generated NodeWaypoint listeners and ordinary operator `FERRUM_DTLS_*` listeners share one `StreamListenerManager`, so a fanout from that path live-swaps operator-owned listeners a mesh slice has nothing to do with (the #3829 policy-confusion vulnerability). Deleting the reload outright is the opposite failure — a generated `dtls` listener would keep the posture it started with across permissive→strict or a client-CA rotation.
- **DTLS ownership is explicit and listener-scoped** (issue #3858): `DtlsListenerOwner::{Operator, MeshNodeWaypoint{listener_key}}` on every `ListenerHandle`, two SEPARATE accepted generation slots sharing one publish lock, and two separate publish entry points (`publish_frontend_dtls_generation` for operator listeners, `publish_mesh_node_waypoint_dtls_generation` for generated ones). A collector applies only its own owner's generation. `swap_active_dtls_frontend_configs` is deleted; do not reintroduce a process-wide DTLS fanout. `build_node_waypoint_dtls_owner_configs` derives each generated route's complete config from the dedicated `FERRUM_DTLS_*` identity + that route's effective `PeerAuthentication` workload/service scope (most-restrictive across the Service's backing workloads; `Strict` ⇒ client CA required, `Permissive`/`Disable` ⇒ none) + the accepted client-CA/CRL snapshot, and runs BEFORE `update_mesh_config` so a malformed CA/CRL, verifier build failure, invalid client-side mode, or a `Strict` route with no client CA rejects the COMPLETE candidate slice and retains both owners' last-good routing and DTLS serving generation. Omitting an unservable `Strict` listener and still accepting the rest of the slice would leave an already-running Permissive listener serving across a Permissive-to-Strict change. The accepted map is stored before the swap so a late-created listener converges; an accepted EMPTY map is a positive withdrawal statement. Ordinary database/file/DP `FERRUM_DTLS_*` behavior and default limits are unchanged.
- A failed inbound `ServerConfig` rebuild (or a client-CA-bundle snapshot read failure) is computed before proxy-config apply and **rejects the whole slice**, keeping the last good config in its entirety (the one `ServerConfig` backs both HTTP/HBONE and the shared TCP+TLS slot, so no authz/policy/ServiceEntry/endpoint update from that slice applies either) — fail-closed. Do not reword the `ServerConfig`/snapshot warns back to a path-local "keeping previous TLS config" framing.
- `Disable` is rejected for Ambient and EgressGateway slice updates and keeps the last good config.

## DestinationRule And Materialization

- DestinationRule `loadBalancer.simple = PASSTHROUGH` materializes `LoadBalancerAlgorithm::Passthrough`. Captured orig-dst (`SO_ORIGINAL_DST`) that matches a healthy subset∩port pool target is dialed (bypassing LB). Unmatched, absent, or ejected orig-dst falls back to round-robin with a warning (`PASSTHROUGH: original destination unmatched/absent, falling back to round-robin`). Do not document PASSTHROUGH as "approximates to round-robin". `MAGLEV` is a hard reject at translation.
- DestinationRule `connectionPool.tcp.connectTimeout` lands on `Upstream.port_overrides[port].connect_timeout_ms` and is enforced by HTTP/H2/H3, gRPC, TCP, and HBONE dispatch.
- Port-level `loadBalancer` and `outlierDetection` land on the same override slot and use isolated per-port LB counters/hash rings and passive thresholds for HTTP-family, gRPC, WebSocket, and HBONE.
- `connectionPool.http.maxRequestsPerConnection` remains parsed/validated but deferred at EVERY scope. `idleTimeout`, `http2MaxRequests`, `h2UpgradePolicy`, `maxRetries`, and `http1MaxPendingRequests` are carried at top-level, `portLevelSettings`, and subset scope with field-level precedence **per-port > selected subset > top-level**. `SubsetTrafficPolicy` and `ResolvedSubsetTrafficPolicy` preserve all five; `GatewayConfig::resolve_dispatch_port_overrides` overlays the exact selected subset onto a per-proxy inherited fallback, so sibling subsets and unmatched proxies cannot leak policy. `h2UpgradePolicy` remains plain-HTTP-only; `DoNotUpgrade` restricts reqwest ALPN to `http/1.1`, and all HTTP-family pool keys include `upstream_subset` (the reqwest key also has its `h1` behavior discriminator and idle `rcfg` segment). `maxRetries` caps only an existing per-request retry policy and never synthesizes retries. `http1MaxPendingRequests` is an honestly reinterpreted concurrent-in-flight-H1 cap keyed by `(host, DestinationRule policy port, selected subset)`; its sharded RAII guard releases on every success/error/deadline/cancellation/retry exit. `idleTimeout` projects onto `pool_idle_timeout_seconds`; `http2MaxRequests` projects onto direct-H2/native-gRPC builders and those pools' keys (reqwest H2 has no equivalent knob — documented transport caveat, not a deferred field). Initial and rotated targets resolve effective policy from the immutable proxy snapshot. Invalid values fail closed with field-specific, value-redacted diagnostics. Translator and status must list only `maxRequestsPerConnection` (all scopes) as deferred for this family.
- Dispatch projects port overrides through `resolve_effective_proxy_for_target()` onto the owned `Proxy` clone; direct H2 and gRPC builders consume H2 caps through `max_concurrent_streams` and `initial_max_send_streams`.
- **INHERITED top-level `connectionPool.http` fallback (#1806, extended to subsets; #3735 for idleTimeout/http2MaxRequests)**: `Upstream.dispatch_port_override_fallback` (`#[serde(default, skip)]` derived) is the cold-path carrier for the inheritable top-level HTTP overlay. ALL five applied HTTP fields (`h2UpgradePolicy`/`maxRetries`/`http1MaxPendingRequests`/`idleTimeout`/`http2MaxRequests`) accumulate there for EVERY upstream via `apply_connection_pool_http_to_port_override` so a selected subset can overlay them without losing source-tier identity. Explicit `portLevelSettings` entries remain on `port_overrides` and win at dispatch. `resolve_dispatch_port_overrides` projects the fallback onto `Proxy.dispatch_port_override_fallback` (`#[serde(skip)]`), overlaying the EXACT effective selected subset's `ResolvedSubsetTrafficPolicy` (`dispatch_port_override_fallback_for_selected_subset`) into a proxy-local derived value — it never mutates the shared upstream and never consults a sibling subset, so sibling subsets and unmatched proxies cannot leak policy. `resolve_effective_proxy_for_target` and `cap_proxy_retry_for_target` consult the fallback (the TOP-LEVEL + selected-subset overlay ONLY — `dispatch_port_override_fallback_from_upstream` does NOT fold per-port entries into it; folding cross-leaks between ports on a multi-port upstream) ONLY when the selected target's POLICY port (`target.dispatch_policy_port()`) has no explicit field on `dispatch_port_overrides` — so an explicit `portLevelSettings` entry wins, giving field-level precedence **per-port > selected subset > top-level**. **Named `targetPort` is covered** (the former #1816 deferral): mesh SD targets whose resolved workload dial port differs from the declared Service port carry the owning Service port in the serde-skipped `UpstreamTarget.service_port_policy_key`, so dispatch keys DR policy by `dispatch_policy_port()` while still dialing `target.port` — an explicit per-port entry is honored even under a named `targetPort` remap (see `docs/mesh.md` "An explicit `portLevelSettings` entry..."). Immediate route-TABLE rebuild on a DR-only fallback/TLS/per-port projection edit is wired (#3243 / #1826): `ProxyState::delta_routes_changed` and the empty-delta publish path compare `#[serde(skip)]` DR-derived proxy fields (`dispatch_port_overrides`, `dispatch_port_override_fallback`, `resolved_tls`, mesh stream-relay dispatch maps) so route-held `Arc<Proxy>` values cannot stay stale. This is runtime-by-selected-port application of the overlay, NOT runtime-resolved target materialization (the rejected outbound-SD rework — see below). Adding these two derived fields churns every `Proxy`/`Upstream` struct literal (E0063) — run `cargo build --lib`.
- **HTTP/3 frontend effective-proxy coverage (#1806/#2020)**: the H3→HTTP plain bridge (`src/http3/cross_protocol.rs` `dispatch_plain`) resolves `resolve_effective_proxy_for_target` per attempt INSIDE its retry loop (an entry-level resolution backs the port-independent retry/buffering decisions), so the per-port `connectionPool.http` effective-proxy overrides (idleTimeout/http2MaxRequests/connectTimeout/TLS/h2UpgradePolicy-ALPN + the SD fallback) apply on the H3→plain reqwest bridge — `get_client` builds the client from the effective proxy and `build_plain_request_builder` reads its `backend_connect_timeout_ms` — and its local dispatch-policy rejects (per-port backend-TLS-SNI incompatibility → 502; `http1MaxPendingRequests` pending-cap → 503) run BEFORE backend admission per attempt, matching H1/H2 ordering. The standalone H3 frontend (`src/http3/server.rs`) applies the selected-target pipeline across ALL FOUR flavors: `cap_proxy_retry_for_target` runs right after target selection (so a DR `maxRetries` cap governs the H3 retry loops and the retry-dependent buffering / native-H3-suppression decisions), the first target's effective proxy backs the native-H3/streaming dispatch decisions, `ctx.matched_proxy` carries the retry-capped BASE proxy (H1/H2 parity — per-port TLS/timeouts are dispatch-time-only, never plugin-visible), and every loop that can rotate retry targets — the buffered native-H3 retry loop, the H3→plain and H3→gRPC bridges, and the H3 WebSocket dial loop — re-resolves the effective proxy per attempt from the capped UNRESOLVED base proxy so a rotated target never inherits the first target's port-level TLS/SNI/H1 policy. Mesh capture itself is TCP/UDP-only, so the H3 FRONTEND is never a mesh capture listener; it IS a mesh EGRESS surface for gRPC since #3284 (see `proxy-protocols.md` → “HTTP/3 And gRPC”), so do not read this as “H3 has no mesh dispatch”. Keep `docs/mesh.md` "Dispatch-path coverage" and the textual pins in `tests/unit/gateway_core/http3_selected_target_policy_tests.rs` in sync.
- `http_max_requests_per_connection` is a legacy carrier only; new DR translation does not populate or consume it.
- `connectionPool.tcp.maxConnections` and `tcpKeepalive` land on `max_connections` and `tcp_keepalive`. `maxConnections` is enforced by EVERY transport whose physical connection lifecycle Ferrum owns, all against ONE shared `backend_conn_limit::BackendConnectionLimiter` on `ProxyState.backend_conn_limit` keyed `(host, DestinationRule policy port)` — stream-family (TCP/TCP+TLS) dispatch; HTTP-family WebSocket dispatch (H1/H2 in `proxy/mod.rs`, H3 in `http3/websocket.rs`), which holds an RAII `BackendConnectionGuard` for the session and rejects over-cap upgrades with 503; the pooled multiplexed transports (see the next bullet); and the reqwest transports (HTTP/1.1 AND ALPN-negotiated HTTP/2), admitted at reqwest's own connector. `tcpKeepalive` is enforced by stream-family dispatch AND the socket-owning H2-family pools (direct-H2 `http2_pool`, `grpc_proxy`, HBONE `hbone_pool`, mesh-mTLS `mesh_mtls_pool`) via the shared `socket_opts::apply_pooled_tcp_keepalive` resolved at connection creation — direct-H2/gRPC key the override by the dial `backend_port`; HBONE/mesh-mTLS key it by the destination's APP/service port (NOT the transport dial port `:15008`/`:15006`) and apply it inside the shared `dial_h2_connect_sender` (so HBONE egress, Sidecar mesh-mTLS egress, raw-TCP egress on both transports, and WebSocket-over-HBONE/-mesh-mTLS are all covered). The per-port DR override takes precedence; the global `pool_config.tcp_keepalive_seconds` remains the fallback. Keepalive is NOT a pool-key field (see `proxy-protocols.md`), so on the shared/pooled HTTP-family connections the FIRST dispatcher to materialize the connection fixes the keepalive (first-materializer tradeoff, like `idleTimeout`/`maxRequestsPerConnection`). The reqwest-backed HTTP pool (shared client) and H3/QUIC (UDP transport) are documented residuals — reqwest keeps the global seconds-only keepalive; QUIC keep-alive is N/A.
- `maxConnections` on the pooled multiplexed transports (direct H2, gRPC, native H3, HBONE, mesh-mTLS) is a PHYSICAL-connection bound, never a request-concurrency counter: the slot is reserved at the moment a NEW connection is constructed (after the pool has already missed its cache, so reuse takes none) and handed to that connection's own lifecycle owner — the spawned hyper/`h2` connection-driver task for the H2-family pools, and the spawned `h3` connection-driver task for QUIC (it owns the `h3_quinn::Connection`, so `poll_close` resolves when the QUIC connection really ends). The slot is deliberately NOT parked on the pooled `H3PooledConnection`/`Http2Sender` handle: an evicted or force-drained handle can drop while the socket is still open, releasing the slot early and letting a replacement push the destination past the cap. That makes retirement exact for free: create failure drops it, idle eviction / unhealthy replace / `clear()` / `force_drain_svid_generation` / reload-update-delete / shutdown end the driver, and multiplexed streams are unbounded (`h2_max_concurrent_streams` is still the stream knob). The reservation is cloned per DNS candidate so a failed candidate frees its clone. An over-cap create is a pre-wire, backend-health-NEUTRAL `ErrorClass::BackendConnectionLimit` (`Http2PoolError::MaxConnectionsExceeded`, `GrpcBackendUnavailableKind::MaxConnections`, `HbonePoolError::MaxConnectionsExceeded`, and for native H3 a typed `BackendConnectionLimitExceeded` preserved in the `anyhow` source chain — a plain `anyhow!` message would classify `RequestError`, which `request_reached_wire` treats as POST-wire). Do NOT downgrade it to the generic `ConnectionPoolError`: that class IS a backend-health signal, so a saturated operator-configured ceiling would record a circuit-breaker failure, a passive-health failure, an LB penalty sample and an adaptive-concurrency shrink, ejecting a perfectly healthy destination. `BackendConnectionLimit` is in `client_side_no_backend_signal` AND pre-wire, which is the full raw-TCP over-cap posture (rotate targets + `cb.record_neutral()`); the retry loops' per-attempt breaker records honor the same neutrality. direct-H2, gRPC and native H3 first fall back to an already-established shard, so a cap below `http2_connections_per_host` / `http3_connections_per_backend` converges on `cap` connections and multiplexes. Only a cap refusal takes that fallback (`pool::is_max_connections_refusal`, which recognizes both the creator's typed chain and a coalesced waiter's `SharedPoolCreateKind::MaxConnections`), and only ALREADY-CACHED healthy shards are reused, so no unrelated create failure is silently retried and no cap is bypassed. A cap refusal is also NOT capability evidence: the H2/H3 capability probes preserve the prior classification instead of downgrading a healthy backend that merely happened to be at its ceiling when the refresh ran. HBONE/mesh-mTLS key the lane by the destination's APP/service policy port, not `:15008`/`:15006`. reqwest (H1 and H2 alike) is admitted in reqwest's CONNECTOR — the one place a new physical socket is dialed — through the vendored `ClientBuilder::connection_admission` hook (`docs/upstream-reqwest-patches/003-connection-admission-hook/`); pooled reuse and multiplexed H2 streams never reach it, and the token it returns is owned by the connection object, so an idle socket reqwest retains after a request STILL holds its slot. A request-lifetime slot would have been wrong on both counts (it reads zero while sockets stay open, and it counts H2 streams). One shared hook across every `reqwest::Client` means divergent pool keys (TLS material, `rcfg`, forced-H1 ALPN, subset) for one destination share ONE ceiling. The dispatch path binds the destination lane (dial `(host, port)` → policy port + cap) to its own dispatch with an RAII `ReqwestLaneLease` held across `send()`, and only when a cap is configured — so a lane exists exactly while a capped request can cause a dial, a removed cap drains with its requests (no epoch registry to sweep or leak), and the retry path leases its own (possibly rotated) target. Because `maxConnections` is deliberately NOT reqwest pool-key material, several logical upstreams can resolve different `(policy port, cap)` for one dial address and SHARE one socket pool; per-connect binding cannot enforce the stricter cap there (the laxer upstream's socket is reused by the stricter one), so conflicts resolve to the STRICTEST live lane — order-independent and fail-closed. Do not replace that with last-writer-wins global state. See `docs/mesh.md` "DestinationRule `maxConnections` enforcement scope" and `src/backend_conn_limit.rs`.
- `maxConnections` exhaustion returns `StreamSetupKind::BackendMaxConnectionsExceeded` on stream-family, a 503 (`rejection_phase=backend_max_connections`) on WebSocket, a pre-wire, health-neutral `ErrorClass::BackendConnectionLimit` on the pooled transports, and a `DispatchPolicyRejected` 503 (backend-health neutral) on reqwest, recognized from the connector error chain via `backend_conn_limit::is_backend_connection_limit_error`; keepalive setsockopt failures warn and continue.
- **Sidecar mesh-mTLS pool width is pressure-gated, not eager** (issue #5043). `MeshMtlsConnectionPool` starts every destination at ONE HTTP/2 connection and widens only while the least-loaded connection has ≥ `MESH_MTLS_GROWTH_PENDING_PER_CONNECTION` (8) requests awaiting response heads AND the pool is below `http2_connections_per_host` (`FERRUM_POOL_HTTP2_CONNECTIONS_PER_HOST`). Load is `MeshMtlsSender::pending_requests`, a shared counter settled by the `PendingResponse` wrapper on head arrival, hyper error, OR dropped future — hyper 1.x `SendRequest::poll_ready` is always Ready, so it carries no load signal; do not go back to `ready()`-probing. Checkouts take the least-pending connection with ties to the lowest index so extra connections drain and expire idle (`select_least_pending`; a stale entry on the read path is a deliberate miss so the write path prunes). Growth uses `SharedCreationSlot::try_claim` (never queues behind a cold-path creator), goes through the SAME `dial_and_publish` as the cold path (so `maxConnections` admission, SVID/CRL pinning, retirement and rotation checks all apply), and a failed growth dial backs off `MESH_MTLS_GROWTH_BACKOFF_SECS` (10 s) per key while traffic keeps flowing on the existing connection. Measured: one connection is a hard ~70k req/s / ~2.5 GB/s ceiling per destination regardless of stream count; 4 connections give 1.8–3.2× at ≥ 16 concurrent with ~2× lower p50; ≤ 4 concurrent never widens and is byte-identical to the old single-connection path.
- **HBONE pool width follows open CONNECT streams and the peer's stream cap** (issue #5465). `HboneConnectionPool` (Ambient/Waypoint egress: pooled HTTP-family requests AND pooled raw-TCP CONNECT tunnels) has the same blind spot in raw `h2`: `SendRequest::clone().ready()` is always Ready, so it carries no load or capacity signal; do not go back to `ready()`-probing for selection. Load is `HboneConnectionLoad` on `MeshH2Transport`: `active_streams` is leased in `open_h2_connect_stream` / `open_h2_ws_connect_stream` from the `send_request` (a CONNECT parked pending-open counts) and released by the `HboneStreamLease` owned by `H2ConnectTunnel`; `peer_max_streams` is sampled from `SendRequest::current_max_send_streams()` on every CONNECT response (which cannot precede the peer's SETTINGS), never on the checkout scan, so the read path stays lock-free. `select_least_loaded` picks the fewest open streams among live entries under their cap, ties to the lowest index so extras idle out; a saturated entry is skipped while a sibling has room. Growth: least-loaded ≥ `HBONE_GROWTH_ACTIVE_STREAMS_PER_CONNECTION` (8) with room → opportunistic `try_grow_sender` (`SharedCreationSlot::try_claim`, `HBONE_GROWTH_BACKOFF_SECS` = 10 s on failure, same `dial_and_publish` as the cold path); every live entry saturated with room → the coalesced cold path dials; saturated at `http2_connections_per_host` → the tunnel queues pending-open on the least-loaded connection, bounded by the caller's connect timeout (a burst above `cap × width` drains instead of failing; this is logged at debug, not surfaced as a new error). Regression: `tests/integration/hbone_pool_width_tests.rs`.
- TCP/UDP/DTLS stream paths engage per-port **LB algorithm** and **`localityLbSetting`** at selection time when all upstream targets share a single port (`initial_dispatch_port_override` non-zero); per-port `connectTimeout`, `maxConnections`, and `tcpKeepalive` also apply. Active/passive health context is threaded into stream target selection unconditionally; the `maxEjectionPercent` cap resolves at the per-port tier only under that same single-port condition and at the upstream/global tiers otherwise. Outlier thresholds are not recorded on stream paths themselves (raw relay sessions carry no response status), so stream-only traffic does not create new passive ejections, but active health and existing passive ejections are honored.

- **DestinationRule lookup-tier evidence must AGREE between CP admission and DP materialization (#2465/#2469).** `policy_target_service_ref` (slice build) and `MaterializationTierScope::eligible_tier` (`apply_destination_rules`) resolve the destination host's owner through ONE shared helper, `slice::destination_host_owner`: `.svc[.cluster-domain]` syntax → inventory-confirmed two-label `name.namespace` → `service_entry_host_owner` (single owner; cross-namespace duplicates and an empty declaring namespace ⇒ `Ambiguous` ⇒ NO service tier). Istio short-name self-scoping stays OUT of it — it reads the POLICY's namespace, so it belongs to `policy_target_service_ref` alone. Both the SOURCES and their ORDER are load-bearing: (a) when the host owner IS resolved it is AUTHORITATIVE for the service tier — do NOT widen it with a conflicting `Upstream.namespace` (`by_upstream.min(by_host)` lets an operator-authored / multi-target upstream in `evil` manufacture service-tier policy for a host owned by `beta`); (b) retain upstream-namespace fallback ONLY when host ownership cannot be resolved — `build_egress_upstream` stamps every ServiceEntry-derived EgressGateway upstream with the GATEWAY's namespace, and the host-owner arm recovers the declaring ServiceEntry for external hosts so owner-authored `trafficPolicy` still applies; (c) do NOT hoist the ServiceEntry arm above the `.svc`/inventory arms — a carrier-supplied ServiceEntry declaring `reviews.beta[.svc…]` would then transfer ownership of `beta`'s service to its own namespace. Missing/empty/whitespace root provenance fails closed (refuse Unscoped; keep independently provable client/service tiers; never restore pre-#2469 permissive bucketing). Re-stamping the synthesized upstream's namespace is the wrong repair — `Upstream.namespace` participates in `FERRUM_NAMESPACE` filtering and per-namespace uniqueness. The DP builds its identity index from the slice's already-narrowed `services`, the CP from the full inventory; that is the one intended divergence. **Per-host LOOKUP is not per-host APPLICATION**: every field a winning rule projects lands on the shared `Upstream`, so `apply_destination_rules` REFUSES (returns `Err` → slice rejected → last-good retained; no mutation) an upstream whose match hosts resolve to DIFFERENT winning rule SETS. Do NOT "fix" that by merging them in sorted order — that is order-dependent cross-service policy transfer, which the deleted test `an_upstream_spanning_two_services_resolves_each_host_independently` masked by choosing non-conflicting fields. Hosts with NO winner do not participate (a destination no rule targets cannot disagree), so single-destination, multi-port, and static-fallback-target upstreams are unaffected. The ambiguity-warning dedup map (`DESTINATION_RULE_AMBIGUITY_REPORTED`) is keyed by the SUBSCRIBER namespace and must stay bounded by namespace count, per-namespace count-values, **and retained key bytes** (`DESTINATION_RULE_AMBIGUITY_NAMESPACE_BUDGET` × `DESTINATION_RULE_AMBIGUITY_COUNTS_PER_NAMESPACE`, with keys over `DESTINATION_RULE_AMBIGUITY_NAMESPACE_KEY_MAX_BYTES` never retained); every saturation path fails toward visibility, never silence.
