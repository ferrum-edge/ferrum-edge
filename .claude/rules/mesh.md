# Mesh Rules

Full operator docs live in `docs/mesh.md`. Keep this file to implementation invariants. Subsystem
invariants live in `mesh-hbone-waypoint.md`, `mesh-capture-cni.md`, and `mesh-k8s-controller.md`.

## Topologies And Runtime

- `MeshTopology` drives listeners: `Sidecar` uses inbound 15006 mTLS and outbound 15001 capture; `Ambient` uses HBONE 15008 and outbound 15001; `EastWestGateway` uses SNI passthrough on 15443; `EgressGateway` uses mTLS inbound 15090 to external ServiceEntry backends.
- All topologies share the normal proxy and plugin chain.
- Mesh runtime state is `ArcSwap<Option<MeshSlice>>` in `runtime.rs`; slice apply is lock-free hot-swap like `GatewayConfig`.
- Startup obtains its initial candidate through `wait_for_initial_mesh_config()`, which retries after config-building failures. `wait_for_first_slice()` is a first-received-slice notification helper.
- Native config consumption uses `MeshConfigSync.MeshSubscribe` gRPC. xDS uses ADS for CDS/EDS/LDS/RDS/SDS/ECDS/RTDS with 25 ms debounce.
- **An RTDS knob that affects request handling must be materialized into the candidate plugin config, never published to a process-global store** (GHSA-83rc-23c9-3g9x): `runtime_overlay_consumers::apply_overlay` runs from `record_applied_slice`, AFTER `ProxyState::update_config` published the new `RequestEpoch`, so a global value straddles the publication gap and every already-admitted request. Pattern: `materialize_fault_runtime_overlay` / `materialize_transformer_runtime_overlay` fold the accepted overlay into each instance's config in `prepare_normalized_gateway_config_for_mesh` (gate/percentage and rules validated, built, and published as ONE generation; one immutable decision per instance). `RUNTIME_OVERLAY_MATERIALIZED_PLUGINS` + `reconcile_runtime_overlay_plugin_generations` are load-bearing: without the `updated_at` stamp an RTDS-only change leaves `ConfigDelta` retaining the old instance.
- The transformer gate stores are STILL published post-accept, as provenance only (`response_caching` pins the response-side publication identity, `request_deduplication` folds its content fingerprint) — deleting those `apply_overlay` calls stops retiring cached/persisted representations. That identity alone is insufficient (a request whose auth phase spans an apply pins the OLD generation and NEW identity), so every retained representation must ALSO bind `RequestContext::response_presentation_policy_digest` (covers the materialized gate and static rules): `response_caching` on its `CacheEntry`, `request_deduplication` via `ResponsePolicyProvenance`. A difference in either half retires it; an unavailable digest retains nothing. `logging` is the one legitimate process-global consumer.
- `FERRUM_MESH_CONFIG_PROTOCOL=file` (`config_consumer::file_source`) builds the slice DP-side from `FERRUM_MESH_FILE_CONFIG_PATH` via `MeshSlice::from_gateway_config` (same materialization as CP paths — do not fork it). The document is `{version?, mesh}` ONLY (`deny_unknown_fields` rejects gateway resources). Initial load fails closed at startup; SIGHUP reload keeps the last good slice on error. No CP URLs / CP-DP JWT secret are required — `EnvConfig::validate()`'s Mesh arm and `MeshRuntimeConfig::from_env_config` gate those per protocol; do not re-add unconditional requirements.
  - Both loads (issue #3776) run on `spawn_blocking` through the shared bounded reader `config::stable_file` (opened-target regular-file check, Unix `O_NONBLOCK`, 64 MiB ceiling streamed at `limit + 1`, byte-identical dual identity/content probe, bounded instability retry). Format is **extension-only** (`.json` → JSON; `.yaml`/`.yml`/unknown/extensionless → YAML) — do NOT re-add content sniffing. Every YAML document still gets the shared bounded libyaml event preflight before `serde_yaml`, and an alias-bearing one a second bounded composition/traversal pass (ceilings: `docs/configuration.md`, `docs/mesh.md`).
  - Rapid SIGHUP coalesces to ONE in-flight generation plus at most one follow-up; the requested generation advances when the signal is **observed**, so an older completed load never installs over a newer request. Shutdown stops accepting candidates without awaiting a started (non-cancellable) blocking job; the `biased` select puts shutdown first so a simultaneous completion cannot publish.
  - A rejected reload (read/parse/validation/revision-gate/join/apply) retains last-good AND raises authenticated-`/health` `config_rejected` via `file_source::MeshLocalSourceRecovery` (shared with the `stock_xds` policy watcher). It clears ONLY when the proxy apply lifecycle accepts the EXACT current recovery candidate (Applied or content-identical no-op) — never on a provisional `install_slice` or a policy channel send. Every recovery transition (cancel, new candidate, policy-identity bind, proxy accept, proxy reject) and its `config_rejected` write share ONE transition-lock critical section (an older callback can neither clear health after a newer failure nor cancel a newer recovery); an uncomputable content identity or a poisoned lock fails closed.
- xDS apply is make-before-break with a coherent required-version gate: per-type `version_info` is tracked independently, but a slice builds only once all required types (CDS/EDS/LDS/RDS/ECDS — ECDS so the first slice is never the unprotected name-only view) share one `version_info` and `reverse_translate` succeeds; the prior slice serves until then. Structural errors (e.g. malformed ECDS carrier) NACK + roll back. A route referencing a service not yet in CDS/EDS/LDS is SKIPPED (debug-logged) and retained, NOT NACKed (a NACKed SotW resource is not resent until reconnect) — do not reintroduce a hard error. `MeshSlice.version` is observability-only (`content_eq` ignores it). The CP force-re-sends subscribed required types when any changes, so name-only types never advance past stale ECDS security carriers; keep DP `REQUIRED_MESH_SLICE_TYPE_URLS` and the CP emitter in sync.
- Warming observability: `ferrum_xds_warming_partial_applies_total{namespace}` is in the normal `/metrics` view (scrape gating: `docs/admin_api.md` → `/metrics`); per-type `version_info` strings and still-missing required types ride only the JWT-gated `GET /mesh/config-drift` `convergence` block (`MeshRuntimeState::set_xds_convergence`). Do NOT move per-type version strings onto `/metrics` (they embed config-change timestamps + content digests and explode label cardinality).
- xDS is Ferrum-CP-to-Ferrum-DP, not stock-Envoy/Istio-interoperable: CDS/EDS/LDS/RDS are name-only (service-port discovery); every security/policy slice field and selector context (authz, PeerAuth, JWT, ServiceEntry, trust bundles, ProxyConfig, VirtualService L4 proxies, workloads, effective labels, outbound policy, telemetry, multi-cluster, sidecar egress scope) rides ECDS as Ferrum mesh-slice carriers. `src/xds/carrier.rs` (`MeshSliceCarrier`) is the single encode/decode source; the CP emits via `translate_mesh_slice_carriers`, the DP recovers in `reverse_translate`, requiring both the reserved resource name and the matching inner type URL. An xDS-built slice must stay functionally equivalent to a native-built one.
- **ACK-time validation covers every policy-bearing carrier field** (#2465/#2469). `validate_ecds_destination_rule_carrier` recognizes a DR carrier by inner `type_url`: a DR-typed resource under any name but the reserved `ferrum-destination-rule-carrier/{namespace}/{name}` NACKs; reserved carriers get the fail-closed JSON + `validate_mesh_export_to` check; unrelated ECDS extension configs route untouched (`MeshConfig::validate` rejects operator `extension_configs` declaring the DR type_url, `translate_ecds` skips one defensively, and a slice-carrier type_url under a non-reserved name also NACKs). `validate_ecds_mesh_slice_carrier` validates `VirtualServiceCorsPoliciesCarrier.export_to` and the `IstioRootNamespaceCarrier` lowercase RFC 1123 namespace. Do NOT restore an early return/skip for non-reserved DR names (the payload would be ACKed and go inert at materialization — fail-open). Diagnostics are field/index-shaped, capped at `XDS_CARRIER_DIAGNOSTIC_LIMIT`, and never echo the carrier-supplied value.
- VirtualService L4 `sourceLabels` / `sourceNamespace` on the `mesh` arm are Sidecar source-workload applicability selectors, not authenticated inbound-peer predicates. Resolve them at slice apply from the unambiguous local workload identity/namespace/labels, drop non-applicable arms fail-closed, and leave remaining subnet/gateway/SNI predicates ordered and AND-combined. Named-gateway arms stay independent; ambient/NodeWaypoint retain exact runtime source-workload evidence. The namespace-projected L4 proxies ride `MeshSlice` (and the matching ECDS carrier), and `content_eq` compares them so updates/deletes cannot retain stale matcher state.
- Native and xDS clients use jittered exponential backoff from 1s to 30s, plus/minus 25%, multi-CP failover via `FERRUM_DP_CP_GRPC_URLS`, and JWT metadata.

- **Config-revision ordering is fail-closed and centralized in `MeshRuntimeState::install_slice` / `modes::mesh::revision`** (issue #2473; operator contract: `docs/mesh.md` → "Authoritative Config Revisions"). `revision = (authority, sequence)`; `sequence` is a durable source cursor, never a wall clock or process-local counter (`MeshSlice.version` is observability-only). Change-log `Single`/`Set` stamps the saturating sum of scoped namespace cursors, `All` the store-wide sum of per-namespace high-water marks, each captured BEFORE its resource load and only then floored. CP startup rejects authorities with control characters or over 128 bytes without echoing them; empty disables publication.
- The gate admits Bootstrap/Newer/Same and quarantines `stale_revision` / `incomparable_authority` / `missing_revision` / `malformed_revision` / `divergent_content` / `unidentified_content` BEFORE the `ArcSwap` swap; a quarantine mutates nothing (no receive metric, no `last_install_at`, no watcher wake). Do NOT downgrade a present ill-formed authority to absent — `admit` refuses it even on bootstrap (xDS reaches the gate without `MeshConfigUpdate` validation); raw non-empty whitespace envelope authorities are malformed, not proto-absent.
- **`Same` installs for IDENTICAL SEMANTIC CONTENT ONLY.** The gate binds `MeshRevisionContentIdentity` (canonical `slice_content_digest`, `version`/`revision` cleared) to every accepted AND applied revision and compares it INSIDE the admission critical section (never caller-side — TOCTOU). Both slots move revision+identity as a PAIR on every transition; the apply token carries the identity. Remote-cluster discovery binds the post-validation/post-trust-domain/post-tagging endpoint set. No digest or content byte may reach a log, metric label, or admin surface.
- Native and xDS quarantines TERMINATE their streams. Do NOT rewind the xDS ADS accumulator (it already ACKed); it is per-CP-URL and reset by `reset_for_new_control_plane` on failover. Do not weaken the required-type/version-coherence gates.
- **Admission is provisional: two watermarks.** `record_applied_slice` → `commit_applied` advances `applied` (including equal-revision replays); a runtime rejection → `record_rejected_slice` → `rollback_rejected` returns `accepted` to `applied`, gated on exact `(authority, sequence)` AND received-slot `Arc` identity so a late rejection of N never rolls back N+1. `wait_for_initial_mesh_config` owes the same rollback for the first slice (issue #4041). Every refusing stage resolves through the ONE guard `MeshRuntimeState::evaluate_received_slice` (rolls back on DROP unless `pass()`): do NOT open-code `record_rejected_slice` or return early without resolving the guard. Never advance the watermark on receipt alone. The `file` source is exempt only because it converts before `install_slice`.
- Escaping copies of the authority (diagnostics, reset response, logs) go through `diagnostic_value`; `is_well_formed` refuses blank/control/over-length authorities. The revision rides `MeshConfigUpdate.config_authority`/`config_sequence` (envelope↔slice agreement in `update_validation`, reason `envelope_revision_mismatch`; malformed revisions refused first with `malformed_revision`) and the xDS `ConfigRevisionCarrier`. `content_eq` deliberately IGNORES `revision`. `GatewayConfig.mesh_revision` is `#[serde(skip)]` — do NOT put it on the ConfigSync `config_json` wire (`deny_unknown_fields` both sides).
- No lockout: a foreign authority is adopted after `FERRUM_MESH_CONFIG_REVISION_ADOPT_SECS` (default 300, `0` disables); a rewind INSIDE one authority is NEVER auto-adopted (recover via `POST /mesh/config-revision/reset` or a new authority id). An intentional rollback is a WRITE (higher sequence); never accept an old generation to roll back.
- **A Kubernetes-controller CP publishes the SEPARATE `k8s` ordering domain** (issue #3611): authority `k8s` / `k8s:<FERRUM_MESH_CONFIG_K8S_AUTHORITY_ID>`, sequence from `k8s_controller::revision::K8sConfigRevisionTracker`. `k8s`/`k8s:…` is reserved (refused on a change-log CP by `EnvConfig::validate`); the composed `k8s:<qualifier>` is validated whenever the CRD controller is enabled, independently of the empty-`FERRUM_MESH_CONFIG_AUTHORITY_ID` switch. A `config_changes` cursor reaches a revision ONLY through `MeshConfigRevision::advance_change_log_sequence` (no-op on the k8s domain) — do NOT reintroduce a raw `revision.sequence.max(cursor)`. The revision lives on `AcceptedK8sOverlay.mesh_revision` and both publishers stamp it via `apply_k8s_mesh_revision` (never on the DB snapshot, which the next poll would wipe).
- Per-scope evidence = max(pre-list boundary read adopted only at `InitDone`, listed-object RVs buffered until that `InitDone`, applied watch-event RVs — deletions carry the DELETION revision). A post-list boundary read would NOT be a sound lower bound. The published sequence is the MIN over registered scopes, read BEFORE `snapshot_all()` under the SAME `ResourceStoreSet` lock; any scope without evidence makes it unavailable, and unavailable RETAINS the last published sequence. Max-over-live-objects, wall clocks, and reconcile-time current-revision reads are all wrong.
- `publish_k8s_reconcile` binds mesh to the revision inside `CpPublicationGate`: equal revision + divergent mesh retains the accepted mesh (overlay slot, `config_arc`, and broadcast together); an advanced sequence releases the newest mesh. A retaining publication MUST call `K8sConfigRevisionTracker::request_evidence_refresh` (per-scope 5 s floor) or propagation stalls for a whole idle-relist window; the refresh acquires proof and never fabricates a watermark. Do NOT weaken `MeshRevisionGate`.
- **MeshSubscribe response binding is centralized and fail-closed** (`config_consumer::update_validation`, issue #2457). BOTH consumers — the native client and multicluster remote discovery — validate a non-heartbeat `MeshConfigUpdate` against the exact `MeshSubscribeRequest` they sent (`MeshUpdateExpectation::from_subscribe_request`) BEFORE `install_slice` / endpoint import: present + major/minor-compatible `ferrum_version`, `update.version == slice.version`, `slice.node_id`/`slice.namespace` equal to the request, and an exact echo of a PINNED `workload_spiffe_id`/`waypoint_name` (an ABSENT echo is a mismatch; an unpinned request gates nothing). Do not fork the rules or add a "skip when the field is missing" branch.
- Rejections are metric-recorded inside the validator (`ferrum_mesh_config_update_rejections_total{consumer,reason}`, both labels `&'static str` from closed enums — never a CP-supplied value) with a sanitized, length-bounded `warn!`. `MeshUpdateRejectReason::terminates_stream` splits BINDING failures (drop the stream → multi-CP failover) from CONTENT failures (drop the frame, keep the stream). Remote discovery fails the whole poll either way, keeps last-good endpoints, retains a per-cluster `MeshRevisionGate` across one-shot reconnect polls, validates endpoint content before advancing it, and applies the foreign-authority adoption policy. Heartbeats route only to `validate_update_ferrum_version`; a heartbeat-marked frame reaching the install path is a rejection. Test CP stubs must echo the request scope (as `functional_mesh_mode_test`'s stub does).

## Datapath Layering: Two Transports (per topology) vs. Materialization

Keep the **transport** (how a peer is reached on the wire) distinct from **materialization** (turning the slice into routable `Proxy`/`UpstreamTarget` objects `find_proxy` can match). "Outbound 404 / no routes" does NOT mean "no transport" — conflating them re-implements transport that exists or, worse, uses the wrong transport for the topology.

**Mesh transports are PER-TOPOLOGY — never assume one (this is the trap):**
- **Ambient / NodeWaypoint / ServiceWaypoint** speak **HBONE** (HTTP/2 CONNECT over mTLS) on **:15008**.
- **Sidecar** speaks plain **SVID-mTLS HTTP** on **:15006** and has **NO 15008 HBONE listener** (an HBONE dial to it would `hbone_required`-502). Source of truth: `listener_plan()` in `modes/mesh/mod.rs` (Sidecar = capture :15001 + mTLS :15006; Ambient = capture :15001 + HBONE :15008).
- **Client-visible failure wording follows the transport, not the shared error type** (issue #3927). Both `MeshMtlsConnectionPool` and `HboneConnectionPool` surface `HbonePoolError`; `MeshTransportLabel` (`proxy/hbone_pool.rs`) picks the public noun. Sidecar dispatch uses `mesh_mtls_pool_error_response` / `mesh_mtls_hyper_error_response` / `sidecar_mtls_*_body_too_large_response` (`Sidecar mTLS backend unavailable`, log noun `Sidecar mTLS`); Ambient/waypoint keeps the `hbone_*` wrappers — never call one from `proxy_to_backend_mesh_mtls[_after_ready]`. Pool-setup bodies come from `MeshTransportLabel::unavailable_body_for_error(&HbonePoolError)`: fixed `HbonePoolError::public_reason()` plus `HbonePoolError::public_status()` (the peer's CONNECT admission status, `ConnectRejected` ONLY — the NodeWaypoint eBPF live gate matches `… tunnel rejected by peer with status 403` to prove a destination POLICY denial, so do not collapse it). Post-establishment and DNS bodies are separately fixed. Never interpolate `Display` into client bodies or the pool-error operator `error!` (it can carry peer address, SPIFFE ID, cert subject, trust root, raw verifier text); operator logs emit closed-cardinality `error_kind`, `error_phase` (`public_reason()`), and `peer_status` only for `ConnectRejected`. Classification, retry/pre-wire boundary, circuit-breaker accounting, and `error_class` stay transport-identical.
- **`FERRUM_MESH_CA_BACKEND=internal` is process-local with no export path** (issue #3927): two processes bootstrapping it hold unrelated roots and cannot mTLS. Do not add persist/export/import of the dev root. Local multi-process meshes use file SVIDs (`FERRUM_GATEWAY_SVID_CERT_PATH` / `KEY_PATH` / `TRUST_BUNDLE_PATH`, all three or none — enforced in `EnvConfig::validate` for mesh mode AND in `load_gateway_svid_bundle`); see `docs/mesh.md` → "File-Based SVIDs: Two-Process Local Mesh".

- **Ingress (inbound).** Sidecar inbound: `materialize_sidecar_inbound_proxies` → loopback routes (`:15006` → `127.0.0.1:appPort`), **one sibling per HTTP-family service port**. Ambient/Waypoint inbound has **no materialization**: `build_inbound_hbone_relay_proxy` (route-miss arm, only for `mesh_direction == Inbound` + `is_hbone_connect`) synthesizes a relay and `handle_hbone_request` dials the CONNECT `:authority` (exercised by `functional_mesh_ambient_egress_routes_a_to_b_over_hbone`). Operator contract: `docs/mesh.md` → "Sidecar Ingress Listeners" and "Inbound Relay Destination Guard".
- **Sidecar `ingress[]` REPLACES the service-port defaults (F6 §6.2, issue #3260).** Resolved CP-side into `MeshSlice.local_ingress_listeners` (gated by `FERRUM_MESH_SIDECAR_ENFORCED`, not dry-run; carrier `LocalIngressListenersCarrier`); `materialize_sidecar_ingress_listener_proxies` emits one `__mesh-ingress-{ns}-{svc}-{port}` HTTP route per HTTP-family listener and one `local_inbound_tcp_routes` relay per stream-family listener.
- **Fail closed on the DECLARED signal.** `MeshSlice.sidecar_ingress_declared` (own carrier `SidecarIngressDeclaredCarrier`) gates the materializer: once declared, the defaults are SKIPPED even if no listener resolved. Omitted `ingress` keeps defaults; a declared `ingress` — *including explicit `ingress: []`* — replaces them. The K8s translator sets `MeshSidecar.ingress_declared` on `spec.ingress` PRESENCE; `resolve_selected_sidecar_ingress` folds `ingress_declared || !ingress.is_empty()`. **`content_eq` MUST compare `sidecar_ingress_declared`** (it can flip while the listener list stays empty).
- Ingress resolution and the local-service anchor are **decoupled from egress-scope inheritance** (`select_applicable_sidecar` + `resolve_local_workloads`): an ingress-only Sidecar usually omits `spec.egress`.
- **Authz on the LISTENER port (security).** Ingress ids classify as `Inbound`, fold into `mesh_inbound_ports`, and match orig-dst AND authority on the listener port (`orig_dst_match_port == authority_port == listener port`). `MeshInboundPortGroup.is_ingress` stamps the selected listener port onto `RequestContext.mesh_inbound_listener_authz_port`, and `mesh_authz` authorizes on it — authorizing on the `defaultEndpoint` backend port would fail a DENY OPEN. An ingress id with no stamped listener port fails closed.
- **Endpoints and protocols.** Loopback and instance-IP (`0.0.0.0`/`::` → loopback) endpoints resolve for HTTP- and stream-family protocols; admissible `unix://` endpoints only for HTTP-family (still subject to the data-plane containment gates). Arbitrary IPs, `Udp`/`Unknown`, inadmissible Unix paths, and omitted `defaultEndpoint` (deserializes to empty) are dropped and stay in `deferred_fields`. The K8s translator uses `sidecar_ingress_app_protocol` (NOT `app_protocol`): `https` → `Http2`, stream tokens → their `AppProtocol`, MISSING → `Tcp`, UNRECOGNIZED → `Unknown` (never guessed); the service-port default path keeps its own `Unknown → HTTP` convention. The status writer uses the SAME shared predicates.
- **Carrier re-validation.** `admit_sidecar_ingress_listeners` re-checks every carried listener (`ResolvedIngressListener::endpoint_is_valid` plus owner/duplicate/dedicated-bind ownership), writes the surviving set onto `mesh.local_ingress_listeners`, and `prepare_*` preserves that admitted set (rejected entries cannot reappear for grouping/CONNECT). A carried Unix backend's protocol must agree with the derived h2c marker; stream-family ingress never widens onto a Unix or UDP lane. **The carried `protocol` has NO compatibility default** — do NOT re-add `default = Http`; an omitted carrier protocol decodes to inert `Unknown`.
- **Authenticated CONNECT remap.** `build_inbound_hbone_relay_proxy` consults `MeshConfig::resolve_sidecar_ingress_connect_relay` BEFORE the open-relay guard and remaps `pod-ip:<listener port>` to the listener's validated loopback `defaultEndpoint` under `__mesh-ingress-connect-relay` (`MESH_INGRESS_HBONE_RELAY_PROXY_ID`), stamping the declared listener port for authz. Byte-stream CONNECT only (never `connect-udp`); the authority host must be in `MeshConfig.local_workload_addresses` AND equal the accepted connection's concrete local IP; the port must resolve to EXACTLY ONE valid, owner-stamped, stream-family listener; anything else Denies. Once ingress is declared, unlisted ports Deny instead of falling through; only an omitted block returns `NotDeclared`. The marker back-projection is **`MeshTopology::Sidecar` ONLY** (an ungated marker would Deny every Ambient/Waypoint transparent relay). `handle_hbone_request` re-checks the EFFECTIVE destination via `sidecar_ingress_connect_relay_endpoint_matches` after the plugin chain. Ambient-only behaviors keyed on `MESH_INBOUND_HBONE_RELAY_PROXY_ID` do NOT apply to the ingress id. PeerAuthentication resolves on the `defaultEndpoint` app port on both shapes.
- **`bind` (issue #3266).** Omitted/unspecified bind keeps the shared `:15006` contract; a dedicated loopback bind is conflict-checked against Gateway/stream/mesh listener ownership and materialized as a real listener (`__mesh-ingress-bind:` proxies + `MeshConfig.sidecar_ingress_bind_overrides`). Dedicated-bind HTTP routes are exact-listener only and NEVER arm single-listener Service remap. Unix/hostname/`ip:port`/non-loopback binds, dedicated-bind+unix-endpoint, and port conflicts fail the WHOLE entry closed (removed from `local_ingress_listeners` too — no shared-capture or CONNECT fallback); `sidecar_ingress_declared` / `declared_ingress_http_ports` stay independent of that admission. `captureMode: NONE` is not honored.
- **Hop-limit guard (issue #6109).** `admit_sidecar_ingress_listeners` refuses a loopback `defaultEndpoint` naming any claimed gateway port (listener plan, every proxy `listen_port`, every dedicated bind this generation), and `materialize_sidecar_inbound_proxies` refuses a resolved inbound `targetPort` on that set. The mesh inbound hop no-increment exemption also requires the backend port to be absent from the published `hop_limit::GatewayListenerPorts` snapshot (no snapshot ⇒ increment).
- `validate_unique_listen_paths` exempts ingress siblings as direction code `2` (outbound 0, service inbound 1). Listener grouping is forward-derived from `local_ingress_listeners` (`mesh_ingress_listener_groups`), never parsed from ids.
- **Multi-port inbound disambiguation** is post-match (`select_mesh_inbound_port_route`, groups from `mesh_inbound_service_groups` over the `serde(skip)` `MeshConfig.local_inbound_services` view): inbound orig-dst (CONTAINER port) → request authority port (SERVICE port) → single-declared-port no-signal fall-through → **fail-closed 502** (`PortSignalUnavailable`/`PortNotMaterialized`; a present-but-unmatched orig-dst never falls through to the authority). A single-listener ingress group requires a present signal to match its listener port; a single-port default group serves no-signal requests but a present signal must name its service or container port. The operator-yield scan excludes only the service's OWN sibling ids.
- `accepted_local_addr` (the CONNECT remap's replica proof) is resolved ONLY on the INBOUND mesh listener and only for a wildcard bind — do NOT widen that gate to `mesh_direction.is_some()` (it would charge a `getsockname` to every captured egress accept).
- **Open-relay guard** (`inbound_hbone_relay_destination_decision` on the current `RequestEpoch` mesh snapshot): the authority must be a destination this terminator owns. Loopback / `localhost` is Sidecar-only; Ambient / waypoints / gateways refuse it. Ordinary TCP and UDP screen concrete DNS answers immediately before dial (mixed answers keep safe candidates; all-loopback fails closed); `ingress[]` remaps and EgressGateway external UDP skip that screen. A peerless CONNECT is rejected (403) before dialing.
- **Egress (outbound) — both captured topologies** (`materialize_mesh_outbound_proxies`, topology-aware): Ambient emits **HBONE** targets, Sidecar emits **SVID-mTLS** targets; a target carries exactly one transport tag.
  - **Ambient egress** → host-routed `/` routes with `mesh.hbone`-tagged targets (dial peer :15008, or the `mesh.hbone_port` tag from `FERRUM_MESH_EGRESS_HBONE_PORT`): `current_dispatch_hbone` (gated by `can_attempt_hbone_backend` = `HttpPool` dispatch + tag + `gateway_svid_bundle` + capability-registry) → `proxy_to_backend_hbone` → `HboneConnectionPool` (`hbone_pool.rs`); a `mesh.hbone=true` target that can't dispatch HBONE → **502 fail-closed** (`hbone_required`).
  - **Sidecar egress** → host-routed `/` routes with `mesh.mtls`-tagged targets (dial peer :15006, or the `mesh.mtls_port` tag from `FERRUM_MESH_EGRESS_MTLS_PORT`): `current_dispatch_mesh_mtls` (gated by `supports_mesh_mtls_backend` = `HttpPool` dispatch + tag + `gateway_svid_bundle`; **no capability registry** — `mesh.mtls` peers are slice-declared sidecars by construction) → `proxy_to_backend_mesh_mtls` → `MeshMtlsConnectionPool` (`mesh_mtls_pool.rs`, plain HTTP/2 over mutual TLS, ALPN `["h2"]`); a `mesh.mtls=true` target that can't dispatch → **502 fail-closed**. Do **NOT** tag Sidecar egress `mesh.hbone`.

## Scope And Policy Semantics

- Scope-aware resources must use the shared `policy_scope_applies_to_workload` / `scope_applies_to_workload` helpers. Do not fork predicates.
- Single-winner precedence (`WorkloadSelector` > `Namespace` > `MeshWide`) applies only where one effective setting is resolved, such as `PeerAuthentication` and `MeshProxyConfig`.
- `MeshPolicy` and `MeshRequestAuthentication` are additive after filtering. `MeshTelemetryResource` merges by section.
- Authorization evaluation is DENY first, then ALLOW. Any ALLOW rule with no match causes implicit deny.
- `RequestMatch` negative fields (`not_methods`, `not_paths`, `not_hosts`, `not_ports`, `not_port_patterns`) are conjunctive with positive fields in one rule. Do not split them into separate deny policies.
- **Outbound traffic policy: THREE precedence tiers, ONE resolver** (issue #3262; tiers, translation table, status and `ALLOW_ANY` scope: `docs/mesh.md` → "Sidecar Outbound Traffic Policy"). `MeshSlice::effective_outbound_traffic_policy` (workload-scoped `sidecar_outbound_traffic_policy` → mesh-wide `outbound_traffic_policy` → `FERRUM_MESH_OUTBOUND_TRAFFIC_POLICY`) is called by both `inject_mesh_global_plugins` (HTTP-family `mesh_outbound_registry`) and `refresh_mesh_outbound_enforcement` (stream-family `MeshOutboundEnforcement` slot), so the families never disagree about whether the gate is **armed**; do not re-derive the precedence at a call site. It shares the armed/disarmed DECISION ONLY, **not** the registry CONTENTS: on multicluster, HTTP injection runs against the MERGED `merged_slice` (remote workloads/services unioned in) while `refresh_mesh_outbound_enforcement` uses the UN-MERGED base slice, so a remote destination can be admitted on HTTP and refused on a stream connect (the fail-closed direction). Do not restate this as "the two lanes are identical".
  - The Sidecar tier is resolved CP-side by `resolve_applicable_sidecar_outbound_policy` (`select_applicable_sidecar` tier precedence, NO egress `inherits_defaults` walk), gated by `sidecar_enforced && !sidecar_dry_run` — the INGRESS gate, not the looser egress one. **One `select_applicable_sidecar` scan is shared** with `resolve_selected_sidecar_ingress` (same gate, tier precedence, `effective_labels`); egress keeps its own scan (`resolve_applicable_sidecar_egress` walks `inherits_defaults` under the looser gate). `select_applicable_sidecar` ranks a ROOT-namespace `workloadSelector` Sidecar ABOVE a selector-less default in the workload's own namespace — a deliberate security divergence from Istio that also decides egress enforcement since #3262, so re-deciding it is a security change, not a cleanup.
  - **`labels_ambiguous` must not relax the gate** (security): `effective_labels` is then only the INTERSECTION of same-SPIFFE workloads' label sets, so the resolver resolves each `policy_candidate_labels` set (empty unless ambiguous) and folds by `outbound_policy_strictness`, keeping the strictest (`Some(RegistryOnly) > None (inherit) > Some(AllowAny)`). The fold includes the intersection answer, so it only TIGHTENS; it is order-independent and cold-path bounded (`candidates × sidecars`). Do not "simplify" it back to the intersection alone.
  - `content_eq` MUST compare `sidecar_outbound_traffic_policy` (a mode-only edit would otherwise keep a stale gate live). Keep its ECDS carrier `SidecarOutboundTrafficPolicyCarrier` separate from `OutboundTrafficPolicyCarrier` (collapsing the tiers breaks the delete-falls-back-to-mesh-wide path).
  - K8s translation never rejects the resource (`classify_sidecar_outbound_traffic_policy`, shared with `istio_status::sidecar_status` so enforced and reported never diverge): a present object with omitted/null `mode` → `AllowAny`, no deferral; omitted block → inherit; unrecognized/non-string `mode`, a non-object block (explicit `outboundTrafficPolicy: null` included), or a present NON-NULL `egressProxy` → `RegistryOnly` + a `deferred_fields` reason; explicit `egressProxy: null` is absent. Do NOT "fix" anything by returning `Err` — `translate_k8s_objects_collecting_skips` DROPS a rejected Sidecar, which drops its `egress` narrowing and WIDENS the slice service view and derived registry. Report degradation in `deferred_fields` plus a per-occurrence `debug!` and exactly ONE process-lifetime `warn!`; do not reintroduce a per-resource `warn!` (translation re-runs every reconcile/full sync) or add per-resource dedupe state.
  - `status.ferrum.translation.outbound_traffic_policy_enforced` is resource-local: ONLY "translatable policy present AND the rollout gate is on", NOT "selected for a workload" (a `workloadSelector` matching nothing still reports `true`); a REJECTED Sidecar reports `false`.
  - `ALLOW_ANY` relaxes ONLY the registry gate; egress scope, `mesh_authz`, PeerAuthentication/mTLS and peer-SVID pinning, the HBONE/mesh-mTLS open-relay guard, DNS/raw-IP strict indexes, and topology transport gates still apply.
- Istio empty-rule translation must preserve action semantics: ALLOW with no `rules` is allow-nothing via a never-matching rule; DENY and AUDIT with no `rules` are no-ops.
- NodeWaypoint per-pod policy scoping (`per_pod_policy_scoping`) is resolved per request/stream from `node_waypoint_policy_scope`. The HTTP/HBONE accept path populates it from the resolver (`proxy/mod.rs`); the TCP stream accept loop resolves the accepted socket's `SO_COOKIE` through `resolve_node_waypoint_stream_scope` (`proxy/tcp_proxy.rs`), and UDP/DTLS sessions resolve it from ingress-interface + registry attribution (`proxy/node_waypoint_udp_identity.rs`, stamped in `proxy/udp_proxy.rs`). An unresolved scope stamps `mesh_authz.scope_missing`: `mesh_authz` rejects the stream while any enforcing namespace/selector-scoped policy is loaded and falls through to mesh-wide-only evaluation otherwise. Never resolve a missing scope to mesh-wide when scoped policy exists, and keep the identity and scope from the same slice generation. Keep this in sync with `docs/mesh.md`'s NodeWaypoint stream-scoping sections.
- Mesh authz `source.ip`/`ipBlocks` uses `direct_client_ip` (immediate peer) and `remote.ip`/`remoteIpBlocks` uses `client_ip` (trusted XFF/PROXY-resolved) on both the HTTP and stream paths. IP-block matchers fail closed when the typed IP evidence is absent.
- **`when:` conditions cover the complete documented Istio key set and distinguish ABSENT from UNSOURCEABLE** (issue #3236; key matrix, value grammars, bounds: `docs/mesh.md` → "Condition keys"). `classify_mesh_condition_key` / `MeshConditionKeyKind` (`src/modes/mesh/config.rs`) is the one classification and `validate_mesh_condition` the one validator behind all three surfaces (K8s translator `condition_match`, `validate_mesh_config`, `mesh_authz`'s `validate_policy_ip_inputs`), with field-specific diagnostics. Dynamic header/claim keys follow Istio `validateMapKey` only — first `[` + final `]` around a non-empty interior, NO `HeaderName` parse or interior-bracket/whitespace restriction. `:authority`, `:method`, `:path`, `:scheme` source typed `RequestContext` facts; other unmaterializable interiors stay absent.
  - A sourceable attribute this request lacks follows ordinary Istio `values` / `notValues`. An attribute the path can NEVER source (`condition_kind_is_sourceable`: an HTTP-only key on L4, i.e. `MeshAuthzRequest.protocol == MeshAuthzProtocol::L4`; a source/remote/destination IP or destination port with no transport evidence; any `experimental.envoy.filters.*` key) fails closed BOTH ways: DENY ignores the field and still matches, ALLOW/AUDIT never match. Do NOT re-express unsourceable as missing (a `notValues`-only ALLOW would grant every raw connection), and keep such keys ADMITTED at translation (rejecting drops the whole AuthorizationPolicy — fail-OPEN for a DENY).
  - **Value grammar is PER KEY** (`condition_scalar_value_matches` classifies once per `when[]` entry): IP-valued keys are CIDR containment; `source.serviceAccount` is EXACT `<namespace>/<service-account>`, a bare `<service-account>` resolves against the OWNING `MeshPolicy.namespace` (threaded `evaluate_mesh_authorization_policies` → `rule_matches` → `matches_conditions`, compared in place with no per-candidate `String`), and any `*` is rejected at admission; `source.namespace` uses `wildcard_match` (every `*` is a wildcard, per Istio `srcNamespaceGenerator`); `source.trustDomain` keeps the presence/prefix/suffix matcher ONLY because `validate_mesh_condition` first enforces `CheckTrustDomainValues`; everything else is `matcher.StringMatcherWithPrefix` (a mid-string `*` is literal). `source.serviceAccount` has Istio's 16-entry / 320-byte caps on BOTH `values` and `notValues`; every other key the common 64-condition / 256-entry / 512-byte caps.
  - `MeshAuthzRequest::default()` is deliberately `L4`; both production callers set `protocol` explicitly. A mesh CONNECT relay (byte-stream or datagram HBONE, any inbound listener, route hit or miss) is authorized as `L4` with no method/path/host/headers/request principal: it is marked via the set-only `RequestContext::mark_hbone_connect_relay` in `hbone_proxy::tag_*request_metadata`, and `mesh_authz` refuses a matched CUSTOM delegation on it. Never judge `to.operation` / `request.*` against the CONNECT's own pseudo-headers.
  - HTTP `destination.ip` comes from `orig_dst` before `RequestContext::destination_ip`. Stream authz reads `StreamConnectionContext::connection_destination_*` (capture/trusted-PROXY evidence first, may fall back to the accepted socket local address); L4 `stream_match.destinationSubnets` reads ONLY `StreamConnectionContext::destination_*`, so a listener bind address never becomes original-destination routing evidence. None of these comes from a header; the HTTP wildcard-bind `getsockname()`/`Connection::local_ip()` fallback is gated on `OperatingMode::Mesh`.

## Mesh Plugin Injection

- `inject_mesh_global_plugins()` auto-injects reserved-ID globals on slice apply: `__mesh_spiffe_identity` priority 940, `__mesh_authz` priority 2075, `__mesh_workload_metrics`, `__mesh_request_auth` only when JWT rules exist, `__mesh_access_log` (a `stdout_logging` instance carrying the Telemetry `accessLogging` filter), `__mesh_outbound_registry` (only when an outbound listener exists and the effective policy is REGISTRY_ONLY), `__mesh_bpf_metrics` (NodeWaypoint only), and `__mesh_request_auth_refused` (plus `__mesh_request_auth_refused_<n>` partitions) instead of `__mesh_request_auth` when an applicable RequestAuthentication was refused in translation.

When `transparent_inbound_capture_requested()` is true, mesh injection forces the reserved `__mesh_authz` instance even when another global `mesh_authz` is present.
- Mesh plugin injection must preserve normal plugin lifecycle ordering and transaction logging.

## PeerAuthentication And TLS Reload

- By default, inbound mesh mTLS mode resolves once from the initial slice.
- When all three `FERRUM_GATEWAY_SVID_*` paths are set, the inbound mTLS/HBONE listener uses a SPIFFE client-cert verifier that validates the peer SAN's trust domain against the gateway SVID local bundle plus slice federated bundles; without SVID material it falls back to chain-only verification over `FERRUM_FRONTEND_TLS_CLIENT_CA_BUNDLE_PATH`. STRICT requires a peer certificate. For non-egress topologies, PERMISSIVE with a trust anchor verifies an offered certificate while allowing cert-less peers; with no anchor the resolver selects the explicit no-trust-anchor posture. EgressGateway PERMISSIVE resolves to required client authentication with an anchor and to `EgressGatewayNoTrustAnchor` without one, which refuses to build the egress mTLS listener (fail closed) rather than admit cert-less peers. The HBONE baggage trust-gate rests on this verified identity.
- Gateway SVID material also backs the inbound listener's **server identity** when no explicit `FERRUM_FRONTEND_TLS_CERT_PATH`/`KEY_PATH` is set (`load_mesh_frontend_server_identity` resolves the SVID leaf+key live from the slot as the server cert via `svid_rotating_mesh_server_identity`): a SVID-only mesh serves mTLS inbound instead of falling open to plaintext under PERMISSIVE. Explicit frontend TLS still takes precedence.
- The gateway SVID slot is fed by **either** configured material (`FERRUM_GATEWAY_SVID_*`, watched + rotated by `identity::svid_source_watch`: file/`file://` sources poll every second, provider sources use their configured secret-refresh cadence, inline PEM stays static until configuration reload) **or** a **CA backend** (`FERRUM_MESH_CA_BACKEND=spire|internal`) via `start_mesh_ca_backend_svid_source` (`src/modes/mesh`): `spire` fetches the gateway's own SVID from the SPIRE Agent Workload API (`FERRUM_MESH_SPIRE_AGENT_SOCKET`) reusing the identity `fetch_loop` (`SvidFetchHandle::from_slot` + `with_installer`); `internal` self-issues from the dev-only `bootstrap_dev_root` `InternalCa`. Either way it live-rotates into the **same** `gateway_svid_bundle` slot (and publishes to a live inbound peer-verifier slot), so the inbound `SvidServerCertResolver`, the SPIFFE peer verifier, and the backend pools pick up rotations with no restart. Startup blocks on the first SVID (`MESH_CA_INITIAL_SVID_TIMEOUT`, 30s; fail-closed) so the inbound listener never binds identity-less; a CA backend REQUIRES `FERRUM_MESH_WORKLOAD_SPIFFE_ID` (the fetched identity is pinned to it); explicit `FERRUM_GATEWAY_SVID_*` material takes precedence when both are configured. Do NOT add a second source-of-truth slot — feed `gateway_svid_bundle`.
- Runtime inbound mTLS fail-closed (`enforce_mesh_inbound_fail_closed` + `decide_mesh_inbound_fail_closed`, issue #1523) runs at the startup TLS-setup path **and on PeerAuthentication live reload** (`plan_mesh_inbound_tls_reload`), with two deliberately different severities:
  - A listener that would serve **plaintext** (resolved `ServerConfig` `None` — PeerAuthentication DISABLE or no usable server identity) is **refused under `FERRUM_MESH_PRODUCTION_MODE=true`**; **dev** allows it with a loud warning. An explicit DISABLE, or a no-identity posture already acknowledged by the config-time `FERRUM_MESH_ALLOW_NO_CA` gate, is intentional, so the runtime gate does not re-consult the opt-out.
  - A **configured-but-unloadable SVID verifier** (all three `FERRUM_GATEWAY_SVID_*` named but `build_mesh_inbound_spiffe_slot` returned `None` while the listener serves TLS) is **fatal regardless of production** (mirrors the hard error a broken SVID cert/key gets in `load_mesh_frontend_server_identity`; `decide_*` is NOT consulted).
  - At reload, "refuse" means reject the slice and keep the last-good mTLS config in its entirety (never crash a live data plane, matching the failed-`ServerConfig`-rebuild contract below). `FERRUM_MESH_PRODUCTION_MODE` is read once at startup and threaded through `MeshInboundTlsReloadState.production` (process-fixed; no per-apply env read). EastWestGateway (SNI passthrough, no termination listener) is exempt.
- The mesh `RequestAuthentication` (`jwks_auth`) plugin requires the JWT `exp` claim by default (`FERRUM_MESH_REQUEST_AUTH_REQUIRE_EXP=true`); operators may relax it. Expiry validation (rejecting present-but-expired `exp`) is always on.
- On NodeWaypoint/ServiceWaypoint, RequestAuthentication follows the DESTINATION workload (issue #6670): waypoint slices carry destination-selecting resources (`MeshSlice::from_gateway_config`, CP `filter_mesh_config_to_request`); `scope_request_auth_to_node_waypoint_destinations` attaches a proxy-group `jwks_auth` (`__mesh_request_auth_dst_*`, replacing the global instance) to NodeWaypoint Service routes whose destination set differs from the waypoint's own, resolved through `mesh_authz`'s `DestinationPolicyScopeIndex`; refused destination resources refuse those routes via the scoped `__mesh_request_auth_refused` trigger and refuse L4 relays in `mesh_authz` (`refused_request_auth_relay_rejection`). Never re-match destination resources against the waypoint's own labels.
- With `FERRUM_MESH_PEER_AUTH_LIVE_RELOAD_ENABLED=true`, only resolved mTLS mode, frontend client CA verifier, and the lock-free SPIFFE SVID bundle slot (federated trust domains) may hot-swap on slice apply.
- Frontend cert/key paths remain restart-required inputs for mesh peer auth reload.
- Coverage includes mesh HTTP/HBONE termination listeners and mesh-shared TCP+TLS stream listeners. Terminating UDP+DTLS is OWNER-SCOPED (issue #3858, below), not part of this fanout. Opaque datagram-over-mesh UDP stays opaque. PeerAuthentication reload must never mutate ordinary `FERRUM_DTLS_*` servers, active or future.
- `apply_mesh_inbound_tls_reload` publishes swapped `ServerConfig` into HBONE and the shared TCP+TLS stream slot ONLY. It must never call a process-wide `DtlsServer` fanout: generated NodeWaypoint listeners and ordinary operator `FERRUM_DTLS_*` listeners share one `StreamListenerManager`, so a fanout from that path live-swaps operator-owned listeners a mesh slice has nothing to do with (the #3829 policy-confusion vulnerability). Deleting the reload outright is the opposite failure — a generated `dtls` listener would keep the posture it started with across permissive→strict or a client-CA rotation.
- **DTLS ownership is explicit and listener-scoped** (issue #3858): `DtlsListenerOwner::{Operator, MeshNodeWaypoint{listener_key}}` on every `ListenerHandle`, two SEPARATE accepted generation slots sharing one publish lock, and two separate publish entry points (`publish_frontend_dtls_generation` for operator listeners, `publish_mesh_node_waypoint_dtls_generation` for generated ones). A collector applies only its own owner's generation. `swap_active_dtls_frontend_configs` is deleted; do not reintroduce a process-wide DTLS fanout. Ordinary database/file/DP `FERRUM_DTLS_*` behavior and default limits are unchanged.
  - `build_node_waypoint_dtls_owner_configs` derives each generated route's complete config from the dedicated `FERRUM_DTLS_*` identity + that route's effective `PeerAuthentication` workload/service scope (most-restrictive across the Service's backing workloads; `Strict` ⇒ client CA required, `Permissive`/`Disable` ⇒ none) + the accepted client-CA/CRL snapshot, and runs BEFORE `update_mesh_config`, so a malformed CA/CRL, verifier build failure, invalid client-side mode, or a `Strict` route with no client CA rejects the COMPLETE candidate slice and retains both owners' last-good routing and DTLS serving generation. Do not omit just the unservable `Strict` listener and accept the rest (an already-running Permissive listener would keep serving across a Permissive-to-Strict change).
  - The accepted map is stored before the swap so a late-created listener converges; an accepted EMPTY map is a positive withdrawal statement.
- A failed inbound `ServerConfig` rebuild (or a client-CA-bundle snapshot read failure) is computed before proxy-config apply and **rejects the whole slice**, keeping the last good config in its entirety (the one `ServerConfig` backs both HTTP/HBONE and the shared TCP+TLS slot, so no authz/policy/ServiceEntry/endpoint update from that slice applies either) — fail-closed. Do not reword the `ServerConfig`/snapshot warns back to a path-local "keeping previous TLS config" framing.
- `Disable` is rejected for Ambient and EgressGateway slice updates and keeps the last good config.

## DestinationRule And Materialization

- DestinationRule `loadBalancer.simple = PASSTHROUGH` materializes `LoadBalancerAlgorithm::Passthrough`. Captured orig-dst (`SO_ORIGINAL_DST`) that matches a healthy subset∩port pool target is dialed (bypassing LB). Unmatched, absent, or ejected orig-dst falls back to round-robin with a warning (`PASSTHROUGH: original destination unmatched/absent, falling back to round-robin`). Do not document PASSTHROUGH as "approximates to round-robin". `MAGLEV` is a hard reject at translation.
- DestinationRule `connectionPool.tcp.connectTimeout` lands on `Upstream.port_overrides[port].connect_timeout_ms` and is enforced by HTTP/H2/H3, gRPC, TCP, and HBONE dispatch.
- Port-level `loadBalancer` and `outlierDetection` land on the same override slot and use isolated per-port LB counters/hash rings and passive thresholds for HTTP-family, gRPC, WebSocket, and HBONE.
- `connectionPool.http.maxRequestsPerConnection` stays parsed/validated but deferred at EVERY scope — translator and status list only it (all scopes) as deferred for this family. `idleTimeout`, `http2MaxRequests`, `maxConcurrentStreams`, `h2UpgradePolicy`, `maxRetries`, and `http1MaxPendingRequests` are carried at top-level, `portLevelSettings`, and subset scope with field-level precedence **per-port > selected subset > top-level** (`docs/mesh.md` → "Port-level and subset policy"); `SubsetTrafficPolicy` / `ResolvedSubsetTrafficPolicy` preserve all of them, and `GatewayConfig::resolve_dispatch_port_overrides` overlays the exact selected subset onto a per-proxy inherited fallback. Initial and rotated targets resolve effective policy from the immutable proxy snapshot. Invalid values fail closed with field-specific, value-redacted diagnostics.
  - `h2UpgradePolicy` is plain-HTTP-only; `DoNotUpgrade` restricts reqwest ALPN to `http/1.1`; all HTTP-family pool keys include `upstream_subset` (reqwest also its `h1` discriminator and idle `rcfg` segment). `maxRetries` caps only an existing per-request retry policy, never synthesizes retries.
  - `http1MaxPendingRequests` is an honestly reinterpreted concurrent-in-flight-H1 cap keyed by stable logical destination (namespace, logical upstream/Service identity, optional Service UID, DR policy port, selected subset), not the endpoint host; its sharded RAII guard releases on every success/error/deadline/cancellation/retry exit.
  - `idleTimeout` → `pool_idle_timeout_seconds`. `http2MaxRequests` is the destination-wide active-request budget scoped `(namespace, logical destination, policy port, selected subset)`, separate from per-connection `maxConcurrentStreams` (`h2_max_concurrent_streams`), which projects onto direct-H2/native-gRPC builders and those pools' keys (reqwest H2 has no equivalent knob — a documented transport caveat, not a deferred field).
- Dispatch projects port overrides through `resolve_effective_proxy_for_target()` onto the owned `Proxy` clone; direct H2 and gRPC builders consume H2 caps through `max_concurrent_streams` and `initial_max_send_streams`.
- **INHERITED top-level `connectionPool.http` fallback (#1806, extended to subsets; #3735 for idleTimeout/http2MaxRequests)**: `Upstream.dispatch_port_override_fallback` (`#[serde(default, skip)]` derived) is the cold-path carrier for the inheritable top-level HTTP overlay. Every applied HTTP field (`h2UpgradePolicy`/`maxRetries`/`http1MaxPendingRequests`/`idleTimeout`/`http2MaxRequests`/`maxConcurrentStreams`) accumulates there for EVERY upstream via `apply_connection_pool_http_to_port_override`, so a selected subset can overlay them without losing source-tier identity; explicit `portLevelSettings` entries remain on `port_overrides` and win at dispatch.
  - `resolve_dispatch_port_overrides` projects the fallback onto `Proxy.dispatch_port_override_fallback` (`#[serde(skip)]`), overlaying the EXACT effective selected subset's `ResolvedSubsetTrafficPolicy` (`dispatch_port_override_fallback_for_selected_subset`) into a proxy-local derived value — it never mutates the shared upstream and never consults a sibling subset, so sibling subsets and unmatched proxies cannot leak policy.
  - `resolve_effective_proxy_for_target` and `cap_proxy_retry_for_target` consult the fallback ONLY when the selected target's POLICY port (`target.dispatch_policy_port()`) has no explicit field on `dispatch_port_overrides`. The fallback is TOP-LEVEL + selected-subset ONLY — `dispatch_port_override_fallback_from_upstream` does NOT fold per-port entries into it (folding cross-leaks between ports on a multi-port upstream).
  - **Named `targetPort` is covered**: mesh SD targets whose resolved workload dial port differs from the declared Service port carry the owning Service port in the serde-skipped `UpstreamTarget.service_port_policy_key`, so dispatch keys DR policy by `dispatch_policy_port()` while still dialing `target.port` (`docs/mesh.md` → "Port-level and subset policy"). This is runtime-by-selected-port application of the overlay, NOT runtime-resolved target materialization (the rejected outbound-SD rework — see the per-port upstream bullet below).
  - Immediate route-TABLE rebuild on a DR-only fallback/TLS/per-port projection edit (#3243 / #1826): `ProxyState::delta_routes_changed` and the empty-delta publish path compare the `#[serde(skip)]` DR-derived proxy fields (`dispatch_port_overrides`, `dispatch_port_override_fallback`, `resolved_tls`, mesh stream-relay dispatch maps) so route-held `Arc<Proxy>` values cannot stay stale.
- **HTTP/3 frontend effective-proxy coverage (#1806/#2020)**: the H3→HTTP plain bridge (`src/http3/cross_protocol.rs` `dispatch_plain`) resolves `resolve_effective_proxy_for_target` per attempt INSIDE its retry loop (an entry-level resolution backs the port-independent retry/buffering decisions), so the per-port effective-proxy overrides (idleTimeout/http2MaxRequests/connectTimeout/TLS/h2UpgradePolicy-ALPN + the SD fallback) apply on that reqwest bridge — `get_client` builds the client from the effective proxy and `build_plain_request_builder` reads its `backend_connect_timeout_ms` — and its local dispatch-policy rejects (per-port backend-TLS-SNI incompatibility → 502; `http1MaxPendingRequests` pending cap → 503) run BEFORE backend admission per attempt, matching H1/H2 ordering.
  - The standalone H3 frontend (`src/http3/server.rs`) applies the selected-target pipeline across ALL FOUR flavors: `cap_proxy_retry_for_target` runs right after target selection (so a DR `maxRetries` cap governs the H3 retry loops and the retry-dependent buffering / native-H3-suppression decisions); the first target's effective proxy backs the native-H3/streaming dispatch decisions; `ctx.matched_proxy` carries the retry-capped BASE proxy (H1/H2 parity — per-port TLS/timeouts are dispatch-time-only, never plugin-visible); and every loop that can rotate retry targets — the buffered native-H3 retry loop, the H3→plain and H3→gRPC bridges, and the H3 WebSocket dial loop — re-resolves the effective proxy per attempt from the capped UNRESOLVED base proxy, so a rotated target never inherits the first target's port-level TLS/SNI/H1 policy.
  - Mesh capture is TCP/UDP-only, so the H3 FRONTEND is never a mesh capture listener; it IS a mesh EGRESS surface for gRPC since #3284 (see `proxy-protocols.md` → "HTTP/3 And gRPC"). Keep `docs/mesh.md` → "Port-level and subset policy" (per-attempt resolution) and the textual pins in `tests/unit/gateway_core/http3_selected_target_policy_tests.rs` in sync.
- `http_max_requests_per_connection` is a legacy carrier only; new DR translation does not populate or consume it.
- `connectionPool.tcp.maxConnections` and `tcpKeepalive` land on `max_connections` and `tcp_keepalive`. `maxConnections` is enforced by EVERY transport whose physical connection lifecycle Ferrum owns, against ONE shared `backend_conn_limit::BackendConnectionLimiter` on `ProxyState.backend_conn_limit` keyed `(host, DestinationRule policy port)`: stream-family (TCP/TCP+TLS) dispatch; WebSocket dispatch (H1/H2 in `proxy/mod.rs`, H3 in `http3/websocket.rs`; an RAII `BackendConnectionGuard` per session, over-cap upgrade → 503); the pooled multiplexed transports (below); and reqwest (HTTP/1.1 AND ALPN-negotiated HTTP/2) at reqwest's own connector. Per-transport contract: `docs/mesh.md` → "DestinationRule `maxConnections` enforcement scope"; code: `src/backend_conn_limit.rs`.
- `tcpKeepalive` is enforced by stream-family dispatch AND the socket-owning H2-family pools (direct-H2 `http2_pool`, `grpc_proxy`, HBONE `hbone_pool`, mesh-mTLS `mesh_mtls_pool`) via `socket_opts::apply_pooled_tcp_keepalive` at connection creation: direct-H2/gRPC key the override by the dial `backend_port`; HBONE/mesh-mTLS by the destination's APP/service port (NOT `:15008`/`:15006`), applied inside the shared `dial_h2_connect_sender` (so HBONE and Sidecar egress, raw-TCP on both transports, and WebSocket over both are covered). Per-port DR override wins; global `pool_config.tcp_keepalive_seconds` is the fallback. Keepalive is NOT a pool-key field (`proxy-protocols.md`), so on shared/pooled HTTP-family connections the FIRST materializing dispatcher fixes it. Residuals: the reqwest HTTP pool keeps the global seconds-only keepalive; QUIC keep-alive is N/A.
- `maxConnections` on the pooled multiplexed transports (direct H2, gRPC, native H3, HBONE, mesh-mTLS) is a PHYSICAL-connection bound, never a request-concurrency counter:
  - The slot is reserved only when a NEW connection is constructed (after a cache miss) and is owned by that connection's driver task (hyper/`h2` driver for the H2-family pools; the `h3` driver owning the `h3_quinn::Connection` for native H3). Do NOT park it on the pooled `H3PooledConnection`/`Http2Sender` handle — an evicted or force-drained handle can drop while the socket is still open, letting a replacement exceed the cap. Create failure drops it; idle eviction / unhealthy replace / `clear()` / `force_drain_svid_generation` / reload-update-delete / shutdown end the driver. The reservation is cloned per DNS candidate so a failed candidate frees its clone. Streams stay unbounded (`h2_max_concurrent_streams` is the stream knob).
  - An over-cap create is a pre-wire, backend-health-NEUTRAL `ErrorClass::BackendConnectionLimit` (`Http2PoolError::MaxConnectionsExceeded`, `GrpcBackendUnavailableKind::MaxConnections`, `HbonePoolError::MaxConnectionsExceeded`, and for native H3 a typed `BackendConnectionLimitExceeded` in the `anyhow` source chain — a plain `anyhow!` classifies `RequestError`, which `request_reached_wire` treats as POST-wire). Do NOT downgrade it to `ConnectionPoolError`, a backend-health signal (CB failure, passive-health failure, LB penalty, adaptive-concurrency shrink would eject a healthy destination). `BackendConnectionLimit` is in `client_side_no_backend_signal` AND pre-wire (rotate targets + `cb.record_neutral()`); retry loops' per-attempt breaker records stay neutral too.
  - direct-H2, gRPC and native H3 first fall back to an already-established shard, so a cap below `http2_connections_per_host` / `http3_connections_per_backend` converges on `cap` connections. Only a cap refusal takes that fallback (`pool::is_max_connections_refusal`: the creator's typed chain or a coalesced waiter's `SharedPoolCreateKind::MaxConnections`), and only ALREADY-CACHED healthy shards are reused. A cap refusal is NOT capability evidence: H2/H3 capability probes keep the prior classification. HBONE/mesh-mTLS key the lane by the destination's APP/service policy port.
  - reqwest (H1 and H2) is admitted in its CONNECTOR via the vendored `ClientBuilder::connection_admission` hook (`docs/upstream-reqwest-patches/003-connection-admission-hook/`); reuse and H2 streams never reach it, and the token is owned by the connection, so an idle retained socket STILL holds its slot — never a request-lifetime slot. One hook across every `reqwest::Client` means divergent pool keys (TLS material, `rcfg`, forced-H1 ALPN, subset) for one destination share ONE ceiling. Dispatch binds the lane (dial `(host, port)` → policy port + cap) with an RAII `ReqwestLaneLease` held across `send()`, only when a cap is configured (a removed cap drains with its requests; the retry path leases its own, possibly rotated, target). `maxConnections` is NOT reqwest pool-key material, so conflicting caps for one dial address resolve to the STRICTEST live lane (order-independent, fail-closed) — do not replace that with last-writer-wins global state.
- `maxConnections` exhaustion returns `StreamSetupKind::BackendMaxConnectionsExceeded` on stream-family, a 503 (`rejection_phase=backend_max_connections`) on WebSocket, a pre-wire, health-neutral `ErrorClass::BackendConnectionLimit` on the pooled transports, and a `DispatchPolicyRejected` 503 (backend-health neutral) on reqwest, recognized from the connector error chain via `backend_conn_limit::is_backend_connection_limit_error`; keepalive setsockopt failures warn and continue.
- **Sidecar mesh-mTLS pool width is pressure-gated, not eager** (issue #5043). `MeshMtlsConnectionPool` starts every destination at ONE HTTP/2 connection and widens only while the least-loaded connection has ≥ `MESH_MTLS_GROWTH_PENDING_PER_CONNECTION` (8) requests awaiting response heads AND the pool is below `http2_connections_per_host` (`FERRUM_POOL_HTTP2_CONNECTIONS_PER_HOST`). Load is `MeshMtlsSender::pending_requests`, a shared counter settled by the `PendingResponse` wrapper on head arrival, hyper error, OR dropped future — hyper 1.x `SendRequest::poll_ready` is always Ready, so do not go back to `ready()`-probing. Checkouts take the least-pending connection, ties to the lowest index (`select_least_pending`; a stale entry on the read path is a deliberate miss so the write path prunes). Growth uses `SharedCreationSlot::try_claim` (never queues behind a cold-path creator) through the SAME `dial_and_publish` as the cold path (so `maxConnections` admission, SVID/CRL pinning, retirement and rotation checks all apply); a failed growth dial backs off `MESH_MTLS_GROWTH_BACKOFF_SECS` (10 s) per key while traffic keeps flowing on the existing connection.
- **HBONE pool width follows open CONNECT streams and the peer's stream cap** (issue #5465). In `HboneConnectionPool` (Ambient/Waypoint egress: pooled HTTP-family requests AND pooled raw-TCP CONNECT tunnels), raw `h2` `SendRequest::clone().ready()` is always Ready — do not go back to `ready()`-probing for selection. Load is `HboneConnectionLoad` on `MeshH2Transport`: `active_streams` is leased in `open_h2_connect_stream` / `open_h2_ws_connect_stream` from the `send_request` (a CONNECT parked pending-open counts) and released by the `HboneStreamLease` owned by `H2ConnectTunnel`; `peer_max_streams` is sampled from `SendRequest::current_max_send_streams()` on every CONNECT response (which cannot precede the peer's SETTINGS), never on the checkout scan, so the read path stays lock-free. `select_least_loaded` picks the fewest open streams among live entries under their cap, ties to the lowest index; a saturated entry is skipped while a sibling has room.
  - Growth: least-loaded ≥ `HBONE_GROWTH_ACTIVE_STREAMS_PER_CONNECTION` (8) with room → opportunistic `try_grow_sender` (`SharedCreationSlot::try_claim`, `HBONE_GROWTH_BACKOFF_SECS` = 10 s on failure, same `dial_and_publish` as the cold path); every live entry saturated with room → the coalesced cold path dials; saturated at `http2_connections_per_host` → the tunnel queues pending-open on the least-loaded connection, bounded by the caller's connect timeout (a burst above `cap × width` drains instead of failing; logged at debug, not a new error). Regression: `tests/integration/hbone_pool_width_tests.rs`.
- TCP/UDP/DTLS stream paths engage per-port **LB algorithm** and **`localityLbSetting`** at selection time when all upstream targets share a single port (`initial_dispatch_port_override` non-zero); per-port `connectTimeout`, `maxConnections`, and `tcpKeepalive` also apply. Active/passive health context is threaded into stream target selection unconditionally; the `maxEjectionPercent` cap resolves at the per-port tier only under that same single-port condition and at the upstream/global tiers otherwise. Outlier thresholds are not recorded on stream paths themselves (raw relay sessions carry no response status), so stream-only traffic does not create new passive ejections, but active health and existing passive ejections are honored.
- Phantom DestinationRule ports are skipped with a warning.
- Materialized per-port outbound upstreams (`__mesh-out-upstream-{ns}-{name}-{port}`) accept `portLevelSettings` ONLY for their owning Service port (forward-derived `outbound_upstream_owner_port` map in `apply_destination_rules` — never parse ids) and FAN that one entry OUT to every distinct target dial port: targets dial the per-workload resolved `targetPort` (numeric or **named**, which can resolve differently across replicas), dispatch keys overrides by the LB-selected target's port, and every target is owned by the one Service port by construction. Do NOT move these upstreams to runtime service discovery for this: SD-resolved targets are absent from `Upstream.targets`, so the capability registry never probes them and `retain_keys` evicts their records — every Ambient HBONE dial would 502 `hbone_required`; SD also drops per-pod one-to-one identity pinning, local-cluster filtering, and slice-atomic endpoint freshness (30 s poll + delta-gated reconcile).
- Admin API POST/PUT of `Upstream.port_overrides` is rejected; DestinationRule is canonical.
- `materialize_east_west_gateway_proxies()` creates SNI-passthrough TCP proxies only for east-west topology.
- East-west alias labels (`cross_cluster_service_sni_label`) key on the port number plus DECLARED L4 transport (`p<port>` / `p<port>-udp`), never `protocol_overrides` and never sibling ports. More than one declared port on one alias (HTTP+raw TCP, K8s TCP+SCTP, duplicate entries) is skipped cross-cluster on BOTH ends with a rate-limited warn; no source (K8s included) drops the Service for it.
- `materialize_egress_gateway_proxies()` creates HTTP-family proxies from `mesh_external` ServiceEntries only for egress topology.
- **DestinationRule lookup-tier evidence must AGREE between CP admission and DP materialization (#2465/#2469).** `policy_target_service_ref` (slice build) and `MaterializationTierScope::eligible_tier` (`apply_destination_rules`) resolve the destination host's owner through ONE shared helper, `slice::destination_host_owner`: `.svc[.cluster-domain]` syntax → inventory-confirmed two-label `name.namespace` → `service_entry_host_owner` (single owner; cross-namespace duplicates and an empty declaring namespace ⇒ `Ambiguous` ⇒ NO service tier). Istio short-name self-scoping reads the POLICY's namespace, so it stays in `policy_target_service_ref` alone. The DP builds its identity index from the slice's already-narrowed `services`, the CP from the full inventory; that is the one intended divergence.
  - Both the SOURCES and their ORDER are load-bearing: (a) a resolved host owner is AUTHORITATIVE for the service tier — do NOT widen it with a conflicting `Upstream.namespace` (`by_upstream.min(by_host)` lets an operator-authored / multi-target upstream in `evil` manufacture service-tier policy for a host owned by `beta`); (b) keep the upstream-namespace fallback ONLY when host ownership cannot be resolved (`build_egress_upstream` stamps every ServiceEntry-derived EgressGateway upstream with the GATEWAY's namespace; the host-owner arm recovers the declaring ServiceEntry for external hosts so owner-authored `trafficPolicy` still applies); (c) do NOT hoist the ServiceEntry arm above the `.svc`/inventory arms (a carrier-supplied ServiceEntry declaring `reviews.beta[.svc…]` would transfer ownership of `beta`'s service to its own namespace).
  - Missing/empty/whitespace root provenance fails closed (refuse Unscoped; keep independently provable client/service tiers; never restore pre-#2469 permissive bucketing). Re-stamping the synthesized upstream's namespace is the wrong repair — `Upstream.namespace` participates in `FERRUM_NAMESPACE` filtering and per-namespace uniqueness.
  - **Per-host LOOKUP is not per-host APPLICATION**: every field a winning rule projects lands on the shared `Upstream`, so `apply_destination_rules` REFUSES (returns `Err` → slice rejected → last-good retained; no mutation) an upstream whose match hosts resolve to DIFFERENT winning rule SETS. Do NOT "fix" that by merging them in sorted order (order-dependent cross-service policy transfer). Hosts with NO winner do not participate, so single-destination, multi-port, and static-fallback-target upstreams are unaffected.
  - The ambiguity-warning dedup map (`DESTINATION_RULE_AMBIGUITY_REPORTED`) is keyed by the SUBSCRIBER namespace and must stay bounded by namespace count, per-namespace count-values, **and retained key bytes** (`DESTINATION_RULE_AMBIGUITY_NAMESPACE_BUDGET` × `DESTINATION_RULE_AMBIGUITY_COUNTS_PER_NAMESPACE`, with keys over `DESTINATION_RULE_AMBIGUITY_NAMESPACE_KEY_MAX_BYTES` never retained); every saturation path fails toward visibility, never silence.
