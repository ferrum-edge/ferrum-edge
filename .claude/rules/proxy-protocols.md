# Proxy And Protocol Rules

## Routing And Proxy Contracts

- Route order per host tier is exact host, wildcard, catch-all. Within each tier: exact path `=/path`, indexed prefix, indexed regex `RegexSet`, then host-only fallback.
- Never replace prefix matching with O(n) scans or regex matching with sequential per-pattern checks.
- Router cache is a `DashMap`, sized by `FERRUM_ROUTER_CACHE_MAX_ENTRIES` (explicit values clamp to 1,000–10,000,000; the default `0` means `proxies * 3` clamped to 10,000–1,000,000). Negative lookups are cached.
- Exact listen paths match after query stripping. Regex listen paths use `~` and are auto-anchored full-path. Prefix-style regexes must end with `.*`.
- HTTP-family proxies (`backend_scheme` `http` or `https`) route by hosts and listen path. At least one is required. WebSocket and gRPC are detected per request; HTTP/3 support of an `https` backend is learned by the capability registry. Optional `listen_port` scopes matching to that frontend port (Gateway API listener identity); omit it for port-agnostic matching.
- Stream-family proxies (`tcp`, `tcps`, `udp`, `dtls`) route by `listen_port`; `listen_path` must be `None`.
- Host-only HTTP proxies match all paths for their hosts; `strip_listen_path` is a no-op there.
- HTTP-family `backend_scheme` accepts `http` or `https` and defaults to `https`. Stream-family requires an explicit scheme.
- gRPC and WebSocket are runtime flavors, not schemes. `backend_dispatch::detect_http_flavor()` classifies once, with one header lookup and no allocation.
- Because the client picks the flavor, a flavor's plugin view must never silently drop the route's authentication or admission policy: H1/H2 and H3 dispatch refuse a request whose view carries `PluginCapabilities::OMITS_ROUTE_ADMISSION_POLICY` (403 / gRPC `PERMISSION_DENIED`) after resolving the view and before any plugin runs; `shared_invariant_parity_tests.rs` pins that order in both dispatchers. The same bit marks the plain `Http` / `WebSocket` view of a gRPC-intended route (a route-scoped gRPC-only gating plugin, issue #6110), and the composed gRPC-Web view only when it cannot run a gRPC-only admission instance (route-scoped OR global — gRPC-Web declares gRPC intent), so the dispatchers need no second check. Their ONE exemption is a bodiless CORS preflight on the plain HTTP, non-gRPC-Web view that carries `PluginCapabilities::ANSWERS_CORS_PREFLIGHTS` (a `cors` instance without `preflight_continue`; `proxy::is_cors_preflight_request`, via `grpc_intended_refusal_exempts` / `h3_grpc_intended_refusal_exempts` inside the refusal condition): only the #6110 rule marks that view, so no other refusal is relaxed. "Bodiless" is no `Transfer-Encoding` and `Content-Length` absent or `0` on every protocol, plus the transport proof: H1/H2 `is_end_stream()` (END_STREAM on the H2 HEADERS frame), H3 the request stream ENDING with no DATA frame (`h3_request_stream_ends_without_data`, which waits at most `min(backend_read_timeout_ms, H3_PREFLIGHT_END_OF_STREAM_WAIT_MS)` = 2 s, the fixed cap alone when the timeout is `0`: the wait runs before any plugin, so it must never inherit the route's backend upload timeout; a timeout is no exemption) — never the declared framing alone. An exempted preflight is NEVER forwarded: both dispatchers refuse it with the same `403` / `route_protocol_admission` right after `on_request_received` when no plugin answered it (`cors` forwarding an unmatched preflight, or a trigger skipping it).
- A client's `Connection` nominations are resolved at ingress (`headers::confine_connection_nominated_request_headers`, before the raw headers reach `RequestContext`): nominated client fields are removed and `Connection` keeps only connection options and request hop-by-hop names. Routing/framing fields and the forwarding fields client-IP resolution reads (`X-Forwarded-*`, `Forwarded`, `X-Real-IP`, the configured `FERRUM_REAL_IP_HEADER`) are never removed by a nomination. The backend boundary's Connection-listed strip runs over the final map, so it must never see a nomination of a gateway assertion (consumer identity, claim headers). Every raw-header capture site must confine first; `shared_invariant_parity_tests.rs` pins the set.
- A single `https` proxy serves plain HTTP, gRPC, and WebSocket traffic. HTTPS backends are classified into H1, H2 TLS, H3, H2 TLS gRPC, and H2C gRPC buckets.

## Protocol Validation

- `check_protocol_headers()` runs on every inbound request. Preserve rejects for HTTP/1.0+TE, CL+TE smuggling, duplicate/mismatched/empty Content-Length, duplicate Host, HTTP/1.1 missing Host (RFC 9112 §3.2.2; empty Host is present-but-invalid and also 400; HTTP/1.0 and absolute-form URI authority are not rejected), bad H2/H3 TE, non-numeric Content-Length, TRACE, and unsupported CONNECT.
- A CONNECT that is not a WebSocket Extended CONNECT is never gRPC: `detect_http_flavor` returns `Plain` for it and both frontends skip gRPC-Web negotiation for it, so every refusal of a CONNECT keeps its HTTP status. A gRPC Trailers-Only or gRPC-Web HTTP `200` is a `2xx` answer to CONNECT, which means "tunnel established" (RFC 9110 §9.3.6); hyper strips the body on H1 and turns the H2 stream into a tunnel or resets it.
- The bounded proxy-frontend `h1_framing_guard` records CL+TE from raw HTTP/1 heads before Hyper can discard `Content-Length`; preserve its order-independent handoff and the RFC 9112 §6.1 connection close after a CL+TE rejection.
- `check_host_authority_consistency()` rejects H2/H3 Host vs `:authority` disagreement before routing after default-port normalization, and rejects the both-absent case (RFC 9113 §8.3.1 / RFC 9114 §4.3.1). `:authority`-only (including RFC 8441 / RFC 9220 Extended CONNECT) and Host-only remain valid.
- Host/authority normalization strips valid ports, preserves bracketed IPv6, rejects unbracketed IPv6, strips trailing dots, and lowercases ASCII.
- Allowed CONNECT variants: H2 Extended CONNECT (RFC 8441) and H3 Extended CONNECT (RFC 9220) with `:protocol=websocket`, plus H3 `:protocol=connect-udp` (RFC 9298) when `connect_udp::connect_udp_profile_available()` holds — `FERRUM_HTTP3_CONNECT_UDP_ENABLED=true` AND a build target that can enforce RFC 9298 §3.1 non-fragmentation (default off ⇒ 501; unenforceable target ⇒ startup validation error, and 501 if reached). Enablement is process-wide: every H3 HTTP route whose routing and `allowed_methods` policy admits CONNECT can match a `/udp/host/port/` suffix, so deploy a dedicated MASQUE route and method-filter routes that must not expose CONNECT. The URI-template `udp` segment is a case-sensitive path literal. CONNECT-UDP in TLS 1.3 early data is always 425 Too Early, even when `CONNECT` is in `FERRUM_TLS_EARLY_DATA_METHODS`, and that refusal runs before routing, plugins, or any socket work. Everything else — plain CONNECT, `webtransport`, `connect-udp` on H2 — is 405. An unregistered `:protocol` token never reaches the handler: vendored h3 fails `Protocol::from_str` and resets the stream with `H3_MESSAGE_ERROR`.
- `src/http3/connect_udp.rs` is the whole RFC 9298 surface (capsule-only profile, admitted never load-balanced destinations, fail-closed live re-checks, DF-socket and error-classification rules, authorization lifetime). Read `.claude/rules/connect-udp.md` before changing CONNECT-UDP admission, capsule handling, the tunnel socket, or teardown.
- CONNECT-UDP per-client tunnel admission uses `FERRUM_HTTP3_CONNECT_UDP_MAX_SESSIONS_PER_IP`; IPv4 is counted per address, while IPv6 grouping follows the shared `FERRUM_PER_IP_IPV6_PREFIX` setting (default `/64`). This live-tunnel cap is independent of the per-IP request cap and remains held until relay teardown.
- H3 WebSocket client frames are MASKED, exactly as on H1/H2. RFC 9220 §3 adopts RFC 8441's Extended CONNECT and RFC 8441 §5 hands the stream to RFC 6455 unchanged, so RFC 6455 §5.1 applies: the shared relay framer runs `accept_unmasked_frames = false` on every frontend, unmasks compliant client frames, and closes an unmasked one with 1002. The H3 pumps relay bytes verbatim and never parse frame headers. There is no RFC 9220 masking exemption — §5 of RFC 9220 is IANA Considerations (issue #5011).
- Response paths strip hop-by-hop headers across protocols: `connection`, `keep-alive`, `proxy-authenticate`, `proxy-connection`, `te`, `trailer`, `transfer-encoding`, `upgrade`.
- `X-Gateway-Error` / `X-Gateway-Upstream-Status` / `X-Ferrum-Diagnostic-Ref` are gateway-owned and listed ONCE in `headers::GATEWAY_OWNED_DIAGNOSTIC_RESPONSE_HEADERS`. `is_backend_response_strip_header` drops backend copies (headers and trailers) at every backend boundary; the final client-wire sanitizer deliberately does NOT, because reject builders carry the gateway's own token in the same map. Builders strip leftovers (`strip_gateway_owned_diagnostic_response_headers`, `finalize_h3_response_routing_headers`) before writing their own value. Derive `X-Gateway-Error` from `x_gateway_error_for_response(ctx, ..)` / `apply_authoritative_gateway_error_header_for_response` wherever a `RequestContext` exists, so a route-deadline `504` no backend held reads `request_timeout`, never `backend_timeout`.
- Diagnostic references (`src/diagnostic_ref.rs`, issue #5767) are stamped LAST, never by a builder: H1/H2 in `handle_proxy_request_on_frontend_port` on the response hyper receives, H3 by `diagnostic_ref::stamp_h3_response` wrapped around EVERY `send_response` head (the request task's slot is a task-local installed by `diagnostic_ref::run_h3_request`, which takes the `handle_h3_request` future by pinned reference, never by value). Each stamp strips any copy first and mints only for a closed-set `X-Gateway-Error` token, never on a slot marked origin-served (`DiagnosticSlot::serves_origin_response`, set by `note_rejecting_plugin` for a `rejects_with_origin_response()` plugin and by `record_rejection` for a request marked by `RequestContext::serves_origin_representation`), in any mode (issue #5860); with references off the same two boundaries still strip a plugin/hook copy (`diagnostic_ref::strip_response_header`). The detail comes from the terminal `TransactionSummary` through `log_with_mirror`, so a no-consumer shortcut that skips building the summary must still build it when `ctx.diagnostic_slot()` is set and the response can carry `X-Gateway-Error`.
- `FERRUM_DIAGNOSTIC_REFS=all` (issue #5846) also references a gateway rejection without a token, and ONLY one whose site recorded it in the slot before the head was written: the shared rejection-log funnel (`log_rejected_request_with_path_and_backend_state` → `diagnostic_ref::record_rejection`), the H1/H2/H3 routing-`404` and mesh `REGISTRY_ONLY` sites (`record_route_miss`), and the H1/H2 frontend admission fences (`record_admission_fence`). Never infer "gateway-authored" from the absence of a backend dispatch: a relayed backend `4xx`/`5xx` must stay unreferenced, and so must an origin representation a plugin replays or relays as its short-circuit — `record_rejection` skips a request marked by `RequestContext::serves_origin_representation` (cache/dedup replay, semantic-cache hit, serverless terminate) or whose rejecting plugin returns `Plugin::rejects_with_origin_response()`. Every recording site passes the status of the head it will write (a gRPC Trailers-Only head is `200`), and the stamp requires that exact status. Recorded phases are interned against the compiled-in `diagnostic_ref` phase set (`other` otherwise); add a new phase label there. In `errors` mode only a `5xx` rejection is recorded. Request-phase reject arms (including the `on_final_request_body` chain) note the plugin (`note_rejecting_plugin`) before the funnel runs. Backend attempts are recorded with `ctx.record_backend_attempt` once per attempt a retry replaces (at the retry-commit point, before backoff) plus once at the final dispatch site — NOT from `record_backend_dispatch_outcome`, which some loops call twice for one attempt — and the final-site record is skipped (`last_attempt_recorded`) when the loop ended without dispatching again (backoff deadline, open breaker, refused rotated target). TLS detail is noted from the typed error at the dispatch failure site (`note_backend_tls_failure`) and attached only to a `tls_error` attempt.
- H1/H2 terminal accounting survives hyper dropping the handler (issue #6768). `handle_proxy_request_inner` (and the WebSocket upgrade handler it calls) BORROW the `RequestContext` from the `proxy::client_abort_scope::ClientAbortScope` that `boxed_handle_proxy_request_inner` keeps in the same box; the scope `complete()`s in the same poll the handler returns in. A drop before that settles exactly once by `RequestContext::terminal_record_state()`: `NotStarted` → one record whose cause (`TerminationCause`) needs evidence — explicit HTTP/2 stream evidence first (the cause the vendored hyper publishes while dropping the stream, `hyper::ext::take_h2_stream_termination`, Hyper patch 006 + h2 patch 004: peer reset → `499`, local reset → `400`), then gateway closes for otherwise ambiguous losses (retired trust → `444` UNAUTHENTICATED; sibling authorization close → `444` UNAVAILABLE; `OverloadState::drain_wait_ended` → `444` shutdown), then lost HTTP/2 transport or an HTTP/1.1 drop → `499`, and an HTTP/2 drop with no cause → `444` unattributed; `InFlight{status}` → only `record_request(status)` because `log_with_mirror`'s `TerminalDeliveryGuard` finishes the UNSTARTED sinks (never re-invoking a started one), runtime counters, and mirrors in detached delivery; `Finished` → nothing. Every H1/H2 handler counting site marks `ctx.terminal_record.mark_counted()`, and a counted request is never counted again; a new counting site must mark too, and should count AFTER its awaited log. Keep the context in the scope: only the streaming `DeferredTransactionLogger` takes it by value (`hand_off()`). Detached terminal-log paths mark the latch started AND finished; a serving mode must `await overload::end_shutdown_drain_wait` once its drain wait ends and BEFORE observability delivery shuts down: it closes the H1/H2 connections still serving requests (their serve loops select on `wait_for_drain_wait_end`) and waits ≤250ms so those terminals are delivered. Never let the scope rewrite a status already handed to hyper.
- `otel_tracing` CLIENT attempt spans (issue #5864) reuse that hook: `record_backend_attempt` also ends the attempt's span. Every instrumented dispatch site (the H1/H2 loop's initial, no-retry, and three retry arms; the four native gRPC dispatch calls; the H3 frontend buffered loop, streamed-body, streamed-response, header-refined, and native-gRPC dispatches; the H3→gRPC bridge's `dispatch_grpc` / `dispatch_grpc_streaming`; the H1/H2 and H3 WebSocket handshake loops, issue #5867; the H3→HTTP plain bridge `cross_protocol::dispatch_plain`, issue #5875) calls `ctx.begin_backend_attempt_span(url, headers)` (`begin_backend_attempt_span_for_header_list` + `span.header_list(base)` for a WebSocket header list) IMMEDIATELY before dispatch, dispatches `span.headers(base)` (the attempt's own `traceparent` copy), and polls the attempt in the span's scope (`await_backend_attempt_route_deadline` or a pinned `span.scope(..)`, never a by-value wrapper around a large dispatch future; pin a future that borrows `ctx` in an inner block so the borrow ends with the dial). A new dispatch site that records attempts must do all three; one that does not keeps the SERVER `traceparent` and exports nothing. `dispatch_plain` has dozens of terminal exits, so each reqwest arm classifies its attempt into a `PlainAttemptEnd` BEFORE acting on it and records it once (`PlainAttemptEnd::record`, derived for every request: it records the dispatch provenance through `record_backend_dispatch_outcome`, which `request_deduplication` and other response-side plugins read, before the diagnostic/span record; never gate the provenance on `RequestContext::records_backend_attempts()`; the bridge's gateway error terminal, `write_plain_gateway_error_terminal`, runs the committed observers over its normalized response after `X-Gateway-Error` is applied, so they see the token through a read-only view, unlike proxy core, which restores it after them); a new exit in an attempt must be a variant handled after that record, never a record (or a return) of its own. WebSocket dial-policy refusals (the Unix authority screen, the H3 mesh request-target check, and `websocket_backend_dial_refusal`'s literal-IP egress / unsupported SNI screen) are decided BEFORE the attempt's span begins and record no attempt, like the HTTP retry planner's pre-dispatch refusals; a resolver-time egress denial still ends a begun attempt. Dropping the request's `BackendAttemptTrace` exports a handed-off attempt that never reached `record_backend_attempt` as `error.type = cancelled` (client disconnect); an attempt counts as handed off at its first scoped poll, except where the dispatch admits first and calls `span.handoff_reported_by_dispatch()` (the two `proxy_to_backend` sites, whose `BackendAttemptHandoff::mark_handed_to_backend` reports it), so an admission-rejected attempt is never exported. Pools report reuse/setup through the task-local `otel_tracing::note_backend_*` hooks (direct HTTP/2 and gRPC pools today) and take setup timings from `otel_tracing::backend_attempt_clock()` / `backend_connection_setup_clock()` (`None`, with no clock read, outside a traced attempt; the setup clock also notes the setup in the same task-local lookup) through the `note_backend_*_since` hooks; never report an unmeasured value as zero.
- Cross-replica lookup (issue #5846, ADR `docs/plans/diagnostic_ref_cross_replica_adr.md`): opt-in `FERRUM_DIAGNOSTIC_REF_REPLICA_TAG` mints `fd2_<8 hex replica>_<32 hex>` with a per-process CSPRNG replica id derived from nothing. A store resolves only the format and replica it mints; a foreign `fd2_` reference is `DiagnosticRefLookup::NotOwned`, answered as the plain `404` plus `X-Ferrum-Diagnostic-Owner-Replica`, reached only after the scope, `ns`, and store-namespace checks. Keep the owner read from the reference alone (never from shared state), keep the miss body identical, and do not add CP fan-out without revisiting the ADR.
- `sanitize_client_response_headers_for_wire` is the one final client-response boundary and its `Content-Length` decision is a TYPED `ClientResponseFraming`, never a bool and never inferred from a response header: `ExactBody` publishes the derived length, `Streaming` REMOVES the field (an unverifiable claim on bytes not yet written), `Head` is the only arm that preserves a valid `1*DIGIT` representation length, and `TrailersOnly` removes it. Derive `Head` only from the trusted request method / gateway-selected status (`for_streaming_response` / `for_buffered_response` / `for_final_reject`). Streaming writers that need the declared length internally (H3 graceful-close completeness, direct-H2 large-response coalescer bypass, body preallocation) must capture it with `preserved_response_content_length` BEFORE the boundary. Plugin/config surfaces may not author these destinations: `is_protocol_managed_plugin_response_destination` gates `response_transformer`, `response_mock`, `mesh_route_dispatch.response_transform`, `security_headers.set`, `opa.deny_headers`/`fail_closed_headers`, and `mcp_gateway.sessions.downstream_session_header`.
- Frontend TLS/DTLS handshakes are bounded by `FERRUM_FRONTEND_TLS_HANDSHAKE_TIMEOUT_SECONDS` before HTTP header timers start.
- Backend TLS/H2/gRPC/H3 handshakes are bounded by the per-proxy `backend_connect_timeout_ms` end-to-end connect budget.
- TLS/DTLS-terminating frontends must complete frontend crypto/admission before backend dispatch. Frontend handshake failures and plugin rejects must not dial backends or trip backend circuit breakers.
- HTTP/3 0-RTT is disabled by default, method-gated by `FERRUM_TLS_EARLY_DATA_METHODS`, strips client `Early-Data`, and reinjects `Early-Data: 1` outbound. CONNECT-UDP is never admitted in early data (425 Too Early before routing/plugins/socket), even when `CONNECT` is on that allowlist: UDP has no `Early-Data: 1` header for a target to refuse a replay. WebSocket Extended CONNECT is gated on the wire method `CONNECT` on BOTH H2 (`req.method()`, the `method` binding is already `GET`) and H3 (before its `GET` rewrite), so `GET` alone answers it 425 (issue #6107, pinned in `shared_invariant_parity_tests.rs`). When enabled on a non-mTLS listener, QUIC rustls `max_early_data_size` is `u32::MAX` (quinn accepts only `0` or `2^32-1`; no finite QUIC TLS byte cap). A listener with a frontend client-cert verifier sets that TLS value to `0` and refuses the 0.5-RTT `into_0rtt()` accept path (`zero_rtt_admitted`), because 0.5-RTT materialization precedes client authentication and makes `peer_identity()` unknowable. H3 peer identity + early-data state are one per-connection `ArcSwap` snapshot (`http3::peer_identity::H3ConnectionIdentity`), read once per accepted request stream and published exactly once after a successful handshake. Early data is a per-stream fact (issue #5761): the 0.5-RTT accept loop owns quinn's `ZeroRttAccepted` itself (`ZeroRttCompletion`, never relayed through another task) and every accepted stream is classified through `H3ConnectionIdentity::accepted_stream_snapshot`, which re-polls it without waiting and outside tokio's coop budget, so a stream is early only if the signal was still pending at that re-poll (which implies quinn's `is_0rtt()`) and a 1-RTT request arriving with the client's `Finished` never gets 425 or `Early-Data: 1`. The converse is deliberately relaxed: a 0-RTT stream re-polled after the handshake completed is handled as 1-RTT (replays never complete a handshake; RFC 8470 §6.2/§6.4). An identity-bearing snapshot is never early data, and a failed/cancelled handshake leaves the slot empty and early-data-gated.

## Protocol Paths

- HTTP/1.1: hyper frontend to Ferrum's direct hyper HTTP/1.1 backend pool by default (`FERRUM_POOL_HTTP1_DIRECT=true`, hyper `client::conn::http1`) when `direct_h1_dispatch_eligible` admits the body state and HTTP/1-only backend selection; reqwest through `ConnectionPool` when the flag is off or eligibility fails. Streaming is the configured/default body mode, not a guarantee for every response: small known-length bodies may be eagerly buffered under the response-buffer cutoff (body-bearing SSE bypasses that cutoff only).
- HTTP/2: hyper ALPN to reqwest or `Http2ConnectionPool`; streaming default.
- HTTP/3: quinn/h3 standalone server to `Http3ConnectionPool` or cross-protocol bridge; streaming through the shared H3 coalescer.
- gRPC: hyper H2 direct through `GrpcConnectionPool`, not reqwest, to preserve trailers.
- WebSocket: hyper upgrade or H2/H3 Extended CONNECT to backend WebSocket transport; persistent and frame-by-frame.
- TCP: `TcpListener` to `TcpStream::connect`; splice on Linux for unauthenticated plain-to-plain sessions (`tcp_proxy::tcp_plain_splice_eligible`; a session with an authorization deadline keeps the userspace deadline-aware relay, issue #3816) and for TLS frontends when kTLS install succeeds, else userspace copy. Frontend-TLS kTLS handoff (`proxy::ktls_accept`, `ktls_record`, `ktls_confidentiality`, `socket_opts::ktls`) is TLS 1.2 only, ChaCha20-Poly1305 only, and falls back to the buffered userspace accept on every refusal; read `.claude/rules/ktls.md` before changing it. The splice loops enforce `tcp_idle_timeout_seconds`, `tcp_half_close_max_wait_seconds`, `backend_read_timeout_ms`, and `backend_write_timeout_ms` inline via per-direction watermarks — there is no eligibility gate based on timeout configuration. Opt-in outbound PROXY protocol v2 (`backend_proxy_protocol: v2`) writes the header on the backend TCP socket immediately after connect and before any relayed bytes (including before backend TLS handshake and before splice/kTLS engagement).
- UDP: `UdpSocket` per session; GSO-batched send on Linux.
- `Proxy.dispatch_kind` is precomputed at config load by `GatewayConfig::resolve_dispatch_kind()`.
- Buffer request bodies when a plugin requires it, retry needs replay (retry replay retains the request body), or the transport requires it (the H3 frontend buffers a deadline-bound gRPC-Web pass-through upload on the plain bridge so cancellation cannot strand its body pump; `src/http3/server.rs`). Buffer responses for `response_body_mode: buffer`, a body-requiring plugin, or the small-response cutoff (known `Content-Length` <= `FERRUM_RESPONSE_BUFFER_CUTOFF_BYTES`); retries otherwise decide from headers and stream, except the native-H3 retry loop and H3 plain-HTTP mesh attempts, which buffer (see `docs/response_body_streaming.md`). Body-bearing SSE bypasses the small-response cutoff, but body policies may still buffer or refuse it.
- `ProxyBody` response coalescing uses one generic `Coalescing<S: FrameSource>` adapter with reqwest, H2/gRPC, and H3 sources. Do not create parallel per-protocol coalescers. Its accumulator is lazy (issue #5040): construction reserves nothing, the first DATA frame is held as `Bytes`, and the aggregation `BytesMut` is allocated only when a second frame must be merged. Keep the one-frame, idle-body, and large-frame-bypass paths free of both the reservation and the copy.
- Direct-H2 plain responses bypass `coalescing_h2_body` only when `Content-Length` is known, within max response limit, and at least 512 KiB.
- Inbound HBONE relays are fenced for their whole lifetime, not just at CONNECT (issues #5042 and #5568, `proxy/hbone_admission_fence.rs`; full invariants in `.claude/rules/mesh-hbone-waypoint.md`). Four rules bind code in THIS directory. **Publish the mesh inbound mTLS verifier's trust slot ONLY through `ProxyState::publish_mesh_inbound_trust_bundle`** — it stores, advances the in-force trust revision when the X.509 material actually changed AND the candidate compiles as ONE atomic set (the verifier's own rule; a candidate it would reject keeps the previous revision in force), and then `request_sweep()`s, so a live tunnel whose peer chain would no longer complete a handshake here is revoked (`peer_trust`) instead of serving under retired trust. The same in-force anchors gate every CONNECT: a pooled inbound mTLS session is never re-handshaked, so `HbonePeerCredential::from_admitted_connect` re-verifies the retained chain and both HBONE handlers refuse the CONNECT (`hbone_peer_trust_withdrawn` / `hbone_udp_peer_trust_withdrawn`) rather than seeding a tunnel as verified against trust that never judged it. That slot, NOT `RequestEpoch::gateway_trust()`, is the credential gate's trust input: the fence's verdict means "this peer's next CONNECT would be refused", and the epoch's bundles are separately-built material (CP/DB override vs. additively-merged SVID roots), so judging by the epoch both false-revoked peers under a freshly rotated SPIRE root and silently exempted peers in the gateway SVID's own trust domain. **Publish gateway trust ONLY through `ProxyState::publish_live_gateway_trust`** — it is the ONE writer of the request-facing trust generation and it stores and then `request_sweep()`s, the defence-in-depth half of that two-publication step; `fence_gateway_trust_generation` deliberately does not sweep, because fencing carries the same material forward. **Publish PeerAuthentication ONLY through `ProxyState::publish_mesh_inbound_tls_policy` or `ProxyState::publish_mesh_inbound_app_port_aliases`** — both store and then `request_sweep()`, so a direct `mesh_inbound_tls_policy.store()` silently skips the sweep (and clobbers a concurrent `ArcSwap::rcu` partial update), leaving live tunnels serving under a transport mode that no longer admits them. And **every relayed tunnel, TCP and datagram, must go through `tcp_proxy::bidirectional_copy_for_fenced_relay` / `relay_hbone_udp` carrying `AdmittedHboneTunnel::revocation_token()`, call `retire()` the instant the relay ends (before the summary and the logging chain), and classify its own close from the relay's `first_failure`, never from a flag a sweep can flip in that window.** A relay that bypasses the fence keeps serving under a withdrawn policy generation.

## HTTP/3 And gRPC

- H3 clients can hit any `https` backend. Native H3 backend dispatch is used only when the capability registry proves the concrete target supports H3.
- H3 WebSocket bridges to the same backend WebSocket transport and frame-plugin pipeline as H1/H2; the H3 frontend never speaks WebSocket directly to a backend.
- H3 cross-protocol request bodies use bounded channel bridges: Plain streams into reqwest and non-replayable native gRPC streams DATA/trailers into `GrpcBody::Channel`; retry/body-plugin/pre-buffered gRPC retains the buffered representation. Responses stream with the H3 coalesce window when retry/plugin policy allows.
- Forward gRPC trailers with `send_trailers` on buffered and streaming H3 bridge responses.
- H3 QUIC admission: frontend and backend transports both call `config::disable_quic_datagrams` (no consumer reads QUIC DATAGRAM frames; an advertised, undrained queue lives outside flow control). A frontend `Incoming` whose source address is unvalidated is admitted only inside the per-listener `address_validation::UnvalidatedHandshakeBudget` (`FERRUM_HTTP3_MAX_UNVALIDATED_HANDSHAKES`), holds no `ConnectionGuard` until its handshake completes (`H3ConnectionAccounting`, the single `ConnectionGuard::new` site), never takes the 0.5-RTT path, and gets a stateless Retry once the budget is full. Check `adopted_quic` before `Incoming::retry()`: quinn unwraps the endpoint's server config there, so a stale Initial queued before the listener was disabled must be refused, not retried.
- QUIC connection migration must compare `remote_address()` per request. Rebuild `Arc<str>` only on actual change so per-IP limits follow migrated clients.
- The vendored `h3` crate at `vendor/h3-0.0.8-ferrum-patched/` carries Ferrum's frame-drain-on-QUIC-close, H3 WebSocket Extended CONNECT, buffered-trailer-peek (`peek_recv_trailers`), `SendStreamStopped` watch, and receive-side buffered non-`DATA` frame ceiling patches. Keep `docs/upstream-h3-patches/` lifecycle notes in sync when touching H3 dispatch, graceful-close classification, or the vendor copy.
- H3 receive bounds derive from `FERRUM_MAX_HEADER_SIZE_BYTES` (issue #4261): the frontend listener advertises it as `SETTINGS_MAX_FIELD_SECTION_SIZE` (floored 16 KiB, clamped to the QUIC varint range), and both the frontend and every production pooled H3 backend-client constructor install 2x it as the vendored `max_buffered_frame_len`. Direct-backend (`create_connection`) and explicit-target/retry (`create_connection_to_target`) paths both opt into that frame ceiling via `h3::client::builder()`, and both also set `max_field_section_size` to `config::h3_backend_response_max_field_section_size` — the frame ceiling capped at `H3_BACKEND_RESPONSE_FIELD_SECTION_SIZE_CAP`, a bounded decoded-response limit that stops QPACK expansion short of the `HeaderMap` field-count ceiling. Do not replace it with `FERRUM_MAX_HEADER_SIZE_BYTES` itself (a request-header policy must not become an H3-only backend response-header limit) and do not remove it (an unbounded decoded field section lets a compact QPACK block expand without limit). Keep the raw frame bound (`max_buffered_frame_len`) and the decoded field-section bound distinct. `h3::client::new` is the unbounded frame-decoder default and must not be used on a production path that receives backend frames. The standalone `Http3Client` is integration-test/non-hot-path support and has no `EnvConfig`. A non-`DATA` frame whose DECLARED length exceeds the ceiling is a CONNECTION error of type `H3_EXCESSIVE_LOAD`, refused when the type/length varints are decoded — before any payload byte is buffered and before `FrameDecoder` arms `expected`. QUIC flow control does not bound this: reads re-grant credit. The comparison is on the raw `u64` varint before any `usize` conversion. `DATA` lengths are NEVER capped by it (bodies stream under the existing body-size policy), request/response streams AND the peer's unidirectional control/push streams both decode under it, and the frontend post-decode 431 stays as defence in depth. A header policy whose derived ceiling is not a representable varint fails `EnvConfig::validate` rather than being clamped.
- gRPC uses `GrpcBody::Streaming { incoming: UploadSource, ... }` for H1/H2 frontends and `GrpcBody::Channel` for the H3-to-H2 bridge when no body plugins and no retries. Otherwise use a buffered variant.
- Streaming gRPC responses use `coalescing_h2_body`, preserve trailers, and keep the 128 KiB target unless tests justify a change.
- Native-gRPC mesh transport dispatch is materialized in exactly ONE place, `proxy::resolve_grpc_dispatch_transport` → `grpc_proxy::GrpcDispatchTransport::for_target`, and BOTH native-gRPC frontends route through it so target validation, dial-plan resolution, error mapping, and transport lifecycle cannot drift (issues #3284, #3728). The H3→gRPC bridge is the ONE H3 surface that does so: both `dispatch_grpc` (buffered/retryable) and `dispatch_grpc_streaming` (channel-backed) resolve the LB-selected target BEFORE reading the body or dialing, and re-resolve it PER RETRY ATTEMPT. The standard H1/H2 native-gRPC branch in `proxy/mod.rs` resolves it once before its split/mixed/fully-streaming dispatch and re-resolves per retry attempt the same way; its `MeshMtls`/`UnixSocketH2c` classes never arrive there (`grpc_mesh_dispatch_falls_through` routes them onto the generic path first) and are refused defensively. A native-gRPC retry may rotate between `Direct` and `Hbone`/`HboneCrossCluster` targets (both are hyper HTTP/2 with an identical trailer contract) but must still fail closed on any other class rather than switching response pipelines mid-loop, and a fully-streamed non-replayable upload is never retried at all. `Direct` is the untagged pool; a `mesh.mtls` target rides `state.mesh_mtls_pool` (same-cluster pinned peer, or the cross-cluster east-west branch) with the request `:authority` from the SHARED `proxy::mesh_mtls_dispatch_authority`; a `mesh.hbone` target rides a NESTED `hyper::client::conn::http2` client over `state.hbone_pool`'s CONNECT byte tunnel (the destination relay byte-copies to the app socket, so the inner connection is ordinary h2c and trailers survive — which the generic HTTP-family HBONE path's inner HTTP/1.1 client cannot do). There is deliberately NO “direct dial anyway” arm: an unsupported class, an ambiguous both-tags target, or unmaterializable identity/SNI/trust metadata FAILS CLOSED with a Trailers-Only gRPC UNAVAILABLE whose message is a fixed constant that never echoes a SPIFFE ID, SNI name, trust domain, or dial address. For plain HTTP and WebSocket, H3 shares the H1/H2 HBONE and Sidecar mesh-mTLS egress pools; native-H3 selection forces mesh-tagged targets onto those bridges, and neither bridge may fall back to a direct dial when secured transport materialization fails. Unix-socket targets remain refused because the H3 bridges have no Unix dialer.
- `handle_h3_request` has a HARD stack budget. It is the ONE generic H3 request future every stream — Plain, gRPC, WebSocket, CONNECT-UDP — is polled through, and at `opt-level = 0` each future awaited inline in it gets its own fixed frame slot with no sharing between branches: the frame is the SUM of those futures, charged to every request whether or not its branch runs. Large branches must therefore go through an `#[inline(never)]` factory that boxes a thin `async move` trampoline (`boxed_dispatch_grpc_native_h3`, `boxed_proxy_to_backend_h3_streaming`, `cross_protocol::boxed_dispatch_grpc_streaming`, `boxed_handle_h3_connect_udp`, `crate::proxy::boxed_proxy_h3_plain_http_mesh_buffered`), or through a `Box::pin(async { … })` block for an inline reject ladder. `Box::pin(relay(..))` at the call site is NOT enough — that still materializes the relay as a stack temporary in the caller. Re-inlining one of these overflows a 2 MiB Tokio worker on the `functional_h3_plain_*` mesh-mTLS functional tests (production gives workers 8 MiB via `thread_stack_size` in `src/main.rs`); `h3_request_handler_boxes_its_largest_dispatch_relays` is the structural guard.

## Stream Proxy Rules

- `passthrough: true` stream proxies forward encrypted bytes without termination. TCP peeks ClientHello for SNI, then `bidirectional_copy`; UDP parses first DTLS ClientHello for SNI and uses a plain UDP backend.
- Passthrough is stream-only, mutually exclusive with `frontend_tls`, and rejects backend TLS fields.
- Opaque-TLS SNI routing is NOT limited to passthrough (issue #3264). The plane is `Proxy::joins_opaque_tls_sni_plane()` — `passthrough: true` on any stream scheme, OR an ordinary `tcp` listener with `frontend_tls: false`. `stream_listener::joins_sni_plane` mirrors it and the two must stay in step: grouping and validation would otherwise disagree about which listener owns a port. A port becomes an `__sni_{port}` group when more than one passthrough candidate shares it OR any plane candidate declares `hosts`; every plane candidate on such a port joins the group (a hostless one is its catch-all). `tcp_proxy` re-derives "this is an SNI group" as "any candidate is passthrough or declares hosts" — sound only because an `__l4_{port}` group can contain neither. `hosts` on a stream listener that cannot read a ClientHello (`frontend_tls`, `tcps`, non-passthrough `udp`/`dtls`) is a validation ERROR, never silently inert.
- Route precedence on an SNI group is absolute, not declaration order: exact host → wildcard → the single empty-`hosts` catch-all → refuse. An empty-`hosts` candidate is the DEFAULT route and does NOT count as a host overlap (validation caps it at one); do not re-route it through `hosts_overlap`, which is the HTTP router's helper and would make the third tier unreachable. Candidates that all carry `stream_match` keep Istio first-match-wins instead.
- `src/proxy/sni.rs` is the ONE ClientHello parser (opaque SNI routing, mesh inbound, kTLS gate, DTLS passthrough). `extract_sni_from_tcp_stream` is a projection of `peek_client_hello_sni`; `peek_client_hello_sni`/`classify_client_hello` answer "what hostname, and why not" as `ClientHelloSni`. Route classification MUST validate the bounded wire span and the complete declared ClientHello BEFORE invoking the lenient hostname extractor: an early readable SNI must never hide an oversized hello, malformed trailing extension data, a duplicate extension of ANY type (the TLS grammar forbids repeating any extension type, not just `server_name`), or a `ServerNameList` repeating any `name_type`. Both duplicate checks use a fixed code-point bitset (`SeenCodePoints`), never a rescan of the already-seen values — the extension vector is attacker-controlled up to the 16 KiB cap, so a quadratic detector would be hostile-input work. `extract_sni_from_client_hello` is the shared raw-slice extractor used only after that strict gate (and by non-admission consumers). Do not add a second parser and do not loosen the DNS validator (kTLS depends on its strictness).
- SNI route selection fails closed: `Sni` routes by host, `NoSni` uses the catch-all tier, `NotTls` is refused unless `FERRUM_STREAM_SNI_PLAINTEXT_FALLBACK=true`, and EVERY `Indeterminate` (timeout / 16 KiB peek cap / EOF / truncated / malformed / unrepresentable `server_name`) is refused REGARDLESS of that flag — an unreadable hello may have declared any tenant's hostname. Refusal happens before route resolution, so no backend is selected, dialed, health-scored, or breaker-charged. The peek is non-consuming, so every inspected byte is replayed verbatim to the chosen backend.
- `StreamConnectionContext.sni_hostname` and `consumer_username` from `effective_identity()` must flow to stream lifecycle plugins.
- Do not move terminating TLS/DTLS frontends to backend-first ordering.
- TCP userspace `copy_bidirectional` fast path is enabled only when idle timeout, half-close max wait, backend read timeout, and backend write timeout are all zero. The Linux splice and io_uring splice paths enforce these bounds inline and stay engaged regardless of timeout configuration.
- Direction-tracking userspace TCP relay is the default when any bound is nonzero; it provides idle timeout, half-close cap, byte counters, and first-failure attribution.
- TCP read/write timeouts refresh on read progress or partial-write progress. Slow but progressing backends must not be classified as inactive. This applies to userspace copy, splice, io_uring splice, and kTLS splice paths uniformly — `splice_one_direction_no_guard`, `libc_splice_loop`, and `io_uring_splice_loop` refresh the same per-direction watermarks the userspace path uses.
- `stream_proxy_protocol` is a STREAM-family control with two framings, not a TCP-only one (issue #3289): the v1/v2 connection header on `tcp`/`tcps`, and the PROXY v2 DGRAM envelope on EVERY datagram for `udp`/`dtls` (`proxy::datagram_client_address`). The datagram envelope is stripped once at the receive boundary, refusals DROP the datagram with no fallback to the socket peer, and only the authenticated envelope may set `client_ip`; read `.claude/rules/datagram-proxy-protocol.md` before changing the gate, its MAC binding, or freshness.
- Stream proxy port validation happens at config, admin API, startup reconcile, and runtime reconcile. Startup bind is fatal in db/file and non-fatal in DP. Runtime reconcile never crashes.
- DP does not revalidate CP-pushed port conflicts; bind failure skips only the conflicting proxy.
- TCP `FERRUM_ACCEPT_THREADS > 1` accept loops share one exclusive listen socket via duplicated fds (never `SO_REUSEPORT`): a second process cannot bind the same TCP proxy address/port. Those loops are supervised as peers: any unexpected loop exit cancels siblings, clears `started`, and fails the listener task so reconcile/readiness cannot stay healthy with silently reduced accept capacity. Operator shutdown remains a clean success.
- DTLS frontend `DtlsServer::run` is supervised beside `accept()`: unexpected recv-loop exit (error, panic, or unexpected cancel) clears `started` and fails the listener for reconcile/restart; operator/global shutdown remains a clean success.

## Pool Keys And DNS

- Pool keys must include every field affecting connection identity: destination, protocol/TLS, DNS override, upstream subset, direct-H2/gRPC effective `pool_http2_max_concurrent_streams`, CA, mTLS cert/key, SNI, SAN digest, verification flag, and SVID generation.
- HTTP key shell: `{dest}|{proto}|{dns_override}|{subset}|{ca}|{mtls_cert}|{mtls_key}|{sni}|{san_digest}|{verify}|{svid_generation}|{rcfg}`.
- The trailing `rcfg=…` segment on the reqwest pool key encodes every client-level setting that `create_client` bakes into the shared `reqwest::Client` (idle timeout, TCP keepalive, H2 keepalive/windows/adaptive/max-frame). Adaptive window (`aw=1`) takes precedence over fixed initial windows, so `sw`/`cw` appear only when adaptive is off. Secrets never appear in pool keys or key logs. Reqwest does not consume `http2_max_concurrent_streams`, so that field stays out of `rcfg`.
- gRPC and direct-H2 keys include host, port, DNS override, subset, effective H2 max concurrent streams from `PoolConfig::for_proxy` (`none` when that effective cap is unlimited, otherwise decimal), TLS identity fields, verification, SVID generation, and shard suffix `#N`. Identical effective caps share a key (inherit-global == explicit-global; `Some(0)` == `Some(1)` after clamp).
- H3 keys include host, port, LB target index, DNS override, subset, TLS identity fields, verification, and SVID generation.
- Exclude request-only policy fields that dispatch can apply per request (connect/read timeouts). Exclude `max_idle_per_host` from the reqwest key by deliberate global-only tradeoff (per-proxy values would over-fragment). Direct-H2/gRPC may still document first-materializer tradeoffs for remaining builder settings that are not in those keys (for example keepalive), but `pool_http2_max_concurrent_streams` is keyed.
- Subset must partition pools so DestinationRule subset TLS overlays cannot share connections accidentally.
- Request-only policy fields are applied per request. Shared reqwest clients must not leak request timeouts across proxies; client-baked settings are isolated by the `rcfg` key segment instead.
- Per-request `connect_timeout` depends on the vendored reqwest patch at `vendor/reqwest-0.13.4-ferrum-patched/` (`docs/upstream-reqwest-patches/001-per-request-connect-timeout/`). Do not change pool sharing or timeout semantics without preserving that request-scoped override behavior.
- Every production `reqwest::Client::builder()` must install `DnsCacheResolver` from the shared DNS cache.
- DNS cache is shared, prewarmed, native-TTL by default, floored by `FERRUM_DNS_MIN_TTL_SECONDS`, stale-while-revalidate, and supports TCP fallback for truncated UDP.

## Capability, Errors, And Health

- Backend capability registry chooses native H3, direct H2, or reqwest for plain HTTPS by concrete target, but capability state is only one input to dispatch, not a universal reqwest guarantee for `Unknown`/`Unsupported`. An eligible `Unknown` target may still take direct H2 when an `Upgrade` (`h2UpgradePolicy`) preference applies (`Upgrade` never overrides a proven `Unsupported` verdict), and a per-request backend SNI override forces direct H2 whatever the verdict, even under `DoNotUpgrade`, because reqwest cannot apply per-request SNI (`should_dispatch_direct_h2`), and an eligible H2-TLS `Unsupported` target may take the default-enabled direct-H1 pool when `direct_h1_dispatch_eligible` admits it. Reqwest remains the path where the relevant direct-H2/direct-H1 predicates do not select a direct pool.
- Warmup populates capabilities when `FERRUM_POOL_WARMUP_ENABLED=true`; otherwise the refresh task runs an initial probe. Reloads coalesce to at most one in-flight refresh and one queued rerun.
- H3 downgrade must use `mark_h3_unsupported`/`mark_h2_tls_unsupported` guards and must not treat client disconnects, payload-size errors, graceful remote close, or `H3_NO_ERROR` GOAWAY as capability failures.
- A proven client abort before response headers (request-stream reset with any code, `STOP_SENDING`, or a connection the client closed) records the ONE terminal in `proxy::client_abort` on every HTTP-family path: `499` in logs/metrics (never written to the client), native gRPC `CANCELLED`, `ClientDisconnect`, `client_disconnected`, neutral backend health (issue #6772). Mint it only from `ProvenClientAbort` evidence, never from `ErrorClass::ClientDisconnect` alone, which also covers gateway deadline/auth-lifetime terminals. H3 upload reads go through `stream_util::classify_h3_request_read_error`: a peer reset or a peer-closed connection is an abort (an idle-timeout expiry is not); a framing violation is malformed (`400`/`INVALID_ARGUMENT`); anything else, including the gateway's own `H3_NO_ERROR`/`LocallyClosed` close, is the gateway-closed `503`/`UNAVAILABLE` — unless `ProvenClientAbort::from_peer_connection` shows the client closed the connection (Quinn reports a read after a peer close as a bare `ClosedStream`, which h3 surfaces as `StreamError::Undefined`), so every gateway-closed decision point settles against `ctx.peer_connection` first. The QUIC watch answers from a write-once `ConnectionCloseLatch` (first observed close wins; `QuicCloseVerdictGuard`, declared after `h3_conn`, latches before the h3 destructor's `close()` overwrites a peer close with `LocallyClosed`); never re-read `close_reason()` for attribution. Watchers prove an abort only via `STOP_SENDING` or `PeerConnectionSignal::closed_by_peer`. On the H3→gRPC bridge a frontend terminal applies only when `GrpcBody::Channel` relayed the failure (`frontend_failure_relayed`) AND the returned error is the gateway's own h2 reset (`error_chain_is_local_h2_reset`: reset, not `is_remote`, not `is_library`). An idle-timeout expiry is never an abort. Pre-header dispatch waits race the response direction (`peer_response_stopped`) with settled-result/deadline precedence, and frontend-selected terminal writes take the terminal-write grace. After headers commit, keep the committed status and only mark `client_disconnected`.
- `BackendResponse::connection_error` means exactly "the request body never reached the backend application layer."
- For H3, `H3PoolError::request_on_wire()` is authoritative for `connection_error`; do not AND it with generic error-class labels.
- Connect-phase reset/refused is a pre-wire connection failure. Mid-stream transport failures can still be capability-downgrade signals.
- Active health is shared per upstream target. Passive health is isolated per proxy. Never merge these maps or key passive health by upstream.
- `compute_health_bitset()` keeps a stack `u128` bitset for up to 128 targets, with Vec fallback above that. It must not probe the health maps per selection: active eligibility comes from the per-balancer `ActiveEligibility` snapshot keyed on `ActiveUnhealthyTargets::{id, generation}`, passive from the per-`(balancer, proxy)` `PassiveEligibility` table keyed on `PassiveUnhealthyTargets::generation()`. Every mutation of either map must go through the wrapper (`insert`/`insert_if*`/`remove*`/`retain`/`clear`/`get_mut`) so it publishes a generation bump; never call `DashMap::is_empty()`/`len()`/`iter()` on them from the request path (each locks — and `iter()` allocates for — every shard).

## Performance Guards

- Keep `Arc<UpstreamTarget>` selection, response-header `get_mut()` before key allocation, preallocated body Vec from Content-Length, and retry header maps only when retry is configured.
- Keep hyper HTTP/1 `.writev(true)` on cleartext and TLS server builders.
- Request-header passthrough (issue #6671): a plain H1/H2 non-mesh, non-`OPTIONS` route with an empty resolved plugin chain and no path-parameter captures leaves `ctx.headers` empty and unmaterialized when `RequestContext::try_begin_request_header_passthrough` accepts the wire block (unique names, UTF-8 `from_str`-valid values, no reserved assertion names). Core code on that dispatch path must read request headers through `ctx.request_headers_view(..)` / `ctx.effective_request_header(..)` or a `RequestHeaderLookup` helper, never `ctx.headers` directly; a consumer that needs the map calls `RequestHeaders::to_map()` or `ctx.end_request_header_passthrough()` (which builds the exact eager map, `Host` backfill and hop count included). Never write into `ctx.headers` while passthrough is active; a `debug_assert!` before dispatch guards it. `request_header_passthrough_tests.rs` pins the equivalence.
- Avoid `Proxy.clone()` in gRPC/TCP hot paths; extract fields into parameter structs.
- Preserve H2 flow control budgets for gRPC, UDP `recvmmsg` frontend receive, QUIC 32 KiB response coalescing (min = max default; `FERRUM_HTTP3_COALESCE_MIN_BYTES` / `FERRUM_HTTP3_COALESCE_MAX_BYTES`) with a 200 µs flush interval (`FERRUM_HTTP3_FLUSH_INTERVAL_MICROS`), and Linux splice for plain-to-plain TCP.
- Backend HTTP/2 flow control is fixed-window by default (`PoolConfig::http2_adaptive_window = false`, issue #5464). hyper's `adaptive_window(true)` is not additive: it resets both initial windows to 65,535 and grows from there, and h2 (>= 0.4.16) sizes its small-DATA-frame flood budget to `max(25,600, connection_window / 2)`, so a 64 KiB connection window shared by hundreds of streams ends in `GOAWAY ENHANCE_YOUR_CALM too_many_data_frames`. Keep h2 at >= 0.4.19 (0.4.16 charged END_STREAM frames and used a flat 25,600 budget). Every hyper-based client builder (`connection_pool.rs`, `http2_pool.rs`, `grpc_proxy.rs`, `mesh_mtls_pool.rs`) must keep passing `pool_config.http2_adaptive_window`; the raw-`h2` HBONE pool floors its windows via `hbone_pool::h2_window_sizes` when adaptive is on.
- Never splice TLS without kTLS.
- Keep active optimizations unless tests prove removal is safe: router cache eviction CMS, `IP_BIND_ADDRESS_NO_PORT`, `TCP_FASTOPEN`, Date cache, RED shedding, adaptive UDP buffers, `lazy_timeout`, cacheability predictor, `TCP_INFO`, kTLS, io_uring splice, UDP GSO, PKTINFO reply-source selection, `SO_BUSY_POLL`, and `HealthBitset`.
- TLS handshake offload (`src/tls_offload.rs`) is reserved and not wired at startup; `FERRUM_TLS_OFFLOAD_THREADS` must remain `0` or `EnvConfig::validate()` fails.
