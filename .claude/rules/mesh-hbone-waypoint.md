# Mesh HBONE And Node-Waypoint Rules

Implementation invariants for this mesh subsystem. Shared mesh invariants: `mesh.md`; operator docs:
`docs/mesh.md`.

## HBONE Identity Boundary

- HBONE is HTTP/2 CONNECT over mTLS on port 15008.
- `is_hbone_connect()` only detects the wire shape (H2 CONNECT + optional `x-ferrum-mesh-protocol`/`x-istio-protocol: hbone` marker); it does not imply authentication and is only safe for non-relay decisions (path normalization, metadata tagging, body-buffering branch).
- Relaying a CONNECT as an HBONE tunnel requires an authenticated, trust-domain-verified peer (`ctx.peer_spiffe_id.is_some()`, i.e. `is_authenticated_hbone_connect()`). `handle_hbone_request` rejects a peerless CONNECT — bare or marker-bearing — with `403 Forbidden` before dialing/circuit-breaking any backend, stamping `mesh_authz.deny_policy=hbone_unauthenticated_peer`. The explicit marker path is not a bypass. This is separate from (and additive to) TLS-time trust-bundle peer verification.
- Baggage `source.principal` rewrites the authz principal only when the authenticated peer is in `mesh_authz.trusted_hbone_assertors` and the baggage trust domain matches the peer cert or `FERRUM_MESH_TRUST_DOMAIN_ALIASES`. Ambient UDP may additionally carry `source.pod_uid`; use it for namespace/selector scope ONLY after that same principal trust gate succeeds and the live slice maps the exact, unambiguous pod UID to the same SPIFFE ID. Missing/malformed/stale/mismatched/untrusted UDP evidence evaluates mesh-wide policies only.
- Untrusted assertors keep their own peer-cert identity even when baggage is present.
- **Matching `trusted_hbone_assertors` is NECESSARY but NOT SUFFICIENT (issue #4274).** Every entry also carries an `AssertionGrant` deciding WHICH identities that peer may assert, and `mesh_authz` + `workload_metrics` consume ONE shared three-way verdict (`hbone_assertion_verdict` → `Allowed` / `UntrustedAssertor` / `OutOfScope`) so telemetry attribution can never honor what authorization refused. Grants: a bare service-account name or a bare exact SPIFFE pin ⇒ `SameNamespace` (both SPIFFE paths must carry `/ns/<ns>/` and match; a namespace-less peer may assert only itself); `{"assertor": …, "asserts": [ids]}` ⇒ exactly those identities, `[]` authorizes NOTHING; `{"assertor": "spiffe://…", "scope": "mesh_wide"}` ⇒ the old namespace-blind power for one exactly pinned peer, with a construction-time warning; bare service-account matchers MUST be rejected for `mesh_wide`. A peer matching several entries gets the UNION of the matched grants; an empty allow-list authorizes nothing. Plugin construction compiles the allow-list into exact-SPIFFE and service-account maps (duplicate matchers union their grants); request-time `hbone_assertion_verdict` looks up the peer plus at most one SA key and must not linearly scan NodeWaypoint inventory. Gate order is `untrusted_assertor` → `trust_domain_mismatch` → `assertion_out_of_scope` → honored; do NOT reorder (it would relabel existing diagnostics). Only redacted reason codes may be emitted — never the forged identity. Identity-backed `NodeWaypoint` is why `MeshSlice.node_waypoint_assertors` is `Vec<NodeWaypointAssertor>` (`spiffe_id` + the `asserts` identities that NodeWaypoint fronts, forward-derived by `node_waypoint_assertors_from_workloads` from the same destination-visible, CP-scope-authorized, **and bearer-`ns`-authorized** `Workload.node_waypoint` bindings that admitted the assertor) and why `inject_mesh_global_plugins` projects each entry as an OBJECT: bare SPIFFE strings would fall back to `SameNamespace` and break legitimate cross-node source assertion. An assertor whose asserted identities are all filtered out is dropped, never serialized empty. Do not restore namespace-blind assertion globally; `scope: mesh_wide` is the only mesh-wide opt-in, must stay per-entry, and must use an exact SPIFFE matcher. Do not add a second telemetry-only predicate. **Telemetry lockstep is conjunctive across every enabled global `mesh_authz`:** PluginCache executes all of them (capture-on force-injects `__mesh_authz` beside an operator global). Injection stamps `_effective_mesh_authz_baggage_gates` on `__mesh_workload_metrics` from those enabled configs after ensure/force; disabled rows are omitted; honor requires every compiled gate to honor; each gate keeps its own absent/null/default, `[]`, and alias contract; a trigger is still required (fail-closed); malformed/over-bound (max 16) lists fail construction; direct `workload_metrics` without the field keeps its single-gate config; multi-gate refusal uses the same redacted precedence and never labels the forged identity.
- Baggage dropped because a trusted assertor exceeded its grant surfaces as `mesh_authz.ignored_baggage.assertion_out_of_scope=true` / `mesh_authz.deny_policy=assertion_out_of_scope` / `mesh.ignored_baggage=assertion_out_of_scope`, and increments the NodeWaypoint ADR counter `reason="assertion_out_of_scope"`.
- Never infer Ambient UDP pod scope per datagram. `NetnsUdpCaptureManager` fixes the node-agent-registry-derived `(pod UID, SPIFFE ID)` evidence per pod-netns producer and `get_datagram_tunnel` stamps it on the authenticated CONNECT. Conflicting identities in one shared netns suppress the stamp (mesh-wide fallback).
- Dropped baggage must surface in transaction metadata as `mesh_authz.ignored_baggage.untrusted_assertor=true`; denied requests contribute `mesh_authz.deny_policy=untrusted_assertor`.
- Trust-domain mismatches use the existing `trust_domain_mismatch` reason.
- Default trusted assertor service accounts are `ztunnel` and `waypoint`. `FERRUM_MESH_TRUSTED_HBONE_ASSERTORS` accepts bare service-account names or full SPIFFE IDs; both forms grant SAME-NAMESPACE assertion only (see the grant rule above). Object entries with `asserts` / `scope` are configured on a `mesh_authz` plugin override, not through the env var.
- Explicit empty `trusted_hbone_assertors: []` disables baggage rewriting entirely.
- Keep fallback baggage key aliases in `HboneIdentity::from_headers()` in sync with tests.
- **Admission is re-applied for the tunnel's lifetime, not just at CONNECT (issue #5042, `proxy/hbone_admission_fence.rs`).** Every relayed HBONE tunnel (TCP and datagram) registers with `ProxyState.hbone_admission_fence` via `admit()` and relays through `tcp_proxy::bidirectional_copy_for_fenced_relay` / `relay_hbone_udp` with the tunnel's `revocation_token()`; a relay that bypasses the fence would keep serving under a policy generation that no longer admits it. The relay calls `AdmittedHboneTunnel::retire()` the instant it ends — before the summary and the logging chain — and classifies its own outcome from `first_failure == HBONE_ADMISSION_REVOKED_MESSAGE`, never from a flag a sweep can flip in that window. Retirement and revocation share ONE atomic terminal-state word (`TUNNEL_LIVE` → `TUNNEL_RETIRED` | `TUNNEL_REVOKED_BASE + reason`), so `retire()` and `claim_revocation()` are each a single compare-exchange and exactly one wins: never split them back into two atomics, which let a sweep count, meter, and log a revocation for a tunnel that had already stopped carrying bytes and made the datagram relay — which reads `revoked_reason()` AFTER `retire()` and has no `first_failure` to cross-check — report an idle/EOF close as a revocation. Sweeps are coalesced and run on every request-epoch publication (`publish_request_epoch_with_gateway_trust`) and every PeerAuthentication swap, re-applying the gates in the CONNECT PATH's order — the `reason` label is the operator's only attribution, so a tunnel failing two gates must carry the one its peer's next CONNECT would be refused with: the authorize chain with `MESH_AUTHZ_REEVALUATION_METADATA_KEY` set (`authorization_denied`, resolved from the SAME protocol / gRPC-Web plugin view the CONNECT was admitted with), then peer-auth transport mode (`peer_auth_transport`), then relay destination ownership including the post-DNS loopback screen on the dialled address (`relay_destination`). `handle_proxy_request_inner` authorizes BEFORE it branches into `handle_hbone_request`, which gates transport then destination — do not reorder the sweep to match reading order. Ahead of all three sits the proxy lifecycle generation check (`proxy_withdrawn`), which is not a CONNECT gate: a withdrawn proxy is never routed to. A re-evaluation that cannot produce a verdict fails closed (`reevaluation_failed`). Revocations count on `ferrum_mesh_hbone_tunnel_revocations_total{proxy_id,reason,namespace}`, never as relay failures; the per-SWEEP summary is `info`, the per-TUNNEL record is `debug` (a namespace-wide DENY emits one per tunnel). A revocation ACCOUNTS FIRST and cancels LAST (`claim_revocation` → counter + metric + log → `publish_revocation`): the cancellation token is the only edge anything outside the sweep waits on, so cancelling before the accounting left a real window in which a revoked tunnel was reported by nothing. The recorded plugin view is the one the request path resolved, never a hardcoded `ProxyProtocol::Http`; for an HBONE CONNECT it is always plain HTTP in practice, because a CONNECT declaring a gRPC (or gRPC-Web) content type classifies as gRPC before the HBONE branch and is refused trailers-only by the gRPC POST requirement — a peer cannot label its CONNECT into a different authorize chain.
- **Only `Plugin::reevaluates_live_admission() == true` plugins are re-run by a sweep** (default `false`; `mesh_authz` and `access_control` opt in). A sweep is not a new request: it must not consume a budget, take a permit, mutate admission state, dispatch a mirror, accumulate a score, or make an external call — a `rate_limiting`/`opa`/`waf`/`request_mirror` re-run would drain a real client's quota and then revoke healthy tunnels. Within `mesh_authz`, CUSTOM ext_authz delegation is additionally NOT re-consulted; the original verdict stands. A sweep's DENY is still recorded in the `/mesh/policy-denies/recent` ring, tagged `reevaluation: true` (part of the grouping key), but must NOT touch the request-shaped counters — `NodeWaypointDestinationPolicyRejectReason::AuthzDeny` and the mesh ext_authz `ProviderConflict` record are both withheld on a re-evaluation, because they describe checks a request provoked and a sweep provokes none. The fence's OWN metric is `ferrum_mesh_hbone_tunnel_revocations_total`. Classify any NEW authorize plugin deliberately and update `tests/unit/gateway_core/authorize_reevaluation_contract_tests.rs`.
- **The fence bounds POLICY *and* CREDENTIALS (issues #5568 and #5574).** An established inbound HBONE mTLS session is never re-handshaked, so the credential gate is what bounds it. `HboneAdmissionSnapshot` carries an optional `HbonePeerCredential` (peer SPIFFE id, the leaf + intermediate DER as `Arc` clones of the accept path's, the leaf's `notAfter` as a MONOTONIC `AdmittedLeafExpiry`, `anchored_at_admission`, and the inbound admission trust revision the CONNECT VERIFIED the chain against). **The credential gate runs at the CONNECT too, not only in the sweep (issue #5568 re-review).** An inbound mTLS session is never re-handshaked and many CONNECTs multiplex over one pooled connection, so `HbonePeerCredential::from_admitted_connect` RE-VERIFIES the retained chain against the anchors currently IN FORCE and returns `HboneConnectCredential::Refuse` when it does not anchor; both `handle_hbone_request` and `handle_hbone_udp_request` then refuse the CONNECT `403` through the SAME terminal/body/accounting as the unauthenticated-peer gate, with reasons `hbone_peer_trust_withdrawn` / `hbone_udp_peer_trust_withdrawn` (chain withdrawn or un-judgeable) or `hbone_peer_revoked` / `hbone_udp_peer_revoked` (enforced CRLs revoke a certificate on the chain, issue #5574) — a fixed four-value set on `HboneConnectRefusal`, with one shared fence counter `connect_trust_refusals()` and a response body byte-identical to the unauthenticated one. Seeding `verified_trust_revision` from a revision a CONNECT merely READ disabled the gate for exactly the tunnel that needed it — the replacement a revoked peer opens on the same connection. Do NOT swap this for a sweep-on-every-admit: under a CONNECT burst that is a continuous full-registry scan. `reevaluate` applies it FIRST, ahead of the authorize chain, because the handshake and `spiffe_identity` decide it before a request exists — and within it expiry precedes trust, because the chain re-verification validates at the current instant and would otherwise report an aged-out leaf as `peer_trust`. **The trust half reads the INBOUND ADMISSION SLOT, never `RequestEpoch::gateway_trust()`.** The fence's verdict means "this peer's next CONNECT would be refused", so the anchors it judges against must be the anchors that would refuse it: the `tls::SharedBundleSlot` the mesh inbound SPIFFE client-cert verifier reads, bound to the fence by `ProxyState::install_mesh_inbound_admission_trust` at mesh startup (both at CA-backend slot creation and after `build_mesh_inbound_spiffe_slot_with_federation`). The epoch's bundles are DIFFERENT material built by different code — `install_gateway_runtime_svid_bundle` REPLACES the SVID's roots with the CP/DB override, while `publish_runtime_svid_to_inbound_slot` merges the SVID source's roots ADDITIVELY and files a slice-local bundle of a differing trust domain as FEDERATED — so reading the epoch both false-revoked every peer under a freshly rotated SPIRE root the verifier had just accepted and silently exempted peers in the gateway SVID's own trust domain whenever the slice's local domain differed. Do not reintroduce an epoch read here. The trust half is still a REGRESSION check: `anchored_at_admission` records that the CONNECT's chain was POSITIVELY VERIFIED against the trust then in force, and a tunnel without it (nothing in force to verify against) is never judged — a chain-only inbound posture installs no slot at all (peers verified against the operator client-CA bundle, already bounded by `tls::client_trust`/#3857) and must not be mass-revoked. The skip key is the SLOT's own trust revision (`MeshInboundAdmissionTrust`), which advances ONLY when the published X.509 material differs (local + federated trust domains and their `x509_authorities`; leaf/key/JWT authorities deliberately excluded), compared against the tunnel's last VERIFIED revision (`AdmittedHboneTunnelInner::verified_trust_revision`, advanced on every `Trusted` verdict) — so a tunnel pays certificate path building once per trust change, never once per sweep, and an unchanged republish does none. Publish that slot ONLY through `ProxyState::publish_mesh_inbound_trust_bundle`, which stores, advances the in-force revision when the material changed AND compiled, and then `request_sweep()`s; both mesh writers (`publish_runtime_svid_to_inbound_slot`, `publish_staged_spiffe_bundle`) end there and nothing may call `slot.store()` on it. Verifiers are compiled ONCE per IN-FORCE REVISION, at publish time, by `tls::spiffe::AdmittedPeerTrustAnchors::compile(material, crls)` and cached on `MeshInboundAdmissionTrust`; neither a sweep nor a CONNECT builds one. **The ENFORCED CRLs are compiled INTO those anchors (issue #5574), not consulted beside them, and there is ONE accepted artifact the HANDSHAKE reads too**: `ProxyState::mesh_inbound_admission` (`tls::InboundAdmissionArtifact`) carries the enforced records AND the compiled anchors in force. `SpiffeClientCertVerifier` verifies against those anchors whenever any are in force; its own `SpiffePeerVerifierCache` compile (raw slot + raw records, last-known-good) is ONLY the startup fallback before the fence's first publication, never a second opinion after it — two retained histories let a rejected trust candidate (still STORED in the slot, which also backs the server identity) keep the verifier on its previous set forever, so a later CRL publication never reached a handshake while the fence already enforced it. `tls::SvidServerCertResolver` keeps reading the raw slot (leaf/key rotation must be immediate). Publish records ONLY through `ProxyState::publish_mesh_inbound_crls`, which goes through the fence's single publisher `publish_inbound_admission_crls`: byte-identical records publish nothing, an UNUSABLE candidate (unparseable / not-yet-valid / no `nextUpdate` / already expired, via `crl_policy::usable_crl_records`) takes NO force and is not published at all with one sampled `warn!`, and otherwise the records are stored, the cached anchors are RECOMPILED with them, the anchors are published to the artifact BEFORE the revision advances (so a reader that observes a revision observes anchors at least as new as it names, which is what keeps the skip key sound). Those two stores are NOT atomic and the ordering does NOT make the handshake universally stricter: for the length of the publisher's critical section a handshake can verify against anchors one generation NEWER than the fence's in-force snapshot, which is stricter for a CRL addition or a trust withdrawal and LOOSER for a CRL removal or a trust addition (the CONNECT gate then refuses what the handshake just admitted). Both directions fail closed, the window is bounded by that critical section rather than by any wall-clock figure, and the surfaces converge when the publication completes, the in-force revision advances from the SAME fence-wide sequence, and only then `request_sweep()`. ALL THREE publishers — `install_inbound_admission_trust`, `publish_inbound_admission_trust`, `publish_inbound_admission_crls` — take ONE fence-owned `publish_lock` created in `HboneAdmissionFence::new` (never per installed trust: the install is one of the racers, because production arms the backend CRL watcher before mesh installs the inbound slot), and every equality comparison is re-taken UNDER it against both the published records and the records the anchors in force were compiled with; a publication that `publish_enforced_crl_set` reports as no change must recompile nothing and advance nothing. The ONLY production republisher of the records is `ProxyState::reload_backend_tls_material` under `FERRUM_BACKEND_TLS_LIVE_RELOAD_ENABLED` (default true, cadence `FERRUM_BACKEND_TLS_WATCH_INTERVAL_SECONDS`), and its whole-surface backend TLS validation runs first, so an unrelated backend TLS failure withholds the mesh inbound publication. There is ONE skip key for both halves — do not reintroduce a separate `mesh_inbound_crl_generation` on the snapshot or a two-generation fast path, whose divergence is the exact gap #5574 closes. **`compile` is ATOMIC and must stay identical to `SpiffePeerVerifierCache::build`'s rule**: any declared domain that does not build — including one with no `x509_authorities`, which a JWT-only federated domain produces from valid config — fails the WHOLE set. A candidate that does not compile is STORED in the slot (it also backs the inbound server identity) but does NOT advance the revision and does NOT replace the cached anchors, because the verifier keeps its last-known-good set in exactly that case; one sampled `warn!` names the trust-domain CLASS (`local`/`federated`/`absent`) only. The SAME last-known-good posture governs a REBIND of `install_inbound_admission_trust` to a different slot: a replacement whose material does not compile while anchors are in force keeps the existing binding (not replaced, not cleared, no new revision) and takes its own sampled `warn!`. `InboundAdmissionArtifact::put_in_force` therefore takes `Arc<AdmittedPeerTrustAnchors>`, never an `Option` — the cell is structurally unclearable, because clearing it would strand an already-built verifier on its ORIGINAL slot's own compile while the fence lost its anchors and every arriving CONNECT took the unanchored path. A replacement slot that DOES compile still replaces the binding with a fresh revision; a FIRST install that compiles nothing is unchanged. Judging per domain revoked tunnels in the domains that DID compile while the verifier was still admitting their peers. Reasons are `peer_expired` / `peer_trust` / `peer_revoked`, plus `reevaluation_failed` when the retained leaf is unparseable or was not retained, or when a CRL that IS in force has itself reached `nextUpdate` (a fence failure, never `peer_expired` — the label is the operator's only attribution). The three credential reasons sit in webpki's OWN precedence (`notAfter` before any anchor; `UnknownIssuer` before revocation, which is consulted only after an anchor matches; `Error::most_specific` ranking `CertRevoked` above `UnknownIssuer`), so the label matches the refusal the peer's next handshake would produce. An uncompilable bundle, and an unusable CRL CANDIDATE, are NOT `reevaluation_failed`: neither is in force, so neither becomes what the fence judges against. Gateway trust still publishes ONLY through `ProxyState::publish_live_gateway_trust`, which stores and then `request_sweep()`s as the defence-in-depth half of the two-publication step; `fence_gateway_trust_generation` deliberately does NOT sweep. A bounded single-task expiry watcher (`arm_expiry_watcher`, parked on the earliest live deadline, nudged ONLY when a new tunnel's deadline is strictly earlier — an unconditional nudge cost a full registry scan per CONNECT — gone when no finite deadline is left) runs the one non-publication sweep, and it sweeps DIRECTLY under `sweep_serial` rather than through the coalescing `request_sweep` — a coalesced pass could have read the clock before the deadline fired, leaving the watcher spinning on an elapsed deadline. `HboneRevocationReason` is declared, indexed, and rendered in GATE ORDER with `reuse_withdrawn` (the only reason whose tunnel would still be ADMITTED) after every gate that is a refusal and `reevaluation_failed` last; keep `ALL`, `index()`, `as_str()`, the docs, and `docs/prometheus_metric_contract.json` in step.
- **The request path captures `HboneAdmissionFence::sweep_epoch()` BEFORE reading the request epoch / PeerAuthentication policy, and `admit()` rechecks it.** Without that publish-then-recheck a CONNECT in flight across a tightening apply escapes the fence permanently, because the publication's own sweep can read the registry before the insert. Publish PeerAuthentication ONLY through `ProxyState::publish_mesh_inbound_tls_policy` or `ProxyState::publish_mesh_inbound_app_port_aliases` (an `ArcSwap::rcu` partial update) — a direct `mesh_inbound_tls_policy.store()` skips the sweep and can clobber a concurrent swap.
- **Source-side inner application connections are REUSED across fenced tunnels (issue #5042 step 2, `proxy/hbone_inner_pool.rs`).** The plain-HTTP dispatch keeps an EXCLUSIVE inner HTTP/1.1 sender and the native-gRPC dispatch keeps a BOUNDED SET of shared nested HTTP/2 senders per key; raw-TCP, WebSocket (RFC 8441) and datagram tunnels carry no inner request/response exchange and are untouched. Reuse is granted by the DESTINATION and by nothing else: `handle_hbone_request` stamps `x-ferrum-mesh-tunnel-reuse: fenced` (`modes::mesh::hbone::TUNNEL_REUSE_HEADER`) on the CONNECT `200` ONLY while `AdmittedHboneTunnel::fence_in_force()` holds — the registry still owns that exact entry and neither `retire()` nor a sweep has claimed it — so a tunnel nothing can reach never advertises. **AND only when the chain that ADMITTED that CONNECT is UNANIMOUSLY reuse-safe (issue #5583)**: `admitting_chain_allows_inner_reuse` folds `Plugin::allows_hbone_inner_reuse_for` with `HboneReuseContext` over the dispatcher's own `plugins` slice — the protocol-scoped view that actually decided this CONNECT, never a set re-derived from `HboneAdmissionView` (a `Copy` record of the protocol selectors and sweep epoch, which holds no plugins). The fence re-issues exactly two time-varying things — the local authorize verdict on every published generation, and the peer's mTLS credential (expiry + in-force trust) — and reuse elides CONNECTs whose attributes would have been IDENTICAL, so TIME is the only thing that could have differed. A plugin may declare `true` only when it takes no per-operation decision and has no per-operation side effect, or when every decision it takes is re-issued by the fence for the tunnel's whole life. The default is a LITERAL `false`, so everything unclassified — including every custom plugin — REFUSES, and no other marker can change that: `is_authorize_plugin()` describes the AUTHORIZE PHASE only, so deriving the default from it silently opted in a plugin that charges a quota or calls an external service from `on_request_received` and reports `false` there (issue #5583 re-review). **Eligibility is re-judged for the tunnel's whole life.** `HboneAdmissionSnapshot.advertised_inner_reuse` records the fold BEFORE `admit()` and the CONNECT response READS IT BACK (`fence_in_force() && snapshot().advertised_inner_reuse`) rather than re-folding, so the header and the fence's obligation are one value; `HboneAdmissionSnapshot.reuse_context` retains the admitting listener's `mesh_direction` and `frontend_listen_port` unchanged; every sweep then uses those SAME facts and re-runs the SAME `admitting_chain_allows_inner_reuse` over `admitting_request_view`'s `plugins()` for the CURRENT generation and revokes `ReuseWithdrawn` when it no longer holds — a pure boolean fold, never `authorize`/`on_request_received`/any quota or external hook. It is the LAST gate because its tunnel's CONNECT would still be admitted; tunnels admitted WITHOUT the advertisement are never judged by it, and a chain that BECOMES reusable does not disturb live tunnels. Reusable today: `mesh_authz` iff `ext_authz.is_none()` (a sweep never re-consults a CUSTOM provider), `access_control` and `spiffe_identity` (both case (b) — the sweep re-runs the one, the credential gate re-verifies and expires the other), and the pure-observability set `workload_metrics` / `stdout_logging` / `prometheus_metrics` / `otel_tracing` / `proxy_alerts` / `bpf_metrics` (which implements no request hook at all). `mesh_outbound_registry` is classified per admitting CONNECT (PR #5595): **reuse is advertised only for CONNECTs the registry did not decide**. `allows_hbone_inner_reuse_for` requires a nonempty scope AND `!should_enforce_for_request_facts(admission.mesh_direction, admission.frontend_listen_port)`. The request hook's FIRST statement delegates to that SAME facts predicate; EVERY instance skips `Some(Inbound)` before lookup, metrics, or rejection, even on a matching port. Scoped instances on matching `Some(Outbound)` or non-mesh listeners enforce and MUST refuse reuse: CONNECT termination is not direction-restricted, and NodeWaypoint capture is stamped Outbound and can terminate an authenticated CONNECT against a configured route. A sweep never re-runs the registry lookup. Unscoped instances (including `deny_all`) always retain the fail-closed classification, even on skipped Inbound requests. The context-free trait default stays literal `false`; the context-aware default delegates to it for other plugins, and `PluginInstanceWrapper` must forward both methods. Auto-injection still names outbound capture ports and removes the plugin when none exist. Inbound scoped chains therefore keep reuse and survive REGISTRY_ONLY publication; an advertised tunnel whose recorded listener becomes subject to a new registry scope is revoked `ReuseWithdrawn`. Do not infer reuse from a nonempty port scope or assume every capable CONNECT terminator is Inbound. `MeshRuntimeConfig::validate_listener_direction_ports` is defense in depth on both runtime construction (`run` / `validate`) and pre-bind preparation: planned inbound/outbound TCP listeners must use different nonzero port NUMBERS even on different addresses; UDP capture and port `0` are excluded. The three literal `false` overrides restate the fail-closed trait default at their per-operation charge sites: `rate_limiting` (token per operation, in EVERY `limit_by` mode), `adaptive_concurrency` (permit), `request_mirror` (mirror dispatch). Do NOT opt in a bearer-credential plugin — the fence bounds the mTLS leaf and nothing else. `handle_hbone_udp_request` advertises NOTHING unconditionally: a datagram tunnel has no inner request/response exchange to pool. An absent or unrecognized value is per-request behaviour, byte for byte as before; the header authorizes NOTHING and must never be read for any other decision. Classify any NEW plugin deliberately and update `tests/unit/gateway_core/hbone_inner_reuse_classification_tests.rs`. The key (`write_hbone_inner_pool_key`) is the COMPLETE transport and admission identity — inner protocol, app endpoint as dialled, dial peer + HBONE port, pinned peer / SNI / remote trust domain, the asserted source principal AND whether it was asserted rather than the gateway's own SVID, namespace + proxy id + upstream id + proxy lifecycle generation, the SVID leaf fingerprint (at fixed index 2, which is what the rotation drain resolves) + backend SVID generation, and `write_pool_config_key` — and deliberately EXCLUDES per-request policy (connect/read/write timeouts, route body ceilings) exactly as `unix_backend_pool` does. Every lease is bounded by the earliest SOURCE credential deadline that admitted it (`RequestContext::credential_deadline_at` folded with the gateway leaf's `notAfter` through the SAME `parse_leaf_credential_deadline` the receiver fence uses, with `Invalid` folded to an already-elapsed deadline so an unparseable leaf is never poolable), so reuse can never prolong a credential; `CredentialDeadline::Unbounded` publishes `None`, which is "no representable bound", never "expired". H1 returns to the idle set ONLY after a clean fully-consumed response — a streaming body carries its lease as a `PooledBackendLease` and releases it on proven clean EOF only — and H1 liveness/H2 liveness are both `!is_closed()`, the same predicate `Http2PoolManager::is_healthy` applies. The at-most-one PRE-WIRE `try_send_request` handback is the ONLY replay reuse adds, and it does not change retry semantics: `take_message()` returns `Some` only when nothing reached the wire, and `retry::should_retry` with its `retryable_methods` guard stays the only thing that may replay a request. The pool is OWNED by `HboneConnectionPool` so `drain_retired_fingerprints` and `force_drain_all` reach it structurally; do not move it onto `ProxyState`. Clearing the maps is only HALF a drain and on its own is a FAIL-OPEN: a CHECKED-OUT lease is not in them (`take_idle_h1` removed it) and its check-in would re-insert it under the same key, which is exactly what a CRL reload — `force_drain_all` with no gate retirement and no fingerprint change — would resurrect. Every retirement (`drain_all`, `retire_svid_fingerprints`, `retain_live_routes`) therefore advances `HboneInnerConnectionPool::drain_generation` FIRST; each lease records the generation current when it was taken or when its CONNECT was dialled, `checkin_h1_when_idle`/`checkin_h1` compare it before AND after the insert (withdrawing by entry id), and `publish_h2` does the same plus the outer pool's own mid-dial refusal (`HboneConnectionPool::source_dial_fence` / `source_dial_fence_intact`: SVID slot ptr, CRL slot ptr, current fingerprint). Do not reduce this to a single read, and do not bump the generation AFTER the pass. Clearing the maps is not the whole of the ENTRY side either: both whole-pool retirements bump, then walk shard by shard, so a checkout can win a shard the walk has not reached and take a PRE-DRAIN entry — serving under retired material and stamping the CURRENT lease generation onto its check-in, which both fence reads then accept. A SECOND counter, `entry_drain_generation`, advanced ONLY by `drain_all` and `retire_svid_fingerprints`, is stamped onto every `IdleH1`/`SharedH2` at insert and re-read INSIDE the shard guard by `take_idle_h1`/`checkout_h2`, which EVICT a mismatch — never hand it out, and never launder it by adopting the caller's generation (`unix_backend_pool::take_idle_h1` carries the identical rule). `retain_live_routes` must NOT advance it: it removes retired keys by name, and stamping against a publication-advanced counter would evict every resident entry on every key whenever any route was withdrawn. A check-in a retirement refused counts on the `fenced` event value, never `discard`: the two answer different operator questions. `retain_live_routes` runs from `ProxyState::reconcile_hbone_inner_pool` on every publication that becomes current, comparing the key's route-generation SPAN — `|namespace|proxy_id|lifecycle_generation`, recorded by `write_hbone_inner_pool_key` and never re-derived by splitting a key that may contain `|` — against `collect_live_hbone_inner_routes`. The EFFECTIVE upstream id is in the KEY but deliberately NOT in that span, and the live set is deliberately a SUPERSET (every declared proxy with keep-alive on, HBONE-tagged upstream or not): a route override resolves an effective upstream the published proxy does not declare, so comparing on it would retire live routes on every publication. An entry whose route carries NO lifecycle generation is EXEMPT because the configuration cannot name it. Bounds are fixed constants (`MAX_IDLE_H1_PER_KEY`, `MAX_SHARED_H2_PER_KEY`, `MAX_POOLED_INNER_CONNECTIONS`, `MIN_INNER_IDLE_TIMEOUT_SECONDS`), not env knobs, except the nested-H2 width, which is `FERRUM_POOL_HTTP2_CONNECTIONS_PER_HOST` clamped by `MAX_SHARED_H2_PER_KEY`. Nested carriers TRACK the peer's `SETTINGS_MAX_CONCURRENT_STREAMS` and are selected least-loaded-with-room, so native-gRPC concurrency to one destination under one key is bounded by `cap x width` — document any change to that ceiling in `docs/mesh.md`. That cap is kept CURRENT by the carrier's own connection driver: `open_hbone_grpc_sender` creates the `HboneInnerH2Load` BEFORE the spawn and the driver stores `Connection::current_max_send_streams()` after every poll. Do NOT go back to a one-shot sample after `await_peer_settings`: hyper exposes the value only on the `Connection`, `h2` defers applying the peer's SETTINGS until it writes the ACK, and the early read therefore returns hyper's pre-settings `DEFAULT_INITIAL_MAX_SEND_STREAMS` of 100 for every peer — which silently disables the widen decision and restores the head-of-line queueing the width exists to prevent. The OTHER input, `active_rpcs`, is released when the gRPC dispatch returns (response headers for a streaming RPC, not stream end), so saturation under-reports on long-lived streaming RPCs; the error only delays a widen and never exceeds what `h2` accepts. `checkout_h2`/`publish_h2` honour `pool_config.enable_http_keep_alive` exactly as the H1 pair and `collect_live_hbone_inner_routes` do — a keep-alive-off key is absent from `live`, so leaving it poolable makes EVERY publication retire it and fence every outstanding lease pool-wide. A pooled connection holds one outer H2 stream for as long as it is pooled, AND is a live entry in the destination's `HboneAdmissionFence.tunnels` that every policy publication there re-sweeps. Metric: `ferrum_mesh_hbone_inner_pool_events_total{protocol,event,namespace}`.

## Node-Waypoint Per-Pod Policy Scope

- One node-waypoint listener serves many pods; source pod identity comes from the eBPF `connect4`/`connect6` cgroup-stamped `SO_COOKIE` record, resolved through `NodeWaypointIdentityResolver`. The hooks read the identity from `FERRUM_WORKLOAD_IDENTITY` keyed by `bpf_get_current_cgroup_id()` — the *container leaf* cgroup, a child of the pod cgroup on every K8s cgroup driver — so the node-agent enrolls the identity under the **whole pod cgroup subtree** (pod inode + descendant container-cgroup inodes via `cgroup::collect_cgroup_tree_inodes`) and re-walks on reconcile so late-starting/restarted containers are picked up. Keying only the pod inode would miss the leaf and fail closed in real pods. `FERRUM_INCLUDE_PORTS` (per-pod `includeOutboundPorts` narrowing) is keyed the same way and enrolls the same subtree, re-walking on every reconcile (like identity) so a container leaf that starts/restarts after the initial pod event still picks up the policy; unannotated pods short-circuit before any walk.
- **Lazy-identity reclamation:** the production enrollment path (hash-join in `resolve_record`) binds no cgroup and nothing calls `remove_identity`, so the periodic sweep (`sweep_cgroup_stale_identities`, gated by `FERRUM_MESH_NODE_WAYPOINT_CGROUP_SWEEP_INTERVAL_SECS`) reclaims a non-cgroup-bound identity only when its `pod_uid` is no longer referenced by any live cookie record **and** its identity `Arc` has no other holder (`strong_count == 1`) — a churned pod's accept-side cookies age out of `cookie_records` (the `sock_ops` program removes the orig-dst record on TCP close, so closed-connection cookies don't linger in the LRU map until pressure — without that, dead pods would never age out on a low-churn node), so its orphaned identity and per-pod scope are reclaimed instead of accumulating. The `strong_count` guard is load-bearing, not decoration: HTTP/HBONE connections store the resolved identity `Arc` for their lifetime and re-query the per-pod scope per request, so the BPF LRU evicting a live connection's cookie must not let the sweep drop its scope (it would downgrade later streams to mesh-wide); the held `Arc` keeps the pod un-evictable until the connection closes. TCP resolves its scope once at accept and never re-queries, so it's covered by the cookie-reference check alone. A still-live idle pod re-enrolls on its next connection. cgroup-bound identities remain the cgroup-binding pass's domain — the idle pass never touches them.
- HBONE/HTTP and raw **TCP** stream accept paths both resolve the connection's pod identity and stamp `node_waypoint_policy_scope` (HTTP: `RequestContext`, TCP: `StreamConnectionContext`) via `policy_scope_for_pod(pod_uid)`, so `mesh_authz` enforces Namespace/WorkloadSelector-scoped policies per source pod. The TCP path threads the resolver `ProxyState` → `StreamListenerManager::set_node_waypoint_identity_resolver` (injected before the first stream reconcile) → `TcpListenerConfig` → accept loop (`resolve_node_waypoint_stream_scope`).
- **GAP-2M accept-side bridge** (applies to both HBONE/HTTP and TCP paths equally; **IPv4 and IPv6**): `connect4`/`connect6` key the orig-dst record by the connecting-socket cookie, but accept paths look up the accept-side `SO_COOKIE`. The bridge is implemented in the kernel `sock_ops` program (`ebpf/ferrum-ebpf/src/sock_ops.rs`): at active-established it re-keys the record by `(netns cookie, connection tuple)` (`FERRUM_ORIG_DST_BY_TUPLE4` / `FERRUM_ORIG_DST_BY_TUPLE6`), and at passive-established it re-stamps it into `FERRUM_ORIG_DST4`/`FERRUM_ORIG_DST6` under the accept-side cookie, so the resolver (fed by `orig_dst_bridge`) resolves scoped policies with no further proxy-side changes. The IPv6 ctx address words (`local_ip6`/`remote_ip6`) are read element-by-element with verifier-safe **volatile** per-`u32` loads at explicit ctx offsets (`read_ctx_ip6` over the four offsets — the same per-element technique `connect6` uses; a whole-`[u32;4]` ctx copy trips the verifier), keyed by `ConnTuple6`, so v6 resolves on the same footing as v4 (the userspace resolver already merges both families by socket cookie, so only the kernel re-stamp was missing). Per-pod identity enrollment is wired with no separate channel: slice apply installs a `workload_spiffe_hash` → SPIFFE index alongside the policy scopes, and `resolve_record` lazily enrolls `pod_uid` → identity by hash-joining that index against the eBPF-stamped `(pod_uid, workload_spiffe_hash)` on first sight (an unmatched hash fails closed as `UnknownPod`). The current slice index is re-checked on **every** resolve, not only first-sight: a cached `pod_uid` whose workload a later slice removes (its hash leaves the index) stops resolving — the cached-identity branch fails closed (HBONE drops, TCP downgrades to mesh-wide) instead of serving the orphaned identity, and re-validates for free if the workload returns. The gate (`workload_spiffe_hash`→SPIFFE) and the scope index are **one `ArcSwap<NodeWaypointSlice>` generation**: scope is keyed **strictly** by the exact **pod UID** the eBPF stamps (`scopes_by_pod_uid`, built from the slice's per-pod workloads' `metadata.uid`) — a captured pod is **never** resolved through a SPIFFE-keyed index, so pods that share a service account (one SPIFFE) but carry different labels are scoped independently (each against its own labels) rather than collapsed to the label intersection, and a pod whose workload is absent from the live slice fails closed (no scope) instead of borrowing a same-SPIFFE workload's labels. Scope is reclaimed by slice updates, not identity lifecycle (`remove_identity`/sweep do not touch it). `resolve_*` returns the identity **and** its scope from a single load of that generation, so a slice reload can never pair a resolved identity with an old/missing scope (the "never partial" invariant for scoped authz). The TCP path captures both at accept and persists them for the stream; HBONE/HTTP re-queries the scope per request, each read from one coherent generation. The `netns_cookie` (`bpf_get_netns_cookie`) is load-bearing, not decoration: captured connections all target `127.0.0.1:15001` / `[::1]:15001`, so the tuple collapses to loopback + an ephemeral port that can collide across pod netns in this one global map — the per-netns cookie keeps each pod's key distinct (preventing cross-pod record overwrite / identity misattribution) while staying identical for the two ends of a same-netns connection. Do not drop it from the key. (**Distinct from** the in-netns OUTBOUND capture listener + `connect6`'s `ipv6_outbound_deny`, which remain IPv4-only — those concern the pod-loopback redirect datapath, not the accept-side cookie bridge fixed here.) **Verification:** CI compile-checks the program (`build-ebpf`) and load/attach-tests every program — incl. the bridge — on a real ≥5.7 kernel (`ebpf-live`, which already caught and forced fixes for `connect6`/`getpeername6`/`sock_ops` verifier rejections); the full connect→capture→accept datapath (tuple byte-order, end-to-end resolution) is **not** CI-verified and needs a live multi-pod node. Safe by construction: a tuple/byte-order mismatch writes no accept-side record → resolution stays fail-closed, never misattributed.
- **In-netns outbound capture listeners** (always on for NodeWaypoint topology): `connect4` rewrites a captured pod's outbound TCP `SOCK_STREAM` `connect()` to `127.0.0.1:15001` in the **pod's** loopback (UDP/DTLS `connect()` is left unrewritten — the capture listener is TCP-only; NodeWaypoint UDP/DTLS uses the host-netns PKTINFO channel), but a single outbound listener bound `127.0.0.1:15001` in the host/proxy netns can never receive a pod loopback connection — so a host-only listener leaves node-waypoint outbound capture non-functional on a real multi-pod node (connections refused, scoped enforcement never engages); the GAP-2M `sock_ops` cookie bridge also independently requires the accept socket to share the connecting pod's netns. `NetnsCaptureManager` (`src/proxy/netns_capture.rs`) opens one `127.0.0.1:15001` listener **inside each enrolled pod's netns** (`setns(CLONE_NEWNET)` on a dedicated thread, deduped by netns inode), so captured pod-loopback connections are accepted there and the same-netns cookie bridge resolves source identity. Pod discovery reuses the pinned-path IPC pattern: the node-agent publishes a registry dir `FERRUM_MESH_NODE_WAYPOINT_POD_REGISTRY_DIR` (default `/run/ferrum/node-waypoint-pods`), one file per enrolled pod (name = pod UID, contents = pod cgroup path), written on enroll / removed on teardown; the manager polls and reconciles listeners (open on add, close on removal). The listener binds pod loopback on the configured `outbound_listen_addr` port (not a hardcoded `15001`, and not the configured IP — `connect4` always rewrites to loopback; skipped when that port is `0`), shares one `max_connections`-sized connection semaphore across all in-netns listeners, reopens when the pod's registered IP changes (so `source_ip_override` tracks the pod IP; the marker is retracted before reopen so a failed reopen can't look ready), and closes when a pod UID moves to a different netns (preserving the transient-unresolvable grace). **Deferred-redirect readiness gate:** to avoid redirecting a pod before its listener exists, the node-agent defers attaching `connect4` at enrollment (`connect6` is instead attached up front as a **fail-closed IPv6 denier** — the in-netns listener and bridge are IPv4-only, so the `ipv6_outbound_deny` capture-config flag makes `connect6` return `EPERM` for captured v6 rather than letting IPv6 egress bypass `mesh_authz`; excluded v6 via CIDR/port excludes still flows) and enables `connect4` only after the proxy writes `<registry_dir>/.ready/<pod_uid>` (on listener open; removed on close/reopen), polling on a 1s tick with a ~30s bounded fallback — so the registry dir must be mounted RW for the proxy. Linux-only (`setns`, `/proc/<pid>/ns/net`); non-Linux is an unsupported stub. Reconcile/registry logic is unit-tested; the `setns`/bind path and full pod-loopback datapath are **not** CI-testable (need a live multi-pod node) — implemented, live-datapath-unverified.
- A missing scope sets `mesh_authz.scope_missing=true` and, when any namespace/selector-scoped policy is configured, **fails closed** (Reject 403, `mesh_authz.deny_policy=scope_missing`) on **both** the HTTP/HBONE request path (per request) and TCP/UDP streams (at accept) — a missing scope means the pod's workload left the live slice generation (it is derived from the same generation that vouches the identity, so it is not an enrollment race), so a long-lived HTTP/2 connection from a removed workload must not keep serving with scoped policies silently withheld. With only mesh-wide policies the mesh is fully evaluable and both paths fall through to mesh-wide-only. (At connection accept the HBONE listener still drops outright on an *unresolved identity*; this per-request/per-connection check additionally covers a workload removed *after* accept.)
- **UDP/DTLS** stream proxies scope per source pod through a DIFFERENT channel (issue #3286, `src/proxy/node_waypoint_udp_identity.rs`), never the socket cookie: a shared UDP frontend socket carries one cookie for all clients, so resolving the listener socket's cookie would misattribute every session to one identity — do not "fix" it that way. The channel is the kernel-reported INGRESS INTERFACE (`IP_PKTINFO`/`IPV6_PKTINFO`) joined against the node-agent registry's published pod addresses + attested SPIFFE ID, reusing `host_udp_capture::plan_host_udp_bindings` so Ambient host capture and NodeWaypoint attribution cannot disagree on what counts as an attributable pod. Both facts are kernel-provided: forging a source address does not change the ingress interface, and an interface claimed by two enrolled pods refuses BOTH. `NodeWaypointUdpSourceScoping::resolve` first snapshots the published attribution binding, then `policy_scope_for_pod_identity` proves that exact pod UID + SPIFFE principal against one coherent live-slice generation while returning its scope; the admission path revalidates both snapshots after plugin hooks. The resolved `PolicyScopeCache` + SPIFFE principal are stamped BEFORE `on_stream_connect` — so an unattributable session keeps `node_waypoint_policy_scope: None` and hits the same fail-closed gate as TCP. A scoped listener FORCES `IP_PKTINFO` on regardless of `FERRUM_UDP_PKTINFO_ENABLED`; DTLS sets `DtlsServerLimits::capture_ingress_ifindex`, which switches the demux to the shared `RecvMmsgBatch` reader (no second cmsg parser) and drops a datagram claiming an established peer address from a different interface. That demux drain is BOUNDED per readiness wake-up (`DTLS_INGRESS_CAPTURE_DRAIN_LIMIT`): `try_io` consumes no tokio cooperative budget and `dispatch_datagram` has no await point, so an unbounded inner loop would hold a runtime worker for as long as a sender keeps the receive queue non-empty and would never observe shutdown. An admitted session PINS its binding and re-authorizes EVERY datagram against the current generation via `attribution_eq` (generation excluded, so an unchanged republish is inert) — veth reuse / same-address UID change / registry removal terminate it. **Terminating is reserved for the SESSION's own evidence changing.** A UDP session is keyed by a forgeable source tuple, so `revalidate_datagram` splits the two facts: when the datagram's ingress interface differs from the pinned one AND the pinned binding still resolves, the verdict is `DropDatagram` (refused, never forwarded, session untouched); otherwise it is `CloseSession`. Collapsing them back lets any neighbouring pod with `CAP_NET_RAW` — or an off-node sender — end a session it has no relationship to by naming its 4-tuple. Refusal reasons are a closed `&'static str` enum with a per-reason rate-limited warn; never put a registry- or peer-supplied value in a label. A scoped listener that cannot enable the cmsg for EVERY family its bound socket serves does NOT start: `socket_opts::enable_ingress_pktinfo` reads `IPV6_V6ONLY` off the socket, requires BOTH options on a dual-stack `[::]` bind, and returns a typed `IngressPktinfoError` that both the plain-UDP listener and `DtlsServer::from_socket_with_limits` propagate — `v4_ok || v6_ok` is NOT an acceptable outcome there, because it starts a listener that reports healthy while denying every session on the family it actually serves. When a DTLS session ends, the losing relay tasks are aborted AND joined (`abort_and_join_dtls_relays`, skipping the `select!` winner so a resolved `JoinHandle` is never re-polled); `abort()` alone only requests cancellation, so returning without the join releases the session's scope pin and accounting while a relay can still forward. **The listener surface is `materialize_node_waypoint_udp_listeners` (issue #3286), NOT a VirtualService L4 proxy.** `decode_virtual_service_l4_proxies` can never carry a datagram listener — its CP candidate filter (`slice.rs::from_gateway_config`) requires a non-empty `stream_match` and `Proxy::validate` rejects `stream_match` on `udp`/`dtls`; the localized file source rejects a `proxies:` section outright. The materializer sidesteps that chain the way every other mesh listener does: it runs DP-side in `prepare_normalized_gateway_config_for_mesh` (like `materialize_egress_gateway_proxies`) and emits reserved-id `__mesh-nw-udp-*` listener proxies + upstreams straight into `GatewayConfig.proxies`, one per in-mesh `MeshService` UDP-family port, gated by `FERRUM_MESH_NODE_WAYPOINT_UDP_LISTENERS_ENABLED` (default OFF — a NodeWaypoint is hostNetwork, so enabling it claims node-wide ports). `AppProtocol::Dtls` is the SAME L4 transport as `Udp` (`is_udp_mesh_protocol` covers both); it only selects `frontend_tls: true` on the listener, and it is sourced from an `appProtocol: dtls`/port-name hint on a `protocol: UDP` Service port or a `dtls` Istio port protocol — a `protocol: TCP` port must never become `Dtls`, and the EgressGateway refuses `Dtls` outright (no DTLS origination at a terminate-and-re-originate boundary). It runs BEFORE `fail_closed_node_waypoint_udp_dtls_scoped_policies` so non-Linux strips the listeners through the same path (and that suppression strips BOTH UDP upstream prefixes — see `is_node_waypoint_suppressible_udp_upstream_id`). A bind failure stays visible as a `StreamBindFailure` instead of a started black hole. **Same-port Services are SUPPORTED, not refused** (issue #3861): compatible plain-`udp` claimants on one port share ONE bound socket (`__nwudp_{port}` group in `StreamListenerManager`) and are demultiplexed by the exact kernel-reported local destination address via `NodeWaypointUdpDestinationRouter` — selected BEFORE pending/established session lookup, plugin hooks, `on_stream_connect`, backend choice and accounting, with the session key `(client tuple, destination IP, exact namespaced route owner, listener spawn generation)` so one client socket addressing two ClusterIPs cannot collide and a destination that changes namespaced owner cannot reuse the previous Service's session, pending setup, or last-client cache. There is NO fallback route: a missing or unknown local destination is dropped before any allocation. Route tables are `ArcSwap` snapshots republished under the running socket, so adding B never withdraws A and removing A never interrupts B; group membership is deliberately NOT part of the listener restart key. Fail-closed refusals, each with a closed reason: duplicate exact `(ClusterIP, port)` claims refuse BOTH claimants, a port mixing `udp` and `dtls` refuses EVERY claimant, more than one `dtls` claimant on a port refuses EVERY claimant (one `DtlsServer` = one socket = one frontend config), and a headless Service is refused on a shared port while a headless Service ALONE on its port keeps the direct-node-address lane. A single-claimant port keeps an individual listener with no destination table — that is what preserves the direct-address boundary. **Preparation must not publish Service-path steering.** `materialize_node_waypoint_udp_listeners` may attach desired destinations as `GatewayConfig` metadata; `StreamListenerManager` publishes only the subset whose listeners are actually bound on the accepted serving generation, and retracts on bind failure, deferred DTLS, withdrawal, task failure, and shutdown — so a rejected candidate cannot change the live datapath and a destination is never marked without a serving socket. The live gate (`run_node_waypoint_udp_datapath_checks` in `tests/k8s/node_waypoint_ebpf_live/run.sh`) drives REAL datagrams through it: admitted/denied/unattributed/raw-socket-spoofed sources plus a policy change + withdrawal proven with the ambient DaemonSet restart count unchanged. The spoof assertion is emission-gated: the probe pod is granted `NET_RAW` and prints `SPOOF-SENT:` only after `sendto` returns, so a refusal is recorded ONLY when a forged datagram was actually emitted and the backend log proves it never arrived — a sandbox that cannot forge FAILS the required gate rather than recording a refusal nothing attempted. The relay is authorized past `tc_inbound` by a CONJUNCTION whose head is non-forgeable (issues #3956, #3957): `relay cgroup AND relay mark AND (configured node source OR exact live reply source)`, evaluated BEFORE the DNS-response carve-out. The scoped listener's FRONTEND socket (replies to the enrolled source pod) and its per-session BACKEND socket (forward to the enrolled destination pod) both carry `NODE_WAYPOINT_INBOUND_AUTH_MARK`, but a mark and a source address are BOTH chosen by whoever emits the packet — a same-node workload with `CAP_NET_ADMIN` in the HOST netns can `SO_MARK` the public mark and bind a node address or (via `IP_TRANSPARENT`) a published ClusterIP — so both UDP arms first require `bpf_skb_cgroup_id()` to hit `FERRUM_UDP_RELAY_CGROUPS`, the node-agent's host-side resolution of the relay pod's own cgroup subtree. Do NOT delete either source lane to "fix" the forgery (the two competing attempts each deleted one and left the other forgeable while black-holing half the datapath: the backend dial needs the node-source lane, the source-pinned reply needs the reply-source lane), and do NOT hoist a source lane outside `udp_relay_sender_authorized`. The helper answers only at the tc EGRESS hook of the pod's host-side veth, where the relay's locally generated datagram still carries its socket; forwarded traffic and the tc INGRESS hook report `0` and deny. Marking the frontend socket is a startup precondition — without it every session relays and its reply is silently dropped. **The mark is only half the reply's admission proof: the guard also requires the reply's SOURCE to be a trusted node source IP, and a reply's source is not route-selected — it is pinned by `IP_PKTINFO`/`IPV6_PKTINFO` to the exact local address the client addressed.** So a NodeWaypoint UDP/DTLS listener can only answer a client that addressed it at an address in `FERRUM_NODE_AGENT_NODE_IP`/`_NODE_IPS`; at any other node-local address the datagram reaches the backend and every reply dies in this node's own guard. Do not repair that by dropping the pinning (a `connect()`ed client — every DTLS client — discards a reply whose source is not the address it dialed), by implicitly widening the trusted set, or by auto-rendering `status.hostIP` into the chart (the render contract explicitly forbids implicit probe-source trust). **That contract governs the DIRECT-address lane only; the STEERED Service path is authorized by `FERRUM_UDP_REPLY_SOURCES`/`FERRUM_UDP_REPLY_SOURCES6`** (issue #3286): the pinned reply source there is the Service ClusterIP, which is never a node IP, so the marked and correctly scoped reply used to die in this node's own guard. In the **tc UDP arm only**, a datagram to an enrolled pod passes when `bpf_skb_cgroup_id()` hits `FERRUM_UDP_RELAY_CGROUPS` AND the nonzero `node_waypoint_inbound_auth_mark` matches AND its source is either a configured node source (the relay's backend dial) or an EXACT `(address, port)` entry in those maps. All three are required; TCP reads none of them and is byte-for-byte unchanged; the mark comparison stays in the single `enrolled_destination_authorized` helper so the arms cannot drift; entries are exact addresses with an exact port — never a CIDR, a service range, or a port-blind form — and BOTH families plus `FERRUM_UDP_RELAY_CGROUPS` and the shared `FERRUM_UDP_REPLY_SOURCE_GATE` are required by `validate_required`. The relay cgroup set is derived HOST-SIDE by the node-agent from the pod UID the proxy publishes (`FERRUM_MESH_NODE_WAYPOINT_RELAY_POD_UID`, chart-rendered from downward-API `metadata.uid` and refused as an `ambient.env` override): the manifest supplies a NAME, never an id, and the node-agent refuses a UID naming an enrolled workload, a resolved id inside an enrolled pod's subtree, an unresolvable identity, or a set over `UDP_RELAY_CGROUP_MAX_ENTRIES`. A proxy with no relay identity refuses every ACTIVE publication while an INACTIVE withdrawal generation stays publishable, so teardown is always provable. Manifest protocol is `v3`; `v1`/`v2` manifests and acks are unparseable by design (`v2` equated an empty source set with withdrawal and would drop a bound headless listener's sender proof). Publication is bound to the SERVING lifecycle inside `NodeWaypointUdpSteering`, and **publishing is NOT applying** — the node-agent owns every map write, so a claim on disk is a REQUEST, not evidence. The reconcile therefore installs setup rules only after the node-agent has ACKNOWLEDGED the exact generation it published; a pending/missing/stale acknowledgement is `SteerReconcileOutcome::PendingAck`, keeps or REVERTS the rules absent, and retries on the next ordinary tick (no wait, no sleep, no blocked worker). Order is: remove the outgoing rules, publish the generation, wait for its acknowledgement, install; teardown mirrors it (the exact-name rule teardown must SUCCEED before the INACTIVE generation is published) and is only `Removed` once that INACTIVE generation is acknowledged, so a failed rule teardown retains the outgoing authorization and every unproven withdrawal keeps retrying. A publication or acknowledgement-read failure is a distinct `Failed` that attempts strict datapath teardown; if teardown itself fails, predecessor state remains explicitly unproven and the next reconcile retries. Without the gate every add/update had a steered-but-unanswerable window and a wedged node-agent left new steering installed forever. Ownership is unchanged — the node-agent stays the SOLE writer of every BPF map and the proxy's bpffs mount stays READ-ONLY (a writable one would also let the proxy rewrite the pinned orig-dst identity records), so the channel is two well-known files under `<pod registry dir>/.udp-reply-src/` (`src/proxy/node_waypoint_udp_reply_source.rs`): `desired`, proxy-written, ONE bounded strictly parsed manifest of the WHOLE set plus its `(owner, sequence, active)` generation, staged and `rename`d so a 250 ms reader can never see a partial set; and `applied`, node-agent-written, naming the generation whose COMPLETE IPv4+IPv6 set is live in both maps. Claim lines are `<family>-<hex address>-<port>`, strictly ascending and unique — hex, not textual: `::1` and its expanded spelling must be ONE line or one address would hold two authorizations — and a duplicate, reordering, count/body mismatch, bad line, trailing byte, or oversized file refuses the WHOLE generation, never a narrowed subset. The owner is a secure-random per-process 16-hex token, NOT a secret: it exists so a crashed predecessor's `applied` file cannot satisfy a successor's generation (which restarts at sequence 1), and unavailable randomness fails publication closed rather than using a collision-prone fallback. The node-agent retracts the acknowledgement, DISABLES the one BPF gate shared by all three maps, replaces the relay-cgroup map FIRST (so a sender-proof write failure returns before any source tuple is written — sources live without a sender proof beside them is the #3957 replay) and then both source families while every entry is inert, re-reads the exact `desired` manifest, enables the gate only for that complete generation, and writes `applied` last. An acknowledgement-unlink failure still attempts to disable the gate and, when fencing succeeds, retries without mutation; any partial-family or later failure leaves residual keys inert. If gate disable fails, mutation/acknowledgement stop and the hard residual is surfaced rather than claimed revoked. It refuses the whole generation with NO acknowledgement on an over-bound set, either required map absent (INCLUDING an empty withdrawal), any scan/remove/insert or partial-family failure, an unreadable/malformed manifest, and any entry naming an enrolled pod address (the relay may authorize a Service address, never a workload's own — the remainder is NOT authorized in its place). An absent, unreadable, or refused channel disables the shared gate and authorizes nothing. Every source-index manager-future exit also calls `steering.shutdown()`; another retained `Arc` must not preserve steering after attribution disappears. Do NOT add ClusterIPs to `FERRUM_NODE_IPS*`, loosen `source_is_node`, widen kubelet probe sources, weaken the TCP arm, admit arbitrary marked UDP sources, unpin the transparent reply source, or admit any UDP datagram without the relay-cgroup sender proof. The live gate therefore probes at a trusted node source address (`node_waypoint_listener_ip`), and the captured ingress ifindex is NEVER reused as the send-side egress interface — `PktinfoLocal::send_ifindex` derives it and yields `0` for IPv4 and global IPv6, carrying the index only for scoped IPv6 sources. The `DtlsServer` owns its own socket, so `apply_scoped_dtls_socket_options` applies all THREE scoped options before the server object exists — `DtlsServerLimits::socket_mark` (the same relay auth mark), `::transparent_reply_source` (`IP_TRANSPARENT`/`IPV6_TRANSPARENT`, without which the kernel refuses a ClusterIP reply source), and `::capture_ingress_ifindex` (the pktinfo capture) — and a scoped DTLS listener that cannot apply any of them fails construction and surfaces as a bind failure. Mesh mode loads DTLS material from the DTLS-SPECIFIC `FERRUM_DTLS_CERT_PATH`/`_KEY_PATH`/`FERRUM_DTLS_CLIENT_CA_CERT_PATH` — never `FERRUM_FRONTEND_TLS_*`, which is the inbound TCP listener's server identity (`load_mesh_frontend_server_identity`); the PeerAuthentication DTLS reload reads the same DTLS-specific pair, so startup and reload can never diverge, and without material an ordinary (non-generated) `dtls` listener stays visibly `FrontendDtlsDeferred`; when generated NodeWaypoint DTLS listeners are required, a missing dedicated DTLS cert/key or a Strict route without `FERRUM_DTLS_CLIENT_CA_CERT_PATH` rejects the complete candidate before apply and retains last-good. `run_node_waypoint_dtls_datapath_checks` live-gates the DTLS half twice over. The DIRECT-NODE-ADDRESS boundary: a real `openssl s_client -dtls1_2` handshake against the materialized listener (`node_waypoint.dtls.listener_bound`), an admitted enrolled source whose decrypted datagram the backend logs (`…listener_allow_attributed_source`, which is also the end-to-end proof the frontend mark applied), and a scoped-policy-denied source the backend never sees (`…listener_deny_scoped_policy`). The ORDINARY user path, via the Service DNS name / ClusterIP through the steering rules: `…service_path_allow_attributed_source`, `…service_path_deny_scoped_policy`, and `…service_path_deny_unattributed_source`. The direct probes are a distinct boundary and are NOT substitute evidence for the Service path — do not delete either group. DTLS frontend mTLS, IPv6 DTLS, and DTLS across a PeerAuth live-reload swap remain unit/integration-only. `node-waypoint-ebpf-live.yml` `paths:` must keep listing every file in this channel (`src/proxy/udp_proxy.rs`, `udp_batch.rs`, `node_waypoint_udp_identity.rs`, `host_udp_capture.rs`, `stream_listener.rs`, `src/dtls/**`, `src/socket_opts.rs`, and the test modules incl. `socket_opts_tests.rs`). `fail_closed_node_waypoint_udp_dtls_scoped_policies` (and the matching `node_waypoint_dns_slice_for_prepared_config` DNS carve-out) now run ONLY when `node_waypoint_udp_identity::source_identity_supported()` is false (non-Linux); the two MUST stay gated on the same condition or DNS would hide services whose routing survived.
- **Materializing a NodeWaypoint UDP/DTLS listener does not make it REACHABLE — Service-path steering does** (issue #3286 root review, `src/proxy/node_waypoint_udp_steering.rs` + `crate::capture::node_waypoint_udp_steer_setup_script`). Without it a workload's datagram to the Service ClusterIP is DNAT-ed by kube-proxy to a backing pod and then dropped by the pod-veth guard: a black hole, not a bypass. The rules exempt `-i <pod veth> -d <ClusterIP> --dport <port>` from conntrack in `raw PREROUTING`, mark it in `mangle PREROUTING`, and route the mark to LOCAL delivery through Ferrum-owned `ip rule fwmark 0x736 lookup 33136` + `ip route add local … dev lo table 33136`. **Nothing is rewritten**, so the source address, the ingress interface, and the ClusterIP-as-local-address all survive and feed the existing attribution + reply-source pinning. Load-bearing invariants: (a) `udp` AND `dtls` are both steered — the `DtlsServer` pins the whole captured `PktinfoLocal` per peer (`DtlsSessionState::reply_local`) and sources EVERY record from it through the single `send_dtls_record` helper (initial flight, ordinary drain, retransmits, application replies, final shutdown flush) over an `IP_TRANSPARENT` socket, and on a scoped listener a datagram with NO capture or a NON-MATCHING capture is dropped before session state is allocated or delivered (`dtls_scoped_capture_admits`); do not re-add a `send_to` on a scoped DTLS path; (b) the steered interface set is the **published** source generation (`NodeWaypointUdpSourceIndex::publish` → `PublishedSourceGeneration::ifaces`), never the planner's pre-publication list, so a contested/malformed/UID-mismatched/duplicate/over-bound input steers nothing; (c) the FIRST reconcile of every process runs the exact-name teardown even for an empty plan (Ferrum-owned objects outlive their process; the old `applied.is_none() ⇒ Unchanged` short-circuit leaked a crashed predecessor's rules for the life of the new process), while later unchanged polls run no command; (d) the setup script EMPTIES the mangle mark chain before repopulating the raw notrack chain, so nothing is marked under a generation whose notrack/local-delivery prerequisites do not match it — a brief unsteered (fail-closed) window is acceptable, cross-generation/wrong-destination admission is not; (e) teardown attempts IPv4 and IPv6 independently (a missing/broken family tool or any inspection/delete/verify failure cannot block the other available family); overall success still requires every family to be proven, so a missing tool, permission/resource/lock/dump/delete/verification error stays nonzero and never sets `reaped` or publishes a replacement; within a family, mark→notrack must be proven before local routing is removed (inert leftover routing is safer than marked traffic without local delivery); if shared `ip` is unavailable, every safe xtables cleanup is still attempted and routing is retained; it probes/deletes only exact Ferrum-owned objects, treats only genuine absence as idempotent success (iproute2's `FIB table does not exist` dump for a never-created or just-emptied Ferrum table 33136 is that absence — a raw `ip route show table N` under `set -e` otherwise aborts first-pass teardown forever and the Service path stays a kube-proxy DNAT black hole); (f) every PUBLISHED family installs completely or the whole apply fails under `set -e` and retries — there is deliberately NO per-family best-effort arm; (g) mesh preparation is a pure preparer — it may carry desired destinations as candidate metadata but must not `publish_plan`/`retract_plan`; `StreamListenerManager` publishes only destinations whose listeners are actually bound on the accepted serving generation and retracts them before those sockets go away. Destination/interface updates share one cold-path mutex so the backend reconcile always derives from the latest combined state (a stale cloned plan must never install last). Task exit marks that exact spawn generation non-serving before retraction; a failed predecessor cannot retract a replacement on the same key. Shutdown fences bind-watchers under the listener-map lock, retracts, then closes sockets. Serving ownership is the generated `NamespacedResourceId` / reserved `__mesh-nw-udp-` proxy id prefix (`is_node_waypoint_udp_listener_id`), never a substring of the namespace-qualified runtime key. `NODE_WAYPOINT_UDP_STEER_MARK` (0x736) and table 33136 must stay distinct from the TPROXY mark/table, the relay auth mark (0x734), and the tc ingress-redirect mark (0x735); compile-time asserts pin that. `OUTPUT` is never hooked, so the waypoint's own relay dials and replies cannot be re-steered into itself.
- **NodeWaypoint UDP/DTLS backend locality is exact-node, not local-cluster.** `materialize_node_waypoint_udp_listeners` may emit targets only for workloads whose `node_waypoint.node_name` equals the non-empty `FERRUM_K8S_NODE_NAME`; the relay socket's `NODE_WAYPOINT_INBOUND_AUTH_MARK` is node-local metadata and cannot cross to another node's pod-veth guard.
