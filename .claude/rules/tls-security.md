# TLS, Secrets, And Security Rules

## Boundary Security

- Validate hostile input at trust boundaries: path traversal, malformed PEM/DER, invalid SANs, oversized bodies, recursive embedded credentials, and archive/file names.
- Escape user input when interpolating JSON/XML response bodies.
- Preserve transaction metadata redaction for all logger sinks.

## TLS-Only And Frontend Admission

- Port `0` on plaintext proxy/admin/CP gRPC listener settings disables plaintext and is excluded from `reserved_gateway_ports()`.
- Gateway warns if plaintext is disabled and no TLS listener is configured.
- TLS/DTLS-terminating client-facing protocols must complete frontend crypto and plugin admission before dialing a backend.
- Frontend handshake failures and plugin rejects must not trip backend circuit breakers.
- Frontend TLS/DTLS handshakes are bounded by `FERRUM_FRONTEND_TLS_HANDSHAKE_TIMEOUT_SECONDS`, default 10s. `0` disables.
- DTLS demux state is capped before per-peer channel/task allocation and released on handshake timeout.

## TLS Rotation Model

- Most file-based TLS materials are static operational inputs. Cert/key file changes require gateway restart or rolling redeploy unless explicitly listed below.
- Mesh peer-auth reload is limited to resolved inbound mTLS mode and frontend client CA verifier when `FERRUM_MESH_PEER_AUTH_LIVE_RELOAD_ENABLED=true`.
- Frontend cert/key live reload is enabled only when `FERRUM_FRONTEND_TLS_LIVE_RELOAD_ENABLED=true`.
- Frontend watcher covers proxy HTTPS/H2/H3 and admin HTTPS cert/key paths at `FERRUM_FRONTEND_TLS_WATCH_INTERVAL_SECONDS`, default 30s.
- On validated frontend change, rebuild rustls `ServerConfig`, rerun early-data and kTLS-secret-extraction settings, swap `SharedFrontendTls`, and notify H3 to call `Endpoint::set_server_config`.
- Reload parse, expiry, not-yet-valid, or key mismatch failures keep the previous config and emit `warn!`.
- In-flight TLS sessions keep their original `ServerConfig`; swapping must not tear down live sessions.
- DTLS frontend and operator-supplied per-proxy backend TLS paths remain static under frontend live reload.
- Gateway SVID cert/key/trust-bundle files are watched for backend client SVID rotation. Valid reload updates the SVID slot, preserves CP-delivered trust-bundle override, bumps `|svidg=<generation>`, drains old backend TLS caches, restarts HTTP health probes, and optionally force-drains old-generation pool entries after `FERRUM_MESH_SVID_ROTATION_DRAIN_SECONDS`. This watcher rotates the **backend (outbound)** identity, and — when the gateway SVID also backs the **mesh inbound** listener's server cert (issue #1523 — no explicit `FERRUM_FRONTEND_TLS_*` set) — the inbound server certificate as well: the inbound credential is a live `ResolvesServerCert` (`tls::SvidServerCertResolver`) reading the same shared SVID slot, so new handshakes present the rotated leaf with no restart. The resolver is fail-closed: an empty slot or rotated-in material rustls rejects fails handshakes (warned once per bad snapshot, cached so there is no per-handshake rebuild), never serves a stale previous leaf. The **`FERRUM_MESH_CA_BACKEND=spire|internal`** source feeds the *same* slot instead of files (`start_mesh_ca_backend_svid_source`, mesh-only: `spire` = SPIRE Workload API fetch loop reusing `SvidFetchHandle`; `internal` = dev-only `bootstrap_dev_root` + `InternalCa`), blocked on the first SVID at startup (`MESH_CA_INITIAL_SVID_TIMEOUT`, 30s) so listeners never bind identity-less, then live-rotates it — so the identical `SvidServerCertResolver` + backend-pool-repartition rotation applies; the source differs, the slot and consumers do not. Explicit `FERRUM_GATEWAY_SVID_*` file material takes precedence when both are configured, and `FERRUM_MESH_WORKLOAD_SPIFFE_ID` pins the CA-fetched identity. Keep resolver and slot semantics in sync with `docs/mesh.md`'s mesh-identity section.
- Backend CA bundles and ordinary backend client cert/key paths remain restart-required.

## Backend Trust

- Backend CA chain order is proxy `backend_tls_server_ca_cert_path`, then global `FERRUM_TLS_CA_BUNDLE_PATH`, then webpki/system roots.
- Opt-out is explicit: `backend_tls_verify_server_cert: false` or `FERRUM_TLS_NO_VERIFY=true`.
- Proxy backend reqwest paths pass a fully built rustls `ClientConfig` through `use_preconfigured_tls(...)`; trust store construction stays in-house.
- Custom CA is exclusive and replaces built-in roots. For reqwest use `.tls_certs_only([cert])`; for rustls start with `RootCertStore::empty()`.
- Reqwest no-custom-CA helper clients use `rustls-platform-verifier` through the bundled `rustls` feature: macOS keychain, Windows cert store, then webpki fallback on Linux.
- Helper-client verifier behavior applies only when no global or per-plugin CA is configured.

## Validation, Expiry, And CRL

- Per-proxy TLS paths are validated by `validate_all_fields_with_ip_policy()` at config load.
- File mode refuses startup for invalid TLS paths. DB mode warns. DP rejects the update and keeps cached config. No silent fallback.
- `check_cert_expiry()` checks `notBefore` and `notAfter` on all surfaces. Expired certs are hard failures.
- Warn within `FERRUM_TLS_CERT_EXPIRY_WARNING_DAYS`, default 30.
- `FERRUM_TLS_CRL_FILE_PATH` is PEM, loaded once, and `Arc`-shared.
- CRL applies to frontend mTLS for H1/H2/H3/DTLS, all rustls backend paths, and rustls logging sinks.
- CRL does not apply to DP-to-CP gRPC or reqwest-based plugin paths because those stacks do not expose compatible CRL config.
- CRL reload requires restart.

## Pooling And Non-Rustls Paths

- Reqwest TLS paths use distinct `reqwest::Client` instances per cert/trust identity.
- The shared `PluginHttpClient` disables HTTP redirect following (`reqwest::redirect::Policy::none()`) in every constructor, matching the backend proxy client. A server-returned 3xx is surfaced to the caller, never chased, so a spoofed/compromised upstream cannot bounce plugin egress (log/webhook sinks, OIDC/JWKS discovery, AI federation) to an internal or cloud-metadata host. First-hop host pinning in callers like `jwks_auth` is necessary but not sufficient; the `DnsCacheResolver` IP screen goes through the resolved `BackendEgressPolicy` (`BackendEgressPolicy::is_allowed`), which by default blocks cloud-metadata/link-local, multicast, and unspecified ranges even under `FERRUM_BACKEND_ALLOW_IPS=both` (the dangerous-range baseline), while leaving loopback/RFC1918 reachable. A restrictive mode (`private`/`public`) or `FERRUM_BACKEND_DENY_CIDRS` tightens it further; `FERRUM_BACKEND_ALLOW_CIDRS` is the explicit escape hatch. The legacy `check_backend_ip_allowed(addr, &BackendAllowIps)` primitive remains for fixed-mode callers like ACME (always public).
- Rustls direct H2 and gRPC paths configure TLS per connection.
- `kafka_logging` uses librdkafka/OpenSSL: map `FERRUM_TLS_CA_BUNDLE_PATH` to `ssl.ca.location`, `FERRUM_TLS_NO_VERIFY` to `enable.ssl.certificate.verification=false`, and `FERRUM_TLS_CRL_FILE_PATH` to `ssl.crl.location` when verification is enabled (fail-closed on conflicting `producer_config.ssl.crl.location`).
- Redis applies global TLS flags through `PluginHttpClient` accessors.
- Rustls logging sinks (`tcp_logging` TLS, `ws_logging` wss, `udp_logging` DTLS) apply gateway CRLs through `PluginHttpClient::tls_crls()`.
- Plugins that bypass proxy dispatch and use shared `PluginHttpClient`, such as `ai_federation`, get global TLS only. For private endpoints, include internal CAs in the global bundle and include public roots too because custom CA is exclusive.

## External Secrets

- Secret resolution runs at startup before config load and before concurrent env access.
- Env suffixes resolve the base key: `_VAULT`, `_AWS`, `_AZURE`, `_GCP`, and `_FILE`.
- Backends are grouped per provider so one client is reused.
- Two providers setting the same base key is a conflict and must fail.
- Do not expose resolved secret values in errors or logs.
- Do not expose a secret's *source reference* either — file paths, Vault paths, ARNs, Key Vault URLs. Backend errors are sanitized at one boundary in `src/secrets/registry.rs` (`redact_source_reference`), which every startup and single-key fetch passes through; leaf backends additionally do not interpolate the reference themselves. Errors stay at base-key + provider + failure-class level. Redaction covers the *provider-normalized* components too, not just the operator's original string: `source_reference_candidates` re-parses the reference through `azure::parse_keyvault_reference` and adds the vault URL, secret name, optional version, and their recombined unversioned/versioned forms, because the SDK echoes the components it was actually asked for rather than the operator's original spelling. A one- or two-byte reference cannot be selectively replaced without shredding arbitrary text, so if it appears in provider-controlled detail the whole detail fails closed to a fixed key-level diagnostic. Never leave a short reference untouched. A new provider that rewrites its reference before fetching must add its normalized components there.
- Azure Key Vault references accept `/secrets/<name>` (latest) and `/secrets/<name>/<version>` (pinned). Extra path segments fail closed. A versioned URL must request that exact version via `SecretClientGetSecretOptions::secret_version` — never silently fetch latest. Typed TLS `azure://` sources may also set `?version=`; when both a path version and `?version=` are present they must match, otherwise the load fails closed. `MaterializedMaterial.version` / TLS inventory version come from the version Key Vault actually returned, not from a configured label that was never sent. Fetch-time normalization must not rewrite configured source identity (`CertSource` identifier + options).
- A **direct provider URI** (`vault://`, `aws://`, `azure://`, `gcp://` TLS material) leaks its reference through the *error wrapper*, not just the backend detail. `MaterialError::{Secret,InvalidSource,Io}` interpolate a `source_id` and their `Display` reaches `validate` output and startup logs, so `tls::source::load_secret_material` wrapping the scrubbed detail next to a full Vault path/ARN/Key Vault URL re-disclosed exactly what `redact_source_reference` had just removed. Error and log surfaces use `CertSourceUri::redacted_source_id()` / `CertSource::redacted_source_id()`, which withhold the identifier and keep the scheme — a bounded, fixed-set provider label an operator needs and that discloses nothing the config does not already state. `SourceScheme::is_secret_provider()` is the classifier; `file`/`k8s`/`acme`/`managed`/`pkcs11` identifiers are operator-authored local configuration and stay verbatim. Identity and display are **separate representations**, and conflating them broke rotation once already. `CertSource::source_id()` / `CertSourceUri::source_id()` are the *identity*: they key `tls::inventory` entries, `tls::events` `cert_id`/`source_id`/filtering, and the `MaterialFingerprintEntry` inside `MaterialSetFingerprint`, whose `Eq` **is** the rotation predicate. They stay verbatim and distinguishing; do not redact them in place and do not put them in operator-facing text. The redacted rendering lives on `MaterializedMaterial` as `display_source_id` — named that way deliberately, so it cannot be used as an identity by accident — and is stamped by the producer (`load_secret_material`, `load_file_material`, the managed/acme/k8s loaders) because it is interpolated into PEM-parse and verifier-construction failures across `tls::mod`, `tls::backend`, `dtls`, `identity::file_loader`, `config::types`, `config::env_config`, `config::mongo_store`, `grpc::dp_client`, `ldap_auth`, `tcp_logging`, `ws_logging`, `soap_ws_security`, `spec_expose`, `http_client`, and `modes::mesh` — one producer is the only enforceable point, and the `Debug` impl renders the same redacted field. A consumer that needs to tell two sources apart must go back to the `CertSource`: `subscription::material_set_fingerprint` and `inventory::InventoryEntryBuilder::into_entry` both take their identity from the configured source, never from the materialized value. Taking it from `display_source_id` instead makes every `vault://` reference render identically, so two distinct references with equal bytes and version compare equal — a configured source change then evades reload/rebuild detection and distinct sources collapse onto one event and inventory identity. `tests/unit/tls/source_redaction_tests.rs` pins both halves.
- Startup env-secret resolution must not consult the conf-file-aware resolver **anywhere on its call graph**, not just in the registry. `crate::config::conf_file::resolve_ferrum_var` initializes the process-wide `CONF_FILE_CACHE`, and priming it before `FERRUM_CONF_PATH_FILE` is materialized silently pins the wrong settings file for the whole process. Two reads are therefore split into startup/runtime pairs: `startup_secret_fetch_timeout()` vs `secret_fetch_timeout()` (`FERRUM_SECRET_FETCH_TIMEOUT_SECONDS`), and `gcp::endpoint_override_from_env()` / `GcpClientWrapper::new_for_startup()` vs `gcp::endpoint_override()` / `GcpClientWrapper::new()` (`FERRUM_GCP_SECRET_MANAGER_ENDPOINT`) — the GCP client is built *during* `resolve_all_env_secrets`, so any non-empty `_GCP` secret was enough to trip it. The conf-aware variants stay for the later runtime single-key/TLS-material fetches. A new provider that reads configuration while constructing its startup client must add the same split; `env::var` directly is the safe default.
- Resolved values must be NUL-free before they reach `std::env::set_var`, which panics on a NUL byte. `registry::resolve_all_env_secrets` rejects them as ordinary fetch failures (base key + provider, never the value) and `main::resolve_startup_secrets` re-checks at the unsafe block. Without this, a `_FILE` source pointing at binary material aborts `validate` before it can report anything.
- Smart/default path discovery in `src/cli.rs` must yield to a suffixed external source (`cli::externally_sourced` -> `secrets::external_source_configured`). Discovery runs in `main()` *before* resolution, so an auto-set `FERRUM_CONF_PATH`/`FERRUM_FILE_CONFIG_PATH` would otherwise look like a competing user-provided source and fail the command with a multiple-sources error in any directory containing `./ferrum.conf` or `./resources.yaml`. An **explicit** `-s`/`-c` path is a real conflict and still errors. `EXTERNAL_SECRET_SUFFIXES` is deliberately not feature-gated: an unsupported suffix is a fail-closed error, so every build must agree a key is externally sourced.
- File-mode inference (`cli::infer_file_mode`) is the lowest rung of `CLI > env > conf file > smart defaults > hardcoded` and therefore runs in `main()` **after** `resolve_startup_secrets()`, not inside `apply_run_overrides`/`apply_validate_overrides`. Running it earlier broke three higher-precedence sources at once: an externally sourced `FERRUM_MODE_*` was invisible *and* the synthetic `FERRUM_MODE=file` it wrote became a competing second source for that base key, failing the command with `Multiple secret sources configured for FERRUM_MODE`; a secret-backed spec path needed a pre-resolution `externally_sourced` probe as a special case; and a `FERRUM_MODE` in `ferrum.conf` was silently overridden, because `EnvConfig` gives the environment precedence over the settings file. After resolution all three are observable: `FERRUM_MODE` and `FERRUM_FILE_CONFIG_PATH` are materialized, and `FERRUM_CONF_PATH` is final so the settings file can be consulted. Read the conf mode with a fresh `ConfFile::load()`, never `conf_file::resolve_ferrum_var` — the latter memoizes `CONF_FILE_CACHE`, and this helper must not be what pins it for the process. A blank conf value is "not configured"; a load failure is not treated as a configured mode, so the real parse error still surfaces from `EnvConfig`.
- The `validate` report is a fourth disclosure surface, separate from returned errors and tracing records: it is written with `println!`, so `RecordWriter::submit` never sees it and a *successful* validation produces no error to filter. Every value-bearing field goes through `cli::report_field`, which withholds **by key** (`secrets::is_external_secret_key`) before falling back to the textual `redact_external_secret_values` pass. Key-tied is load-bearing, not belt-and-braces: the report re-renders values, and `Mode: {:?}` turns a resolved `database` into `Database` — a form `derive_candidates` deliberately does not produce, and widening it to would be exactly the open-ended normalization the design rejects. The spec-document counts are not covered because they are cardinalities of the loaded spec, not renderings of any env value. A new value-bearing `validate` line must name the variable it came from and go through `report_field`. The same re-render problem exists on the **`run`** path: `main.rs`'s `info!("Operating mode: ...")` reaches the tracing boundary but the structural redactor cannot match `Database` either, so it goes through the shared `secrets::report_env_field("FERRUM_MODE", ...)` (which `cli::report_field` now delegates to) and is formatted with `{}`, not `{:?}`, so the withheld placeholder is not re-quoted. `main.rs:741` was the *only* enum/typed re-render on the startup log surface — bind addresses are `String` (verbatim, candidate-matched) and ports are integers whose canonical `Display` may fall below the derived-candidate minimum — key-tied through `report_env_field` at each listen/port log site, not admitted globally as `80`. A new startup line that re-renders a typed config value must go through `report_env_field`.
- `_FILE` reads run on a detached OS thread, not `tokio::task::spawn_blocking`. A FIFO or stalled mount blocks uninterruptibly; timing out a `spawn_blocking` join handle returns on schedule but runtime teardown then waits for the blocking pool, so `validate`/`run` hung anyway after honoring the timeout. A detached thread is owned by no runtime and is not joined at process exit. Do not "simplify" this back to `spawn_blocking`.
- Resolved values must not resurface in later config diagnostics. `secrets::record_external_secret_keys()` records the externally loaded base keys before config load; `config::env_config_macro::invalid_env_value` withholds the value for those keys, and `secrets::redact_external_secret_values()` filters the final rendered `validate`/`run` failure as a backstop. That backstop is a single left-to-right pass over the *original* diagnostic with deduplicated, longest-first values: substituted placeholders are never re-scanned. Do not reintroduce a `replace()` loop over the running message — resolved values that are substrings of the placeholder (`value`, `external`, `a`) then feed each pass the previous pass's output and amplify one startup error into megabytes. There is deliberately no minimum length for the value *as materialized*; mangling a diagnostic is acceptable, unbounded growth is not.
- Returned-error redaction is not sufficient on its own, twice over. (a) Validators re-render values before echoing them — list parsers trim entries, `FERRUM_TLS_EARLY_DATA_METHODS` uppercases them, the fmt layer JSON-escapes the record — so `secrets::derive_candidates` expands each value into a **bounded, enumerable** set of those forms (`(2 + 32 segments + 5 reference + 2 scalar) * 3 * 2` max). The rewrites Ferrum itself performs on a value are reproduced there rather than re-audited at every print site: `derive_reference_forms` covers the provider-rewritten source id (`vault://x` is echoed back by `SecretBackend::source` as `vault:x`, the shape a single-key `resolve_secret` caller echoes), the scheme-stripped `file://` path, the query-stripped `CertSourceUri` identifier, and the credential-redacted `db_backend::redact_url` rendering; `derive_scalar_forms` covers the canonical `Display` of a parsed integer/float (`03601` -> `3601`) and the canonical boolean (`1` -> `true`). Each is a single deterministic rewrite of the value itself, never of another derived form, so the set stays additive rather than combinatorial, and `redact_url`'s `<invalid-url>` sentinel is deliberately excluded. Derived candidates carry a 3-byte minimum with **no exemptions**; the exact value does not. In particular a derived form is *not* admitted for being no shorter than the value it came from: equal length is not equal content, so an external `Db` would arm `db` and `DB` process-wide, and `db` matches text (`dbname`, `mongodb`) that the exact value never would — the blind short-substring corruption the minimum exists to prevent. The unavoidable cost is that a short **whole-value transformation** is the only rendering an operator sees and the textual pass cannot reach it: `FERRUM_MODE_FILE=DB` is lowercased by `OperatingMode::resolve`, so the diagnostic carries `db`, two bytes, filtered. The same applies to a shortening rewrite (`trim()` of a padded one-character value, a short list segment). Every such surface is covered **key-tied** instead, which is exact on provenance and length-independent: `report_env_field`, `config::env_config_macro::invalid_env_value`, and `OperatingMode::resolve` itself (`is_external_secret_key("FERRUM_MODE")`, because it is a hand-written `format!` that never passed through `invalid_env_value`). A new hand-written validator that re-renders a value must do the same rather than widen this filter. Do not replace this with an open-ended normalization or a per-message candidate rebuild. (b) `warn!`/`info!` emitted *during* config parsing never pass through a returned `Result` at all — a non-GET `FERRUM_TLS_EARLY_DATA_METHODS_FILE` leaks on a **successful** `validate`. `secrets::redact_log_record` therefore filters at the single emission boundary in `logging::non_blocking::RecordWriter::submit`, gated by a relaxed `AtomicBool` so processes without external secrets pay nothing, then by an allocation-free `RedactionPlan::contains_candidate` screen so an armed process still pays nothing per record that holds no resolved value. That boundary is **structural, not textual**: every producer reaching it emits JSON (the fmt layer is `.json()`, access records use `try_write_json`, the sink's failure notice is a JSON literal), and because a resolved value has no minimum length and no required shape, a flat text pass over the *serialized* bytes lets a secret of `"` or `,` rewrite the record's own delimiters and a secret of `level`/`target`/`message` rewrite its schema keys. So the record is parsed into the order-preserving `secrets::LogJson`, redacted per value — object keys rewritten **except** where they sit in the tracing envelope, because access records are *not* all-static: `TransactionSummary.metadata` and `StreamTransactionSummary.metadata` serialize plugin-inserted `HashMap` keys, and `plugins::utils::log_schema` promotes operator config into key position outright (`rename:`, `static_fields:`, and `MetadataPolicy::Flatten`'s prefix). A key that matches a candidate has the key **and the value beneath it** replaced, and duplicate placeholder keys collapse to the first (a JSON object with repeated keys is ambiguous). The envelope names stay exempt because their presence is structural, not derived — `level` is in every fmt-layer record whatever a secret holds, so leaving it discloses nothing while rewriting it would break every downstream consumer. That exemption is scoped by **provenance and position, never by spelling**, because `filename`/`level`/`message` are equally reachable as operator- or plugin-supplied keys: `secrets::LogRecordSource` is threaded from the emission site (`TracingEnvelope` for the `MakeWriter` path and the sink's own fixed failure-notice literal; `Dynamic` for `try_write_json` access records and `try_write_bytes`), and within a tracing record `secrets::EnvelopePosition` exempts only the root object (`secrets::TRACING_ENVELOPE_ROOT_KEYS`: `timestamp`, `level`, `fields`, `message`, `target`, `span`, `spans`, `threadId`, `threadName`, `filename`, `line_number`) and `message` inside the root `fields` object (`secrets::TRACING_ENVELOPE_FIELDS_KEYS`). A `Dynamic` record has **no** exempt key at any depth including the root — a depth test alone is insufficient, since `MetadataPolicy::Flatten` and `rename:` put dynamic keys at the same depth the genuine envelope occupies. Do not re-broaden this to rewriting all keys, do not narrow it back to rewriting none, and do not restore a global spelling-based exemption. A new sink producer must state its `LogRecordSource`; `Dynamic` is the safe default. String values matched after unescaping and re-escaped on output, numeric/boolean values matched against their rendered form and replaced whole — then reserialized with field order intact. Fail-closed: a record that is not well-formed JSON, is not UTF-8, or cannot be reserialized is replaced by `secrets::withheld_log_record()`, never by anything derived from it. That is the fixed `WITHHELD_LOG_RECORD` template with its **own field values** put through the same structural redaction when the plan is built — an exact secret has no minimum length, so `WARN`, `secret`, `values`, and `ferrum_edge::secrets` are all values the template itself carries, and emitting it verbatim would disclose a short secret on the one path that exists to withhold one. Keys and JSON syntax stay untouched (same reasoning as for a real record); `{}` is the fallback if even the template cannot be reserialized. Do not go back to emitting the raw constant. Do not "simplify" this back to running `RedactionPlan::redact` over the serialized record. A record that grows past `FERRUM_LOG_MAX_RECORD_BYTES` under substitution is dropped through the existing oversized path, not enqueued past its reservation. Because a `validate` failure is filtered twice (returned error, then serialized record), redaction is **idempotent**: a span already equal to the placeholder is skipped verbatim unless a candidate at least as long matches there. Removing that skip does not leak, but it lets pass two shred pass one's placeholders on `value`/`external`/`source`-shaped secrets. Non-tracing operator output (`emit_bootstrap_error`, `validate`'s `Spec (...)` line) bypasses that boundary and is filtered at its own call site.
- Startup env discovery iterates `std::env::vars_os()`, never `std::env::vars()`, which **panics** on any non-Unicode name or value — and panics *during iteration*, before the `FERRUM_` filter runs, so one unrelated non-UTF-8 variable anywhere in a POSIX environment aborted `run`/`validate` with no diagnostic. The prefix is screened on raw bytes (`as_encoded_bytes().starts_with(b"FERRUM_")`) so unrelated variables are skipped without being decoded. Fail-closed cases: an undecodable `FERRUM_*` **name** errors (the suffix is at the end, so it may be a configured source we cannot read), and an undecodable **value** on a recognized suffixed source key errors (an unusable reference). An undecodable value on an ordinary base key fails closed (next bullet); it must still count as a directly configured source for conflict detection, which is why the conflict check and both set-probes use `env_var_os_is_set` (`var_os`) rather than `var`: `var` reports non-Unicode as `Err`, i.e. as *unset*, which would let a suffixed source resolve on top of a real direct value instead of failing the "only one source is allowed" check. Diagnostics name the variable through `sanitize_env_key`, which reduces it to its ASCII skeleton (`?` for every other byte) so undecodable bytes are never echoed and the message is deterministic.
- An undecodable value on an **ordinary direct** `FERRUM_*` variable also fails closed, and this is a silent-misconfiguration guard rather than a secret-resolution one. Every downstream config resolver reads the environment with `std::env::var`, which reports non-Unicode as `Err` — i.e. as *unset* — so a non-UTF-8 `FERRUM_ADMIN_HTTP_PORT` or `FERRUM_CONF_PATH` was skipped by resolution and then ignored by everything after it, letting `ferrum.conf` or a built-in default take over settings the operator never chose. Every `FERRUM_*` name is Ferrum's own configuration namespace and no Ferrum setting parses from anything but a `String`, so there is no "definitely unrelated" name to carve out — including `NON_SECRET_FILE_SUFFIX_KEYS`, which are ordinary path settings that merely end in `_FILE`. Unrelated non-Ferrum variables never reach the check: the raw-byte prefix screen skips them undecoded. Reported **after** the conflict check, deliberately: an undecodable direct value that competes with a suffixed source is a genuine multiple-sources misconfiguration and gets that more specific diagnostic (the conflict check already counts it via `env_var_os_is_set`), so the generic Unicode error must not mask it.
- `ResolvedEnvSecrets` vectors are sorted by base key. Candidate discovery iterates a `HashMap`, so reporting order would otherwise vary between processes.

## Identity And SPIFFE

- Preserve SPIFFE/SVID trust-domain parsing and URI SAN validation behavior.
- SVID rotation must not mix stale cert/key material with new trust bundles.
- Gateway SVID pool-key generation uses the SVID generation marker to prevent pool poisoning across rotations.
- kTLS paths must zeroize secret material on drop and must not consume the TLS stream before kernel install is confirmed.
- Dev-only identity shortcuts stay double-gated. The self-signed CA bootstrap (`bootstrap_dev_root`) requires `FERRUM_MESH_CA_BOOTSTRAP_DEV=true`, the `StaticAttestor` requires `FERRUM_MESH_ALLOW_STATIC_ID=true`, and a `mesh` data plane with **no workload identity** — neither file-based gateway SVID material (`FERRUM_GATEWAY_SVID_*`) nor a CA backend (`FERRUM_MESH_CA_BACKEND=spire|internal`, now wired to load + rotate a runtime SVID into the same slot; `internal` is itself the dev-only `bootstrap_dev_root` path) — requires `FERRUM_MESH_ALLOW_NO_CA=true` (enforced in `EnvConfig::validate()`; fail-closed otherwise; a CA backend also requires `FERRUM_MESH_WORKLOAD_SPIFFE_ID`, and file material takes precedence when both are set). All three opt-ins are read directly from the environment (NOT from `ferrum.conf`/`EnvConfig`) and are refused unconditionally when `FERRUM_MESH_PRODUCTION_MODE=true` — itself read via the canonical `identity::production_mode()` helper — so a config-file-only value can never bypass the production guard. Do not relax any gate or collapse the per-posture opt-ins (`FERRUM_MESH_CA_BOOTSTRAP_DEV`, `FERRUM_MESH_ALLOW_STATIC_ID`, `FERRUM_MESH_ALLOW_NO_CA`) into a single flag.
- The `FERRUM_MESH_ALLOW_NO_CA` config-time presence check (no identity *named* at all) has a runtime complement (`enforce_mesh_inbound_fail_closed`, `src/modes/mesh`), at both the startup TLS-setup path and PeerAuthentication live reload, with two deliberately different severities: a listener that would serve **plaintext** (resolved `ServerConfig` `None` — PeerAuthentication DISABLE, or no usable server identity) is refused under `FERRUM_MESH_PRODUCTION_MODE=true` and allowed-with-warning in dev (an explicit DISABLE, or a no-identity posture the config-time gate already acknowledged, is intentional); a **configured-but-unloadable SVID verifier** (all three `FERRUM_GATEWAY_SVID_*` named but the bundle failed to load while the listener serves TLS) is **fatal regardless of production**, mirroring the hard error a broken SVID cert/key already gets. At reload, refusal rejects the slice and keeps the last-good mTLS config (fail-closed by retention). Gateway SVID material also backs the inbound server cert when no `FERRUM_FRONTEND_TLS_*` is set, so an SVID-only mesh serves mTLS rather than plaintext. The runtime gate reads only `identity::production_mode()` (captured once at startup, threaded into the reload path); `identity::allow_no_ca()` is consulted **only** by the config-time gate. Do not move these guardrail reads into `EnvConfig`.
