# Mesh Capture, Injector, Node Agent, And CNI Rules

Implementation invariants for this mesh subsystem. Shared mesh invariants: `mesh.md`; operator docs:
`docs/mesh.md`.

## Injector, Node Agent, And CNI

- Injector mode serves `POST /mutate` Kubernetes AdmissionReview and emits JSON patches only.
- Sidecars run as `PROXY_UID`; optional iptables init container requires `NET_ADMIN`.
- IPv4/IPv6 capture CIDRs must stay partitioned into `iptables` and `ip6tables` blocks. `FERRUM_MESH_IP6TABLES_ENABLED=auto|true|false` controls IPv6 fan-out.
- **UDP capture uses TPROXY, not REDIRECT** (F3 §3.3 Stage 2, `FERRUM_MESH_CAPTURE_UDP_ENABLED` default-OFF/inert): TCP's `nat` REDIRECT rewrites the destination (orig-dst via `SO_ORIGINAL_DST`), which has no UDP analogue, so captured UDP uses `mangle`-table TPROXY (`FERRUM_MESH_UDP_INBOUND`/`FERRUM_MESH_UDP_OUTBOUND`, `-j TPROXY --on-port <FERRUM_MESH_CAPTURE_UDP_PORT, default 15011> --tproxy-mark <FERRUM_MESH_TPROXY_MARK, default 0x733>/<mask>`) — delivers the datagram WITHOUT rewriting dest (orig-dst recovered per-datagram from `IP_RECVORIGDSTADDR` in Stage 3) — plus raw `ip rule add priority 100 fwmark <mark>/<mask> lookup 33133` + `ip route add local 0.0.0.0/0 dev lo table 33133` (and `ip -6` under the v6 fan-out). **The `ip rule` priority is a low constant `TPROXY_ROUTE_RULE_PRIORITY=100`, SEPARATE from the routing TABLE `TPROXY_ROUTE_TABLE=33133`**: the RPDB is priority-ordered and the kernel `main` rule is priority 32766, so the fwmark rule MUST sit below it or `main` resolves the marked datagram first and captured UDP black-holes. Table `33133` is Ferrum-owned, NOT Istio's `133`, so cleanup never risks a co-resident Istio table. **Capture is EGRESS-ONLY (#1808):** the OUTBOUND chain rides `mangle PREROUTING` scoped `-m addrtype ! --dst-type LOCAL` (remote dest). The INBOUND `--dst-type LOCAL` catch-all chain/jump is **gated off** (`emit_inbound = false` in `udp_tproxy_commands_for_family`) — there is no inbound UDP relay yet, and the egress-only capture listener would divert pod-app-bound UDP and DROP it (black-hole for UDP-serving pods), so inbound-to-pod UDP is left uncaptured and flows normally to the app; teardown still reaps any prior inbound chain. The OUTBOUND `! --dst-type LOCAL` scope is the pod-IP-agnostic mirror of the TCP chains' hook separation; re-enable inbound (the gated catch-all, kept ordered after the outbound jump) when an inbound UDP relay lands. **Fail closed when routing is unavailable**: the setup script FATALLY preflights `command -v ip` BEFORE any UDP rule (no `iproute2` ⇒ `set -e` exits, installing NOTHING — TPROXY and routing go in together or not at all, never a TPROXY-without-routing black-hole) and the load-bearing routing ADDs are NOT `|| true`; only the delete-before-add (idempotence) and cleanup stay best-effort. **Routing is installed BEFORE the two `mangle PREROUTING` jumps**: the jumps start steering UDP into the chains, the injector init script has NO cleanup trap, so a routing ADD that failed after the jumps were appended would leave TPROXY live without policy routing (the half-installed black-hole) — emitting `ip rule`/`ip route` first aborts `set -e` before any capture is wired (chains/rules are inert until the jumps append last). **Pod-netns ONLY (host-netns node-agent limitation):** the `--dst-type LOCAL` split is correct only where the pod IP is LOCAL (the injector's pod netns); the node-agent DaemonSet runs `hostNetwork: true` where pod IPs are FORWARDED, so inbound-to-pod would match the OUTBOUND `! --dst-type LOCAL` discriminator. There is no host-netns-safe `addrtype` discriminator without per-pod IP knowledge the fallback lacks, so `CaptureConfig::host_netns` makes `udp_tproxy_commands_for_family` emit NO UDP TPROXY rules for the node-agent (a one-shot warn when UDP capture is on) — eBPF is the supported node-agent UDP path; the host-netns iptables fallback is TCP-only. The UDP listener port is DISTINCT from the TCP outbound port (UDP+TCP can't share a socket). The default mark `0x733` (1843) is Ferrum-owned and deliberately NOT Istio's conventional TPROXY mark `0x539` — Ferrum's `ip rule` matches the mark to steer into the Ferrum table, so defaulting to `0x539` would hijack a co-resident Istio's marked packets (and break Istio); `0x733` sits in a gap clear of Istio's exact marks AND of common MASKED CNI mark classes — Cilium matches `skb->mark & 0xF00`, so the prior default `0xFE3` ALIASED Cilium's `0xF00` class (`0xFE3 & 0xF00 == 0xF00`) and could be misclassified by a co-resident CNI, whereas `0x733 & 0xF00 == 0x700` does not (compile-time asserts in `src/capture/mod.rs` pin the masked-class non-aliasing) — and is collision-free within Ferrum (no other packet marks; the `1337` proxy UID is a socket-owner match, disjoint from `skb->mark`). **TPROXY runs only in PREROUTING** (jumping into a `-j TPROXY` chain from `mangle OUTPUT` is invalid), so the pod's OWN locally-generated UDP egress (which never traverses PREROUTING) is captured via a separate **MARK-only `FERRUM_MESH_UDP_OUTPUT_MARK` chain jumped from `mangle OUTPUT`**: it MARKs egress with the TPROXY fwmark (the proxy-UID `-m owner` self-exclusion lives HERE — owner-match is OUTPUT-context-only, invalid in the PREROUTING chains), the fwmark `ip rule` reroutes the marked datagram to `lo`, and a mark-match `FERRUM_MESH_UDP_REINJECT` PREROUTING rule TPROXY-captures the looped datagram. So sidecar-self-egress UDP IS handled (no longer deferred); the full loop's live validation rides `netns-capture-live`. Default OFF (opt-in): the rules and the consuming listener come up together behind the same flag, so UDP is never redirected into a void; when off NO mangle/TPROXY/routing rules are emitted. Cleanup removes the mangle chains + tears down routing by deleting the EXACT Ferrum-owned rule (`ip rule del priority 100 lookup 33133`) + exact route, never by-lookup or table-flush. The 3 vars are parsed in ONE place (`capture::udp_capture_settings_from_env`), shared by `CaptureConfig::from_env` (node-agent) and the injector.
- **UDP datagram-over-mesh egress (F3 §3.3 Stage 4, DUAL-TRANSPORT — mirrors raw-TCP egress)**: the Stage-3 capture→drop is replaced by capture→frame→mesh-tunnel→peer→unframe→local `UdpSocket`, plus the return path. Materialization mirrors raw-TCP VIP egress and is now **dual-transport** (#1808): `materialize_mesh_outbound_udp_upstreams` gates `Ambient => Hbone, Sidecar => SidecarMtls, _ => return` — **Ambient** relays the datagram tunnel over an HBONE CONNECT (`:15008`), **Sidecar** over a mesh-mTLS CONNECT (`:15006`, `MeshMtlsConnectionPool::open_datagram_tunnel` — the Sidecar counterpart of `get_datagram_tunnel`: same `udp` marker + baggage, 1:1 fresh connection per session, NO capability probe, REQUIRED pinned peer). `build_outbound_mesh_targets` stamps the per-transport tag (`mesh.mtls` + pinned `mesh.spiffe_id` for Sidecar). `service_udp_stream_ports` × `cluster_ips`, `mesh_outbound_udp_upstream_id` (DISTINCT `__mesh-out-udp-upstream-*` id space), `mesh_outbound_udp_relay_proxy` (scheme `Udp` — the HBONE probe gate accepts `Http | Tcp | Udp`). Route table: `HostRouteTable.mesh_udp_egress` via `mesh_udp_egress_decision`, strict `(VIP, UDP port)` (canonicalized for mapped-IPv6). **DR connect timeout**: the synthesized relay proxy carries the UDP upstream's `dispatch_port_overrides` (per-port `portLevelSettings` connectTimeout/keepalive), and `apply_destination_rules` ALSO seeds a DR top-level `trafficPolicy.connectTimeout` onto the upstream's per-TARGET-port overrides (only where no per-port value exists, so portLevelSettings wins) so BOTH `get_datagram_tunnel` AND `open_datagram_tunnel` honor it — the UDP egress upstream is referenced by NO `config.proxies`, so the top-level timeout (applied only to config proxies) would otherwise be lost and the dial would fall back to the relay proxy's 5s default. Capability enrollment: a THIRD pass in `collect_mesh_tcp_egress_capability_targets` enrolls ONLY the Ambient `mesh.hbone` UDP targets (same `retain_keys` trap; widened probe gate or every UDP dial 502s) and SKIPS Sidecar `mesh.mtls` UDP targets (mirrors the raw-TCP passes — never a `:15008` probe to a sidecar; the Sidecar egress branch requires NO capability record). **Framing** (`src/proxy/mesh_udp_frame.rs`): `[u16 BE len][payload]`, max 65535; stateful `read_datagram` decoder over the byte-stream tunnel (partial reads normal; EOF mid-frame ⇒ None, never a partial; 0-length datagram preserved); GRO-coalesced reads framed PER segment. **Marker**: `UDP_PROTOCOL="udp"` + `is_udp_hbone_connect` (NARROWER than `is_hbone_connect` — requires the explicit `udp` marker; the two are DISJOINT, so an old dest 404s a `udp` CONNECT = fail-closed skew). Do NOT loosen `is_hbone_connect`. **Capability probe**: a UDP target probes with `HboneConnectionPool::warmup_datagram_connection` (`udp`-marked datagram CONNECT, mirrors `get_datagram_tunnel`) — NOT the byte-stream `warmup_connection` (`hbone` marker), which would hit the dest's byte-stream relay (TCP→app) instead of its `udp` relay; `probe_hbone` branches on `HboneProbeTarget.is_udp` (set from `BackendScheme::Udp`). **Source-capture producers (per topology, #2013)**: `MeshRuntimeConfig::udp_capture_listener()` emits the current-netns `PlaintextUdpCapture` listener for **Sidecar ONLY** (the injected sidecar shares the pod netns where the injector installed the TPROXY rules). **Ambient** binds NO host-netns listener — its proxy runs outside the pod netns, so a host listener would receive nothing; instead mesh startup runs the per-pod-netns producer `NetnsUdpCaptureManager` (`src/proxy/netns_udp_capture.rs` + `ProxyNetnsUdpBackend`), which installs the UDP TPROXY rules + binds the transparent capture/reply sockets INSIDE each enrolled pod's netns via `setns` (reusing `IptablesPlan::udp_setup_script`/`udp_teardown_script` over the shared `udp_tproxy_commands_for_family`, the shared `run_mesh_udp_capture_on_socket` loop, and a `PodNetnsReplySocketFactory`). **OUTBOUND-ONLY**: `udp_tproxy_commands_for_family` now takes an `emit_inbound` param — the injector passes `true`, the producer passes `false` (`udp_only_commands_for_family`). The producer installs rules in EVERY enrolled pod netns incl. DESTINATION pods, where the inbound `--dst-type LOCAL` chain would capture+drop the HBONE relay's own delivery to the local app AND the source pod's return-path reply → black-hole both ways. It rides the node-agent per-pod registry (now published for Ambient too when UDP capture is on: `should_publish_registry = node_waypoint_in_netns || udp_capture_enabled` — UDP alone, NOT anded with `outbound_capture_enabled`, so a port-0 TCP outbound listener cannot suppress UDP registry publication; does NOT flip the NodeWaypoint ipv6-deny/connect4-deferral posture), binds the socket BEFORE the rules (no black-hole), tears down only its own rules on removal (graceful shutdown `shutdown_all().await`s the per-netns teardown tasks), and disables the proxy-UID owner-match RETURN (no co-located proxy to exclude; keeping `1337` would fail-open a `1337`-app). **Fail-closed startup**: a malformed capture config OR a runtime image missing `sh`/`ip`/`iptables` (`preflight_capture_tools`) aborts mesh startup, never silent-retry. Helm requires `nodeAgent.enabled=true`+ebpf when the ambient UDP producer is on, and the UDP-enable chart predicate accepts only `true`/`1` (matches `parse_bool_env`). **Ambient per-pod authz evidence:** the node-agent registry publishes the pod's SPIFFE ID beside the pod UID; the per-netns producer fixes that pair for its lifetime and `get_datagram_tunnel` stamps `source.principal` + `source.pod_uid` in the existing authenticated HBONE baggage. Destination `mesh_authz` uses it only after the shared trusted-assertor/trust-domain gate and an exact live pod-UID↔SPIFFE slice lookup; otherwise it evaluates mesh-wide policies only. NodeWaypoint UDP/DTLS is a SEPARATE, node-local channel (issue #3286: ingress interface + registry pod addresses) and is unaffected by this HBONE-baggage evidence path. A topology with NO UDP relay (EastWestGateway / EgressGateway / waypoints) with `FERRUM_MESH_CAPTURE_UDP_ENABLED=true` emits NO listener/producer + a one-time `warn!`. `EnvConfig::reserved_gateway_ports()` reserves the host capture port for **Sidecar ONLY** — the Ambient producer binds in the pod netns, so the host port stays free. **Injector/init TPROXY-rule gating for Sidecar is MATCHED to the listener gate** (#1808): the injector only emits Sidecar pods, and `injector::sidecar_udp_capture_supported()` (a central `const fn` switch, now `true`) ENABLES the init container's UDP TPROXY rules, the sidecar's runtime-enable env, AND the transparent-bind capability (`NET_ADMIN`) TOGETHER — so an injected Sidecar with the operator's `udp_capture_enabled` flag set both diverts UDP and binds a listener (the first working end-to-end UDP path). (`udp_tproxy_commands_for_family` itself still gates only on `host_netns`; the topology decision lives in the injector, the only pod-netns emitter. The node-agent/ambient host-netns path installs no UDP rules (`host_netns` short-circuits `udp_tproxy_commands_for_family`); Ambient's UDP source-capture instead rides the **per-pod-netns producer** (#2013, installs rules INSIDE each pod netns) and relays over HBONE. eBPF UDP capture (#1803) stays a non-goal.) **Egress datapath** (`mesh_udp_capture.rs`): the recv loop does route lookup + admit + drop-on-full `try_send` only (hot-path-light); a per-session mpsc+task opens the datagram tunnel via a **dual-transport branch mirroring `mesh_tcp_egress::handle_mesh_tcp_egress`** (1:1 dial, `udp` marker): **Ambient `mesh.hbone`** → `HboneConnectionPool::get_datagram_tunnel` (dial `:15008`, capability-record-gated + pinned `mesh.spiffe_id` plus optional per-pod source evidence); **Sidecar `mesh.mtls`** → `MeshMtlsConnectionPool::open_datagram_tunnel` (dial `:15006`/`mesh.mtls_port`, REQUIRED pinned `mesh.spiffe_id` via `target_mesh_mtls_expected_peer`, NO capability registry); a target with neither tag ends the session. Both share the LB guard + gateway-SVID-present gate; frames+writes. A `LoadBalancerConnectionGuard` is held for the session's lifetime (acquired right after LB selection, like `mesh_tcp_egress`), so least-connections LB sees active UDP sessions. Session teardown removes the map entry via `remove_if` keyed on a per-session `session_id` token (not unconditional `remove`), so an idle-sweep reap + same-key replacement in the gap before the task observes its closed channel never clobbers the replacement / double-decrements the cap. **Egress idle is bidirectional** (mirrors `relay_hbone_udp`): a shared `last_activity` atomic is bumped on BOTH client→egress sends and return-path (tunnel→client) datagrams, watched by one watchdog — a one-way reply stream (client quiet, dest streaming) does NOT time out mid-flow. **Tunnel writes are batched and bounded** (issue #5048): the egress loop drains only ALREADY-queued datagrams (`drain_queued_datagrams`, `try_recv`, never waiting for a batch to fill) into one `mesh_udp_frame::FrameBatch` (≤16 KiB wire / ≤1024 datagrams, the first datagram always joins, an over-bound follower is `held` and opens the next batch so FIFO holds) and writes it as ONE tunnel write under the write deadline (the idle window, or a fixed fallback when idle is disabled); byte reservations are released per dequeued datagram exactly as before, and a failed/stalled write accounts only the datagrams the tunnel fully accepted (`BatchWriteFailure`). `relay_hbone_udp`'s socket→tunnel arm does the same with `try_recv` on the destination socket. Coalescing is load-bearing, not just cheaper: h2 0.4.16 budgets sub-256-byte DATA frames per connection (`too_many_data_frames` → `ENHANCE_YOUR_CALM` GOAWAY), so one-frame-per-datagram bursts of small datagrams can kill the pooled HBONE connection; do not regress to per-datagram `write_all`. A stalled HBONE peer / exhausted flow-control tears the session down (drop tunnel, decrement `active_sessions`, `remove_if`-owned) instead of leaking a stuck task. **Return path (risk #1)**: a per-session transparent `UdpSocket` bound NON-LOCALLY (via `IP_TRANSPARENT`) to the captured orig-dst, so replies are SOURCED FROM the VIP:port the pod dialed (PKTINFO sets only the source IP, not port — a bound transparent socket sets both). **IPv4-mapped clients are canonicalized at capture**: the dual-stack `[::]` socket reports IPv4 senders as `::ffff:a.b.c.d` (`SocketAddr::V6`) while the orig-dst cmsg for the same packet is `SocketAddr::V4`; the client addr is unmapped to its V4 form BEFORE keying the session and building the reply socket, so the reply socket's family matches the orig-dst family and `send_to(client)` succeeds (genuine IPv6 clients are untouched). The session key uses the canonicalized client so key + reply agree. **Dest side**: `is_udp_hbone_connect` flows through the SAME transparent-relay synthesis (`build_inbound_hbone_relay_proxy` + open-relay guard) as the byte-stream relay (a combined `is_hbone_connect_any` drives path-norm / body-buffering-avoidance / CONNECT-405-bypass / route-miss-synthesis); `handle_hbone_udp_request` unframes the tunnel into a local `UdpSocket` to the CONNECT authority (open-relay guard applies — AND is RE-CHECKED on the post-route-override EFFECTIVE destination via `inbound_hbone_relay_destination_allowed`, since the unknown-id synthesized relay proxy inherits the global plugin chain and a route-override plugin could otherwise move the destination outside the loopback / slice-declared-workload allowlist after the build-time guard ran) and frames replies back. `relay_hbone_udp`'s idle is refreshed on activity in BOTH directions (shared `last_activity` atomic + watchdog), so a one-way tunnel→app flow (e.g. telemetry) doesn't time out while the tunnel is active. The destination relay (`handle_hbone_udp_request`/`relay_hbone_udp`) is e2e functional-tested by `functional_mesh_udp_dest_*` **in isolation** (Stage 7: a `udp` mTLS CONNECT → framed datagram → local (non-enrolled) UDP echo → framed reply; + off-allowlist-refused + untrusted-peer-fail-closed; no root/netns needed) — this does NOT cover the destination pod being an ENROLLED Ambient pod, where the `tc_inbound` eBPF guard drops UDP to the pod IP and the pod's own OUTPUT-mark rules re-capture the app's reply to a host-netns relay socket. Two gaps remain, both fail-CLOSED (dropped, not leaked) and out of scope for the transport-half producer (#2030): (1) the live **source-capture** e2e (TPROXY → tunnel → return-source spoofing), which rides the §3.1 `netns-capture-live` follow-up; and (2) the full **e2e Ambient relay to an enrolled destination pod**, pending a TC-inbound UDP admit keyed on the relay socket's mark/identity (`ebpf/ferrum-ebpf/src/tc_inbound.rs`) + moving the dest-side inbound relay socket INSIDE the destination pod netns (so the reply is pod-LOCAL, excluded by the existing `! --dst-type LOCAL` scope) — a two-pod (both enrolled) live verification (tracked under #2013). **DTLS passthrough (Stage 5):** a DTLS port on THIS path is declared `protocol: UDP` and rides the SAME egress datapath **OPAQUELY**, with no `AppProtocol::Dtls` involved (that variant exists only for the NodeWaypoint listener surface of issue #3286 and is refused outright at the EgressGateway): the mesh never terminates DTLS, parses the ClientHello, or routes on DTLS SNI (UNLIKE the standalone `passthrough` UDP/DTLS stream proxy, which peeks the ClientHello for SNI). The inner DTLS stays end-to-end between workloads; the outer mesh hop is HBONE/mesh-mTLS-secured. East-west pod→peer only; EgressGateway external **DTLS** stays out of scope. Opaque relay pinned by `dtls_handshake_datagram_round_trips_opaque` in `mesh_udp_frame`.
- **External UDP egress via the EgressGateway (issue #3263) — BOTH halves**: the TERMINATOR is the gateway's `:15090` SVID-mTLS listener; `materialize_egress_gateway_proxies` publishes the runtime-only allowlist `MeshConfig.egress_udp_destinations` (rebuilt + reassigned on EVERY apply, empty off `EgressGateway` / with `FERRUM_MESH_EGRESS_STREAM_ENABLED=false`), consulted by `mesh_egress_udp_destination_dial_endpoint` / `mesh_egress_udp_destination_allowed`. **AUTHORITY ≠ DIAL DESTINATION** — each admission carries a precomputed bounded `dial_endpoints` set (`MAX_EGRESS_UDP_DIAL_ENDPOINTS` per destination + closed total `MAX_EGRESS_UDP_DESTINATIONS` allowlist cap, modulo-cursor selection, one relaxed atomic per CONNECT; entries beyond either cap are refused fail-closed). Post-override `mesh_egress_udp_destination_allowed` matches **dial endpoints only** (a STATIC hostname authority must never become an effective socket target — that would DNS-bypass `endpoints[]`; DNS/NONE and STATIC endpoint-IP dial targets remain usable because they are themselves dial endpoints; original-authority lookup and the authenticated-peer gate are unchanged): under `STATIC` a host authority dials the declared `endpoints[]` and is NEVER DNS-resolved, an endpoint-IP authority dials ONLY the endpoint it names, and a `STATIC` port with no usable endpoint is refused OUTRIGHT (never fall back to resolving the host); under `DNS`/`NONE` the single dial endpoint is the authority host itself. Do NOT collapse `host` and `dial_endpoints` back into one field. The PRODUCER is `materialize_mesh_external_udp_egress_upstreams` (`Sidecar`/`Ambient` only — the topologies with a UDP source-capture producer), gated by the SAME `FERRUM_MESH_EGRESS_STREAM_ENABLED` opt-in as the gateway allowlist (flag-off clears/publishes nothing so the two halves cannot disagree): for each `MESH_EXTERNAL` `ServiceEntry` UDP port with `resolution: STATIC` + IP-literal endpoints it emits `MeshConfig.external_udp_egress_routes` (`serde(skip)`, id space `__mesh-out-udp-ext-upstream-*` / `__mesh-out-udp-ext-relay-*`) plus ONE upstream whose single target dials the operator-configured `FERRUM_MESH_EGRESS_GATEWAY_ADDR` tagged `mesh.mtls` + `mesh.mtls_port` + REQUIRED pinned `mesh.spiffe_id` (`FERRUM_MESH_EGRESS_GATEWAY_SPIFFE_ID`) with `mesh.mtls_authority_host` = the EXTERNAL endpoint. Never `mesh.hbone`: the gateway has no `:15008`. `RouterCache::build_route_table` folds those routes into the SAME `mesh_udp_egress` `(dest ip, port)` index AFTER the in-mesh VIP loop (`or_insert`, so an in-mesh VIP always wins) — `mesh_udp_capture` therefore needs no external special case. **The two halves must refuse the SAME entry shapes**, or the producer publishes a route whose CONNECT the terminator is guaranteed to 404: the per-entry admission tests are kept identical to `build_egress_proxies_and_upstreams`'s — `location == MESH_EXTERNAL`, `service_entry_exported_to_namespace` against THIS workload's namespace (re-applied producer-side because `prepare_gateway_config_for_native_slice` takes a CP/xDS slice that `MeshSlice::from_gateway_config` never re-narrowed, and an empty `exportTo` is namespace-local), and a NON-EMPTY `hosts[]` (the gateway skips a host-less entry before the UDP branch, so it admits nothing at all — not even its endpoint-IP authorities). Fail closed with field-specific diagnostics at every step (no configured gateway ⇒ no route; non-`STATIC` resolution ⇒ refused, since a datagram carries no Host and only a declared endpoint address can attribute it; one env var without the other ⇒ startup error), and never a direct unauthenticated dial of the external destination.
- **UDP fail-closed contract (F3 §3.3 Stage 6 — consolidates Stage 3–4 hardening; full gate table in `docs/mesh.md`)**: the UDP datapath mirrors the raw-TCP egress fail-closed table gate-for-gate, and **every gate drops/rejects on doubt with NO plaintext or alternate-hop fallback** — every dial-error path ENDS the session. Do not regress any of: **routability** (orig-dst ∈ `mesh_udp_egress`; non-match drops BEFORE a slot/task is reserved), **gateway SVID present** (no SVID ⇒ end session, never plaintext), **Ambient capability probe** (un-enrolled `Udp` ⇒ drop, never blind-dial; the probe gate stays `Http|Tcp|Udp`), **pinned-peer SPIFFE** (missing/corrupt ⇒ refuse dial), **transport selection** (materializer stamps exactly one of `mesh.hbone`/`mesh.mtls`; runtime precedence HBONE→mesh-mTLS, neither ⇒ end session; a both-tags target — corrupted-only — resolves to HBONE, never relaxing a gate), **dest authenticated-peer** (`peer_spiffe_id.is_none()` ⇒ 403 before any socket opens; enforced inline in the handler, predicate-pinned; the fail-closed OUTCOME is e2e-tested by `functional_mesh_udp_dest_untrusted_peer_fails_closed` — under STRICT inbound the unchained peer is rejected at TLS, handler 403 stays predicate-pinned), **dest open-relay guard** (loopback / slice-declared workload addr+port only, RE-checked on the post-route-override effective destination ⇒ 403), **marker discipline** (`is_udp_hbone_connect`/`is_hbone_connect` disjoint AND exhaustive — a present-but-unparseable/non-UTF-8 marker fails closed to neither, NOT markerless; an unknown/future/malformed marker ⇒ neither ⇒ the dispatcher 405s the unrecognized CONNECT, pinned by `connect_marker_classification_is_exhaustive_and_fail_closed`), **session DoS bounds** (count + queued-bytes + idle), **return-path isolation** (per-session transparent socket bound to orig-dst, send-only, reply only to the captured client). Each gate has a named regression pin (see the `docs/mesh.md` table); posture confirmed by two independent audits + an adversarial red-team over 10 attack classes (no fail-open found). The ONE residual — the inbound guard validating the destination *string* before DNS resolution — is **not UDP-specific** (identical to the byte-stream relay's `connect_backend`) and inert in practice (workload addresses are pod IPs/loopback); out of scope for this stage.
- **Sidecar TCP capture listeners are family-complete (#4271).** `iptables` and `ip6tables` REDIRECT at the SAME ports, so the Sidecar listener plan is derived from whether IPv6 capture rules exist (`FERRUM_MESH_CAPTURE_IPV6_ENABLED`, derived from `FERRUM_MESH_IP6TABLES_ENABLED` + include/exclude CIDR families when unset; set explicitly by the injector when the rendered init plan contains `ip6tables` commands). A WILDCARD capture address becomes ONE dual-stack `[::]` listener with `IPV6_V6ONLY` explicitly disabled (a sibling `0.0.0.0` bind on the same port would be `EADDRINUSE`), downgrading to `0.0.0.0` ONLY on genuine IPv6 unavailability (`EAFNOSUPPORT`/`EADDRNOTAVAIL`/`EPROTONOSUPPORT`) and NEVER on `EADDRINUSE`. A LOOPBACK capture address becomes TWO listeners (`127.0.0.1` + `[::1]`) because `REDIRECT` in `OUTPUT` targets `127.0.0.1`/`::1` and a `[::1]` socket never sees v4-mapped traffic. Any other specific literal is a startup error from `validate_capture_listener_families` (`listener_plan()` stays infallible and warn-falls-back for read-only callers). `original_dst_from_raw_fd` folds a v4-mapped local address to IPv4 BEFORE choosing `SOL_IP`/`SOL_IPV6`, and compares the recovered destination against the CANONICAL local address.
- **`nat FERRUM_MESH_OUTBOUND` leads with `-m addrtype --dst-type LOCAL -j RETURN` (#4276)**, both families, ahead of every REDIRECT, gated on `!host_netns` exactly like the UDP sibling's `addrtype` direction split. Without it the shipped catch-all REDIRECT hairpins intra-pod `127.0.0.1` TCP into the outbound proxy. Order is load-bearing: once REDIRECT fires the chain returns.
- **Inbound HBONE relay screens resolved DNS answers (issue #4150).** A relay destination that resolves to loopback is refused immediately before the ordinary TCP/UDP dial via `MeshConfig::screen_inbound_relay_resolved_ips` on the current `RequestEpoch` mesh snapshot: mixed answers retain only the non-loopback candidates, an all-loopback answer fails closed. Canonicalisation folds IPv4-mapped IPv6 (`::ffff:127.0.0.1`) BEFORE the check, because `IpAddr::is_loopback()` is false for the mapped form while the dial still reaches `127.0.0.1`. Sidecar retains its own-network-namespace loopback privilege; Sidecar `ingress[]` remaps and separately authorized EgressGateway external UDP skip the screen.
- Cleanup scripts are best-effort even when `ip6tables` is missing.
- Injected SPIFFE ID format is `spiffe://{trust_domain}/ns/{namespace}/sa/{service_account}`.
- JWT secrets in injected manifests use `SecretKeyRef`, never plaintext.
- Opt in with `ferrum.io/inject=true` or `ferrum.io/mesh=enabled`; opt out with `sidecar.istio.io/inject=false` or `ferrum.io/inject=false`.
- Node-agent CNI is opt-in with `FERRUM_NODE_AGENT_CNI_ENABLED=false` by default.
- When enabled, node-agent binds `FERRUM_NODE_AGENT_CNI_SOCKET_PATH` and the `ferrum-cni` binary forwards kubelet ADD/DEL/CHECK/STATUS/GC over that socket.
- STATUS (CNI 1.1.0 only) is a fail-closed readiness probe: success means the node-agent listener is up, the main loop has completed initial pod sync, and a bounded live Kubernetes API pods list probe (same RBAC as ADD metadata; ≤750ms, under the 5s CNI RPC timeout) succeeded so ADD can be serviced; socket/IPC failure or not-ready replies map to CNI error code 50 without attachment fields or secret/input/Kubernetes-detail echoing. Older negotiated versions keep ADD/DEL/CHECK and fail closed on STATUS.
- Explicit node-global iptables fallback has no pod watcher or per-pod metadata dependency: its CNI ADD/CHECK/STATUS/GC remain unavailable until fallback rule installation completes, after which STATUS reflects node-global capture readiness rather than the eBPF relist/API probe.
- GC (CNI 1.1.0 only) reconciles Ferrum-owned CNI attachments against the required `cni.dev/valid-attachments` valid set and never removes watcher-only, another CNI network's, another pod's, or foreign-generation state. Ownership is mirrored into a crash-safe durable file beside the absolute `FERRUM_NODE_AGENT_CNI_SOCKET_PATH` (bound to the exact socket path identity) so GC can rehydrate Ferrum-owned `(network, containerID, ifname) -> pod UID` identity and the cleanup snapshot required to tear down stale eBPF state after node-agent restart. GC waits for the initial pod relist before using restored cleanup keys; rejected durable state and unresolved enrollment ownership fail closed without sweeping.
- In explicit node-global iptables fallback, CNI passthrough is gated on completed rule installation. GC may no-op only when the socket-bound durable file proves that the requested network has no stale eBPF claim; otherwise it fails closed and retains the record for an eBPF-capable generation to reconcile.
- kube-rs watcher remains source of truth; CNI only closes the kubelet-vs-watcher race and does not carry labels or annotations.
- **The chained conflist is a node-wide pod-creation dependency, not an optimization** (#3609): ADD fails closed on IPC transport failure, so while the chain is installed an unreachable node-agent leaves every new pod on the node in `ContainerCreating`. That posture is deliberate — do not relax ADD to pass through unenrolled — but its lifecycle is load-bearing and must not be weakened. DEL is the opposite: IPC transport failure (missing socket, connect refused, timeout) emits the CNI empty-success response so kubelet can finish teardown; stale Ferrum state is reclaimed by CNI GC and node-agent sweeps (#4309). CHECK transport failure stays fail-closed per the CNI spec (cannot verify attachment); node-agent rejection still fails CHECK. `install` publishes in a FIXED order and each step exists to make the next failure recoverable: under the install lock, preflight the configured target conflist (absent → proceed; present → proceed only when it is a bounded regular single-link file opened `O_NOFOLLOW` whose Ferrum marker names this same owner — refuse unmarked/malformed/oversized/symlink/non-regular/hard-link/other-owner with no shared side effects; REMEMBER the marker + device/inode/length) → **find the primary, build the chained conflist, and serialize it, ALL before any shared write** (these are the steps that fail on input the installer does not control, so they must not run after the manifest or binary has been touched) → stage the binary in the destination dir under an `O_EXCL | O_NOFOLLOW` unguessable temp name (hashing as it is written) → **gate the shared binary** → write the sibling `.ferrum-cni-owned.marker` manifest (owner/generation, `confFileName`+`binaryFileName`, the staged digest and an ATTESTED previous digest) → publish the binary by atomic same-dir `rename` → write the conflist LAST. The manifest lands BEFORE the shared binary, so nothing this install can leave behind is un-provable and therefore nothing is un-removable; the conflist lands last because the moment it does every pod ADD traverses `ferrum-cni`. Do NOT reorder the binary ahead of the manifest, and do NOT move validation/construction back after the shared writes. **`previousBinarySha256` is an attestation, not an observation**: hashing whatever occupies `/opt/cni/bin/ferrum-cni` proves nothing, so it is recorded ONLY when the manifest already on disk carries this same owner, names these exact artifact names, and had itself already recorded that digest; every other case writes `null` and the pre-existing binary stays unremovable (inert, so chain cleanup still succeeds). **Install applies the shared-binary rule in the other direction too**: while another remaining `.conf`/`.conflist`/`.json` names `ferrum-cni`, the shared executable is NOT replaced with different bytes — byte-identical republication is allowed, an unclassifiable installed object or an unscannable directory fails safe (`SharedBinaryInUse`, no shared mutation). **A failed install must not strand a same-owner chain**: on the ordinary error path, if the preflight found this owner's previous chain, install removes it under the same lock after re-proving owner AND generation AND device/inode — a different owner or a generation that overtook the run is retained and logged, and the original error is always surfaced. Without that, a failed N-1 → N upgrade leaves every pod ADD traversing a dead socket while the replacement's watcher (scoped to the never-published N) correctly reports `NeverPublished` and removes nothing. In-place upgrade semantics are part of the contract: publish is `rename`-only (never truncate-in-place, so an already-exec'd plugin keeps a valid inode), and a staged digest identical to the installed one SKIPS the rename entirely. `uninstall` removes ONLY marker-matching artifacts, conflist FIRST then binary. `/opt/cni/bin/ferrum-cni` is SHARED: it goes only when this chain is cleared, NO remaining `.conf`/`.conflist`/`.json` names `ferrum-cni`, the manifest names THESE artifacts, and the digest matches — an unscannable directory or mis-bound manifest keeps it (retaining an inert file beats breaking another release). Every mutating run holds an exclusive `flock` on `.ferrum-cni-install.lock` in the conf dir for its whole duration; artifacts are opened `O_NOFOLLOW`, classified against the OPEN HANDLE, read under a hard byte cap that does not trust the pre-read length, hashed through that SAME handle, and removed only after a re-open confirms the same device/inode. Cleanup succeeds only when the conflist is gone or provably another owner's; a foreign conflist exits non-zero rather than declaring success. `rollback-watch` (chart: a native sidecar ordered BEFORE the installer) runs in TWO phases: it first waits for a conflist carrying its OWN owner AND generation to appear (the install-completed proof — the readiness budget MUST NOT start before that, or the watcher can delete state an installer is still publishing), then applies the readiness budget. Phase 1 must NOT probe STATUS at all: the socket path is node-scoped and outlives an install, so an `Ok` from an earlier node-agent generation would return `Ready` and permanently disarm the rollback for a chain this generation has not published yet (pinned by `a_status_probe_before_publication_can_never_disarm_the_rollback`). Outcomes are distinct and truthful — `Ready` / never-published / rolled-back / superseded / incomplete — and only rolled-back may claim the dependency was lifted. Helm wires cleanup as a `pre-delete` **DaemonSet** (one pod per node; a Job strands a multi-node cluster) whose readiness marker is retracted at process start (never following symlinks; a non-regular file at the marker path is REFUSED, not deleted) and published atomically only after THIS run's cleanup succeeded — never add `pre-upgrade`/`pre-rollback` to that hook, or a rolling replacement would uninstall still-required CNI state. Both cleanup pods MUST stay `hostNetwork: true`: a pod needing its own CNI sandbox cannot start on a node whose chain is broken, so the hook would deadlock exactly where it is needed. **Helm hook-deletion semantics decide the rest of the graph**: on Helm **3.19+ and v4** a hook failure deletes every EARLIER hook carrying `hook-succeeded` (`deleteHooksByPolicy(executingHooks[0:i], HookSucceeded, ...)` in `pkg/action/hooks.go`; 3.18 and older delete only the FAILING hook via its `hook-failed` policy and reach the succeeded sweep only when the whole phase passed — do not restate this as "v3 and v4"), so the cleanup ServiceAccounts + Role + RoleBinding are ORDINARY release resources (never hooks) and the cleanup DaemonSet carries `before-hook-creation` ONLY. That policy would ALSO delete the DaemonSet the instant it was created on every Helm version (`WatchUntilReady` treats a non-Job/Pod kind as succeeded on creation), so the shape is right regardless of Helm version. The wait Job (which may keep `hook-succeeded`, being last) deletes that DaemonSet itself with FOREGROUND propagation and refuses to report success until the API server 404s it; its Role is `get`+`delete` on the named DaemonSet plus `get` on its status — no list/watch/unnamed access, ever. A controller-observed `0/0` cleanup report is a failure, not vacuous success: with no scheduled cleanup pod there is no evidence that any node's chain was lifted, so the wait Job retains the DaemonSet and blocks release deletion. A failed wait therefore leaves the DaemonSet, its logs and the identity intact and `helm uninstall` retries cleanly. Hosted evidence is the Rust integration suite, the normal CI Helm rendering/static contract assertions, and the privileged live kind suite in `tests/k8s/cni_lifecycle_live/run.sh` (workflow `.github/workflows/cni-lifecycle-live.yml`). Post-readiness crash-loops are deliberately NOT auto-rolled-back — recovery is the manual path in `docs/node_agent.md` "Recovering a node".
