# Rust CodeQL extraction diagnostic

The default CodeQL Rust scan completes, but its initial run at
`00d94309caa774eee28409b5f9fef779e583ba14` reported macro-expansion,
unbuilt-procedural-macro, and missing `OUT_DIR` diagnostics. Its extractor
enabled all features, including the mutually exclusive `crypto-ring` and
`fips` profiles. Scanning every file does not establish complete macro or
generated-code coverage, and these diagnostics are not verified vulnerabilities.

After this workflow has landed on `main`, a maintainer can run:

```sh
gh workflow run codeql-extraction-diagnostic.yml --ref main
# Add extractor detail when investigating unresolved macro expansion:
gh workflow run codeql-extraction-diagnostic.yml --ref main -f extractor_log_level=debug
```

The workflow runs only on explicit dispatch in the public upstream repository,
on standard Ubuntu runners. The two jobs run sequentially, without a shared
build cache or artifact upload. CodeQL CLI 2.27.3 matches the initial baseline
and is pinned by its release asset's SHA-256 digest.

The ordinary profile selects `default,cloud-secrets`; the FIPS profile selects
`fips,cloud-secrets` without default features. Each installs the build-script
prerequisites and creates a database in build mode `none`, which lets the Rust
extractor build scripts and procedural macros without a full application build.
It does not evaluate queries, upload SARIF, replace default scanning, change
merge requirements, or establish FIPS certification.

Compare each job's complete extraction log, summary, and generated-binding
inventory. Database creation uses `--no-cleanup` so finalization retains the
build workspace. The evidence step prints SHA-256 hashes and paths for Rust
files generated by this application's build script, including protobuf and
custom-plugin bindings. An absent inventory fails the evidence step instead
of silently omitting the proof. No database or build artifacts are uploaded;
the runner discards them after the job.

Debug output can be large. That mode retains the complete log only on the
ephemeral runner and prints a bounded view: initial configuration, the eight
lines preceding each warning/error (up to 2,000 contexts), and completion/timing
records. The job summary still counts warnings from the complete log.

In particular, check Tokio `select!` expansion, SPIFFE Workload API
bindings, and the custom plugin registry. The raw WARN-line count is a
reproducible log measure, not a count of missing files or security alerts.
Warnings may repeat; absence of a warning does not prove complete modeling.
The binding inventory proves file existence only, not extraction of every path.

## Verified pilot and remaining work

[Run 40898938550](https://github.com/ferrum-edge/ferrum-edge/actions/runs/40898938550)
created both databases successfully at `d5bfd4417f47902830dbe151d7bf232ef401da2a`.
Its valid profiles removed the unbuilt-procedural-macro, conflicting-feature,
expected-pattern and `OUT_DIR` warnings. Ordinary/FIPS extraction still reported
808/807 unique warning messages, including the same six Tokio macro expansion
warnings in five production source files. The pilot did not retain its generated
binding inventory, which the retention flag and mandatory inventory now address.

The six production warnings affect Mongo lease renewal, HTTP/3 upload
cancellation, two plugin implementations, WebSocket shutdown, and a frontend TLS
deadline. A small, separately compiled reproducer with Tokio 1.54.1,
tokio-macros 2.7.0 and async-trait 0.1.92 extracts successfully with CodeQL 2.27.3
on macOS. That result does not explain the Linux project failures. The extractor
reports these warnings in its
[semantic-expansion fallback](https://github.com/github/codeql/blob/codeql-cli/v2.27.3/rust/extractor/src/translate/base.rs#L462-L475); its
generic diagnostic does not identify the cause. Keep the affected runtime code
unchanged until a project-level diagnostic establishes a safe remedy. Do not
classify an upstream defect as confirmed solely from this warning.

Both profiles also report unavailable semantic analyzers for optional or
platform-specific modules. Linux `ebpf` is needed for `src/ebpf/loader.rs`;
`pkcs11` is needed for the HSM-backed TLS implementation; a Windows target is
needed for the Windows tenant-file implementation. Benchmark/fuzz helpers have
separate feature gates. `gateway_entry.rs` is included by `main.rs`, so its
standalone-module notice alone does not establish missing startup coverage.

## Coverage decision required before migration

Keep default setup enabled while testing this diagnostic. Any migration to
advanced setup requires a separate approval and must preserve Actions, C/C++,
Python and Rust, default queries, alerts-only operation, and standard public
runners. A concrete candidate is:

| Rust profile | Standard runner | Features |
| --- | --- | --- |
| Linux ordinary release | `ubuntu-26.04` | `default,cloud-secrets` |
| Linux FIPS release | `ubuntu-26.04` | `fips,cloud-secrets` |
| Linux ordinary optional security features | `ubuntu-26.04` | `default,cloud-secrets,acme,pkcs11,ebpf` |
| Linux FIPS optional security features | `ubuntu-26.04` | `fips,cloud-secrets,acme,pkcs11,ebpf` |
| Windows ordinary release | `windows-2025` | `default,cloud-secrets` |
| macOS ordinary release | `macos-15` | `default,cloud-secrets` |

Run the two Linux release profiles on the existing default/protected-branch
push/PR triggers and weekly schedule. Run the additional optional/platform
profiles weekly and on manual dispatch initially; keep heavy Rust jobs
sequential. Preserve the three non-Rust analyses and their current triggers.
Validate extraction and generated bindings for every proposed row before
switching setup mode. Query results and processed uploads must then succeed
before declaring those profiles covered. New categories may change alert
grouping; this proposal does not authorize dismissing existing alerts.

Benchmark/fuzz feature configurations remain explicitly outside this production
proposal. Source/branch changes and overlapping conditional code require review;
even this matrix would not prove every feature combination or macro path.

These two profiles are a diagnostic comparison. They do not cover every optional
feature or platform, and must not replace the current scans without a separate
coverage decision. Existing CodeQL baseline alerts still need independent
triage. This extraction-only workflow neither counts nor validates those alerts.
