# OIDC Relying Party

Ferrum Edge can act as an OpenID Connect relying party for browser-facing routes with the `oidc_relying_party` plugin. The plugin starts an authorization-code flow with PKCE, validates the returned ID token against provider JWKS, creates an encrypted gateway session cookie, optionally enriches claims from UserInfo, and can fan selected claims out to upstream request headers. The session uses a sliding idle window and, when a refresh token is available, transparently refreshes the access/ID tokens before they expire.

## Minimal Configuration

```yaml
plugin_name: oidc_relying_party
config:
  providers:
    - issuer: "https://idp.example.com/"
      discovery_url: "https://idp.example.com/.well-known/openid-configuration"
      client_id: ferrum-edge
      scopes: ["openid", "profile", "email"]
      redirect_uri: "https://edge.example.com/oidc/callback"
      callback_path: "/oidc/callback"
      client_auth:
        method: client_secret_basic
        client_secret: "${OIDC_CLIENT_SECRET}"
      audiences: ["ferrum-edge"]
      claim_headers:
        email: X-Authenticated-Email
  session:
    encryption_secret: "${OIDC_SESSION_SECRET_32_BYTES_MIN}"
  behavior:
    post_login_default_path: "/"
```

Exactly one provider is supported. Use `discovery_url` for normal OIDC providers, or set `authorization_endpoint`, `token_endpoint`, and `jwks_uri` explicitly for providers without discovery. Provider endpoints must use HTTPS except for `localhost` or literal loopback development endpoints.

A discovery document is used only when its `issuer` member is exactly the configured `issuer` ([OpenID Connect Discovery §4.3](https://openid.net/specs/openid-connect-discovery-1_0.html#ProviderConfigurationValidation)); a missing or different issuer fails discovery (logged, retried with backoff) and browser challenges answer `503` until it resolves, so a discovery URL pointing at the wrong tenant can never send users or the client credential to that tenant. Once the issuer matched, discovered endpoints must use HTTPS but may live on other origins — Google publishes its token, JWKS, and UserInfo endpoints on hosts other than `accounts.google.com`, and Microsoft Entra ID publishes UserInfo on `graph.microsoft.com`. Plain HTTP is accepted only for a loopback development `discovery_url`, and only on that URL's own origin. Every provider call still dials through the shared plugin HTTP client, whose backend egress policy screens the resolved address.

`userinfo_endpoint` and `end_session_endpoint` may be set alongside `discovery_url`. An explicitly configured value overrides the discovery document (and still applies when discovery omits that field); the overridden discovery value is never read, so an advertisement discovery would refuse cannot fail discovery. Optional endpoints that do come from discovery keep the fail-closed endpoint validation above. `authorization_endpoint`, `token_endpoint`, and `jwks_uri` remain mutually exclusive with `discovery_url`.

## Request Lifecycle

The plugin is active in four phases, plus the successful-WebSocket-handshake decorator (priority `1075`):

| Phase | Responsibility |
|---|---|
| `on_request_received` | Serves `providers[].callback_path` (authorization-code exchange) and `providers[].logout_path` (local cookie deletion, optional RP-initiated logout and revocation) before any proxying |
| `authenticate` | Opens the session cookie, enforces the absolute/idle bounds and the claims-freshness gate, refreshes tokens when due, resolves the consumer identity, and issues the browser challenge when there is no usable session |
| `before_proxy` | Installs `claim_headers` on the backend request and removes this plugin's own cookies from the forwarded `Cookie` header |
| `after_proxy` | Emits the rolling/refreshed session cookie as `Set-Cookie` on the proxied response, preserving any cookie the backend also set. A successful WebSocket handshake (HTTP/1.1 `101`, HTTP/2 and HTTP/3 Extended CONNECT `200`) bypasses `after_proxy`, so the same staged cookie is appended by the handshake response decorator instead; a refresh or idle slide performed while authenticating a WebSocket is never lost |

## Security Behavior

- `redirect_uri` must be an absolute URI with no fragment ([RFC 6749 §3.1.2](https://www.rfc-editor.org/rfc/rfc6749.html#section-3.1.2)); a fixed query component is allowed. The callback path is handled by the plugin before proxying. Before starting a browser flow, Ferrum requires the request `Host`/`:authority` to identify the same host as `redirect_uri`; DNS names compare case-insensitively, IP literals compare by address, and ports are ignored because cookies are not port-scoped. Trailing-dot DNS callback hosts, missing or malformed request authorities, and different hosts are rejected before state, cookies, or an authorization redirect are issued. In particular, a request on `app.example.com` cannot use a callback on `auth.example.com`; route the initial login through the callback host or configure a same-host callback instead. Forwarded-host headers do not override the request authority for this check.
- The ID token issuer, audience, expiry, not-before, and nonce are validated.
- ID token signature verification is bound to the header `kid`; a missing, empty, or unknown `kid` fails closed with no all-keys fallback. An unknown non-empty `kid` additionally triggers at most one out-of-band JWKS fetch per cooldown window (the shared JWKS store's `kid_miss_refresh_cooldown_seconds`, 30 s by default), so an identity-provider key rotation recovers without waiting out the refresh interval. The triggering request still fails closed; a later request verifies once the refreshed key set is published. This plugin has no cooldown field of its own — it consumes the process-wide JWKS store `jwks_auth` uses.
- ID tokens require a non-empty `sub`; multi-audience tokens require `azp` to identify the configured client. UserInfo must carry the same `sub` before any UserInfo claim is consumed.
- Sessions are sealed with AES-256-GCM and cryptographically bound to a versioned provider/client/audience/policy context. The context covers only what a sealed session asserts: the issuer and endpoints, the client and its authentication method, the redirect URI and callback path, scopes, audiences, required scopes and roles and their claim paths, the identity and header claims, `claim_headers`, the ID-token clock skew, and the session store, lifetimes, and cookie scope (`secure`, `http_only`, `same_site`, `domain`, `path`). Presentation and admission settings — the challenge statuses, `html_accept_substrings`, the redirect allowlist and default path, the pending-flow cache sizes and lifetime, `refresh_skew_secs`, the logout path and behavior, and `max_cookie_bytes` — are not part of it, so changing one of them on a reload keeps every user signed in. Changing a context field (for example `client_id` or `required_roles`) invalidates existing sessions and in-flight logins, which then re-authenticate. `session.encryption_secret` must be at least 32 bytes; `session.encryption_secret_previous` supports cookie rotation within the same context. Both fields are rejected at admission when they hold a known-public value: Ferrum's documented `${OIDC_SESSION_SECRET_32_BYTES_MIN}` placeholder stored literally, the key Ferrum Foundry's OIDC relying-party template published, the sequential and fixture secrets Ferrum's own examples and tests used, or an obvious placeholder (`changeme`, `change-me`/`change_me`, `replace-me`/`replace_me`, `placeholder`, `your-secret`/`your_secret`). Screening covers the supplied value and its effective key material: standard Base64 is decoded only when it yields at least 32 bytes, otherwise the raw value is used before HKDF. Base64 spellings of denied values are rejected, and so is an unresolved `${NAME}` environment placeholder (a `${` followed by a name and `}`) anywhere in either textual value, with its own error. Other text containing `${` is not treated as a placeholder. The rejection runs on every write path — Admin API create/update, batch, restore, and file/database config load — and surfaces as an Admin API `400` naming the field without revealing the secret. Generate a unique random secret per deployment.
- When `session.cookie_name` is omitted, Ferrum derives a context-specific name so differently configured relying parties on one host do not reuse a default cookie, and prefixes it to match the attributes the cookie is actually emitted with. A cookie prefix carries its own rules and a browser discards a cookie that violates them, so the prefix is chosen from the effective scope: `__Host-` when `session.secure` is true, `session.domain` is unset, and `session.path` is `/` (all defaults); `__Secure-` when `session.secure` is true but a `Domain` or a non-root `Path` is configured; and no prefix at all when `session.secure` is false, because `__Secure-`/`__Host-` both require `Secure`. An explicit `session.cookie_name` opts out of automatic naming and is emitted verbatim. Upgrading from a release that used the unprefixed default name forces users to log in again.
- `session.store` supports only `cookie`; Redis-backed server-side sessions are rejected until implemented.
- `providers[].callback_path` and `providers[].logout_path` must already be canonical request paths: no percent-escapes, empty (`//`) or dot (`.`/`..`) segments, or backslashes. The frontend canonicalizes every request path before any plugin runs and these paths are compared with that canonical form, so a spelling canonicalization would change (`/oauth/%63allback`) could never match and one the frontend refuses (`/oauth//callback`) could never be reached; both are rejected at admission.
- `session.cookie_name`, `session.path`, `session.domain`, `providers[].callback_path`, and `providers[].logout_path` are validated against cookie syntax at admission, because they are concatenated into `Set-Cookie` verbatim. A cookie name must be an RFC 6265 `cookie-name` token (ASCII, no control characters, spaces, or separators such as `;` `=` `,` `"`); a cookie path must start with `/` and contain no control characters, spaces, commas, or `;`; a domain must be a bare DNS name (optionally with the legacy leading dot) with no scheme, port, path, or attribute delimiter. An explicit `__Host-` name additionally requires `session.secure: true`, no `session.domain`, and `session.path: /`, and an explicit `__Secure-` name requires `session.secure: true` — a browser discards a prefixed cookie that violates its prefix, which would otherwise present as a silent login loop.
- Browser authorization-code flows are sealed into a distinct short-lived, host-only HttpOnly/SameSite correlation cookie with AES-256-GCM under the same `session.encryption_secret` (and optional `encryption_secret_previous`) as sessions, but with a distinct associated-data label so session cookies cannot be reused as pending-flow state. The OAuth `state` query parameter stays an opaque handle that selects the cookie name; the PKCE verifier, the original redirect, expiry, and context binding live only in the sealed cookie — never in URLs, logs, or unsealed cookie values. The authorization request itself sends `state`, `nonce`, and the PKCE `code_challenge` **and** `code_challenge_method` over the wire (alongside `response_type`, `client_id`, `redirect_uri`, and `scope`) to the identity provider; the nonce is appended to the authorization URL by design so the provider echoes it in the ID token, and the callback compares it against the value recovered from the sealed cookie. `session.domain` applies only to the durable session cookie and is never applied to this pending-flow cookie. With the default `session.secure=true`, the correlation cookie is named with `__Host-`, carries `Secure`, has `Path=/`, and never carries `Domain`, preventing sibling hosts from planting a parent-domain cookie with the same name. When `session.secure=false` for allowed localhost or literal-loopback HTTP development callbacks, it has no prefix and remains scoped to `providers[].callback_path`. Sealed pending-flow cookies honor `session.max_cookie_bytes`; oversized, expired, wrong-context, wrong-browser, tampered, or otherwise invalid state fails closed. `session.max_cookie_bytes` is admitted in the range `1024`–`8000`: the sealed correlation cookie has a hard floor near 500 encoded bytes before any original-URL bytes, so a smaller cap would start a plugin that answers `503` to every login instead of being refused at admission. Deployments that preserve long post-login URLs (up to 2048 bytes) need proportionally more headroom than the minimum.
- **Session cookie size.** Browsers silently discard a cookie whose name and value exceed 4096 bytes, and the sealed session carries the ID, access, and refresh tokens plus the merged claims, so enterprise tokens with large group or role claims routinely exceed one cookie. `session.max_cookie_bytes` bounds the whole sealed session value; when the complete `Set-Cookie` line for it would exceed 4000 bytes (name, value, and every attribute), the value is split across `<cookie_name>.0` … `<cookie_name>.N` chunk cookies — at most 9, each line within 4000 bytes — and reassembled on the next request. Chunk `0` carries the chunk count, and the AEAD tag over the whole value authenticates the reassembly, so a missing, reordered, or substituted chunk fails closed and is cleared like any other invalid session. Switching between the single and chunked forms expires the other form in the same response. A session larger than `session.max_cookie_bytes` is refused at the callback with `{"error":"OIDC session exceeds session.max_cookie_bytes"}` and a warning naming the estimated size, instead of being emitted for the browser to drop into a login loop; a refreshed session that would grow past the cap is served without a cookie update and logs the same warning. A `session.cookie_name`, `session.domain`, and `session.path` combination that leaves fewer than 1024 bytes of value per chunk is rejected at admission. Chunk cookies are gateway credentials: they are stripped from the backend `Cookie` header with the session cookie.
- Every session cookie carries `Max-Age` equal to the session's remaining absolute lifetime (`session.ttl_secs` measured from login), recomputed each time the cookie is re-issued, so a configured lifetime survives a browser restart instead of ending with the browser session. The idle bound is still enforced by the gateway on every request.
- Pending-flow **admission** (DoS bounds) remains process-local per plugin instance via `behavior.state_cache_max_entries` (default `10000`) and `behavior.state_cache_max_entries_per_source` (default `32`). Those caps limit how many logins an instance will *start*; they do not need to be shared across replicas for a callback to succeed. The per-source cap is enforced whether or not the replay cache is full: once `state_cache_max_entries` entries are pending, further logins are still started as sealed-only flows (no local replay entry; the sealed cookie and the provider's one-time code still protect them), each charged to its source until it expires or its callback arrives, up to one more `state_cache_max_entries`; beyond that, new login starts answer `503`. Same-instance callback replay is rejected after the sealed state is first accepted on that instance; cross-replica completion relies on the sealed cookie plus the provider's one-time authorization code.
- `behavior.trusted_redirect_hosts` gates post-login redirects as origins, not bare host names. A target must use the same scheme as `redirect_uri` (an `https` login is never sent on to `http`), carry no userinfo, and match an entry by host and port: an entry without a port (`app.example.com`) admits only the scheme's default port, and `host:port` admits exactly that port. Entries compare case-insensitively. If no trusted redirect is available, the plugin uses `behavior.post_login_default_path`.
- UserInfo `sub` must match the ID token `sub`. UserInfo can neither override nor supply protected claims: `iss`, `sub`, `aud`, `exp`, `iat`, `nbf`, `nonce`, `auth_time`, `azp`, `at_hash`, `c_hash`, and the top-level key of the configured `scope_claim`, `role_claim`, `consumer_identity_claim`, and `consumer_header_claim` are taken from the verified ID token only, and a UserInfo value for one of them is ignored even when the ID token lacks it. A provider that publishes the identity, scope, or role claim only from UserInfo therefore needs that claim added to its ID token (or a different claim configured); otherwise the session resolves no identity and requests are rejected. Other UserInfo claims (for example an `email` used only in `claim_headers`) are merged.
- Claim header mappings reject reserved headers, including `Authorization`, `Host`, hop-by-hop headers, and Ferrum consumer identity headers.
- The gateway session cookie and the sealed pending-flow correlation cookies are removed from the `Cookie` header forwarded to the selected backend, on every protocol this plugin serves (HTTP/1.1, HTTP/2, the HTTP/3 cross-protocol bridge, gRPC, and the WebSocket handshake). Unrelated application cookies are preserved exactly, and the strip runs after authentication so it never changes an authentication decision. Encryption keeps a backend from *reading* the session, but not from replaying it: the sealed value is a complete gateway credential that any other route under the same OIDC policy would accept. The upstream already receives the verified identity and `claim_headers` values, so it does not need the credential itself. Set `session.hide_session_cookie: false` to opt back into passthrough when a backend genuinely requires the raw cookie.

Provider-call diagnostics for discovery, UserInfo, token grants, and revocation
use a structurally redacted endpoint (`scheme://host:port/redacted`) and a safe

from error strings as well as shared HTTP-client logs.

## Multi-replica deployments

Fresh logins work behind non-sticky load balancers when every Ferrum replica shares the same `oidc_relying_party` configuration and `session.encryption_secret` (plus `encryption_secret_previous` during rotation). Both the durable session and the pending authorization-code state live in sealed cookies, so the callback may land on a different replica than the one that issued the challenge; sticky sessions are not required for login completion. Keep encryption secrets identical across the fleet; a replica with the wrong secret or a different provider/session context rejects sealed pending-flow cookies and fails closed.

Token refresh is the one place the cookie store's replica independence still shows. Refresh coalescing (see [Concurrent refreshes and spent refresh tokens](#concurrent-refreshes-and-spent-refresh-tokens)) is per instance: two replicas that both receive the same refresh-due cookie both submit the refresh token, and with a rotating provider only one can win. No replica can hand another the winner's tokens without a shared server-side session store, so the loser's contract is what protects the browser: it sees `invalid_grant`, emits no `Set-Cookie`, and does not re-submit that generation for `25` seconds. The browser keeps the winner's rotated cookie, and the only cost is one rejected grant per additional replica per generation. Providers that revoke the whole token family on detected reuse ([RFC 9700 §4.14.2](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14.2)) can still invalidate the winner in that case; routing requests for one session cookie to one replica (cookie-based affinity on the session cookie name) removes the duplicate submission entirely and is recommended with such providers.

## Session Lifetime and Token Refresh

The gateway session has two bounds, both enforced on every request:

- **Absolute lifetime** — `session.ttl_secs` (default `3600`) measured from login. A session is never valid past this, regardless of activity.
- **Idle timeout** — `session.idle_ttl_secs` (default `1800`) of inactivity. This is a *sliding* window: each request advances the session's last-touch time, so an actively used session stays valid until the absolute lifetime. To keep the per-request cost and `Set-Cookie` churn low, the cookie is re-issued at most about twice per idle window (once more than half of `idle_ttl_secs` has elapsed since the last update), not on every request.

Every re-issued session cookie carries `Max-Age` equal to the remaining absolute lifetime, so both bounds hold across a browser restart.

When the provider issues a refresh token (typically by adding the `offline_access` scope), the plugin proactively refreshes the tokens `behavior.refresh_skew_secs` (default `30`) before the earlier of the access-token expiry and the stored ID-token/UserInfo claims expiry:

- A new access token, a rotated refresh token, and an optional new ID token are accepted. A returned ID token is re-validated against the provider JWKS and must bind to the same subject; if it carries a `nonce` it must match the original login.
- On success, refreshed claims drive scope/role checks and claim-header fan-out, and the session cookie is re-issued. If the provider refreshes only the access token, the previous claims remain usable only until their stored claims expiry.
- Refresh is best-effort while the stored claims are still fresh. If the token endpoint remains unavailable or the provider omits fresh claims until the stored claims pass expiry plus clock skew, the plugin fails closed and re-challenges instead of serving stale authorization claims.

Both a sliding update and a refresh re-issue the session cookie on the proxied response via `Set-Cookie`, preserving any cookie the backend also set.

Both lifetimes are bounded at admission to `1`–`31536000` seconds (one year), and `providers[].id_token_clock_skew_secs` (default `60`) to at most `3600`. These values are added to a Unix timestamp on every authenticated request, so a value that cannot take part in that arithmetic is rejected before startup instead of failing on a live request. A provider-supplied `expires_in` is clamped the same way: a missing value falls back to `session.ttl_secs`, a negative one is treated as already expired, and an absurd one is capped at one year.

### Concurrent refreshes and spent refresh tokens

A browser routinely sends several requests carrying the same refresh-due cookie at once (parallel tabs, a page plus its asset fetches). Providers that rotate refresh tokens accept the token exactly once, so each such burst must submit it exactly once:

- **Single-flight per token generation.** Within one Ferrum instance, every request whose cookie carries the same refresh token joins one refresh transition, keyed by a SHA-256 digest of that token (the registry never holds the raw credential). The first request runs the grant; the others wait for its outcome without any lock and receive the winner's session state, so each of them re-issues the rotated cookie. A completed transition stays addressable for `25` seconds, so a request that decrypted the old cookie just before the winner finished, or a tab that still carries it, adopts the rotation instead of re-submitting the spent token. The retained registry is bounded (4096 completed records per instance, oldest evicted first); live transitions are never evicted. Requests whose cookie is not due never touch the registry.
- **`invalid_grant` re-seals nothing.** When the token endpoint answers `invalid_grant` (RFC 6749 §5.2: the token is spent, revoked, or expired), the request is still served while its stored claims are fresh, but it emits **no** `Set-Cookie` — the sliding-idle update is suppressed for that request as well, so an ordinary active-browser request cannot republish the spent credential. The browser therefore keeps whatever cookie it holds — the rotated session whenever a winner exists anywhere in the fleet — rather than being handed the spent credential again. The instance records the spent identity for `25` seconds, so repeat requests with the same stale cookie are not re-submitted either. When the stored claims have already expired, the freshness gate still re-challenges, but that challenge does **not** delete the session cookie either: deleting it by name would also delete the winner's rotated cookie the browser may already hold if this response is applied last. The same holds for every indeterminate outcome below.
- **An accepted grant spends the token even if its result is unusable.** When the token endpoint answers `2xx` but the response cannot be adopted — an unreadable or malformed body, a non-bearer token type, or a refreshed ID token or UserInfo result that fails validation (for example an ID token signed by a key the JWKS store has not fetched yet) — the provider has already consumed, and with rotation replaced, the submitted refresh token. The session keeps its existing, still-validated claims but drops the refresh token, and that state is re-issued to this request and to every request sharing the transition; nothing from the unverified response is adopted. The spent token is never re-sealed or resubmitted, so a rotating provider cannot see a reuse that would revoke the token family ([RFC 9700 §4.14.2](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14.2)). The session then serves until its claims expire and re-challenges.
- **Transient failures keep the token.** A failure before the provider accepted the grant — a transport error or a non-2xx response without `invalid_grant` — leaves the token live; the unchanged payload is re-sealed with the next attempt deferred by `30` seconds, and every request sharing the transition carries that same backoff. A transport error after the request was sent is indistinguishable from an unsent request, so it is treated as transient.
- A follower whose leader is cancelled (client disconnect) re-elects exactly one replacement; one that outlives the leader's wait bound serves without a session update and never issues a duplicate grant. An indeterminate outcome (follower wait bound exceeded, re-election budget exhausted, or a winner's sealed state that would not open) is treated exactly like a spent credential: the request emits no `Set-Cookie`, because the transition it could not observe may already have rotated the browser's cookie.

## Authentication Age and Authorization Parameters

`providers[].max_age_secs` applies the OpenID Connect `max_age` policy ([OpenID Connect Core §3.1.2.1](https://openid.net/specs/openid-connect-core-1_0.html#AuthRequest)). The value is sent on the authorization request; the callback requires the ID token to carry `auth_time` no older than `max_age_secs` plus `id_token_clock_skew_secs` and otherwise answers `400` with `{"error":"Invalid ID token auth_time"}`; and the login's `auth_time` is kept in the session, so once it is older than the policy the next request re-challenges instead of refreshing (a refresh never re-authenticates the user). Use it on routes that need a recent interactive login. It is bounded to `0`–`31536000`.

`providers[].authorization_params` adds static parameters to every authorization request — for example `prompt: login`, `acr_values: urn:example:mfa`, `login_hint`, or `ui_locales` — after the parameters the plugin owns. Names the plugin sets (`response_type`, `client_id`, `redirect_uri`, `scope`, `state`, `nonce`, `code_challenge`, `code_challenge_method`, `max_age`, `response_mode`, `request`, `request_uri`) are rejected case-insensitively, values must be strings without control characters, and at most 16 entries of at most 512 bytes each are accepted. The plugin does not itself verify `acr`/`amr` in the returned ID token; combine `acr_values` with `required_roles`/`required_scopes` or a provider policy when assurance must be enforced.

## Upstream Access Token

With `providers[].forward_access_token: true` the backend receives the session's current access token as `Authorization: Bearer <token>`, the refreshed one after a token refresh, so it can call downstream APIs on the user's behalf. The backend `Authorization` header is then gateway-owned on routes this instance protects: every client-supplied copy is removed before the token is installed, so a request authenticated by another mechanism, or a session whose access token is not a plain visible-ASCII bearer value, forwards no `Authorization` header at all. The token is staged only for the accepted principal, carried in redaction-protected request metadata, and never logged. The default is `false`, which leaves the `Authorization` header untouched.

## Client Authentication

Supported `client_auth.method` values are:

| Method | Notes |
|---|---|
| `client_secret_basic` | Sends the client secret with HTTP Basic auth. The client identifier and secret are `application/x-www-form-urlencoded` before the Basic encoding, per [RFC 6749 §2.3.1](https://www.rfc-editor.org/rfc/rfc6749.html#section-2.3.1), so credentials containing `:`, `+`, spaces, or non-ASCII characters work against a conforming provider |
| `client_secret_post` | Sends client credentials in the token request body |
| `private_key_jwt` | Signs a client assertion with RSA, EC, or EdDSA keys (`RS256`, `RS384`, `RS512`, `ES256`, `ES384`, `EdDSA`). Admission signs a throwaway assertion, so a key that cannot support the selected algorithm — an `ES256` client holding a P-384 key, for example — is refused at config load instead of failing the first token exchange after the authorization code has been spent |
| `none` | Public client mode, allowed only for localhost or loopback token endpoints |

## Logout

Requests to `providers[].logout_path` expire the browser's local session cookie. Logout is state-changing — it deletes the session, revokes the refresh token, and ends the provider session — so it is screened against request forgery with the browser's `Sec-Fetch-Site` header ([issue #6660](https://github.com/ferrum-edge/ferrum-edge/issues/6660)): a `GET` or `HEAD` must report `same-origin` or `none` (a typed URL or bookmark), and a request without the header is refused because a cross-site link cannot otherwise be told apart; a `POST` is refused only when the browser reports `cross-site` or `same-site` (a sibling host), so non-browser clients can still `POST`; any other method answers `405`. A refused request answers `403` with `{"error":"Logout must be a same-origin request"}`, clears nothing, and contacts no provider. Link to logout from pages on the same origin, or submit a same-origin `POST` form. A logout link on another site (an identity-provider portal, say) is refused; send such users to the provider's own logout instead. `logout_path` must not resolve to the same path as `callback_path` (compared with duplicate slashes collapsed and a trailing slash ignored): the callback branch is evaluated first, so a colliding logout path would answer `Missing state` and never reach the logout handler. With an authentic, context-bound session cookie and `behavior.rp_initiated_logout` enabled (the default), Ferrum redirects to the provider's `end_session_endpoint` with the stored ID token as `id_token_hint`, the configured `client_id`, and `post_logout_redirect_uri` when configured. Without a session cookie, or with an invalid cookie, logout returns the local logged-out page and does not contact the provider. An expired ID token may still be sent as a logout hint; it does not authorize a proxy request.

When discovery advertises a validated `revocation_endpoint` and the session contains a refresh token, RP-initiated logout first POSTs that token using RFC 7009 (`token_type_hint=refresh_token`) and the configured client authentication. The complete revocation attempt is bounded to five seconds, with no retries or response-body processing. Failure is best-effort and does not prevent cookie deletion or the logout redirect. Revocation can also run without an end-session endpoint; the browser then receives the local page. Setting `behavior.rp_initiated_logout=false` disables both provider operations.

**Residual validity:** sessions are stateless, so deleting a browser cookie does not invalidate copies captured before logout. A copied cookie can still authenticate while its stored claims and configured absolute/idle lifetime checks permit; activity can keep the idle window sliding up to the absolute `session.ttl_secs` bound. Successful provider refresh-token revocation prevents future refresh with that token, but does not immediately invalidate the gateway cookie or its stored claims. Revocation failure or an absent endpoint leaves provider refresh-token validity unchanged. Full immediate session invalidation requires server-side session state, which this plugin does not implement.

## Configuration Schema

The `OidcRelyingPartyConfig` component in `openapi.yaml` models what constructor admission accepts, including the required `openid` scope, the discovery/explicit-endpoint alternatives and their mutual exclusion, method-specific client credentials, the 32-byte encryption-secret minimum, cookie-name/path/domain syntax, the session lifetime and cookie-size bounds, the allowed challenge statuses, and `SameSite=None` requiring `secure`. Optional string fields accept `null` as "unset" and `same_site` is case-insensitive, both matching runtime behavior.

Five rules relate two values and are enforced only by the constructor: `behavior.refresh_skew_secs <= session.ttl_secs / 2`, `behavior.state_cache_max_entries_per_source <= behavior.state_cache_max_entries`, `providers[].redirect_uri`'s path equalling `providers[].callback_path`, `providers[].logout_path` not colliding with `providers[].callback_path`, and a `private_key_jwt` key that supports the selected algorithm. The constructor also alone rejects dot segments in `callback_path`/`logout_path`, case variants of reserved `authorization_params` names, and a cookie name/domain/path combination too long for a usable chunk cookie. The discovery/explicit-endpoint alternatives treat a present `null` as unset, matching the constructor.

## Related Plugins

Use `oauth2_introspection` for API requests that already carry bearer access tokens and do not need a browser login flow. Use `jwks_auth` for self-contained JWT access tokens where local signature verification is enough.
