# ai_federation

Part of the [Plugin Reference](../plugins.md).

**Priority:** 4060 · **Phases:** `before_proxy`, `transform_request_body_with_context`, finalized request egress, `enforce_final_backend_header_policy`, `on_final_request_body_with_context`, origin response-header boundary, `after_proxy`, `response_stream_inspector`, on_response_stream_terminated (HTTP only) · **Protocols:** HTTP · **Failure policy:** `KeepLastKnownGood`

HTTP-family AI gateway that routes OpenAI Chat Completions JSON to supported providers, translates native request/response shapes, and returns an OpenAI-shaped synthetic response. Provider dispatch runs from the finalized-request-egress phase, after request decompression, body transforms, and the complete final request-policy hook pass. Native gRPC is deliberately unsupported rather than advertised with an inert pass-through.

**Streaming (`"stream": true`) is an explicit opt-in.** The buffered terminate-and-respond path cannot relay a stream, so by default a streaming request that matches a configured provider is rejected with HTTP `501` and an OpenAI-shaped error body rather than being silently downgraded to a buffered response. Adding the root `streaming` block turns on a second, non-buffering execution path:

```yaml
plugin_name: ai_federation
config:
  streaming:
    enabled: true
    max_event_bytes: 262144       # optional; 4096–1048576, default 262144
    read_timeout_seconds: 0       # optional; 0–86400, 0 = unbounded.
                                  # Omit to inherit the selected provider's
                                  # own read_timeout_seconds.
  providers:
    - name: openai
      provider_type: openai
      api_key: "sk-..."
      model_patterns: ["gpt-*"]
```

**Credentials can live outside plugin configuration.** `api_key`, `google_service_account_json`, `aws_access_key_id`, `aws_secret_access_key`, and `aws_session_token` accept either a literal value or a whole-value `${FERRUM_PLUGIN_SECRET_<NAME>}` reference (`<NAME>` is uppercase `[A-Z_][A-Z0-9_]*`), resolved from the gateway process environment when the plugin is constructed — exactly like [`ai_stream_router`](../plugins.md#ai_stream_router)'s `api_key`. The `FERRUM_PLUGIN_SECRET_` namespace is itself materializable from `_FILE` / `_VAULT` / `_AWS` / `_AZURE` / `_GCP` sources at startup, so provider keys and a Vertex service-account private key need not be stored or replicated as configuration rows and can rotate without a config write. A `${...}` reference to any variable outside that namespace, or to an unset or empty one, is refused at configuration admission, and diagnostics never echo the reference or its value. The resolved value is screened exactly like a literal (a static credential must be a valid HTTP header value). A referenced AWS key pair counts as provider-config credentials, so it is not subject to the [ambient AWS endpoint scope](serverless_function.md#ambient-aws-credential-scope). Because resolution reads the environment of the process that builds the plugin, the variable must also be set where configuration admission runs (for example the control plane) for that admission to succeed.

With it enabled, `before_proxy` claims the streaming request, commits exactly one provider, and rewrites the routing decision through the request's route-override fields so the **normal proxy dispatch path** relays the provider's SSE incrementally. On a proxy with backend-path policy, this hook runs in the deferred pass only after the effective target path is authorized; provider I/O still waits for finalized request egress after all final-body policy. Time to first token, client-disconnect cancellation, byte budgets, retained-response ceilings, and shutdown accounting all come from the shared streaming response machinery rather than a plugin-private relay; the plugin itself creates no queues, channels, or detached tasks.

**The provider commit boundary is fail-closed.** Fallback across providers happens **only** during pre-commit selection, before a single downstream-visible byte exists — an open circuit breaker, a streaming-ineligible provider, or an unusable endpoint moves to the next matching provider in priority order, and `ai_federation.streaming_provider_attempts` records how many were considered. After the claim is written the provider, credential, destination, backend TLS, DNS decision, and backend-visible query are committed exactly once:

- a **non-2xx** provider response still carries a real status and is relayed as the provider's own error envelope; no second provider is tried;
- a failure once body bytes are committed can only **truncate**, so the stream ends with one gateway-authored terminal SSE `error` event. A second provider is **never** spliced into the same logical stream.

**Streaming eligibility is narrow by design.** A provider may serve a stream only when its native streaming wire format already **is** the OpenAI Chat Completions SSE contract — `openai`, `mistral`, `xai`, `deepseek`, `meta_llama`, `hugging_face`, `azure_openai` — and its credential is a static request header. `anthropic`, `google_gemini`, `google_vertex`, `aws_bedrock`, and `cohere` need provider-native SSE translation and fail closed with a field-specific `501` (`streaming_provider_representation_unsupported`); use [`ai_stream_router`](../plugins.md#ai_stream_router) for Anthropic/Gemini streaming. AWS SigV4 and Google OAuth2 providers fail closed with `streaming_provider_auth_unsupported`: SigV4 signs the exact final body that only exists *after* the claim, and OAuth2 has no per-attempt refresh boundary at this layer.

**Streaming bounds and contract enforcement.** A claimed stream retains at most one SSE event — the partial event being assembled, or, once the provider frames its completion, the terminal event alone — capped by `streaming.max_event_bytes`, so retention grows with neither stream length nor transport chunk size: the ceiling is checked on every complete and partial event *before* any of its bytes are retained or released, so a hostile multi-megabyte chunk with no event terminator is refused without being buffered. The contract guard forwards ordinary events verbatim and in order, so time to first token is unaffected.

**The terminal `data: [DONE]` event is held back until the provider's body actually ends.** A client following the OpenAI streaming contract is entitled to stop reading at `[DONE]`, so a marker released before upstream EOF could be accepted as a successful completion while the gateway went on to refuse the stream — the client would never see the error. The guard therefore retains the provider's own terminal event (bounded by the same `max_event_bytes` ceiling) and releases it **verbatim** only at a clean EOF with nothing else outstanding. Any provider byte after that retained marker — a second terminal event, a data event, a comment / `id` / `retry` line, an oversized or non-UTF-8 block, or a trailing partial line at EOF — fails the stream closed and the marker is **dropped**: the client receives one gateway-authored terminal SSE `error` event and **no completion marker at all**. "EOF" here is the end of the *response body* — the terminating chunk on HTTP/1.1 or `END_STREAM` on HTTP/2 — not the end of the connection, and providers emit it immediately after `[DONE]`, so the hold costs one read and does not affect time to first token. A provider that emits `[DONE]` and then leaves the body open is bounded by the streaming read timeout.

A truncated stream (clean EOF with no terminal marker, or a trailing partial event) fails closed the same way. Terminal detection follows the SSE field grammar: an event is terminal only when the **concatenation of all its `data` lines** is exactly `[DONE]`, so `data: [DONE]\ndata: …` is ordinary data and cannot smuggle a payload past the post-terminal check. `CR`, `LF`, and `CRLF` line endings and their legal mixed blank-line forms are all recognized. An event that is not valid UTF-8, a **duplicate** terminal marker, an oversized event, a content-coded stream, and a 2xx that is not `text/event-stream` all fail closed with one gateway-authored terminal SSE `error` event — no invalid or post-terminal provider byte is ever forwarded. Every diagnostic is a fixed-cardinality gateway-authored string; no provider byte, header, model, or URL is ever echoed or logged. Terminal usage is relayed unchanged (usage arrives in its own event *before* `[DONE]`), so OpenAI-compatible clients should send `stream_options.include_usage: true` to receive it.

**Streaming accounting, model resolution, timeouts, and response headers.**

- **Concurrency.** A claimed stream takes one non-queuing `max_concurrent_requests` permit and holds it for the whole life of the response — including a non-2xx provider error body that may still be streaming after response headers. It is returned exactly once on ordinary `[DONE]` completion, non-2xx body termination, client disconnect, a downstream policy cut, a backend error, a pre-header cancellation, or a fail-closed final-body rejection. Exhaustion returns the same `503` (`provider_concurrency_exhausted`) the buffered path returns.
- **Circuit breaking.** Selection reserves a real admission from the provider's circuit, so a half-open circuit still grants exactly **one** concurrent probe no matter how many streams arrive. The reservation resolves exactly once from the complete outcome: a 2xx is a circuit **success** only after the SSE guard proves a valid terminal marker; truncation, an oversized/malformed/post-terminal event, a content-coded or non-event-stream 2xx, a configured `fallback_on_status_codes` status, and a redirect are circuit **failures**; so is any provider **transport fault** — a dispatch that timed out, was reset, or was refused before a provider header arrived (proxy core answers it with a gateway-authored `502`/`504`, scored as a failure whatever `fallback_on_status_codes` lists, so a timed-out half-open probe reopens the circuit instead of closing it), and a body that dies on a read timeout, reset, or protocol error after the headers (even after a non-2xx status that would otherwise score as an answer). The fault is recognized from trusted dispatch and body provenance, never metadata, and the body-phase classes are exactly proxy core's own post-wire backend-failure set (read timeout, reset, close, protocol error, oversized body). Route deadlines are settled exactly as proxy core settles them. A body the route rule's deadline cut — the earlier of its total request deadline and the committed attempt's per-attempt budget — is neutral; it is recognized from the exact fired flag core itself uses (carried on the terminal body outcome by the HTTP/1.1/HTTP/2 body wrapper, the native HTTP/3 relays, and the HTTP/3 cross-protocol bridge), never from a clock, so a provider reset or timeout recorded without that flag scores as a failure however late the termination hook runs. Before the response head, core's own charge decides: a route deadline that expired while the provider held the attempt is charged to the provider (recorded as `read_write_timeout`) and scores a failure, while one that expired before any backend held the request is recorded as the neutral `dispatch_policy_rejected`. Other gateway policy cuts stay neutral too: a client disconnect, an authorization-lifetime termination, and gateway-local refusals (policy, size-limit, buffer-capacity, connection-limit, and trust refusals); an ordinary non-fallback `4xx` the provider chose to return is a success, exactly as the buffered path scores it. A non-2xx verdict is known at response headers but applied only when the error body ends or the claim drops, so a client disconnect after those headers still preserves the provider score rather than treating the exchange as cancelled. Cancellation before headers frees the half-open slot without scoring the circuit at all.
- **Model mapping.** `model_mapping` and `default_model` apply to streams: the claim owner rewrites the final provider-visible top-level `model` to the resolved value and re-asserts `stream: true`. The same rewrite performs the `text_only_with_warning` reduction when the committed provider is configured for it, so the non-text parts never reach the provider. A body with duplicate JSON members is deliberately **not** rewritten (rewriting would collapse the ambiguity) and still fails closed at the final-body hook.
- **Timeouts.** The committed provider's `connect_timeout_seconds` and `read_timeout_seconds` become the streaming route's dispatch budgets, replacing the matched proxy's `backend_connect_timeout_ms` / `backend_read_timeout_ms`. **`read_timeout_seconds` is a whole-exchange bound on this path** — the shared reqwest dispatch applies it from connect through the last response body byte, not as a per-chunk inactivity timer — so a generation that legitimately runs longer than the provider's per-call budget needs `streaming.read_timeout_seconds`, where `0` removes the gateway-imposed bound entirely. TLS and DNS policy are unchanged: the claim still commits explicit verifying backend TLS for an `https` provider and revokes any inherited `dns_override`.
- **Response headers.** Provider response headers on a claimed stream are reduced at the origin response-header boundary to the same bounded safe allowlist the buffered path publishes (`retry-after`, provider request-id fields, `x-ratelimit-*` / `ratelimit-*` families and the combined IETF `ratelimit` field), with values length-capped, control characters refused, names lower-cased, and a hard count cap. Provider `Set-Cookie`, `Location`, auth challenges, validators/digests/checksums, `Alt-Svc`/`Link` steering, and unknown custom metadata never reach the client. The gateway then authors `Content-Type: text/event-stream` and `Cache-Control: no-cache` and drops provider framing. Because the reduction runs *before* the `after_proxy` chain, gateway response plugins (CORS, `security_headers`, correlation/tracing, rate-limit headers) add their own headers normally.

**Streaming changes composition.** Enabling `streaming` makes the plugin declare a backend-boundary header policy and request header/destination mutation, so it cannot be composed with `request_deduplication` or `response_caching` on the same proxy — a `before_proxy` fingerprint cannot witness the final provider boundary. A claimed stream mints the same private provider claim `ai_stream_router` uses, so `request_mirror`, `serverless_function`, `mcp_gateway`, and `mesh_route_dispatch` stand down on it identically, and `enforce_final_backend_header_policy` plus `on_final_request_body_with_context` re-assert the credential, destination, and committed model over the finalized backend-visible request. Non-streaming federation behavior is unchanged when the block is absent.

Config fields named `stream`, `streaming_enabled`, or `enable_streaming` are still rejected during plugin validation, and a per-provider `streaming` key is rejected too: streaming is configured once at the root.

**Model routing fails closed by default.** JSON POST requests with no final body, malformed/non-UTF-8 JSON, malformed supported tool/stop shapes, or no top-level string `model` field are rejected with an OpenAI-shaped `400`. Model identifiers are limited to 256 ASCII bytes and the characters used by ordinary provider IDs (`A-Z`, `a-z`, digits, `.`, `_`, `-`, `:`, `/`, `+`); traversal, URL userinfo/query/fragment syntax, whitespace, and controls are rejected. Requests whose valid `model` does not match any provider are rejected with an OpenAI-shaped `404`. Set `fail_on_missing_model: false` or `fail_on_no_matching_provider: false` only when intentional pass-through to the normal backend is required.

**The fail-closed guarantee is scoped to HTTP JSON POSTs.** Other methods and non-JSON content types continue to the backend; native gRPC is outside the plugin's protocol set. `ai_federation` is therefore not an authorization boundary, and the backend must remain independently protected.

**Authentication rejects share the OpenAI error envelope.** When `ai_federation` or `ai_stream_router` is effective on a proxy, gateway-authored authentication `401` responses from the shared authentication phase — missing credentials (`code: missing_api_key`) and invalid or unknown credentials from `key_auth`, `jwt_auth`, `jwks_auth`, `basic_auth`, `hmac_auth`, `ldap_auth`, `mtls_auth`, `oauth2_introspection`, and `oidc_relying_party` (`code: invalid_api_key`) — are rewritten to the same nested `{"error":{"message","type","param","code"}}` shape the AI plugins use for their own rejects. Status codes and `WWW-Authenticate` challenges are unchanged. Authorization rejects (`acl`, `rate_limiting`, and other `authorize`-phase plugins) and non-`401` authentication outcomes (for example `ldap_auth` dependency `500`s or oversized-principal `403`s) keep Ferrum's flat or plugin-specific bodies.

**Final-body dispatch preserves admission ordering.** All `before_proxy` admission hooks and configured request-body transforms run before federation makes provider I/O. When route-sensitive backend-path policy is active, the gateway first pins the selected target, authorizes and charges its backend-effective method exactly once, and completes deferred `before_proxy` hooks; federation then runs before backend-only admission, circuit breaking, and transport. A `RejectBinary` from the final hook still replaces normal backend dispatch. Mixed-traffic proxies should use the explicit pass-through flags or isolate AI traffic on a dedicated proxy.

**Response guardrails still apply.** Successful synthetic responses returned by `ai_federation` are passed through the normal buffered response-side hooks before reaching the client. This means response-side `ai_semantic_firewall`, `ai_response_guard`, response body transforms, and final-response hooks inspect the normalized provider body. `ai_federation` still writes token metadata directly, and `ai_rate_limiter` records those tokens through its rejection-path `after_proxy` hook.

**Token metering.** Federation's provider dispatch occurs after the normal `before_proxy` admission phase, so an `ai_rate_limiter` on the same proxy can pre-reserve before any provider call without a priority override. Successful provider usage is written to `ai_total_tokens`, `ai_prompt_tokens`, and `ai_completion_tokens`; the rejection-path `after_proxy` hook reconciles that reservation using the original `ai_federation_status`. `charge_estimate` and `warn` work for usage-less federation responses; the synthetic rejection-path limitation for `on_unmetered_response: reject` is documented under `ai_rate_limiter` below.

**Provider usage-metadata expectations.** Metering accuracy depends on the
provider returning a usage object that `ai_federation` / `ai_rate_limiter` can
read: OpenAI-shaped `usage.{prompt,completion,total}_tokens`, Anthropic
`usage.{input,output}_tokens`, Google/Gemini
`usageMetadata.{prompt,candidates,total}TokenCount`, Bedrock Converse
`usage.{input,output,total}Tokens`, and Cohere v2 `usage.tokens.{input,output}`.
When usage is absent, the request falls to `on_unmetered_response`. Streamed
clients are metered by `ai_rate_limiter` from the response stream rather than
from a buffered federation body — `ai_federation`'s streaming path relays
provider events unchanged — so configure OpenAI-compatible callers with
`stream_options.include_usage: true` so a final usage signal is emitted.

**Synthetic-path hook ordering (known divergence).** On the governed synthetic short-circuit path (any plugin-generated 2xx surfaced via `RejectBinary`, including `ai_federation` / `ai_semantic_cache` / `response_mock` bodies, plus final 2xx-5xx `serverless_function` terminate responses) the response-**body** hooks (`on_response_body`, body transforms, `on_final_response_body`) run **before** the `after_proxy` reject hooks, whereas on the normal backend path `after_proxy` runs **before** the body transforms. Provider/protocol normalization is deliberately skipped: a synthetic body is owned by the short-circuiting plugin and is already in its client-visible representation, so request metadata left by an earlier provider router must not reinterpret it as backend-native bytes. This is a deliberate trade-off: the body hooks may *replace* the response when a guardrail rejects the synthetic body, so `after_proxy` must run exactly once and last — over the final response — to preserve one-shot response state (e.g. an `oidc_relying_party` rotated session cookie or a `response_transformer` route override) that would otherwise be consumed against a discarded synthetic response. The consequence is that a body transform which depends on a header/metadata mutation made by an `after_proxy` hook (for example `response_transformer` rewriting `Content-Type` before its JSON body rules) can behave differently on a synthetic response than on an equivalent backend response. If you need such a transform applied identically, drive it from `before_proxy`/body-side configuration rather than from `after_proxy` header mutations on the synthetic path.

**Multimodal content is explicit.** OpenAI Chat Completions content arrays may contain text plus non-text parts such as `image_url`. Provider configs accept `multimodal_mode`:

| Mode | Behavior |
|---|---|
| `reject` | Reject matched requests containing non-text content parts with HTTP `400`. |
| `translate` | Preserve supported non-text parts by converting them to the provider-native request format. Unsupported parts are rejected with HTTP `400`. |
| `text_only_with_warning` | Intentionally drop non-text parts, send only text, log a warning, and set `ai_federation_multimodal_*` metadata. |

Translated providers default to `reject` unless configured otherwise. OpenAI-compatible providers and Cohere default to `translate` because their outbound request shape preserves OpenAI-style content parts instead of flattening them.

Multimodal capability is provider-specific, so a per-provider multimodal rejection (a `reject`-mode provider, or a `translate`-mode provider that cannot translate a specific part — e.g. AWS Bedrock with an HTTP(S) image URL or an unsupported image format) does **not** abort the fallback chain when `fallback_enabled` is set. The request falls through to the next matching provider exactly like a translation failure does, so a mixed list (e.g. a `reject`-mode provider followed by a `translate`-mode one) can still serve the image from the later provider. If **every** matching provider declines the request at the multimodal policy gate and no provider was ever dialed, the caller receives the final HTTP `400`.

**The policy governs streamed requests identically.** With the `streaming` block enabled, `multimodal_mode` is evaluated during pre-commit provider selection, so a `stream: true` request is held to the same provider boundary as a buffered one: a `reject`-mode provider declines it and the next matching provider is considered exactly as above, and a `text_only_with_warning` provider has the non-text parts removed from the provider-visible body before dispatch, with the same `ai_federation_multimodal_*` metadata recorded for the committed provider. Because that path forwards the client's own body rather than building a provider request, the finalized body is re-checked at the egress boundary: non-text content that a later request-body transform reintroduced fails closed with an OpenAI-shaped `400` (`multimodal_policy_violation`) rather than reaching the provider. A provider that cannot stream at all still reports its own `501` first.

**Provider result and fallback contract.** Provider and OAuth response bodies are collected with explicit bounds (8 MiB per provider by default, 64 KiB for OAuth); provider-native request serialization is capped at 64 MiB, and normalized JSON serialization is held to the per-provider response limit so translation/escaping cannot create an unbounded body. Redirects are never followed, and provider `3xx` status codes are preserved when final. Successful `2xx` bodies must match the selected provider's documented shape; a fully received success that cannot be normalized fails with `502` (`response_normalization_failed`) without calling another provider. That generation has already committed, so its original provider/status and non-replayable idempotency tombstone are retained. Neither `fallback_on_protocol_errors` nor the ambiguous-outcome opt-in permits replay of this completed operation, and `2xx` values are rejected in `fallback_on_status_codes`. Safe `Retry-After`, request-ID, and rate-limit headers are forwarded within count/value bounds; cookie, credential, location, hop-by-hop, and unrecognized headers are removed.

Transport fallback is replay-safe by default. DNS, connect, and TLS failures proven to occur before the POST reached the wire may fall through. Timeouts, resets, and response-stream failures are ambiguous and return `502` without another model invocation. `fallback_on_ambiguous_errors: true` is an explicit duplicate-call/duplicate-charge opt-in. Oversized responses are never retried.

**Buffered provider errors use a fixed envelope.** On the buffered path a provider non-2xx response body is never relayed to the client. Whether the status is final or a fallback-eligible status on the last attempt, the client receives `{"error":{"message":"Upstream provider returned status <N>","type":"upstream_error","param":null,"code":"upstream_error"}}` with the provider's real status and the bounded safe provider headers (`Retry-After`, request IDs, rate-limit fields). The provider's own machine-readable error (`context_length_exceeded`, `insufficient_quota`, an Anthropic `invalid_request_error` detail, a Bedrock `ValidationException` message) is deliberately discarded, because provider error bodies can echo request content or internal detail. Clients that branch on `error.code` should branch on the HTTP status (and `Retry-After`) instead behind buffered federation. A claimed stream differs: its non-2xx response is relayed as the provider's own error envelope.

**Generation-control support matrix.** OpenAI-compatible providers and Cohere receive the client body unchanged, so every OpenAI field reaches them (and the provider validates it). The translating adapters build the native request from an explicit field set, so every other semantic control is either mapped or refused — never silently dropped:

| OpenAI field | `google_gemini` / `google_vertex` | `anthropic` | `aws_bedrock` |
|---|---|---|---|
| `messages`, `max_tokens` / `max_completion_tokens`, `temperature`, `top_p`, `stop`, `tools`, `tool_choice` | mapped | mapped | mapped |
| `response_format` `json_object` | `generationConfig.responseMimeType: application/json` | refused | refused |
| `response_format` `json_schema` (a `schema` object is required) | `responseMimeType: application/json` + `responseJsonSchema` (the client schema unchanged); a `strict: true` schema must stay inside the enforced subset below | refused | refused |
| `n` > 1 | `candidateCount` (every candidate becomes a choice) | refused | refused |
| `seed` | `seed` | refused | refused |
| non-zero `presence_penalty` / `frequency_penalty` | `presencePenalty` / `frequencyPenalty` | refused | refused |
| `parallel_tool_calls: false` (with tools) | refused | `tool_choice.disable_parallel_tool_use: true` | refused |
| `logprobs: true`, `top_logprobs`, non-empty `logit_bias`, `tools[].function.strict: true`, `reasoning_effort`, `reasoning`, `verbosity`, `audio`, `prediction`, `web_search_options`, legacy `functions` / `function_call`, non-text `modalities` | refused | refused | refused |

**Strict schemas on Gemini/Vertex.** Google enforces only a documented JSON Schema subset in `responseJsonSchema` and silently ignores the rest (its structured-output guide lists `minLength`/`maxLength`, `minProperties`/`maxProperties`, `uniqueItems`, `contains`, `minContains`, and `maxContains` as ignored). A `json_schema` with `strict: true` is therefore screened recursively — through `properties`, `$defs`, `items`, `prefixItems`, `anyOf`, and `additionalProperties`, to a depth of 32 — and every keyword must be one of `type`, `title`, `description`, `enum`, `format` (only `date-time`, `date`, `time`), `anyOf`, `$ref`, `$defs`, `properties`, `required`, `additionalProperties`, `items`, `prefixItems`, `minItems`, `maxItems`, `minimum`, `maximum`. References are held to Google's documented restrictions as well: a `$ref` node carries no sibling keyword (only the root may pair its `$ref` with the `$defs` it points into), it must name `#` or an existing root `#/$defs/<name>` entry, `$defs` may appear only at the root (and is screened like any other subschema), and the reference graph must be acyclic — Google honours recursion only through optional properties, so a strict schema with any recursive reference is refused rather than guessed at. Any other keyword or reference shape makes the strict schema unrepresentable and it is refused like any other control (naming the keyword, never a schema value). The list is deliberately conservative; a non-strict schema (`strict` absent or `false`) is guidance and is forwarded unchanged. A `json_schema` without a `schema` object is malformed and is refused on every adapter rather than downgraded to JSON-object mode. Reasoning controls are refused rather than mapped because their native equivalents (Gemini `thinkingLevel` / `thinkingBudget`, Anthropic thinking budgets) are model-family specific, so any translation would substitute a setting the client never chose.

Neutral values (`response_format` `text`, `n: 1`, zero penalties, `logprobs: false`, an empty `logit_bias`, `parallel_tool_calls: true`, `strict: false`, `modalities: ["text"]`) are accepted everywhere. A refusal happens during request translation, before any provider I/O, and behaves like any other translation failure: with `fallback_enabled` the next matching provider is tried (so a mixed list falls through to a provider that can represent the control), and when no provider was dialed the caller receives `400` (`provider_translation_failed`) naming the field. Informational fields with no generation effect (`user`, `metadata`, `store`, `service_tier`, `stream_options`, and similar) are not forwarded to the translating adapters.

**Tool calls, candidates, and stop values.** Supported assistant tool calls and tool-result messages are mapped to Anthropic `tool_use`/`tool_result`, Gemini `functionCall`/`functionResponse`, and Bedrock `toolUse`/`toolResult`; native tool responses normalize back to OpenAI `tool_calls`. All supported text blocks are concatenated in provider order, parallel tool calls retain their relative order in `message.tool_calls`, and every Gemini candidate becomes a stable-index OpenAI choice. Cross-type text/tool interleaving is represented by Chat Completions' separate `content` and `tool_calls` fields rather than discarded. Unsupported or malformed blocks fail explicitly. A scalar OpenAI `stop` becomes a one-element array only in native array-only fields; arrays are preserved, with at most four non-empty sequences of at most 1024 characters. Bedrock has no native disabled tool choice, so `tool_choice: none` is represented by omitting `toolConfig` entirely — the request succeeds with no tool available to the model. Cohere v2 accepts only `REQUIRED` and `NONE` and expresses automatic selection by omission, so `auto` drops the field, `required` and `none` become the native enum (a `none` with no declared tools drops the field too, since there is nothing to disable), and a named function choice — which Cohere cannot represent — is rejected with `400` before dispatch rather than forwarded as a selection the provider would refuse.

**Native request-field naming.** Cohere v2 receives the request under its own field names: an OpenAI `max_completion_tokens` becomes Cohere `max_tokens` (an explicit `max_tokens` wins when a client sends both, exactly as the Bedrock adapter resolves the same pair), and `top_p` becomes `p`. Both values are forwarded unchanged rather than clamped into the provider's documented range, so an out-of-range setting is that provider's own validation error instead of a silently substituted different setting.

Gemini function calls do not carry an OpenAI call ID in the native response shape, so federation generates a response-local OpenAI ID. A later `role: tool` message is mapped back to the Gemini function name by finding that ID in the assistant transcript supplied by the client. Anthropic, Bedrock, and Cohere preserve provider call IDs directly. Parallel calls are retained for every native adapter.

**Gemini thought signatures survive the tool-call round trip.** Gemini 3 thinking models (Gemini API and Vertex AI) attach an opaque `thoughtSignature` to a `functionCall` part and reject the next function-calling turn with `400` when that signature is missing. Federation exports it on the OpenAI tool call using Google's OpenAI-compatibility convention, `tool_calls[i].extra_content.google.thought_signature`, and when the client sends that assistant message back it restores the exact signature on the reconstructed native `functionCall` part. Clients must send the assistant message back with each tool call's `extra_content` intact (the same requirement Google's own OpenAI-compatible endpoint imposes); a client that rebuilds tool calls from `id`/`function` alone drops the signature. The signature is bounded at 64 KiB, must be a non-empty string (a malformed value is refused with `400` rather than sent unsigned), and is never logged; an explicit `null` at any level of the extension is treated as absent. Signatures Gemini attaches to plain text parts — including the text part of a candidate that also carries function calls — are not carried: Google's thought-signature contract places the enforced signature on the (first) `functionCall` part and states that a signature on a non-function-call part is optional, that omitting it "won't cause an error", and that the API does not strictly enforce validation for it ([Vertex AI thought signatures](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/thought-signatures)). OpenAI Chat Completions has no per-text-part slot to carry it, and moving it onto a different part would change what the provider validates. Other adapters ignore the extension, and OpenAI-compatible providers receive the client body unchanged.

**Provider configuration fields:**

| Parameter | Type | Default | Description |
|---|---|---|---|
| `name` | String | _(required)_ | Unique provider name for logging |
| `provider_type` | String | _(required)_ | One of: `openai`, `anthropic`, `google_gemini`, `google_vertex`, `azure_openai`, `aws_bedrock`, `mistral`, `cohere`, `xai`, `deepseek`, `meta_llama`, `hugging_face` |

| `priority` | Integer | _(index + 1)_ | Lower = tried first. Equal priorities keep configuration order unless a provider in the group sets `weight` |
| `weight` | Integer | _(unset)_ | Optional weighted-selection share, `1`–`1000`. When any provider in the leading equal-`priority` group of a request's matching providers sets it, the **first** attempt is chosen at random in proportion to the weights (an unset weight counts as `1`; a provider whose circuit cannot currently admit gets no share, nor does one whose `multimodal_mode` refuses the request's content parts or, on the streaming path, a streaming-ineligible provider, so its share is spread over the providers that can serve the request), and the remaining attempts keep the deterministic priority/configuration order. A random value is drawn only when at least two providers of that group can take the first attempt. Applies to buffered and streaming selection. With no `weight` anywhere, selection is fully deterministic |
| `model_patterns` | Array | `[]` (catch-all) | Up to 128 model globs, each 1–256 ASCII bytes containing only letters, digits, `.`, `_`, `:`, `/`, `+`, `-`, and `*`, with no `..` sequence (e.g., `["claude-*"]`). `*` is the only wildcard, matches any run of characters except URL-structural separators (`/ ? # & \`) and whitespace, and the pattern is anchored at both ends — so `*mini` matches `model-mini` and `mini-mini` alike, and never matches `mini-pro` |
| `model_mapping` | Object | `{}` | Up to 1024 valid client model IDs mapped to provider-native names |
| `default_model` | String | _(none)_ | Default model when no mapping matches |

| `max_response_body_bytes` | Integer | `8388608` | Bounded provider response collection (maximum `67108864`) |

  providers:
    - name: anthropic-primary

        success_threshold: 1
    - name: openai-fallback

      priority: 2

Use this only when the normal backend has equivalent authentication, model allow-listing, rate limits, prompt/body validation, and logging. Otherwise a request with an uninspectable body, no valid `model`, or an unsupported `model` can avoid the federated provider path entirely.

**Cross-plugin synergy:** Works with all other AI plugins on the same proxy:
- `ai_transcript_audit` (2740) stages transcript capture before request deduplication and guardrails; `ai_prompt_shield` (2925) scans/redacts PII before federation
- `ai_semantic_firewall` (2968) blocks semantic prompt injection, exfiltration, tool-abuse, and topic-policy violations before semantic cache or federation
- `ai_request_guard` (2975) validates model, tokens, temperature before federation
- `ai_prompt_compressor` (4055) boundedly shortens admitted OpenAI Chat/Text Completions plaintext, stages compatible metadata while limiting private wire-result reuse to 65,536 bytes, records authoritative wire stats after request decompression, and uses a bounded representation-preserving fallback so configured preserve markers cannot bypass sanitation; successful compression rewrites reserialize the complete JSON body
- `ai_federation` (4060) routes that final transformed body to a provider from the finalized-request-egress phase, after the complete final-policy hook pass and before backend dispatch, and writes token metadata to `ctx.metadata`
- `ai_rate_limiter` (4200) records token usage from federation metadata via `applies_after_proxy_on_reject`

**Metadata and metrics:** `ai_total_tokens`, `ai_prompt_tokens`, `ai_completion_tokens`, `ai_model`, `ai_provider`, and `ai_federation_provider` use the same transaction keys as `ai_token_metrics`. Prometheus authorization for token and cost series is carried separately in private typed request state, so backend, serverless, workload-tag, and custom-header metadata cannot mint trusted usage. Federation provider types are normalized to the bounded OpenAI, Anthropic, Google, Cohere, Mistral, or Bedrock metric families without changing the raw `ai_provider` metadata consumed by logs and policy plugins. Circuit observations use `ai_federation_circuit_last_provider`, `ai_federation_circuit_last_state`, `ai_federation_circuit_open_skips`, and `ai_federation_circuit_half_open_probes`. `/metrics` exposes the provider-name-free `ferrum_ai_federation_circuits_open` gauge and `ferrum_ai_federation_circuits_{opened,closed}_total`, `ferrum_ai_federation_circuit_half_open_probes_total`, and `ferrum_ai_federation_circuit_open_skips_total` counters, plus per-provider companions labelled with the configured provider `name`: the `ferrum_ai_federation_provider_circuits_open{provider}` gauge and `ferrum_ai_federation_provider_circuits_{opened,closed}_total{provider}` counters. The `provider` label is the operator-configured name (restricted charset, at most 128 bytes and 128 providers per instance), never a model or request value, so its cardinality is bounded by configuration; instances that reuse a name share its series. The per-provider gauge entry is removed when its circuit closes or is dropped by a reload, and the counters follow the registry's stale-series TTL. Each circuit publishes both gauge families from its current state under a per-circuit lock taken only on open/close transitions, so a half-open close that races a reopen can never leave an open circuit unpublished; a close the circuit already reopened from is still counted in both transition counters. Removing/reloading an open configured circuit decrements both gauges; transition/probe logs carry only the restricted provider name, never an endpoint or credential. When `multimodal_mode: text_only_with_warning` drops non-text parts, the plugin also writes `ai_federation_multimodal_mode`, `ai_federation_multimodal_dropped_parts`, `ai_federation_multimodal_dropped_types`, `ai_federation_multimodal_dropped_roles`, and `ai_federation_multimodal_provider`.

**TLS trust chain:** Buffered (non-streaming) federation bypasses the normal proxy dispatch and makes outbound HTTP calls via the shared `PluginHttpClient`. An eligible `stream: true` request with the `streaming` block enabled instead commits the selected provider as a route override — scheme, host, port, absolute path, authority, a cleared upstream and DNS override, and a default-verify TLS override with no client certificate or per-proxy CA — and is then sent by the **normal proxy dispatch path**. Either way federation uses **global TLS settings only** — `FERRUM_TLS_CA_BUNDLE_PATH`, `FERRUM_TLS_NO_VERIFY` and `FERRUM_TLS_CRL_FILE_PATH` / `_SOURCE`. Per-proxy backend TLS overrides (`backend_tls_server_ca_cert_path`, `backend_tls_client_cert_path`, `backend_tls_verify_server_cert`) do not apply. With a gateway CRL configured and verification on, provider certificates are checked against it and trust comes from `FERRUM_TLS_CA_BUNDLE_PATH` or, without it, the bundled webpki roots rather than the OS store; a refreshed CRL also retires pooled connections (see [Surfaces CRLs do not reach](../frontend_tls.md#surfaces-crls-do-not-reach)). For providers behind private endpoints (e.g., Azure Private Link, VPC endpoints), add the internal CA to the global CA bundle PEM file. Note that when `FERRUM_TLS_CA_BUNDLE_PATH` is set, webpki/system roots are excluded (CA exclusivity) — include public root CAs in the bundle if some providers are public and others use internal CAs.

`base_url` requires HTTPS by default. Set `allow_plaintext: true` only for an explicitly trusted cleartext endpoint; this does not enable redirect following. URL userinfo, queries, and fragments are rejected so credentials remain in dedicated fields. Azure resource/deployment/API-version, Vertex region/project, AWS region, and request-selected path models use strict component grammars. Google service-account OAuth is pinned to `https://oauth2.googleapis.com/token`. Logs use redacted endpoint placeholders, and every shared-client construction path disables ambient HTTP proxy discovery, including the policy-preserving fallback builders. The repository-wide ambient-proxy advisory remains open for dedicated plugin clients outside this shared client.

Federation parses the authoritative final JSON once and serializes that canonical value into every provider request. Duplicate object names therefore cannot leave one parser-evaluated representation for policy while sending a different raw representation to the provider; malformed provider success shapes are likewise rejected before a client response is committed.
