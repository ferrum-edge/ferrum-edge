# Centralized rate limiting: design notes

Part of the [Plugin Reference](../plugins.md). These notes describe how `rate_limiting`, `graphql`, and `grpc_method_router` enforce request quotas in centralized mode (`sync_mode: "redis"`). The operator-facing contract — accuracy bound, ACL requirements, topology limits, failure policy, and reload behavior — is in the [`rate_limiting`](../plugins.md#rate_limiting) section.

## Charge-then-compensate

**Centralized mode** (`sync_mode: "redis"`): Rate limit counters are stored in Redis so multiple gateway instances (e.g., multiple data planes) share a single global rate limit. Admission is **charge-then-compensate**, using only native RESP commands on the ordinary pooled connections — no Lua, no `EVAL`/`EVALSHA`, no `WATCH`, and no per-request connection. One atomic `MULTI`/`EXEC` charges **every** configured window (`GET` each older sub-bucket, `INCR` the sub-bucket this request lands in, `EXPIRE` that sub-bucket) and ends with one `TIME`, and the decision is read off that increment against the server clock that `TIME` returned, so two gateways can never both admit against one stale read or against two different ideas of "now". If every window fits, the request is admitted and the tightest window's remaining budget is reported. If any window refuses, one compensating atomic `MULTI`/`EXEC` (`DECR` + `EXPIRE`) hands the charge back on **every** window this request incremented — the ones that fit included — and the refusal names the first refusing window. **A refused request therefore leaves no lasting charge on any window**, so sustained excess traffic keeps being throttled at the configured rate instead of re-arming its own exhaustion, and a tighter window's refusal never consumes a looser window's budget. There is no optimistic-retry budget for a hot key to exhaust: every decision costs exactly one round trip on the request path, and a refusal's hand-back is a second round trip issued off it. Between a refused attempt's `INCR` and its compensating `DECR` the transient charge is visible, so a concurrent request for the same identity may be refused against a count that is about to be handed back; the limiter can refuse slightly early under contention and never over-admits. The whole decision — the charge transaction, reading its reply, settlement, and any compensation — runs on a task of its own that holds the shared Redis client, and the request only awaits its result, so cancelling the request — a gRPC deadline elapsing, a client disconnect, a configuration reload retiring the plugin instance — while the charge is in flight cannot strand an over-limit increment: the detached task still reads the reply and hands a refused charge back. The compensation is in turn issued from its own detached task, so the refused caller does not pay the second round trip inline. If the compensation cannot be delivered because Redis went away mid-decision, the charge stays until the window's TTL elapses, the failure is recorded like any other Redis failure (so `redis_failure_policy` governs the next decision), and this request's refusal still stands. The only other way a refusal leaves a lasting charge is a process exit between the charge and its compensation: the increment is already on the server, and it stays until the window's TTL elapses. **Algorithm — sub-bucketed trailing window.** Every configured window is split into **16** equal sub-buckets keyed `{prefix:key}:{window_seconds}:{sub_index}`, and a window's count is the FULL sum of the sub-bucket the request lands in, the **17** sub-buckets before it, and the one after it — nineteen counters, every bucket at face value, with no decay term. The trailing 18 of those counters always span at least one whole window, so a burst clustered anywhere inside the exact trailing window is counted whole and can never be discounted while it is still live; they span at most two sub-buckets more than a window measured from where the reader *selected*, and at most three measured from where Redis *executed* it, so the limiter over-refuses by at most three sixteenths of a window of history. Reading **one sub-bucket further back than the window itself** is a correctness requirement: a charge's key can be one sub-bucket older than the sub-bucket Redis executed it in, so a reader that stopped at `window` exactly would drop a still-live peer charge off the old end. (The forward counter is empty in ordinary operation; see **Concurrency and clocks** below.)

## Concurrency and clocks

**Concurrency and clocks.** Bucket selection happens before the pooled connection is acquired, so a charge always executes a little after it was built. Reading the sub-bucket *after* the charged one closes the reordering case: a request that selected bucket `b` and a peer that selected `b + 1` are both inside one trailing window, and whichever transaction reaches the server second observes the other, so they can never both be admitted against a one-request quota. Beyond one sub-bucket that cover is gone, so each charge transaction carries a `TIME` as its last command and the **server's own clock at `EXEC`** decides, in **both** directions:

- If the server applied the transaction at `b + 2` or later, the ladder may have missed a peer's charge.
- If it applied the transaction **before** `b`, the charge was placed in the future, where no peer's trailing window reaches it — a gateway whose clock runs ahead of Redis, a wall-clock step, or an offset learned before a server-side clock change.

Either way the charge is handed back and the ladder is rebuilt from that server instant for exactly **one** more transaction, and a second mis-settlement refuses (fail closed) with a sampled warning. The rebuild waits for its own hand-back to be confirmed first — the rebuilt ladder reads the sub-bucket the abandoned pass charged, so rebuilding before the `DECR` lands would count that charge against the very request that abandoned it; a hand-back that fails or does not answer inside the screened per-command deadline refuses instead of rebuilding, and the stranded charge expires with the window's TTL. This is a settlement rebuild on a *successful* transaction, not a retry of a failed command — a Redis error still costs exactly one round trip and is never retried.
>
> **Operational note.** The late rebuild triggers when the server applies a transaction a whole sub-bucket after its bucket was selected. How long a stall that takes is phase-dependent — between one and two sub-buckets, depending on where inside its own sub-bucket the request arrived — so roughly **62.5–125ms for a one-second window** and **3.75–7.5s for a one-minute one**. **The stall that matters is execution, not the round trip.** Settlement is judged on the `TIME` the transaction itself carried, so a transaction the server *applies* inside its own sub-bucket settles correctly however late its *response* arrives. A Redis whose execution regularly stalls that long will rebuild on most requests and, when the rebuild stalls too, refuse. A Redis that merely answers slowly does not rebuild at all — but a reply held past one sub-bucket also stops teaching the offset (see **Clock contract** below), so the base freezes at whatever the connection's probe seeded: enforcement stays correct until the server's clock moves under it, and from then on every request mis-settles on its first pass *and* on its rebuilt one — the rebuilt pass selects from the server instant the abandoned pass carried, which that same late response already leaves stale by more than the settlement band — so it refuses. Those refusals are counted and routed as an *unavailable centralized store* (`redis_failure_policy`: `local_fallback` for `rate_limiting`, `fail_closed` elsewhere), not as quota refusals — which is the intended reading: a store that cannot answer inside one sixteenth of the window cannot enforce that window. Longer windows scale the tolerance with them (3.75–7.5s for a one-minute window, 225–450s for an hourly one), so this is only reachable for sub-minute policies against a badly overloaded store.

## Clock contract

> **Clock contract.** Sub-buckets are selected on the **Redis server's clock**, not on each gateway's. Every charge transaction ends with a `TIME` inside the same `MULTI`/`EXEC` — no extra round trip — and each gateway keeps a continuously corrected offset (`server_time − local_time_at_reply`) that the *next* request selects its bucket with. Bucket selection and settlement are judged on the Redis server clock; the local clock is used only through that offset. Before its first selection a gateway establishes the connection — and therefore runs its `TIME` probe — first, so even the first request after start selects on the server clock.
>
> **The correction does not put gateways on the same clock, and this design does not depend on it doing so.** The offset is sampled one *reply latency* after the server read its clock, so each gateway's corrected clock lags the server's by roughly its own reply latency, and two gateways sharing a quota select on clocks that differ by the *difference* of theirs. What the correction buys is that the disagreement is bounded by round-trip times instead of by NTP discipline. What makes the count correct in spite of it is structural: settlement is two-sided, so every retained charge is keyed within one sub-bucket of the sub-bucket Redis executed it in, and the ladder reads one sub-bucket further back than its own window to cover exactly that.
>
> The guarantees, stated exactly:
>
> 1. **No charge executed inside a reader's trailing window is ever missing from that reader's ladder**, whatever the two gateways' reply latencies are.
> 2. Residual over-admission is bounded by the **concurrent in-flight requests of a single gateway** during the two-pass rebuild window — a request that rolls over hands its charge back and re-charges, and another request of the same process can be decided in between.
>
> Run NTP (or your platform's equivalent) on every gateway host as ordinary hygiene — it keeps logs, TLS and the token-accounting `{prefix:key}:{window_index}` layout honest — but the request-quota ladder does not rest on it.
>
> **A stale reply cannot move the base.** The offset a transaction teaches is only adopted when that transaction's own reply arrived within one sub-bucket of the tightest window it charged. A reply held longer teaches an offset already staler than the ladder's forward cover, so the previous offset stands; the charge that carried it is still settled against the server instant the reply contains, which owes nothing to the offset. A connection whose replies are *never* prompt therefore stops learning entirely and keeps the offset its own `TIME` probe seeded. That is not by itself a degradation: while the server keeps *executing* transactions inside the sub-bucket they were keyed to, every one of them settles and every decision stands. The cost is deferred — the frozen base no longer tracks the server, so a later server-side clock change or a wall-clock step on the gateway is never learned, and once that drift passes the settlement band every request mis-settles on its first pass and hands its charge back. The rebuild does not recover the step either: it selects from the server instant the abandoned pass carried, which the same late reply already leaves stale by more than the band, so the rebuilt pass mis-settles too and the request is routed through `redis_failure_policy`. The latency that starves learning and the staleness the rebuild inherits are the same quantity, so a frozen offset that then meets a clock step is an *unavailable store*, not a permanent double charge. A store whose replies are prompt pays exactly **one** rebuild for the same step, is admitted, and learns the step from that pass's own sample — a rebuild recovers a clock change only while replies are prompt, which is exactly when learning would have recovered it anyway.
>
> **There is no local-clock mode.** `TIME` is required for request quotas (see **Redis ACL requirement** below). A connection whose probe cannot answer a clock — `NOPERM`, unknown command, a non-clock reply, a timeout, a transport failure — is discarded unpublished and the client is marked unavailable, so the configured `redis_failure_policy` governs exactly as it does during a Redis outage: `local_fallback` enforces the quota once per gateway process, `fail_closed` refuses with `503`. A gateway never selects buckets on an uncorrected local clock, because a ladder built that way is not a shared budget and serving one quietly would be enforcement in name only.
