# mcp_gateway

Part of the [Plugin Reference](../plugins.md).

**Priority:** 2992 · **Phases:** `before_proxy`, `transform_request_body`, `enforce_final_backend_header_policy`, `on_final_request_body`, `normalize_response_body`, `transform_response_body`, `after_proxy`, `on_final_response_body` · **Protocols:** HTTP · **Failure policy:** `FailClosed`

HTTP-only Model Context Protocol gateway for AI agent tool traffic. `transparent_proxy` mode preserves MCP JSON-RPC and session headers while routing one Ferrum endpoint to one upstream MCP server. `aggregate_router` mode exposes one Ferrum MCP endpoint for multiple upstream MCP servers, synthesizes downstream `initialize`, lazily initializes upstream sessions, aggregates `tools/list`, `resources/list`, and `prompts/list`, namespaces public names, routes singleton `tools/call`, `resources/read`, and `prompts/get`, rewrites public names back to upstream names, validates tool arguments against discovered `inputSchema`, admits bounded JSON-RPC batch arrays with per-item validation and ordered synthetic response assembly (upstream-routed members must be singleton requests so later plugin phases are preserved), and emits `mcp.*` metadata for existing Ferrum authz, logging, tracing, chargeback, and alert plugins. A private, gateway-authenticated public→upstream tool-name mapping accompanies each aggregate `tools/call` rewrite so `ai_tool_governor` can keep policy keys on the public namespaced identity across that rewrite without trusting forgeable metadata.

`endpoint.path` must be a canonical policy path and may not be `/`. The configured spelling is the only MCP endpoint: `/mcp` and `/mcp/` are distinct paths, ensuring authorization and MCP routing evaluate the same request target. Extra segments (`/mcp/tools`, `/mcp/tools/`), repeated trailing slashes (`/mcp//`), case variants (`/MCP`), percent-encoded separators (`/mcp%2F`), and dot segments (`/mcp/.`) are also different, rejected paths. Variants reaching the plugin return HTTP 404 with JSON-RPC `-32600` / `Unknown MCP endpoint`; encoded separators and dot segments are already rejected with HTTP 400 by the shared HTTP frontend.

The endpoint reserves its whole slash-delimited subtree, including case variants for rejection. A root endpoint would reserve the entire origin and refuse every other handler on the proxy, so `endpoint.path: "/"` remains rejected at admission — use a sub-path such as `/mcp`. Two enabled `mcp_gateway` instances on one proxy may not have overlapping endpoint scopes (`/mcp` with `/mcp/v2`, `/mcp/`, or `/MCP`): admission rejects the pair, because one of them could never be reached. Disjoint scopes such as `/mcp` and `/tools` compose normally. Unrelated sibling paths remain available to other handlers. Query parameters do not change endpoint selection. GET, POST, and DELETE retain their MCP semantics; other methods reaching the plugin return 405 (CORS preflight can be handled by the CORS plugin earlier in the chain).

Transparent mode enforces the same exact `endpoint.path` contract as aggregate mode: trailing-slash aliases are refused before forwarding to the configured `servers.*.upstream_url` path. It has no mediated catalog. Explicit `policy.default_action`, `policy.default_prompt_action`, `policy.default_resource_action`, `policy.tools`, `policy.prompts`, `policy.resources`, `policy.hide_denied_tools`, `servers.*.forward_client_credentials`, `discovery.aggregate_tools`, `discovery.aggregate_resources`, `discovery.aggregate_prompts`, `discovery.namespace_separator`, `discovery.cache_ttl_seconds`, `discovery.hide_denied_items`, `discovery.on_new_tool`, or `discovery.on_schema_change` configuration is therefore rejected at admission, including explicitly configured defaults: every one of them is inert in this mode, and silently accepting it would promise a control that is never enforced. Use `aggregate_router` to enforce those controls; transparent mode never silently removes a configured policy.

A client JSON-RPC id token reflected into a gateway-authored singleton response is bounded at 4096 wire bytes; a larger id is refused with a fixed `-32600` that does not echo it (batch responses stay bounded by `validation.max_batch_response_bytes`, and request stream identities by `sessions.sse_max_stream_id_bytes`).

JSON-RPC numeric IDs retain their exact wire tokens across MCP request/response rewrites and synthetic singleton/batch responses. Request stream admission, cancellation, and response matching use those tokens rather than floating-point values: `1`, `1.0`, and `1e0` are distinct identities, as are adjacent large integers. String IDs remain distinct from numbers. A mismatched or ambiguous response for an open request is replaced by a bounded gateway error and is never framed as that request's event stream or delivered as a successful inline response. These checks retain the existing stream/session byte limits and cancellation lifecycle.

The plugin deliberately does not implement generic auth, rate limiting, retry, timeout, WAF, tracing, DLP, or semantic safety behavior; compose the plugins that do (see [Recommended plugin stack for an agent-facing MCP endpoint](#recommended-plugin-stack-for-an-agent-facing-mcp-endpoint)).

The plugin is HTTP-only: each `servers.*.upstream_url` must be `http://` or `https://`. Unknown keys at the root, in nested fixed-shape objects, and inside each `servers.*` object fail closed. Claude-Desktop-style `command` / `args` / `stdio` fields are rejected with an HTTP-only diagnostic rather than a generic unknown-key error — stdio spawn is not implemented, and a typo of this kind must not pass `validate`.

**Cannot be composed with `request_deduplication` on the same proxy.** Config admission rejects the pair. The public URI/name rewrite is resolved against a per-session catalog re-listed from upstream on `discovery.cache_ttl`, so a deduplicated replay — served before this plugin runs, and without re-applying its rewrite — cannot be proven to match the live mapping. See the `request_deduplication` section for the full reasoning and the remedy.

```yaml
plugin_name: mcp_gateway
scope: proxy
config:
  enabled: true
  mode: aggregate_router
  endpoint:
    path: /mcp
    protocol_versions: ["2025-11-25"]
  discovery:
    namespace_separator: "."
    cache_ttl_seconds: 300
    on_new_tool: hide_until_configured
    on_schema_change: hide_until_configured
  sessions:
    downstream_session_header: mcp-session-id
    upstream_session_header: mcp-session-id
    initialize_upstreams: lazy
    session_ttl_seconds: 3600
    max_sessions: 16384
    max_sessions_per_principal: 128
  servers:
    github:
      upstream_url: http://github-mcp.example/mcp
      namespace: github
      expose_tools: true
    jira:
      upstream_url: http://jira-mcp.example/mcp
      namespace: jira
      expose_tools: true
  policy:
    default_action: deny
    tools:
      github.create_pr:
        action: allow
      jira.create_issue:
        action: allow
  validation:
    validate_tool_arguments: true
    validate_tool_results: false
    max_batch_items: 32
    max_batch_bytes: 1048576
    max_batch_item_bytes: 262144
    max_batch_response_bytes: 1048576
```

Server ids (`servers.<id>`) must match `[A-Za-z0-9._-]+` because they are embedded verbatim in public `mcp://{server_id}/...` resource URIs. There are no result-side observability settings: result logging and result hashing were never emitted, so `observability.log_raw_results` and `observability.log_result_hash` are rejected as unknown keys rather than accepted and ignored. The discovery client shares the gateway's plugin HTTP client; ordinary backend connect/read timeouts are proxy-level configuration and are not repeated here.

Request bodies are admitted by media type, not by exact spelling: `application/json`, `application/json-rpc`, and any `+json` structured suffix are accepted case-insensitively (`application/vnd.example+JSON` is the same media type as `application/vnd.example+json`), and a request with no `Content-Type` at all is still admitted. A `charset` parameter other than `utf-8` / `utf8` (case-insensitive, optionally quoted), or any RFC 2231 `charset*` form, is refused with JSON-RPC `-32600` before routing: the gateway and the governance plugins read JSON-RPC as UTF-8, and a body declared in another charset — UTF-7 is plain ASCII and still parses — would be governed as one text and decoded as another by a charset-aware upstream.

**Multiple instances on one proxy.** Instances with disjoint `endpoint.path` scopes compose, and every phase is instance-scoped: an instance acts on the response of a request only when that same instance admitted it in `before_proxy`. A sibling on another endpoint — or one whose inner `config.enabled` is `false` — never consumes another instance's private routing/validation state and never applies its own `validation.max_upstream_response_bytes` or result policy to traffic it did not route.

**Per-consumer tool grants.** In `aggregate_router` mode an `allow` entry in `policy.tools` can be narrowed to particular consumers by their `acl_groups`, which is how an access approval that adds a group to a consumer (for example a Nexus `nexus:api:<id>:approved` grant) becomes a tool grant:

```yaml
policy:
  default_action: deny
  tools:
    orders.list_orders:
      action: allow
      allowed_groups: ["nexus:api:orders:approved", "orders-readers"]
    orders.delete_order:
      action: allow
      allowed_groups: ["orders-admins"]
      denied_groups: ["suspended"]
```

Pair grants with `policy.default_action: deny` and `discovery.on_new_tool: hide_until_configured` (the defaults): a grant restricts only the key it is written on, so a newly discovered unconfigured tool is callable only when both gates permit it: policy allows it and discovery does not hide it (`policy.default_action: allow` and `discovery.on_new_tool: allow`). Allowing either gate alone is insufficient.

A tool is granted to a request exactly when its action is `allow`, the request carries a gateway-mapped Consumer, that Consumer holds none of the entry's `denied_groups` (which always takes precedence), and the entry has no `allowed_groups` or the Consumer holds at least one of them. The decision fails closed: a request with no mapped Consumer — a proxy with no authentication plugin, or an external identity (`jwks_auth`, `oidc_relying_party`, and so on) that maps to no Consumer — is never granted a tool that carries either list, and a group the Consumer holds but no list names grants nothing. Entries without group lists keep their tool-name-only behavior exactly.

- **Discovery is filtered per caller.** `tools/list` leaves out every tool the caller is not granted, whatever `policy.hide_denied_tools` / `discovery.hide_denied_items` say, so an agent only discovers tools it may call. The same filter applies to every upstream the aggregate catalog merges and to `tools/list` inside a JSON-RPC batch.
- **Calls are enforced, not just hidden.** `tools/call` of a tool the caller is not granted answers JSON-RPC `-32001` / `MCP tool call denied by gateway policy`, the same answer a `deny` or `hide_from_discovery` tool gets, before argument validation and before any upstream dispatch. Once any entry carries a group list, a call naming an unknown tool answers the same `-32001` instead of `-32003` / `Unknown MCP tool`, so a caller cannot probe which hidden tool names exist. No answer names the tool, a group, or the reason.
- **Scope.** Grants cover `tools/list` and `tools/call` only. Prompts and resources are gated per item by `policy.prompts` / `policy.resources` actions (see *Prompt and resource policy*), not per consumer. Methods forwarded by `capabilities.passthrough_unknown_methods` are not policy- or grant-checked; restrict those per proxy with `access_control` or `opa`. That includes MCP task methods: a `tools/call` that starts a task is gated like any other call, but a later `tasks/get` / `tasks/result` for that task is a passthrough method, so a revoke does not stop the same session from retrieving the result of a task it already started.
- **Changes apply on the next request.** Groups are read from the Consumer the authentication phase resolved for the current request from the live configuration snapshot, never from a copy taken when the MCP session was created. Adding or removing a group through the Admin API therefore changes that consumer's next `tools/list` and `tools/call` on the same session, with no restart and no re-`initialize`. The gateway does not yet emit `notifications/tools/list_changed` (on a grant change or a catalog refresh), so the synthetic `initialize` advertises `listChanged: false` and a client sees the new list on its next `tools/list`. Emitting it is a planned follow-up.
- **Later plugins cannot bypass it.** The grant is recorded with the admitted call and re-decided in `on_final_request_body` after the final-body admission check below, against the Consumer on the request at that point, so a later plugin that swaps or clears the identified Consumer cannot carry an ungranted call upstream; that refusal is also `-32001`.
- **Metadata.** `mcp.policy_decision` records `deny_group` (a denied group, or none of the allowed groups) or `deny_no_consumer` (no mapped Consumer) when `observability.emit_metadata` is on.
- **Admission rules.** Each list must be a non-empty array of strings; every entry must contain a non-whitespace character, be at most 255 bytes, and contain no control character other than tab, LF, or CR (the same bounds Consumer `acl_groups` admission applies), and is matched byte-for-byte against `acl_groups`. Rejected at config load: group lists on a `deny` or `hide_from_discovery` entry, one entry naming the same group in both lists, a list longer than 512 entries, more than 512 distinct group names across the whole `policy.tools` map, and a group-conditioned key that is not a configured server's `namespace` followed by `discovery.namespace_separator` and a tool name (a typo, missing namespace, or wrong separator would otherwise leave the grant silently inert). Any configured server counts, including one with `enabled: false` or `expose_tools: false`: such a server publishes no tools, so its grants are inert and only logged as a warning, and switching an upstream off does not require deleting them. Group names are interned at load, so the per-request decision is a fixed-size bit-set intersection with no allocation.

**Prompt and resource policy.** In `aggregate_router` mode prompts, resources, and resource templates are policy-gated like tools. Each family has its own default — `policy.default_prompt_action` and `policy.default_resource_action` — and each falls back to `policy.default_action` (default `deny`), so a deny-by-default gateway lists and routes no prompt or resource until it is allowed. **Breaking:** before this policy existed every prompt and resource of an exposing server was readable by any session holder; set the family default to `allow` to keep that behavior.

```yaml
policy:
  default_action: deny
  default_resource_action: deny
  prompts:
    github.code_review: { action: allow }
  resources:
    "mcp://github/file%3A%2F%2F%2Fproject%2FREADME%2Emd": { action: allow }
    "mcp://github/file%3A%2F%2F%2Fproject%2F{path}": { action: allow }
```

- **Keys.** A `policy.prompts` key is the public namespaced prompt name. A `policy.resources` key is either a public resource URI or a public resource-template URI, exactly as `resources/list` / `resources/templates/list` publish them. Actions are `allow` or `deny`.
- **Discovery.** A prompt, resource, or template whose action is not `allow` is omitted from `prompts/list`, `resources/list`, or `resources/templates/list` (also inside a JSON-RPC batch).
- **Calls.** `prompts/get` of a prompt that is not allowed, and `resources/read` that resolves to a binding that is not allowed, answer JSON-RPC `-32001` before any upstream `initialize` or dispatch. An entry for the exact requested public URI decides first; otherwise every catalog binding of the same upstream URI decides and any deny wins — each exact resource with that upstream URI AND each matching template — so a denied resource cannot be read through an allowed template under another public spelling, and a denied template also covers the exact resources it matches (which are then not listed either). Configured denies are decided from configuration, not discovery: each deny key in `mcp://{server_id}/...` form is decoded at load to the upstream URI (or, for a template, compiled to the same matcher discovered templates use; a template deny key that is not a valid public resource-template URI is rejected at load) and compared with the resolved upstream URI, so a deny holds even when that server's `resources/list` or `resources/templates/list` has never succeeded. With a deny default, a template-routed read whose server's `resources/list` has never succeeded cannot rule out a default-denied exact resource and fails closed with JSON-RPC `-32006`.
- **Metadata.** A refusal records `mcp.item_type`, `mcp.policy_decision: deny`, and `mcp.route_decision: deny` when `observability.emit_metadata` is on.

**Upstream authentication and client credentials.** Aggregate mode talks to each upstream MCP server twice over: requests the gateway originates itself (`initialize`, `notifications/initialized`, every `tools/list` / `prompts/list` / `resources/list` / `resources/templates/list` page, and the session `DELETE`), and client calls it routes there (`tools/call`, `prompts/get`, `resources/read`, passthrough methods). Neither runs the route's plugins on the gateway-originated side, so a protected upstream is authenticated through `servers.<id>.headers`:

```yaml
servers:
  github:
    upstream_url: https://tools.example/mcp
    namespace: github
    headers:
      Authorization: "${FERRUM_PLUGIN_SECRET_GITHUB_MCP_TOKEN}"
```

- **Where they apply.** Every gateway-originated request to that server carries every configured header, and every routed call to it has each configured header installed, replacing any client-supplied spelling. Headers are scoped to their server: another server never receives them.
- **Secrets.** A value that is exactly `${FERRUM_PLUGIN_SECRET_<NAME>}` is resolved from the process environment when the plugin loads, through the same plugin-secret namespace other plugins use (`FERRUM_PLUGIN_SECRET_<NAME>_FILE` / `_VAULT` / `_AWS` / `_AZURE` / `_GCP` materialize it at startup). A `${...}` reference to any other variable is refused before anything is read, and an unset or empty variable is a load error, as is a final value that is not a valid HTTP header value. Diagnostics never echo a configured value. The names join the route's credential-header registry, so they are redacted and withheld from secondary egress such as `request_mirror`.
- **Refused names.** Duplicate names differing only in case, hop-by-hop and framing names, `Host`, `Content-Type`, `Accept`, `MCP-Protocol-Version`, `Last-Event-ID`, `Forwarded` / `X-Forwarded-*`, `X-Ferrum-Hops`, gateway `x-consumer-*` assertion names, and the configured session header names — all gateway- or transport-owned on an upstream MCP request.
- **Client credentials stay home.** The client chooses the upstream of an aggregate-routed call by naming a tool, prompt, or resource, so by default the call does **not** carry the client's `Authorization`, `Proxy-Authorization`, or `Cookie`, nor any header in the route's credential-header registry (such as a `key_auth` key header), nor any query string: the gateway commits an empty backend query for the call (the configured `upstream_url` has none), so a client query credential or a later query rule never reaches the upstream. A credential issued for Ferrum must not reach a third-party MCP server (MCP "token passthrough"). Set `servers.<id>.forward_client_credentials: true` only for an upstream in the same trust domain that must receive end-user tokens; it restores both the client's credential headers and the ordinary query, and configured headers apply either way. `transparent_proxy` forwards the client's request unchanged to its single upstream and rejects the opt-in.
- **Final boundary.** The header boundary is re-asserted over the final backend headers after every later header rule and finalized-egress overlay: client and registry credential names are stripped again (unless opted in) and each configured header is reinstalled, so a later `request_transformer` rule can neither swap in another backend's credential nor reintroduce a client one. Headers outside that set are left alone.
- **TLS.** Routed calls verify the upstream certificate against the system roots; per-upstream custom CA and client-certificate settings are not configurable yet (planned with the shared upstream mTLS work).

## OpenAPI bridge (generated tools)

A `servers.<id>` entry may carry an **`openapi`** block instead of `upstream_url` (exactly one of the two). Its tools are not discovered from an MCP server: each configured OpenAPI operation is published as one MCP tool, and every `tools/call` runs as an ordinary HTTP request to **this proxy's own configured backend**. An API published once — by hand here, or by `x-ferrum-mcp` on `POST /api-specs` ([api_specs.md](../api_specs.md#x-ferrum-mcp-optional)) — becomes callable by AI agents with no MCP server to write or host. `aggregate_router` only.

```yaml
servers:
  petstore:
    namespace: pets
    openapi:
      max_request_body_bytes: 1048576      # 1..16 MiB
      max_response_body_bytes: 1048576     # 1..16 MiB
      max_error_excerpt_bytes: 2048        # 1..64 KiB
      max_structured_content_bytes: 262144 # 1..16 MiB
      forward_request_headers: [x-api-version] # client headers to pass through (optional)
      operations:
        - name: getPet
          method: GET
          path: /pets-api/pets/{petId}     # the PUBLIC path on this proxy
          title: Get a pet
          description: Fetch one pet by id
          parameters:
            - { name: petId, in: path, required: true, schema: { type: string } }
            - { name: verbose, in: query, schema: { type: boolean } }
            - { name: X-Trace-Tag, in: header, schema: { type: string } }
          output_schema:
            type: object
            properties: { id: { type: string } }
        - name: createPet
          method: POST
          path: /pets-api/pets
          request_body:
            required: true
            schema: { type: object, required: [name], properties: { name: { type: string } } }
```

**Same gateway, same decisions.** Generated tools enter the per-session catalog through exactly the entry construction an upstream `tools/list` page takes. Their public names use the aggregate shape — `namespace` + `discovery.namespace_separator` + `name` (`pets.getPet`) — so `policy.tools` actions (`allow` / `deny` / `hide_from_discovery`), `policy.default_action`, `discovery.on_new_tool` / `on_schema_change` / `hide_denied_items`, per-consumer `allowed_groups` / `denied_groups` grants, `validation.validate_tool_arguments`, `validation.validate_tool_results`, and the `mcp.*` metadata (`mcp.public_tool_name`, `mcp.policy_decision`, `mcp.schema_validation`, `mcp.input_schema_hash`, ...) apply to them unchanged. The generated `inputSchema` is a closed object (`additionalProperties: false`) with one property per parameter plus `body` for the JSON request body; annotations default to `readOnlyHint` for `GET`, `destructiveHint` for `DELETE`, and `idempotentHint` for `PUT`, each overridable through `annotations`. A bridge server rejects `expose_resources: true`, `expose_prompts: true`, `initialize_strategy`, `headers`, and `forward_client_credentials`; a gateway whose only servers are bridges cannot enable `capabilities.passthrough_unknown_methods`; and the operation count and tool-definition bytes count against `validation.max_catalog_items_per_list` / `max_catalog_bytes_per_list`.

**Execution goes only to the proxy's own backend.** After policy, grant, and argument validation the call is admitted, and the gateway changes only the backend **method** (from `GET`, `POST`, `PUT`, `PATCH`, `DELETE` — never `HEAD` / `OPTIONS` / `TRACE` / `CONNECT`), **path**, **query**, **headers**, and **body**. No host, scheme, port, upstream, or TLS override is set, so upstream selection, retries (judged by the backend method), the circuit breaker, backend TLS, and observability apply exactly as for a direct request; no tool argument can choose where the call goes, and the URLs of an OpenAPI document's `servers[]` are never dialed. `path` is the operation's public path on this proxy; it is mapped onto the backend exactly as a direct request to that path would be (`strip_listen_path`, then `backend_path`), and a path outside the proxy's listen prefix is refused with `-32603`. `ctx.method` / `ctx.path` and the transaction log (`http_method`, `request_path`) keep the client's `POST` to the endpoint on HTTP/1.1, HTTP/2, and HTTP/3.

**Proxy-level method and path policy sees the MCP request, not the bridged one.** Everything the gateway decides before `mcp_gateway` runs, or keys on `ctx.method` / `ctx.path`, judges the client's `POST <endpoint>`:

- The proxy's **`allowed_methods`** 405 filter runs on the `POST`. `mcp_gateway` therefore applies it again to the bridged method: a bridged tool whose operation method the route does not allow is omitted from `tools/list` (it could never be called), and a call to it is refused with JSON-RPC `-32003` / `Unknown MCP tool` when no grants are configured, or `-32001` when grants are configured. The method check runs after the tool policy and per-consumer grant and before argument validation. `x-ferrum-mcp` rejects such an operation at import.
- **Plugin triggers** conditioned on `match.method` / `match.path`, **WAF** path, method, and query rules, and **authorization** or rate limits keyed on the request path (`access_control`, `opa`, `request_termination`, path-scoped `rate_limiting`, ...) see only the endpoint path and `POST`. A rule that protects `DELETE /api/admin/users/{id}` does not protect the tool bridged onto it.
- Restrict a bridged operation in `mcp_gateway` itself: `policy.tools` `deny` / `hide_from_discovery`, `policy.default_action: deny` with an explicit allow list, per-consumer `allowed_groups` / `denied_groups` grants, or simply not listing the operation. A generated gateway publishes only `GET` operations unless the document selects a mutating one explicitly (see [api_specs.md](../api_specs.md#x-ferrum-mcp-optional)).

- **Path parameters** are percent-encoded one segment at a time and the assembled path must be a canonical policy path, so an argument can never add a `/`, a dot segment, a `?`, or a `#`: a value that would need such an escape (or is empty, `.`, or `..`) is refused with `-32602` before anything is dispatched. A value containing `;` is refused too: servlet containers (Tomcat, Jetty, Spring) strip `;`-parameters before resolving dot segments, so `..;` would climb a segment there, and the bridge does not serialize matrix-style parameters.
- **Query parameters** are `application/x-www-form-urlencoded`; arrays are exploded (`tags=a&tags=b`). The bridged query replaces the MCP request's own query.
- **Header parameters** are comma-joined for arrays and must be valid header values. A header parameter may never name a hop-by-hop or framing field, `Host`, `Authorization`, `Cookie`, `Proxy-*`, `X-Forwarded-*`, `Forwarded`, `Via`, a client-address field (`X-Real-IP`, `True-Client-IP`, `CF-Connecting-IP`, `X-Client-IP`, the configured `FERRUM_REAL_IP_HEADER`), a method or URL override (`X-HTTP-Method-Override`, `X-HTTP-Method`, `X-Method-Override`, `X-Original-URL`, `X-Rewrite-URL`, `X-Original-URI`), `Range` / `If-Range`, trace context (`traceparent`, `tracestate`, `baggage`) or the request's `correlation_id` header, `Early-Data`, `HTTP2-Settings`, an MCP transport field (`Mcp-*`, `Last-Event-ID`, or either configured session header), a service-mesh control field (`X-Envoy-*`, `X-Istio-*`, `L5d-*`), or a Ferrum-internal field (`X-Ferrum-*`, `Ferrum-*`, `X-Gateway-*`, `X-Consumer-*`, `X-Geo-Country`), compared case-insensitively with `_` treated as `-`. That is refused when the plugin loads and again when a call is built.
- **Client request headers are an allowlist.** The MCP request is a JSON-RPC exchange with the gateway, so its headers describe nothing about the REST call. A bridged call forwards only `User-Agent`, `Accept-Language`, `traceparent`, `tracestate`, the header of any `correlation_id` instance on the request, and the names listed in `openapi.forward_request_headers` (at most 32, none reserved as above). Everything else the client sent is dropped — credentials (`Authorization`, `Cookie`), conditional and range fields, method and URL override families, and application headers — and so is any header an earlier plugin added to the backend map. The gateway re-adds its own forwarding (`X-Forwarded-*`), identity (`X-Consumer-*`), and `Host` handling at dispatch; a backend credential or static header belongs in `request_transformer` (priority 3000), which runs after `mcp_gateway`. The bridged request sends `Accept: application/json, */*;q=0.8` and `Accept-Encoding: identity`.
- **Body.** The `body` argument is serialized as JSON (`Content-Type: application/json`), bounded by `max_request_body_bytes`; operations without a `request_body` send none.
- Arguments the operation does not declare are refused whether or not `validate_tool_arguments` ran. Object-typed parameters, array path parameters, and template expressions that do not occupy a whole path segment are refused at load.

**The final request is re-checked.** The backend method, path, query, and body the bridge built are recorded privately with the admission and re-decided in `on_final_request_body`: a later plugin that changes any of them (or the destination) is refused with `-32014` before egress, and the per-consumer grant is re-decided there too.

**Request-body transforms are carried into the REST request or refused, never discarded.** The admission records a SHA-256 digest of the JSON-RPC envelope it admitted. When an earlier request-body transform (an `ai_prompt_shield` or `ai_request_guard` redaction, for example) changed the envelope, the gateway parses it again, requires the same `tools/call` of the same tool and JSON-RPC id, validates the arguments again against the pinned `inputSchema` (with `validate_tool_arguments` on), and rebuilds the REST call. Redacted query, header, and body argument values are carried into that request redacted; a redacted path argument (`[REDACTED:email]`, for example) is not a canonical path segment, so the call fails with `-32602` exactly like any other path value that would need an escape, and nothing is dispatched. The final check then protects the rebuilt request from later changes and refuses drift with `-32014`.

**Responses become tool results.** A JSON-RPC response always rides HTTP 200, so the response is converted in the buffered **normalize** phase — before response guards, transforms, and the authoritative final client-visible policies, which therefore inspect the representation the client receives — and the HTTP status becomes `200`:

- **2xx** → `isError: false`, the body as text content, plus `structuredContent` when it is a JSON object (JSON / `+json` content type) no larger than `max_structured_content_bytes`. A **2xx always stays `isError: false`**, because the operation ran and reporting its representation as a failure would invite an agent to retry a call that may not be idempotent: a JSON body past `max_structured_content_bytes` is returned as text only with a note (checked before it is parsed), and a body over `max_response_body_bytes`, a JSON body with duplicate member names, a non-text body, and a partial (`206` / `226`), content-coded, or event-stream 2xx are omitted with a note saying why — never truncated, never an unbounded buffer. Non-JSON text is returned as text. `204` / `205` produce an empty success.
- **Anything else** (including `3xx`) → `isError: true` with the status line (`HTTP 404 Not Found`) and at most `max_error_excerpt_bytes` of the body, cut at a UTF-8 boundary with a truncation note. A gateway or dispatch failure carries its gateway-error class in the status line (`HTTP 503 Service Unavailable (gateway error: circuit_breaker_open)`, `HTTP 502 Bad Gateway (gateway error: connection_failure)`); a backend 5xx reads `backend_error` / `backend_timeout`. The class is derived from the typed dispatch outcome (backend response, pre-wire failure, post-wire failure, or a gateway rejection before dispatch), never from an `X-Gateway-Error` header a backend sent, and a failure the gateway authored itself is answered from the status line alone.
- Declared-oversize responses are answered from the response head. Bridged requests send `Accept-Encoding: identity`, so a compliant backend never codes the response.
- The client-visible `Content-Type` is `application/json`; validators and representation metadata of the REST body (`ETag`, `Last-Modified`, digests, `Content-Disposition`, `Content-Location`, `Content-Language`, `Content-Range`) are dropped. A backend response that reaches the final phase unconverted is replaced by a gateway-authored result (still `isError: false` for a 2xx) rather than released.
- **Observability of the 200.** Because the client-visible status of every bridged call is `200`, status-code metrics (`ferrum_requests_total` and friends), status-conditioned log sampling, and the transaction log's status see `200` for a bridged failure too, and the wire `X-Gateway-Error` header is not a reliable failure signal for a bridged call: it is derived at the pre-wire boundary from the dispatch outcome and the client-visible `200`, so a bridged backend `5xx` does not carry it. The backend status and failure class survive in the result's status line and in `mcp.bridge.upstream_status` / `mcp.bridge.gateway_error`.
- With `validation.validate_tool_results` on, a tool with an `output_schema` has its `structuredContent` validated exactly as an upstream tool's result is. With `sessions.sse_multiplexing`, the converted result rides the POST's own event stream like any routed answer.

**Metadata.** Besides the shared `mcp.*` keys, a bridged call records `mcp.bridge.operation` (`METHOD /path/{template}`, with `observability.emit_metadata`), and always — whatever `emit_metadata` says, since the client sees `200` — `mcp.bridge.upstream_status` and, for failures, `mcp.bridge.gateway_error`.

**Catalog cost.** A bridge server's tool list is static, so its catalog entries (schemas, compiled `inputSchema` / `outputSchema` validators, hashes) are built once when the plugin loads and shared by every session's catalog; a per-session refresh copies no schema and compiles nothing.

**Scope limits in this version.** Resource and prompt families, `servers[]` URLs, cookie parameters, matrix-style (`;`) and other non-default parameter styles, and non-JSON request bodies are not bridged. Client credentials are not passed through to the REST backend (`Authorization` and `Cookie` cannot be listed in `forward_request_headers`). A batch member naming a bridged tool is refused with `-32009` like any upstream-routed member. Composing an `openapi_validator` that does not bypass the MCP endpoint on the same proxy is unsupported (the client request targets the endpoint; `x-ferrum-mcp` refuses the combination with `x-ferrum-validate`). `ai_tool_governor`'s MCP final-body recheck sees the REST body, not a `tools/call` envelope, for a bridged call.

**Admission holds on the final request body.** In `aggregate_router` mode the policy decision taken in `before_proxy` — catalog membership, `policy.tools` allow/deny, `inputSchema` validation, and the selected upstream — is recorded privately on the request and re-checked in `on_final_request_body` over the exact bytes the upstream will receive, after every request-body transform has run. A routed `tools/call`, `prompts/get`, `resources/read`, or passthrough message whose JSON-RPC message kind (request, notification, or response), `method`, backend destination, mediated upstream session header (`sessions.upstream_session_header`), `params.name`, `params.uri`, or `params.arguments` a later plugin changed (a `request_transformer` body rule that renames a client field into `params.name`, for example) is refused before egress with JSON-RPC `-32014` / `MCP request changed after gateway admission`. A client-sent JSON-RPC response forwarded through `capabilities.passthrough_unknown_methods` (the answer to an upstream sampling, elicitation, or roots request) carries no `method`; it stays admissible as long as it remains a response to the same `id`. The upstream session header is gateway-owned on every request the aggregate router routes: the plugin declares a final backend-header policy that removes every spelling of `sessions.upstream_session_header` and re-inserts exactly the recorded value (or none, for a stateless upstream) at every point the backend header map is completed — after the `before_proxy` chain, after deferred passes, and after a finalized-request-egress header overlay such as a `serverless_function` `pre_proxy` response's `headers` (priority 3025), which is merged after the final request-body hook. A replacement, second spelling, or injection seen before the final request-body hook (a later `request_transformer` header rule, for example) is additionally refused there with `-32014`; one introduced by an egress overlay afterwards is overwritten, so the upstream always receives exactly the session the gateway selected. `mcp-session-id` is on no core request-header strip list (`is_backend_request_strip_header` covers hop-by-hop and framing names only); the gateway's own `set_route_to_server` strip and this policy are what own it. A JSON-RPC envelope carrying both `method` and `result` / `error` is refused at admission with `-32600`, since JSON-RPC 2.0 forbids it and it would otherwise be classified as a reply yet dispatched by its method. The destination check means a later route rewrite is refused too: `mesh_route_dispatch` (priority 2995) runs after `mcp_gateway` (2992), and a mesh destination rewrite of an MCP-routed request now fails closed rather than retargeting the admitted call. The only admissible difference is the gateway's own recorded public→upstream rewrite: the upstream must receive exactly the recorded upstream name or URI, so a body that still carries the public spelling is refused too. A final body that is no longer a single JSON-RPC object, or carries duplicate members, fails closed the same way. The check is shared by the HTTP/1.1, HTTP/2, and HTTP/3 dispatch paths; `mcp.admission_violation` records a fixed reason token when `observability.emit_metadata` is on, and no name, URI, or argument is echoed or logged. Transforms composed with an aggregate endpoint must leave those fields alone.

**Response correlation.** A gateway-authored terminal decided in a response phase (a `validation.validate_tool_results` refusal, an uninspectable or oversized upstream representation, an upstream transport failure or timeout) names the JSON-RPC id of the request it answers, using the exact wire token the client sent. The admitted id is retained privately on the request and bounded at the same 4096-byte reflection limit, so a client waiting on that call always sees a correlated `-32012`/`-32603` rather than an `id: null` error it can never match. Batch bodies and requests whose id was never admitted stay eligible for `id: null`.

`sessions.downstream_session_header` is stamped onto the client response, so it additionally rejects protocol-managed hop-by-hop / framing names (see [Final response framing](../plugins.md#final-response-framing)); `sessions.upstream_session_header` is a backend request field and keeps its own contract. Both configured session header names are registered as credential headers for the route, so they are redacted from diagnostics and policy calls and withheld from `request_mirror` traffic whatever they are called.

`sessions.max_sessions` and `sessions.session_ttl_seconds` bound downstream MCP sessions. Expired sessions are reclaimed when presented again, before accepting new `initialize` calls, and at rest by a per-instance background reaper that runs every half `session_ttl_seconds` (between 1 and 60 seconds), removes each expired session with its catalog and SSE broker session, and hands its initialized upstream sessions to a separate cleanup worker that `DELETE`s them best-effort (at most 8 in flight, each bounded at 10 seconds, from a bounded queue), so a slow upstream never delays the next sweep; both stop with the instance on reload, update, or delete. An upstream session minted by `initialize` is owned by that call until it is committed to its downstream session: if the downstream session was removed meanwhile, `notifications/initialized` fails, or the request is cancelled, the gateway deletes it (best-effort) rather than leaving it orphaned. Lost-owner cleanup runs in an independently owned task bounded at 10 seconds: the request awaits it while present, and cancelling that wait does not cancel the upstream `DELETE`. Aggregate sessions, catalogs, and SSE state are held in memory on the node that minted them: behind several gateway replicas, route every request carrying a given `sessions.downstream_session_header` value to the same replica (session affinity), or clients see `404` and must re-`initialize`. An aggregate `DELETE` without the session header answers HTTP `400` (JSON-RPC `-32600`), like a POST without one, rather than reporting success. `sessions.max_sessions_per_principal` bounds each caller’s live sessions. At that cap, the caller’s own oldest session is evicted; when the aggregate cap is full and the caller has no session to replace, initialization is refused without evicting another principal’s live session. Anonymous sessions are quota-grouped by resolved client IPv6 `/64` (IPv4 remains per-address), so one anonymous source cannot evict another source's session. Admission, in-memory eviction, and insert are serialized so concurrent `initialize` calls cannot exceed either cap, while evicted sessions' upstream `DELETE` cleanup is issued concurrently *after* that critical section so eviction never blocks new sessions behind upstream network round trips. In `aggregate_router` mode the gateway mints a synthetic downstream session id and never forwards it upstream: routed calls strip the downstream session header and carry only a mediated upstream session id when one exists. A downstream session is also **bound to the principal that created it**: the gateway records the authenticated `Consumer` (namespace plus record id, falling back to the username) or, when no Consumer is mapped, the external authenticated identity set by plugins such as `jwks_auth` **together with the realm that verified it** — the authentication mechanism plus the verifying authority (`jwks_auth` provider issuer and key source, `oidc_relying_party` issuer, `oauth2_introspection` issuer and introspection/discovery endpoint, `ldap_auth` directory URL, bind/search base, and identity attribute) — and every later request presenting that session id must carry the same principal. Equal subject strings from different accepted issuers, providers, or authentication plugins (two issuers that both assert `sub: alice`, say) are therefore different owners and cannot reuse each other's session for catalog listing, routed calls, the SSE listener, cancellation, or `DELETE`; a Consumer-mapped caller stays bound by namespace and record id alone. A `jwks_auth` provider that pins no `issuer` (one key set shared by several tenants) also binds each token's verified `iss`, an `oauth2_introspection` provider that pins no `issuer` binds each active response's `iss` (cache hits included), and every realm includes the claim path the identity is read from (`consumer_identity_claim` or its provider override). The realm is an opaque configuration digest committed with the identity at the authentication boundary; it carries no token or claim material. **Changing a provider's `jwks` / `jwks_uri` / `discovery_url`, `issuer`, introspection endpoint, identity claim, or an `ldap_auth` directory URL / bind or search base changes the realm, so existing aggregate MCP sessions owned by external identities under the old realm stop matching and their clients must re-`initialize`.** A mismatch is refused with the same `404` session-not-found response an unknown or terminated session produces, so possession of a session id is not by itself enough to reach that session's private catalog or its mediated upstream sessions, and a refusal does not disclose whether the session exists. Refused reuse does not extend the session's idle lifetime. The comparison runs in both directions, so a session minted on a proxy with no authentication plugin — where there is no principal to record — stays usable only by equally unauthenticated requests. Server ids must be URI-safe (`[A-Za-z0-9._-]`) because they appear in public `mcp://` resource URIs, and `sessions.downstream_session_header`/`sessions.upstream_session_header` must be valid HTTP header names; both are checked at config validation. In `aggregate_router` mode, `validation.validate_tool_results` (default `false`) compiles each discovered tool `outputSchema` at catalog construction, pins that exact validator for each dispatched call, and, when enabled, validates the caller-visible `tools/call` result before release: `structuredContent` is preferred, a single JSON text `content` block is accepted when structured content is absent, disagreeing mixed variants fail closed with JSON-RPC `-32012`, and exact response bytes with duplicate object members are rejected before any JSON rewrite or materialization. Well-formed tool errors (`isError: true` with array `content`) and well-formed upstream JSON-RPC errors are preserved; non-boolean or bare `isError` values and event-stream / non-JSON / oversized results fail closed. Transparent mode rejects the option because it has no mediated tool catalog. Invalid or unrepresentable `outputSchema` values (non-local `$ref`, over-budget document nesting/nodes, over-budget local `$ref` resolution depth, unsupported `$vocabulary`) are refused at catalog admission with field-specific diagnostics and never log result bodies. Changing the flag on reload/update reconstructs enforcement; deleting or disabling the plugin removes it. `initialize_upstreams: startup` is accepted as a V1 alias for `lazy` because MCP upstream initialization requires a downstream client session. In `aggregate_router` mode, advertising a capability with no dedicated dispatch — `capabilities.advertise_completions`, `capabilities.advertise_logging`, or `capabilities.advertise_tasks` — requires `capabilities.passthrough_unknown_methods: true` so those methods (`completion/complete`, `logging/*`, `tasks/*`) are routed to the primary upstream instead of advertised without support. If `observability.log_raw_arguments` is enabled, the gateway logs the arguments it parses from the synchronized request body; when `ai_prompt_shield` redacts earlier in the chain, those arguments are already redacted. Without the shield, raw arguments may contain secrets or PII, so prefer the default argument hashing unless the logging path is explicitly protected.

**Aggregate MCP Streamable HTTP event streams.** In `aggregate_router` mode with `sessions.sse_multiplexing` (default **`false`**), the gateway serves the event-stream half of MCP Streamable HTTP: a client may open **one** `GET` SSE listener per live downstream MCP session (`Accept: text/event-stream` plus the configured session header), and a `POST` carrying a JSON-RPC **request** whose result the gateway does not already hold is answered with its **own** `text/event-stream` response on that same `POST`.

Response placement follows the advertised transport. A `POST` carrying a request is answered on that `POST` — `application/json` when the answer already exists, its own event stream when it does not — `202` stays reserved for a `POST` carrying only notifications and responses, and the session `GET` stream never carries a response to a request that arrived on a `POST`. The single exception the transport allows is *resumption*: a `GET` bearing `Last-Event-ID` replays events an earlier `POST` stream already published, from the same retained ring (see *Resumption* below). With `sse_multiplexing: false` — the default — aggregate `GET` keeps its `405` and every request is answered with `application/json` on its own `POST`, which is equally conforming; the flag adds the event-stream surfaces, it does not relocate any answer. Both surfaces are served over HTTP/1.1, HTTP/2, and native HTTP/3 alike. The `GET` listener is streamed with no `Content-Length` (`ClientResponseFraming::Streaming`), so no representation length is published for bytes that have not been written; a `POST`-attached stream is a complete, bounded body and is framed like any other response.

Every JSON-RPC request is identified by a bounded, **type-sensitive** stream identity derived from its id — the string `"1"` and the number `1` are different streams and can never collide. Objects, arrays, booleans, null, empty, over-`sessions.sse_max_stream_id_bytes`, and control-bearing ids are not representable identities: those responses are answered with `application/json` on the POST instead (never framed under a fabricated identity, never dropped).

*Ready versus deferred, and when the identity opens.* A request whose answer the gateway already holds when `before_proxy` returns it — `ping`, `notifications/initialized` in request form, `tools/list`, `prompts/list`, `resources/list`, `resources/templates/list`, and every gateway JSON-RPC error such as `-32601`/`-32006` — is **ready**, and is written to the POST as `application/json`. A request that must be routed upstream — `tools/call`, `prompts/get`, `resources/read`, and any method sent to the primary upstream by `capabilities.passthrough_unknown_methods` — is **deferred**, and its POST is answered with a `text/event-stream` body carrying the opening `: mcp-sse` comment, one `id:`/`event: message`/`data:` record, and then end of stream. The stream identity is opened **before** the handler runs any catalog refresh, upstream `initialize`, or backend dispatch — for ready and deferred requests alike — which is what bounds per-session concurrency, refuses a duplicate id, and makes cancellation meaningful while the slow work is still running. A session `GET` listener is **not** a precondition: a client that never opens one still gets Streamable HTTP delivery. The client's `Accept` decides the representation: MCP requires a client to list both `application/json` and `text/event-stream`, the server picks between them, and a client that offered only JSON is answered with JSON (RFC 9110 12.5.1) and opens no stream identity at all.

The event bytes are the same bytes an `application/json` answer would have carried, *after* every configured response-body WAF rule, `body_validator` response schema, `ai_response_guard` redaction, and response transform has accepted them; a policy that safely redacts a still-valid `200` JSON-RPC response with the same type-sensitive id frames the redacted bytes. Framing the bytes and RETAINING them are two different decisions. The `mcp_gateway` final-body hook produces the POST body, but it only **stages** the event as a private reservation on the request; the proxy (and the native HTTP/3 writer) commit that reservation at the end of the response lifecycle, after the authoritative final client-visible body policy and final header policy have been re-closed over the generated event-stream representation, after the committed-response hooks, and after the authoritative pre-commit authorization gate. A later phase that replaces, rewrites, or refuses this representation — a policy rejection, an expired credential's terminal, a transport that never delivered the body on HTTP/3 — aborts the reservation instead: the client simply receives the replacement, and nothing about the withheld answer enters replay history. The commit predicate is exact — status `200`, a `text/event-stream` content type, and the byte-identical staged body — so it fails closed in every direction, and the staged reservation is bound to the exact admission that created it, so a lease left over from an earlier request under the same JSON-RPC id can neither retain bytes under the live request's identity nor release its per-session capacity. Dropping the last handle on the reservation aborts it, which is why no path can leak either the retained payload or the stream identity's per-session capacity — note that an ordinary request-context clone shares that one handle, so the abort happens when the last clone goes or the instant any holder commits or aborts, not necessarily when the original context drops. Two boundaries deserve naming precisely. On HTTP/1.1 and HTTP/2 the commit is a **pre-write commitment**: the gateway has decided to send exactly these bytes but has not handed them to the transport yet. On native HTTP/3 it is one step later — every DATA byte accepted by the send stream before FIN — which is a local handoff, not an acknowledgement from the peer, so neither boundary is proof of client receipt; a client whose connection dies afterwards resumes with `Last-Event-ID`, which is the point of retaining the event. A `notifications/cancelled` that arrives in the window between staging and commit suppresses **retention only**: the POST body was already framed and returned as the pipeline's answer, so on H1/H2 the client still receives it and on H3 the DATA frames may already be on the wire. Withholding the answer entirely is only possible for a cancellation observed before the response was framed, which is reported as `mcp.sse.delivery = suppressed`. One lifecycle is deliberately excluded: a **synthetic short-circuit** answer (a `response_mock`, cache, or federation reply to a deferred request) is written by a path that returns before this retention boundary exists, so it is answered with the ordinary inline `application/json` representation — which Streamable HTTP explicitly permits for a POST that carried a request — and recorded as `mcp.sse.delivery = inline`. Three shapes never open a stream: a **notification** (no JSON-RPC response exists at all), a **batch member** (the batch restriction assembles one HTTP response array), and **`initialize`** (its reply carries the session header on the ordinary JSON response). A response the final phase cannot read as a bounded, unambiguous JSON-RPC response naming the same type-sensitive id as the open request — including a non-200, event-stream, non-JSON, compressed, undeclared-length, over-`validation.max_upstream_response_bytes`, over-`sessions.sse_max_event_bytes`, or CR/LF-bearing body (a trailing newline included: SSE line folding cannot carry those octets unchanged, and it is reported as its own `mcp.sse.error = event_framing_invalid` rather than as an oversized payload) — is answered inline on the POST instead of being re-encoded or stripped of its HTTP failure semantics (the same header-time buffering refinement `tools/call` result validation already uses). A duplicate-key body, or one whose `jsonrpc`/`result`/`error` envelope or `id` does not name the open request, is treated differently: it is not delivered at all. The id comparison is **byte-exact** on the JSON-RPC id token (`1`, `1.0`, and `1e0` are different ids, as is the string `"1"`). Such a response is replaced by a bounded gateway `-32603` error naming the request's own id, so the client's pending call still resolves; the upstream body is neither framed nor returned as a successful answer. `mcp.sse.stream = open` records that an identity was opened; `mcp.sse.delivery` records the outcome as `post_stream`, `inline`, `suppressed` (the client cancelled), or `refused` (the mismatch replacement).

*Retention is one ring, with two reservation budgets.* Staging (events published while nobody is attached) and `Last-Event-ID` replay share a single ring bounded by `sessions.sse_max_retained_events` and `sessions.sse_max_retained_bytes`. Reservations against that ring are accounted separately by kind. A **deliverable** reservation — the answer to a request the gateway acknowledged with an empty `202` — is a promise: it is admitted against the ring and every direct publisher counts it, so its commit cannot be lost to a capacity race. A **POST-attached** reservation cannot be refused at all, because its bytes leave on the POST that carried the request whatever the ring holds, so it is best effort: it is never counted against a deliverable promise, and when it commits it yields to any promise still outstanding rather than overbooking the ring. A POST-attached response enters that ring only at the commit boundary described above, and it enters **already delivered** — the client has the bytes on its own connection — so it only ever occupies the replay window, the attached listener's cursor is advanced past it, and a ring too small to keep it costs resumability rather than delivery. A refused retention advances the eviction watermark, so a later cursor that would have needed that event fails closed as `410 Gone` instead of silently resuming across a gap. Already-delivered history is evicted as needed while reserving the incoming event's count and bytes, so a ring exactly at either cap does not refuse new work when safe replay history can make room. `sessions.sse_max_replay_events` bounds how many already-consumed events stay behind for resumption and must not exceed the ring capacity; `0` evicts a consumed event immediately, which means POST streams are delivered but never resumable. The resumption cursor a POST stream publishes is assigned when the response is staged, because the body the client receives has to carry it; concurrent requests on one session can therefore commit out of order, and the ring is kept sorted by id so replay is always ascending. An id whose reservation aborted is simply never retained — resumption always continues at the first retained event after the cursor, so an unused id is not a gap a client can stall on.

*Sizing the retention envelope.* The ring is per session, and broker session cardinality mirrors the MCP session store exactly, so the **worst-case aggregate** retained-event memory for one `mcp_gateway` instance is `sessions.max_sessions × sessions.sse_max_retained_bytes` — at the defaults (`16384 × 1 MiB`) that ceiling is large, so size both together for the deployment rather than raising either in isolation. Two properties keep the practical figure far below that ceiling and keep it finite regardless: retained bytes accrue only for requests a client actually issued on a live session, bounded by `sessions.sse_max_replay_events` per session, and at capacity an `initialize` may replace only that caller's oldest live session when required by the per-principal quota or the aggregate cap; expired sessions are reclaimed first. If aggregate capacity remains full and that caller has no live session to replace, `initialize` is refused. A new caller cannot evict another principal's live session. This formula bounds retained-event bytes, not eager allocation or total process RSS.

*Stream lifecycle.* `sessions.sse_max_streams_per_session` bounds concurrently **open** streams. Delivering a stream's terminal response completes it and returns its capacity, so a session is not exhausted after that many requests. The open identity is owned by a lease held privately on the request, so **every** ending releases it exactly once and never spawns a cleanup task: POST-attached delivery, cancellation, an inline fallback, a fail-closed policy replacement, a backend or body error, and a client transport disconnect all funnel into the same idempotent terminalization, and an already-known cancellation is never overwritten by a later completion. A completed or cancelled identity is retained as a bounded terminal record: a late or duplicate response for it is refused rather than misattributed onto a new stream, and a request that reuses a still-open or already-terminal id inside one session opens no identity (it answers inline, recording the fixed refusal token) so it can never join another request's stream. `notifications/cancelled` with `params.requestId` cancels the named stream as a **side effect only** — the notification keeps its ordinary routing (including passthrough to the primary upstream when `capabilities.passthrough_unknown_methods` is set), and because a JSON-RPC notification never receives an error response an unknown or unrepresentable id records a fixed `mcp.sse.cancel` token instead of changing the HTTP outcome. A cancelled request's own POST stream opens and closes carrying **no** `message` record, which is what "no response will be sent" looks like on the wire.

*Resumption.* With no `Last-Event-ID` a listener attaches at the delivery watermark, so it never replays a response an earlier `POST` already carried — a fresh `GET` is not a way to harvest another connection's answers. A cursor is otherwise explicit and is the transport's sanctioned way to recover a broken `POST` stream: the client hands back the `id:` its stream last published and receives the events after it. Ahead of anything issued is `400`, older than the retained history is `410 Gone` (continuity is never fabricated), non-numeric or over `sessions.sse_max_last_event_id_bytes` is `400`. Event ids come from one per-session counter, so they are unique across every stream in the session. The raw header value never reaches a log or metadata; only `mcp.sse.resume_requested = true` is recorded.

*Bounded lifetime and teardown.* An attached listener lives at most `sessions.sse_listener_max_lifetime_seconds` (default 300) and emits a keepalive comment every `sessions.sse_keepalive_seconds` (default 15), which is how a vanished peer is discovered on a quiet session. Be precise about what that deadline guarantees. The stream's own timer only advances while the transport polls the response body, and a peer that stops reading can park an HTTP/1.1 or HTTP/2 write indefinitely, so on those transports the timer alone is **not** a reclamation guarantee for a client that stalls without disconnecting. Native HTTP/3 does have a hard bound: its writer wraps the whole send loop in this deadline, because `send_data` awaits QUIC flow control and would otherwise park forever. What is guaranteed on **every** transport is that the session's single-listener slot stays usable: a `GET` arriving after the deadline **supersedes** the stalled listener instead of receiving `409`, which ends that listener on its next poll and makes its own release a no-op. Unconditional teardown paths are unchanged and never use a best-effort lock: client disconnect (dropping the response body), session `DELETE`, TTL expiry, cap eviction, and dropping the plugin instance on reload/update/delete all end the stream. Broker session cardinality mirrors the MCP session store exactly — `initialize` admits both under one critical section and **fails closed** with JSON-RPC `-32013` rather than minting a session that could never attach its stream.

Duplicate listeners for the same session return `409` while the attached one is inside its lifetime. A missing configured downstream session header returns `400` (`missing_session`); unknown, stale, or ownership-mismatched sessions return the ordinary `404` that prompts re-initialization. Diagnostics are fixed low-cardinality tokens in `mcp.sse.error` / `mcp.sse.cancel` / `mcp.sse.delivery` — never a session id, JSON-RPC id, header value, or event payload. Transparent mode continues to forward `GET` upstream unchanged and ignores this flag entirely.

**Discovery, catalogs, and locking.** Discovery catalogs are cached **per downstream session**, not gateway-wide, because an upstream MCP server may expose different tools/resources/prompts per initialized session (client identity/capabilities); a shared catalog could leak or hide entries across users. The session that owns the catalog is bound to its creating principal (see `sessions` above), so in authenticated deployments that per-session boundary is a per-user boundary rather than a bearer capability. Catalog refresh is serialized per session (not globally) and upstream `initialize` is serialized per `(session, server)`, so a slow upstream throttles only the affected session/server rather than blocking discovery or initialization for unrelated clients. A consequence of per-session catalogs is that each new session performs its own upstream discovery; that discovery — the tools / prompts / resources lists and the resource-template list alike — queries different servers concurrently (up to 8 at a time), while each server's own families stay sequential on its upstream session. Schema-change hiding (`discovery.on_schema_change: hide_until_configured`) is **not** per session: each instance keeps one schema baseline per server and public tool name, set by the first schema a refresh publishes, so a tool whose schema later changes stays hidden and refused for every session — a new session, another principal, or a session whose catalog is still cached or served last-good — on `tools/list`, `tools/call`, and the final request-body check of a call admitted before the change was seen, until a configuration change constructs a new instance with the current schema as its baseline. The baseline table is bounded by the configured servers times `validation.max_catalog_items_per_list` and holds only published tools (names suppressed by collision handling never occupy it); a tool it cannot baseline once full is hidden. An upstream that deliberately serves different schemas for one tool name to different sessions therefore has that tool quarantined under `hide_until_configured`. Every discovered `inputSchema` passes the same depth, node, and local-reference walk budgets as `outputSchema` (the walk follows `$ref`, `$dynamicRef`, and `$recursiveRef` and descends into every subschema location the compiler processes, including draft 4–7 `dependencies` and `additionalItems`; non-local references, non-fragment `$id`, and `$vocabulary` are refused) before it is compiled, whether or not `validation.validate_tool_arguments` is on; a tool whose `inputSchema` is refused is omitted with a warning while its siblings stay usable. Cached resource-template routes are refreshed against their selected resource server after `discovery.cache_ttl_seconds`; a successful refresh removes withdrawn routes, while a transient refresh failure serves the previously discovered route stale until the next per-server retry window so long-lived sessions remain available. A URI that was never discovered still fails closed. Tool-only servers are not queried for resource templates. When two upstreams produce the same public tool or prompt name after namespacing, the colliding name is skipped from discovery for **all** colliding upstreams (logged as a warning) so it can never route to the wrong upstream, while the rest of the catalog stays usable. Exact resource and resource-template public URIs include the validated-unique server id (`mcp://{server_id}/...`), so their public keys cannot collide across upstreams; defensive duplicate-key suppression for exact resources uses the same fail-closed state. Collision tombstones survive degraded refreshes and are cleared only after every attempted upstream in that family lists successfully, so a temporary outage cannot choose a winner. Per-family tombstone retention is bounded by `validation.max_catalog_items_per_list` multiplied by the number of attempted upstream lists, the aggregate number of items one refresh can contribute. If repeated degraded refreshes exceed that history bound, the gateway retains one bounded overflow marker and returns JSON-RPC `-32006` for the entire affected family until a fully authoritative refresh rebuilds its collision state; it never selects attacker-ordered tombstones or temporarily republishes a formerly ambiguous route. A failing upstream otherwise degrades only itself: each per-server `tools/list` / `prompts/list` / `resources/list` / `resources/templates/list` failure (transport error, non-2xx status, or JSON-RPC error) keeps that upstream's last-good entries for that family served stale and retried on the next refresh window, while every other upstream and family refreshes normally — one unavailable upstream does not fail the whole aggregate catalog. Stale carried entries pass through the same collision handling as fresh ones, and only currently enabled and exposed servers can carry entries forward, so disabled or removed servers still drop out of the catalog. Degraded upstreams are surfaced as warning logs and bounded `mcp.catalog_degraded` metadata (sorted `server:family` pairs). Availability is tracked per catalog family and separately from entry count: if every attempted upstream for the requested family fails before that family has ever listed successfully, that family returns JSON-RPC `-32006` while healthy families remain usable; a prior successful empty list is last-good state and continues to return an empty catalog during a later outage. A partially refreshed catalog retries failed families on the normal `discovery.cache_ttl_seconds` window. A wholly unavailable family is **negatively cached on the same window**: the refresh that discovered the outage still stamps the catalog as refreshed, so requests for that family keep returning JSON-RPC `-32006` from cache — without contacting the upstream again — until `discovery.cache_ttl_seconds` elapses. Recovery is therefore bounded by that TTL rather than picked up on the next request; size `discovery.cache_ttl_seconds` for the recovery latency you are willing to accept, remembering that it equally bounds how often every healthy family is re-listed.

**Reading the catalog from the Admin API.** `GET /proxies/{id}/mcp/tools` (viewer role or above, namespace-scoped like other proxy reads) returns the tools a proxy's `mcp_gateway` instances expose without an MCP session. It reads only the cached catalogs: it never contacts an upstream or starts a refresh. Because catalogs are per downstream session, each instance reports its most recently refreshed session catalog. An upstream may tailor tools per principal, so this can reflect one principal's view. `refreshed_at` and `stale` track tools refreshes, measured against `discovery.cache_ttl_seconds`; resource-template refreshes do not change them. Before any session lists tools the list is empty, `refreshed_at` is `null`, and `stale` is `true`. Each tool carries its public name, its source (the upstream server's `namespace` and upstream tool name, or the generating OpenAPI operation's method and path template), `title` / `description` / `annotations`, the configured action and the effective outcome (including `hidden_until_configured` from `discovery.on_new_tool: hide_until_configured` and `hidden_schema_changed` from `discovery.on_schema_change`), `allowed_groups` / `denied_groups`, and the gateway's stored SHA-256 `schema_hash`. With `validation.validate_tool_results` disabled it covers serialized `inputSchema`; when enabled it covers serialized `inputSchema` and `outputSchema`. Each configured server reports its last `tools/list` outcome (`ok`, `stale` with last-good tools, `failed`, `pending`) with fixed-text errors, and its `upstream_url` reduced to `scheme://host[:port]` plus redaction markers for every role. The catalog is node-local: a control plane, or a data plane that does not serve the proxy's namespace, reports `not_served`. See [Admin API: MCP tool catalog](../admin_api.md#mcp-tool-catalog-get-proxiesidmcptools).

**Aggregated catalog descriptors.** Namespacing changes the public *name* of a catalog entry and nothing else. An aggregated `tools/list` entry keeps the upstream `title`, `inputSchema`, `outputSchema`, and `annotations`; an aggregated `prompts/list` entry keeps the upstream `title` and the standard MCP `arguments` array — each argument's `name`, `title`, `description`, and `required` flag — exactly as the upstream declared them, because that array is what a client reads to know which values to collect before calling `prompts/get`. Argument names are prompt-local and are never namespaced. An upstream that also publishes a nonstandard `argumentsSchema` has it carried through unchanged alongside `arguments`; a non-array `arguments` value is not a conforming argument list and is dropped rather than republished. Only the entry `description` is rewritten, to carry the `[namespace]` prefix.

**Protocol version negotiation.** `endpoint.protocol_versions` is ordered: the first entry is the gateway's preferred version. In `aggregate_router` mode, `initialize` echoes a supported requested `protocolVersion` and otherwise negotiates per the MCP lifecycle — the successful initialize result carries the preferred supported version (recorded as `mcp.protocol_version_negotiated` metadata) and the session is minted on that version instead of rejecting the client. Post-initialize requests remain fail-closed: an `MCP-Protocol-Version` header naming an unsupported version is rejected with HTTP 400. Protocol version `2025-03-26` is admitted: JSON-RPC batch arrays are supported under the validation limits below.

**JSON-RPC batches.** A top-level JSON array is admitted as a JSON-RPC 2.0 batch. Empty arrays are rejected with a single `-32600 Invalid Request` response (not an array). `validation.max_batch_bytes` (default 1 MiB) is enforced on the **raw request body before any JSON parsing**: a body whose first non-whitespace byte is `[` is array-shaped, so an oversized batch is refused without funding a full parse, and malformed array-shaped bodies still fail closed. Only the array framing is then parsed, retaining each member as its exact raw JSON slice: `validation.max_batch_items` (default 32) bounds member count, and `validation.max_batch_item_bytes` (default 256 KiB) is enforced on each member's **raw JSON wire slice before that member is deserialized**. "Member bytes" means the bytes as received — internal whitespace and escape sequences count exactly as written, while the array separators (`,`) and the inter-member whitespace surrounding the member do not — so a member that is large on the wire cannot shrink under the cap by normalizing, and an oversized member never funds a `Value` tree. A member refused by that cap yields a bounded Invalid Request with `id: null` at its input position: its id is never materialized and never reflected, so an oversized attacker-controlled id cannot be echoed. Admitted members are then validated independently for object shape and the same method/session/schema/tool-policy rules as a singleton: non-object or nested-array members yield a bounded `id:null` Invalid Request while valid siblings continue. Response-bearing results preserve JSON-RPC `id` values and input order; notifications never produce a response entry; an all-notification batch of gateway-handled members returns HTTP 202 with an empty body. Assembled batch responses are bounded by `validation.max_batch_response_bytes` (default 1 MiB) and fail closed without returning a partially oversized body. A batch member is dispatched with a private, non-serialized request-context guard rather than public `mcp.*` metadata, so no forged metadata key can grant or revoke a batch member's ability to reach the network. Per-item routing overrides, private tool/resource rewrite state, injected headers, and item-scoped `mcp.*` metadata are reset before each member and after the batch, so one member's decision can never authorize or reroute another; only the request-level summary (`mcp.batch`, `mcp.batch_size`, and the terminal `mcp.route_decision`) survives. Two keys that a *single member* can write but that describe the *request* are republished from request-level inputs at every batch terminal point instead of being left at whichever member ran last: `mcp.protocol_version` is re-derived from the inbound `MCP-Protocol-Version` header only (a member's `params.protocolVersion` still gates that member, but never labels the batch), and `mcp.catalog_degraded` is the bounded sorted union of every member's degraded `server:family` pairs — fixed cardinality at configured servers × catalog families, and absent when no member degraded. A batch member whose session is no longer live contributes a per-item `-32004 MCP session not found` element rather than the singleton's bare HTTP 404, which cannot be expressed per item.

The post-initialize protocol-version gate applies to batch members exactly as it does to singletons: a member whose method is not `initialize` is refused when `MCP-Protocol-Version` names an unsupported version, so a batch can never smuggle a version past the gate the equivalent singleton enforces. Only the HTTP framing of that refusal differs by mode, because a batch response has one status line. In `transparent_proxy` mode the whole request is rejected with HTTP 400 — an HTTP batch body cannot be partially forwarded, so refusing one member must refuse all of them. In `aggregate_router` mode the batch still answers HTTP 200 with a response array and the offending member carries the same `-32600 Unsupported MCP protocol version` object the singleton would have returned in its 400 body, while its valid siblings are answered normally; members already refused earlier as `initialize` (`-32010`) or as upstream-routed (`-32009`) keep those more specific codes, and both are likewise fail-closed.

**MCP `initialize` is a singleton-only HTTP request.** In `aggregate_router` mode, an `initialize` member inside a JSON-RPC batch is rejected with JSON-RPC `-32010` *before* any dispatch. Session minting is not transactional across batch members: a later member's failure or a `max_batch_response_bytes` rejection cannot undo a mint, removing a newly minted session cannot restore a live session that its admission evicted under `sessions.max_sessions`, and a single HTTP response header cannot advertise more than one new session. Consequently **no batch mints or evicts a downstream session, and no batch response carries a session header** — any member result that would advertise one is failed closed with `-32010` instead. Ordinary gateway-handled batch members (catalog lists, `ping`, supported notifications) still refresh an existing session's idle lifetime, matching their singleton forms; known upstream-routed members are rejected before session touch. A notification-form `initialize` in a batch has no response element, so an otherwise all-notification batch reports `-32010` once at batch level. Clients must send `initialize` as its own HTTP request and then use the returned session in subsequent singleton or batch requests.

In `aggregate_router` mode, only gateway-handled (synthetic) members are executed inside the batch: catalog lists, `ping`, `notifications/initialized`, and other terminal gateway responses. Known upstream-routed methods (`tools/call`, `resources/read`, `prompts/get`) are classified *before* any member dispatch — ahead of session touch, catalog lookup/refresh, template refresh, policy/schema routing, upstream initialization, route overrides, header rewrites, and network I/O — and return JSON-RPC `-32009` deterministically (a cold versus warm catalog cannot change the outcome). Passthrough unknown methods that would still resolve to upstream routing remain covered by the private batch upstream-dispatch guard. Executing those members from `before_proxy` would bypass later configured plugin phases (`a2a_gateway`, `mesh_route_dispatch`, `ai_semantic_cache`, request transformers, final request-body hooks, and ordinary proxy response phases) and receive weaker policy than the equivalent singleton; they must be issued as singleton requests so the full plugin chain applies. Their **notification forms are treated the same way**: a notification `tools/call`, `resources/read`, or `prompts/get` is not executed and does not produce a response element, so an otherwise all-notification batch fails closed with `-32009` instead of claiming success with an empty 202. Any other batch notification whose dispatch does not succeed (for example a passthrough notification under a stale session) is reported once at batch level with `-32011` rather than being answered per item. When the batch also contains response-bearing members, the response array is returned and the blocked notifications simply contribute no element — matching JSON-RPC's rule that notifications are never answered.

In `transparent_proxy` mode, every member is validated independently; when all members are valid MCP request/notification envelopes the original batch body continues unmodified to the single upstream through the normal proxy/plugin chain. Because the forwarded body is the whole batch rather than any one member, member-scoped `mcp.*` observability is cleared before that forward too: the request is described by `mcp.batch`/`mcp.batch_size`, not by whichever member happened to be validated last. Transparent mode mediates no gateway session state, so `initialize` members are forwarded like any other member. If any member is invalid, forwarding a partially rewritten batch is impossible, so the gateway returns a synthetic per-item error array (invalid members get Invalid Request; valid siblings get a bounded not-forwarded error) and does not dial upstream. Changing these limits on reload/update reconstructs admission; deleting or disabling the plugin removes batch handling with the instance.

**Response reverse mapping.** For routed `resources/read`, `tools/call`, and `prompts/get` requests, buffered JSON-RPC results use the same per-session catalog bindings as request routing to map upstream resource URIs back to public `mcp://{server}/...` URIs. This covers `resources/read` `contents[].uri`, tool-result `resource_link` items, embedded resource content, and resource content returned by prompts. Tool/prompt routing also loads resource-template bindings for the selected resource-exposing upstream on first use so dynamic resource links can be routed back through the gateway without unrelated or tool-only servers delaying the call. Template expansion preserves upstream percent escapes and percent-encodes non-URI bytes when it constructs the public URI, so reserved-operator templates round-trip without decoding an encoded slash or emitting an invalid link. Exact `resources/read` echoes use the request-private routed binding even if the shared catalog refreshes or the session is removed while the request is in flight; catalog-derived tool/prompt mappings still pass through unchanged on version drift. Unknown or ambiguous bindings and malformed JSON also pass through unchanged. Routed calls strip `Accept-Encoding` only when the selected server can return exposed resource bindings that require reverse mapping; tool/prompt-only configurations keep response streaming and content negotiation unchanged. Only origin-identity JSON with a known original `Content-Length` at or below `validation.max_upstream_response_bytes` (default 4 MiB) is eligible for rewriting, even if another policy already buffered the response; origin-encoded, unknown-length, or larger responses are released unchanged. Gateway response compression remains compatible: the rewrite runs over the identity body before the selected gateway encoding is applied. Origin validators and integrity hashes are removed only after a URI rewrite changes the upstream-native body, so unchanged responses retain valid cache metadata. Internal response-rewrite bookkeeping is excluded from transaction metadata even when MCP metadata emission is enabled. `text/event-stream` responses are never buffered or rewritten, including when retries are configured: once headers arrive, the MCP plugin opts SSE out of retry buffering if no other active body plugin needs it.

## Recommended plugin stack for an agent-facing MCP endpoint

An API exposed to AI agents through `mcp_gateway` — upstream MCP servers, OpenAPI bridge tools, or both — is governed by the same plugins that govern LLM traffic, each of which recognizes MCP `tools/call`. In execution order on the MCP proxy:

| Priority | Plugin | Role on the MCP endpoint |
|---|---|---|
| 950–1400 | an authentication plugin (`key_auth`, `jwt_auth`, `jwks_auth`, `oauth2_introspection`, `mtls_auth`, …) | Identifies the agent's Consumer. Per-consumer tool grants (`policy.tools.*.allowed_groups`) read its `acl_groups`, and every limit and audit record below is keyed on it. |
| 2740 | `ai_transcript_audit` | Records each `tools/call` — consumer, public tool name, keyed `arguments_hash`, optional redacted arguments, and the JSON-RPC outcome (`result` / `error`, `isError`) — plus the gateway's and the tool governor's decisions. Runs first so a call that a later plugin refuses is still recorded, with the refusal as its outcome. |
| 2900 | `rate_limiting` with `mcp_tool_calls` | Per-consumer tool-call budget: only `tools/call` is charged (each member of a batch), optionally per tool, with `x-ratelimit-*` headers and a JSON-RPC `-32015` error on HTTP `200`. A second, ordinary `rate_limiting` instance can still bound raw request rate. |
| 2925 | `ai_prompt_shield` with `scan_fields: mcp_arguments` | PII / secret screening of `params.arguments` only; `redact` rewrites arguments, which an OpenAPI bridge carries into the REST query, headers, and body (a redacted path argument fails the bridged call with `-32602`). |
| 2978 | `ai_tool_governor` with `inspect.mcp_tool_calls: true` | Deterministic allow / deny / approval policy on public tool names and arguments (every batch member). Policy keys are the gateway's public names (`namespace.tool`). |
| 2992 | `mcp_gateway` | Catalog, tool policy, per-consumer grants, `inputSchema` validation, routing, and OpenAPI bridge execution. |

```yaml
plugins:
  - plugin_name: key_auth
    config: {}
  - plugin_name: ai_transcript_audit
    config:
      mode: redacted_body
      capture: { mcp_tool_calls: true, mcp_arguments: true }
      privacy: { include_consumer_username: true }
      sink: { type: http, endpoint_url: https://audit.internal.example.com/mcp }
  - plugin_name: rate_limiting
    config:
      limit_by: consumer
      expose_headers: true
      limits: [{ scope: default, requests_per_minute: 60 }]
      mcp_tool_calls: { endpoint_path: /mcp }
  - plugin_name: ai_prompt_shield
    config:
      action: reject
      scan_fields: mcp_arguments
      patterns: [ssn, credit_card, api_key, aws_key, email]
  - plugin_name: ai_tool_governor
    config:
      inspect: { mcp_tool_calls: true }
      # policies: ...
  - plugin_name: mcp_gateway
    config:
      mode: aggregate_router
      endpoint: { path: /mcp }
      # servers / policy / validation ...
```

Notes:

- **Everything before `mcp_gateway` sees attempts, not admitted calls.** The audit, the tool-call limiter, the shield, and the governor run ahead of the gateway, so a call the gateway then refuses (an unknown or ungranted tool, invalid arguments, an aggregate batch member answered `-32009`) was still audited, counted, and screened. That is usually what an operator wants from an audit trail and a quota; to count only admitted calls, move the limiter after the gateway with `priority_override`.
- **Refusal shapes differ.** `mcp_gateway` and `rate_limiting` (`mcp_tool_calls`) answer JSON-RPC errors on HTTP `200`, which MCP clients surface to the agent. `ai_prompt_shield` and `ai_tool_governor` keep their own HTTP `400` / `403` JSON bodies, which an MCP client reports as a transport error.
- **Bridged calls.** The OpenAPI bridge's REST request is re-checked by the gateway after every request-body transform, the audit records the converted `tools/call` result rather than the REST body, and proxy-level path or method policy (`allowed_methods`, WAF path rules, path-keyed authorization) sees only the MCP `POST` — restrict bridged operations in `mcp_gateway` itself (see *OpenAPI bridge*).
- **Session and discovery traffic is not tool traffic.** `initialize`, `tools/list`, and notifications are not charged by the tool-call limiter and are not audit candidates; bound them, if needed, with an ordinary request `rate_limiting` instance and `request_size_limiting`.
